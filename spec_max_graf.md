# Спецификация: раскрытие/схлопывание вложенных графиков в «Обзоре»

**Задача:** Task 97 (продолжение worklog2.md)
**Статус:** Архитектурный дизайн, готов к ревью тимлидом перед стадией TDD-реализации
**Автор:** Claude (Senior dev), платформа CISStat TS Analysis
**Дата:** 2026-09-03
**Затрагиваемые области:** `packages/ui` (общие компоненты, используемые embedded и standalone), все вкладки, где применяется «Обзор» (Validation, Preprocessing, EDA, Modeling), опционально `apps/api` (сэмплирование)

---

## 1. Проблема

«Обзор» на всех вкладках платформы работает в фиксированном контракте высоты
рабочего окна `flex h-[468px] min-h-0 flex-col` (Task 88), внутри которого
вложенные визуализации (Recharts `ResponsiveContainer` с `height="100%"`,
Task 89) делят это пространство между собой, а иногда и с описанием,
переключателем представлений (бейджи-вкладки) и другими элементами.

При большом количестве точек/рядов/срезов (спектральный анализ CWT,
структурные сдвиги, матрица моделей, декомпозиция с 3–4 компонентами
одновременно и т.д.) плотность информации на графике внутри 468px-окна
становится недостаточной: подписи осей накладываются, легенда обрезается,
тонкие структурные детали (локальные экстремумы, узкие сдвиги, кластеры
scales на CWT-хитмапе) неразличимы аналитиком.

## 2. Цель

Дать аналитику единый, предсказуемый способ «раскрыть» любой вложенный
график из «Обзора» до размера всего окна Обзора и вернуть его обратно —
без перехода на другую страницу, без потери состояния (выбранного
представления, датасета, настроек), одним и тем же жестом на любой вкладке
платформы.

### Вне рамок задачи (non-goals)
- Полноэкранный (viewport) режим/модальное окно поверх всей страницы —
  спецификация ограничивается раскрытием **в пределах контейнера Обзора**
  (буквально «до полного размера окна Обзор», не более).
- Изменение методологии расчётов (PELT, CWT, STL и т.д.) — сэмплирование
  касается только объёма данных, отдаваемых для отрисовки, не самого
  анализа.
- Одновременное раскрытие нескольких графиков — вне скоупа v1 (см. §5.2).

## 3. Пользовательский сценарий

1. Аналитик открывает любую вкладку (например, «Предобработка → Спектральный
   анализ»), видит «Обзор» с вложенным графиком CWT-хитмапа, сжатым до части
   468px-окна.
2. В правом верхнем углу графика — иконка-бейдж (по аналогии с уже принятым
   в проекте стилем «светло-серых круглых бейджей», Task 88/89) с
   пиктограммой «развернуть» (две стрелки по диагонали наружу, Maximize2).
3. Клик по иконке → график плавно (≈200мс transition) занимает всё окно
   Обзора (468px по высоте, полная ширина панели), скрывая соседние
   элементы этого конкретного визуального блока (описание, другие
   sub-графики того же блока), но **не** ломая контракт высоты — Обзор
   не «вырастает» за пределы 468px, он просто отдаёт всё пространство
   одному графику.
4. Иконка меняется на «свернуть» (Minimize2) и остаётся на том же месте
   (правый верхний угол) поверх раскрытого графика.
5. Повторный клик по этой же иконке — или `Esc` — схлопывает график обратно
   к исходному размеру, соседние элементы возвращаются.
6. Если для раскрытого состояния предусмотрено более детальное
   сэмплирование (см. §6) — при раскрытии показывается лёгкий inline-лоадер
   поверх уже видимого (сжатого) графика, без дёргания layout, после чего
   график перерисовывается с более высоким разрешением.
7. Переключение вкладки представления внутри Обзора, смена датасета/target,
   уход со страницы — всегда сбрасывают раскрытое состояние в свёрнутое
   (защита от «залипшего» полноразмерного графика в неактуальном контексте).

## 4. Архитектура компонентов (packages/ui)

Поскольку фича должна работать одинаково на **всех** вкладках и в обоих
приложениях (embedded + standalone) без дублирования кода, она реализуется
как переиспользуемый примитив в `packages/ui`, по той же логике, что и
`TsAnalysisPreprocessing` — общая бизнес/UI-логика, используемая обоими
фронтендами.

```
packages/ui/
  components/
    charts/
      ExpandableChartPanel.tsx        — обёртка вокруг одного визуального блока
      ExpandableChartPanel.test.tsx
      ChartExpandToggle.tsx           — сама иконка-кнопка (бейдж)
      ChartExpandToggle.test.tsx
      ExpandableChartsProvider.tsx    — контекст на уровень одного «Обзора»
      ExpandableChartsProvider.test.tsx
    __contracts__/
      ExpandableChartCoverage.test.ts — контрактный тест по аналогии с
                                         AnalysisWorkspaceHeight/
                                         AdaptiveWorkspaceVisualizations
                                         (Task 88/89): проверяет, что каждый
                                         компонент-Обзор оборачивает свои
                                         визуальные блоки в
                                         ExpandableChartPanel
  hooks/
    useExpandableChart.ts             — хук доступа к контексту раскрытия
    useChartDetailData.ts             — хук условной догрузки детального
                                         сэмплирования (см. §6)
```

### 4.1 `ExpandableChartsProvider`

Контекст-провайдер, инстанцируется **один раз на каждый компонент-Обзор**
(не глобально на всё приложение — раскрытие в одной вкладке не должно
влиять на состояние в другой).

Состояние:
```ts
type ExpandableChartsState = {
  expandedChartId: string | null;
};
```

Инварианты:
- В любой момент времени раскрыт **не более одного** графика в пределах
  одного Обзора (простая модель, не требует z-index-стека).
- `expand(id)` — если уже что-то раскрыто, сначала неявно схлопывает
  предыдущее (single-expand guarantee), затем раскрывает новое.
- `collapseAll()` вызывается автоматически по эффектам, зависящим от
  ключей инвалидации, уже принятым в проекте для профилей (смена
  `datasetId`, `targetColumn`, переключение таба представления внутри
  Обзора, размонтирование компонента).

```tsx
const ExpandableChartsContext = createContext<{
  expandedChartId: string | null;
  expand: (id: string) => void;
  collapse: () => void;
  toggle: (id: string) => void;
} | null>(null);

export function ExpandableChartsProvider({ children }: PropsWithChildren) {
  const [expandedChartId, setExpandedChartId] = useState<string | null>(null);
  const expand = useCallback((id: string) => setExpandedChartId(id), []);
  const collapse = useCallback(() => setExpandedChartId(null), []);
  const toggle = useCallback(
    (id: string) =>
      setExpandedChartId(prev => (prev === id ? null : id)),
    []
  );
  return (
    <ExpandableChartsContext.Provider value={{ expandedChartId, expand, collapse, toggle }}>
      {children}
    </ExpandableChartsContext.Provider>
  );
}
```

### 4.2 `ExpandableChartPanel`

Оборачивает **один визуальный блок** (не весь Обзор целиком) — то есть если
на вкладке «Спектральный анализ» одновременно показаны периодограмма и
CWT-хитмап, каждый оборачивается отдельным `ExpandableChartPanel` со своим
`chartId`, и раскрывается только тот, по которому кликнули.

```tsx
type ExpandableChartPanelProps = {
  chartId: string;                 // уникален в пределах Обзора, стабилен
  title?: string;                  // опционально дублируется в raised-режиме
  className?: string;
  children: ReactNode;             // сам вложенный график (Recharts и т.п.)
  onExpandChange?: (expanded: boolean) => void; // для §6-триггера дозагрузки
};

export function ExpandableChartPanel({
  chartId, title, className, children, onExpandChange,
}: ExpandableChartPanelProps) {
  const { expandedChartId, toggle } = useExpandableChart();
  const isExpanded = expandedChartId === chartId;

  useEffect(() => {
    onExpandChange?.(isExpanded);
  }, [isExpanded, onExpandChange]);

  // Esc закрывает раскрытый график
  useEffect(() => {
    if (!isExpanded) return;
    const onKey = (e: KeyboardEvent) => {
      if (e.key === 'Escape') toggle(chartId);
    };
    window.addEventListener('keydown', onKey);
    return () => window.removeEventListener('keydown', onKey);
  }, [isExpanded, toggle, chartId]);

  return (
    <div
      className={cn(
        'relative min-h-0',
        isExpanded
          ? 'absolute inset-0 z-20 flex flex-col bg-[var(--card-bg)]'
          : 'flex flex-1 flex-col',
        className
      )}
    >
      <ChartExpandToggle
        expanded={isExpanded}
        onClick={() => toggle(chartId)}
        title={title}
      />
      <div className="min-h-0 flex-1">{children}</div>
    </div>
  );
}
```

Ключевой момент: **родительский контейнер Обзора должен иметь
`position: relative`** (в подавляющем большинстве Обзоров это уже так за
счёт существующей вёрстки Task 88/89 — контрактный тест из §7 проверит
это явно), чтобы `absolute inset-0` разворачиваемого блока корректно
перекрывал именно область Обзора, а не весь документ.

### 4.3 `ChartExpandToggle`

```tsx
type ChartExpandToggleProps = {
  expanded: boolean;
  onClick: () => void;
  title?: string;
};

export function ChartExpandToggle({ expanded, onClick, title }: ChartExpandToggleProps) {
  const label = expanded ? 'Свернуть график' : 'Развернуть график до размера окна';
  return (
    <button
      type="button"
      onClick={onClick}
      aria-label={label}
      title={label}
      className={cn(
        'absolute right-2 top-2 z-30',
        'flex h-7 w-7 items-center justify-center rounded-full',
        'bg-[var(--badge-bg)] text-[var(--badge-fg)]',
        'hover:bg-[var(--badge-bg-hover)] focus-visible:outline focus-visible:outline-2',
        'transition-colors'
      )}
    >
      {expanded ? <Minimize2 size={14} /> : <Maximize2 size={14} />}
    </button>
  );
}
```

Используется существующая иконочная библиотека проекта (`lucide-react`,
уже задействована для прочих UI-иконок платформы — единообразие с текущим
стилем бейджей), `Maximize2`/`Minimize2` — семантически однозначные
пиктограммы «развернуть/свернуть» (не «крестик закрытия» — сохраняем
интуитивную симметрию действия, требуемую в задаче: «эту же иконку
раскрывает и схлопывает»).

Доступность:
- `aria-label` меняется в зависимости от состояния;
- фокусируется табом, активируется `Enter`/`Space` (нативное поведение
  `<button>`);
- видимый `focus-visible` outline;
- `Esc` схлопывает при раскрытом состоянии (обработка в `ExpandableChartPanel`, §4.2).

### 4.4 Интеграция в существующие Обзоры

Каждый компонент-Обзор (например, `SpectralAnalysisOverview.tsx`,
`StructuralBreaksOverview.tsx`, `ModelMatrixOverview.tsx` и т.д. — по
факту все ~30+ upstream-узлов из Task 94 плюс модуль «Моделирование»)
получает на верхнем уровне разметки:

```tsx
<div className="flex h-[468px] min-h-0 flex-col ...existing-classes">
  <ExpandableChartsProvider>
    {/* существующие бейджи-переключатели представлений, если раскрыт
        график — их можно скрыть через useExpandableChart().expandedChartId */}
    <ExpandableChartPanel chartId="spectral-periodogram" title="Периодограмма">
      <ResponsiveContainer width="100%" height="100%">
        {/* существующий Recharts-график без изменений */}
      </ResponsiveContainer>
    </ExpandableChartPanel>
  </ExpandableChartsProvider>
</div>
```

Важно: **сам Recharts-график не меняется** — меняется только контейнер
вокруг него. `ResponsiveContainer height="100%"` уже подхватывает новый
раздутый размер автоматически (это уже отработанный паттерн из Task 89
про адаптивность вложенных графиков), поэтому большая часть выигрыша в
читаемости достаётся «бесплатно», без правок самих графиков.

Для Обзоров с несколькими одновременными визуализациями (например, три
компоненты декомпозиции сразу) — оборачивается **каждая** компонента
своим `ExpandableChartPanel` с отдельным `chartId`; при раскрытии одной
остальные (не раскрытые) скрываются через условный рендер
(`expandedChartId && expandedChartId !== chartId ? null : <Panel />`) —
это уже обеспечено самим свойством `absolute inset-0` перекрывать их
визуально, но для производительности имеет смысл не просто перекрыть,
а не рендерить тяжёлые невидимые Recharts-инстансы (см. §7 — тест
производительности).

## 5. Взаимодействие с уже существующими UI-паттернами Обзора

### 5.1 Переключатель представлений (бейджи-вкладки, Task 90–93)

Если внутри Обзора есть свой собственный переключатель представлений
(например, «Паспорт свойств ряда» на 3 вкладках), раскрытие графика не
подменяет и не сбрасывает выбор представления — раскрывается **текущий
активный** график внутри текущей вкладки представления. Смена вкладки
представления во время раскрытого состояния — триггер `collapse()`
(см. §3, п.7), чтобы не путать аналитика раскрытым графиком от другого
представления.

### 5.2 Почему не multi-expand в v1

Раскрытие сразу нескольких графиков потребовало бы либо деления окна
Обзора на несколько под-панелей (усложнение вёрстки, размывание цели
задачи — «раскрыть график до размера **всего** окна»), либо стека
z-index с ручным управлением порядком. Оставляем как явный follow-up
(см. §9), если аналитики запросят сравнение двух раскрытых графиков
бок о бок.

## 6. Сценарий сэмплирования (детализация при раскрытии)

### 6.1 Почему это нужно

Часть визуализаций уже сегодня отдаются backend'ом с зафиксированным
потолком точек/бинов/scales ради производительности и объёма payload
(например, бюджетирование PELT-сетки из Task 76, лимиты точек CWT и
т.п.). Такой потолок разумен для компактного 468px-окна, но при
раскрытии на всё окно у графика физически появляется место для
значительно большей плотности данных без потери читаемости — а
пользователь, который явно попросил «раскрыть», ожидает увидеть
**больше деталей**, а не тот же самый разреженный график, просто
растянутый крупнее.

### 6.2 Модель: два уровня детализации, один и тот же endpoint

Не создаём отдельные endpoint'ы — расширяем существующие профильные
GET/POST-запросы (spectral-profile, decomposition-profile,
structural-breaks, variance-profile, smoothing-profile,
stationarity-profile, feature-generation-profile, scaling-profile,
model-matrix и т.д.) опциональным параметром:

```
GET /v1/.../spectral-profile?session_id=...&detail_level=compact   (по умолчанию)
GET /v1/.../spectral-profile?session_id=...&detail_level=expanded
```

- `compact` — текущее поведение без изменений (обратная совместимость,
  ничего не ломается для клиентов, ещё не знающих о новом параметре).
- `expanded` — тот же самый расчёт (методология не меняется), но с более
  высоким вторичным потолком точек/бинов/scales, зафиксированным в
  конфиге каждого профиля (по аналогии с бюджетом PELT-сетки Task 76 —
  вторичный потолок тоже должен быть явным и протестированным, чтобы не
  провоцировать регресс времени ответа/памяти на render.com).

Таблица предлагаемых вторичных потолков (стартовая гипотеза, подлежит
утверждению тимлидом и калибровке на реальных датасетах):

| Профиль                     | compact (текущий)         | expanded (предлагаемый)      |
|------------------------------|----------------------------|--------------------------------|
| Спектральный (периодограмма) | текущий лимит точек        | ×2, но не более технич. потолка |
| CWT-хитмап                   | текущие scales × time      | ×1.5–2 по каждой оси            |
| Структурные сдвиги (PELT)    | текущий бюджет сетки       | расширенный бюджет (по аналогии с Task 76 budget) |
| Декомпозиция (STL и др.)     | текущее число точек ряда   | без даунсэмплинга (полный ряд, если в разумных пределах) |
| Матрица моделей / backtest   | текущее число фолдов/точек | +детализация по фолдам          |

Точные числа — предмет отдельной калибровочной задачи с бенчмарками
(см. §9, follow-up), в этой спецификации фиксируется **контракт**
(наличие параметра, обратная совместимость, вторичный потолок как явная
константа), а не конкретные цифры.

### 6.3 Клиентский флоу дозагрузки

```
useChartDetailData(sessionId, profileKey, params)
```

1. При `expand()` конкретного `chartId` компонент, отрисовывающий график
   (не сам `ExpandableChartPanel` — он универсален и не знает про data
   fetching), через `onExpandChange` получает сигнал «стал раскрыт».
2. Если для данного профиля кэш `detail_level=expanded` для текущего
   `(sessionId, profileKey, fingerprint)` уже есть — используется сразу,
   без похода в сеть.
3. Если кэша нет — выполняется фоновый повторный запрос с
   `detail_level=expanded`; пока он летит, **на месте графика продолжает
   отображаться уже отрисованный compact-график**, растянутый в
   увеличенный контейнер (Recharts это отрисует корректно за счёт
   `ResponsiveContainer`), поверх — лёгкий unobtrusive-индикатор
   (например, тонкий прогресс-бар сверху панели, не блокирующий
   просмотр текущих данных).
4. По готовности — плавная замена данных графика (без перезагрузки
   компонента, без сброса зума/tooltip-состояния, если такое есть).
5. Кэш детального payload живёт в рамках текущей сессии анализа и
   инвалидируется теми же триггерами, что и остальные профили
   (смена датасета/target/session — уже реализованный паттерн
   инвалидации из Task 90+).
6. **Graceful degradation:** если backend ещё не поддерживает
   `detail_level` для конкретного профиля (поэтапный роллаут, §8) —
   запрос с этим параметром либо игнорируется backend'ом (параметр
   Optional, не ломает существующий контракт), либо, если endpoint
   ещё не тронут вовсе, клиент просто не делает дозапрос и показывает
   compact-данные в увеличенном виде — это уже даёт часть пользы
   (Recharts сам лучше расставит подписи/легенду на большей площади)
   без каких-либо изменений backend.

### 6.4 Что не меняется

- Ни один существующий контракт `compact`-ответа не меняется — только
  добавляется optional query param с default, сохраняющим текущее
  поведение.
- Данные остаются read-only, никакой мутации исходного ряда/сессии.
- Методология расчётов (PELT, STL, CWT-параметры и т.д.) идентична для
  обоих уровней детализации — различается только объём **отдаваемых для
  отрисовки** точек, не сам анализ.

## 7. Тестовая стратегия (TDD, по протоколу AGENTS.md)

### 7.1 RED → GREEN, компонентный уровень

- `ExpandableChartsProvider.test.tsx`:
  - `expand(id)` устанавливает `expandedChartId`;
  - повторный `toggle(id)` того же id — схлопывает (инвариант single-expand);
  - `expand(id2)` при уже раскрытом `id1` — раскрывает только `id2`
    (implicit collapse предыдущего).
- `ChartExpandToggle.test.tsx`:
  - рендерит нужную иконку и `aria-label` в зависимости от `expanded`;
  - клик вызывает `onClick` ровно один раз;
  - доступен по клавиатуре (`Enter`/`Space` через `@testing-library/user-event`).
- `ExpandableChartPanel.test.tsx`:
  - в свёрнутом состоянии — обычный flex-блок, без `absolute`/`z-20`;
  - в раскрытом — применяются `absolute inset-0 z-20`;
  - `Esc` при раскрытом состоянии вызывает `toggle`;
  - `Esc` при свёрнутом состоянии — no-op.

### 7.2 Контрактный тест покрытия (по аналогии с Task 88/89)

`ExpandableChartCoverage.test.ts` — не рендерит компоненты, а статически
проверяет исходники (как уже принято в проекте для похожих контрактов
высоты/адаптивности): перечисляет все файлы компонентов-Обзоров
(паттерн имени файла `*Overview.tsx` во всех разделах Validation /
Preprocessing / EDA / Modeling) и требует, чтобы каждый визуальный блок
внутри них использовал `ExpandableChartPanel`. Тест изначально **RED**
(ни один Обзор ещё не адаптирован) — фиксируется полный список файлов,
подлежащих доработке, что становится чек-листом поэтапного роллаута
(§8).

### 7.3 Интеграционные тесты

- Смена активного таба представления внутри Обзора при раскрытом графике
  → `expandedChartId` сбрасывается.
- Смена датасета/target при раскрытом графике → сброс.
- Размонтирование Обзора (переход на другую вкладку платформы) →
  состояние провайдера уничтожается вместе с компонентом (это происходит
  автоматически, так как провайдер живёт на уровне конкретного Обзора, а
  не глобально — отдельный тест лишь фиксирует этот инвариант дизайна).

### 7.4 Backend-тесты (при подключении `detail_level`, поэтапно)

- Для каждого затронутого профиля: тест, что `detail_level=compact`
  (или его отсутствие) даёт **байт-в-байт идентичный** текущему
  контракту ответ (regression guard от случайного изменения дефолтного
  поведения).
- Тест, что `detail_level=expanded` даёт **не меньше** точек/бинов, чем
  compact, и не превышает зафиксированный вторичный потолок (по аналогии
  с уже существующим тестом бюджета PELT-сетки, Task 76).
- Тест таймингов (budget test) — expanded-режим не должен провоцировать
  таймауты/502 на render.com, аналогично проблеме, исправленной в Task 76.

## 8. Поэтапный роллаут

Учитывая масштаб (все Обзоры на всех вкладках — порядка 30+
компонентов по данным трассируемости Task 94), внедрение делится на
этапы, каждый — отдельная TDD-итерация по протоколу AGENTS.md:

1. **Этап 0 (эта спецификация).** Ревью тимлидом, утверждение вторичных
   потолков сэмплирования (§6.2), решение по открытым вопросам (§10).
2. **Этап 1 — фундамент.** Реализация `ExpandableChartsProvider`,
   `ExpandableChartPanel`, `ChartExpandToggle`, `useExpandableChart`,
   контрактный тест покрытия (RED, фиксирует полный список файлов).
   Без backend-изменений — только визуальное раскрытие с текущими
   (compact) данными.
3. **Этап 2 — пилот на самых плотных визуализациях.** Подключение
   `ExpandableChartPanel` к 3–4 самым «болезненным» Обзорам, где
   проблема нечитаемости наиболее выражена (CWT-хитмап спектрального
   анализа, структурные сдвиги, матрица моделей, декомпозиция) —
   валидация UX на реальных данных перед массовым тиражированием.
4. **Этап 3 — сэмплирование `detail_level`.** Добавление параметра в
   backend для профилей из Этапа 2, `useChartDetailData`, тесты §7.4.
5. **Этап 4 — тиражирование.** Подключение оставшихся Обзоров по
   чек-листу из контрактного теста, до полного GREEN.
6. **Этап 5 — сэмплирование для остальных профилей** (по мере
   необходимости, не обязательно все — часть Обзоров может не выигрывать
   от detail-режима, например простые line-графики с малым числом точек;
   для них раскрытие остаётся чисто визуальным, без дозагрузки).

## 9. Риски и меры

| Риск | Мера |
|---|---|
| Раскрытие ломает `position`-контекст Обзора, если у него нет `position: relative` | Контрактный тест §7.2 расширяется проверкой, что корневой контейнер каждого адаптированного Обзора имеет `relative` (или уже имеет — по факту вёрстки Task 88); при отсутствии — добавляется в рамках той же PR |
| Тяжёлые невидимые Recharts-инстансы (несколько графиков в одном Обзоре) продолжают рендериться под перекрытием, расходуя CPU | Условный рендер невидимых панелей (см. конец §4.4) |
| Рост нагрузки на render.com от `detail_level=expanded` (память/время) | Явный вторичный потолок как тестируемая константа (§6.2, §7.4), budget-тест по аналогии с Task 76 |
| Обратная несовместимость для клиентов API, не знающих про `detail_level` | Параметр Optional с default = текущее поведение; regression-тест «byte-for-byte» (§7.4) |
| Аналитик теряет ориентацию, если раскрытие меняет масштаб/тики графика неожиданно | UX-принцип: сам график не «переизобретается» в раскрытом виде — используется тот же тип отрисовки, просто с большей площадью и (опционально) более высоким разрешением данных |
| Залипшее раскрытое состояние при смене контекста | Явные reset-триггеры, п.7 сценария (§3) и тесты §7.3 |
