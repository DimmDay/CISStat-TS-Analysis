## 1. Краткая хронология наблюдаемого поведения

Сначала — наблюдения на текущем коде. Это последовательности локальных экспериментов на синтетических данных, а не реконструкция инцидента на Vercel/Render. Между независимыми экспериментами создавалось новое изолированное окружение.

| Шаг | Действие / наблюдаемый результат | Доказательство |
|---|---|---|
| T0 | До загрузки сессия не содержит исследуемый датасет и запуск. | Fixture сценариев P01–P09, P24–P25 |
| T1 | Загрузка CSV с одной числовой колонкой `rain`: бэкенд устанавливает цель и `source=auto`. Сначала сеется `target_column_changed`, затем middleware добавляет `upload_completed`. Идентификатор события выбора совпадает в двух слоях. | P01 |
| T2 | При двух числовых колонках цель остаётся пустой, рекомендация `rain` не становится фактом выбора. Ручной выбор `snow` создаёт legacy-совместимое событие без `payload.source`. | P02 |
| T3 | UI поставляет полные карты статусов. Неполная карта отклоняется до записи; полная карта `done` принимается и без исполнения проверок сервером. Повтор одинаковой карты даёт новые события. | P06–P07 |
| T4 | Преобразование `rain` в строковый тип сбрасывает цель в сессии. Событие коррекции содержит `target_column_reset=true`, но метаданные запуска сохраняют `rain`, а функции текста наставника и причины узла используют прежний выбор. | P03 |
| T5 | Restore загружает исходный CSV, восстанавливает `run.target_column` и историческую трассу. Цель снова `rain`, происхождение в сессии пустое; прежний `data_types=done` остаётся, хотя преобразование данных не восстановлено. | P04–P05 |
| T6 | После заполнения буфера старые события выпадают из слоя 1: статус раннего узла и отображаемое начало меняются. Полная история в слое 2 остаётся. | P11 |
| T7 | При локально внесённом отказе сохранения отчёта HTTP=500, но десять событий уже записаны в слой 2. При отказе записи хука исследовательский GET возвращает HTTP=200 без нового долговременного факта. | P08–P10 |
| T8 | Задержанная карта статусов старого запуска принимается после новой загрузки и записывается в новый запуск: тело отчёта не связывает его с исходным контекстом. | P24 |
| T9 | После `eda_check_status=done` повторный GET профиля ACF/PACF создаёт `profile_viewed`: проекция становится `running`. | P25 |

**Хронология разработки по документам, отдельно от собственных наблюдений.** Первичный план PROGR-1…8 ввёл каноническую трассу, граф, два слоя, наставника и отчёты. `spec_progress_v1.1.md` затем описала неполное покрытие действий/узлов/стадий и породила дальнейшие задачи. Журнал `worklog9.md` фиксирует последующее расширение поставщиков, карт статусов, моделирования и правил наставника. PROGR-24 устраняла расхождения с исходными рядами; PROGR-25 последовательно ввела авто-выбор, отображение происхождения, тексты, сквозные проверки и независимые сертификации. Последняя запись до настоящего аудита — PROGR-25-D-CERT с положительным заключением в своём периметре. Даты и результаты прошлых прогонов — факты содержания журнала; настоящим аудитом они целиком заново не воспроизводились.

## 2. Рамка исследования и основной вывод

«Прогресс» пригоден как основа **реестра исследовательских событий и навигации**. Для документирования воспроизводимого исследования существующему контуру недостаёт привязки к версии данных/цели, подтверждаемого происхождения результата, согласованного порядка, идемпотентной доставки и разграничения исторического достижения с действующей валидностью.

Положительно подтверждены: единый конструктор событий, одинаковый event_id при обычном зеркалировании, разделение рекомендации и выбора, честная неоднозначность, проверка формы полных отчётов до записи и вывод статусов из событий без повторного опроса всех профилей.

Обнаруженные расхождения относятся к разным категориям:

- **Дефекты согласованности:** сброс цели, потеря её происхождения при restore, привязка задержанного отчёта к чужому запуску, регресс статуса EDA.
- **Ограничения принятого контракта:** best-effort доставка, доверенная карта статусов от UI, restore исходного файла вместо промежуточного DataFrame, ограниченный сессионный буфер.
- **Методические ограничения:** тип события подменяет результат операции; просмотр результата подменяет утверждение о человеке; одинаковая картинка узла скрывает изменение метода; исторические статусы используются для новых данных.
- **Неустановленные факты эксплуатации:** реально выбранное хранилище на Render, число потерь, частота гонок, поведение живого браузера при ошибках.

Успех предыдущей сертификации PROGR-25 и настоящие находки совместимы: свежая загрузка и происхождение выбора проверены, а сброс цели после коррекции, контекст задержанных карт и интерпретация истории при restore требуют дополнительных контрактов.

## 4. Методическая корректность: что именно является фактом

### 4.1. Необходимые различия

| Сущность                | Что допустимо утверждать                               |                Что из неё не следует                 |
|-------------------------|--------------------------------------------------------|------------------------------------------------------|
| Запрос операции         | Поступило намерение с конкретными параметрами          | Операция завершилась и изменила данные               |
| HTTP 2xx                | Handler вернул успешный ответ по своему контракту      | Факт гарантированно записан в обоих слоях            |
| Серверный результат диагностики | Алгоритм выдал результат на определённом входе | Аналитик просмотрел, согласовал или принял результат |
| Карта статусов UI       | Клиент сообщил отображаемую картину   | Все проверки пересчитаны сервером и привязаны к текущей версии данных |
| `profile_viewed` от GET | Приложение запросило профиль                 | Человек увидел результат; исследование не было ранее завершено |
| EDA `done` | По действующему решению: результат открыт/показан в UI | Качество ряда удовлетворительно либо исследование научно завершено|
| Выбор `auto`            | Правило установило единственного допустимого кандидата | Аналитик явно подтвердил цель                        |
| Коррекция применена | Выполнена попытка применения с сообщённым результатом | Все нарушения устранены либо изменена хотя бы одна строка |
| Исторический `done` | В прошлом при своём контексте было событие достижения | Результат применим к восстановленным или изменённым данным|
| Отчёт Markdown          | Представление имеющегося журнала          | Полная воспроизводимость расчёта без параметров/версий/артефактов |

### 4.2. Подтверждённые ограничения смысла

1. **Тип события и исход операции смешаны.** Общая карта даёт `correction_previewed → warning`, `correction_applied → done` (есть специальные исключения для отдельных типов/статусов). P14 подтверждает: чистый preview получает причину «Найдены нарушения», а no-op apply — `done` без доказательства устранения проблемы. Существование операции и качество результата должны проецироваться отдельно.
2. **Атрибуция человека зависит от доверенного UI-контракта.** Текст `structure_confirmed` — «Временная колонка подтверждена аналитиком». В текущем `DatasetPassportPanel.tsx:475–495` POST выполняется внутри действия capture, что согласуется с текстом. Однако само событие хранит только колонку и default actor, не удостоверяет trigger/явное согласование. Для общего документирующего API действие пользователя следует отличать от программного запроса; автоматический POST даты в текущем UI этим аудитом не установлен.
3. **Первый кандидат — рекомендация, не оценка оптимальности.** Текущая спецификация прямо фиксирует отсутствие ранжирования; P02 подтверждает честное отсутствие выбора при неоднозначности. Такое поведение сохранять.
4. **EDA `done` — намеренно факт просмотра.** Не вводить автоматически warning по «плохому» статистическому профилю вопреки решению v1.1. Улучшение — честно назвать событие показа и отделить его от вычисления профиля.
5. **Наблюдения наставника — отдельная телеметрия.** Частота записей соответствует вызовам правил/эндпоинтов, не числу уникальных научных решений. Интервал `max(ts)-min(ts)` по стадии — календарный span между событиями; его нельзя без дополнительных данных называть временем активной работы.
6. **Методология отчёта берётся из актуального реестра.** Без закрепления версии текста/правила исторический документ может описывать сегодняшнюю методику рядом со старыми фактами. Точный выполненный расчёт должны удостоверять параметры и версия исполнителя; пояснения следует помечать как справочный текст текущей версии.

## 8. Корректировки к будущей архитектуре

Ниже — нормативные предложения этого аудита. Они ещё не реализованы и не переписывают молча принятые решения прежних спецификаций.

### 8.1. Рекомендуемый минимальный контракт

Сохранять канон TraceEvent и legacy-совместимость. Новые поля вводить аддитивно с `schema_version`. Исторические события не исправлять задним числом: добавлять correction/invalidation-события со ссылкой на исходный факт.

| Группа | Предлагаемое содержание | Зачем |
|---|---|---|
| Идентичность/порядок | event_id, run_id, стабильный commit sequence, schema_version | Дедуп и один порядок проекции во всех consumer'ах. sequence — порядок фиксации, не автоматически время научной причинности. |
| Причинность | operation_id / request_id, causation_id; UI report_id | Связь запроса, результата, UI-наблюдения и повторов доставки. |
| Контекст | raw dataset fingerprint, dataset_revision, target column/origin, context_id | Тот же файл после преобразования — другой вычислительный вход. context_id вычислять/проверять сервером. |
| Происхождение | producer, trigger=human/auto/background, actor_kind и при наличии actor_id | Кто выполнил действие, кто его инициировал и кто увидел результат — разные вопросы. |
| Результат | outcome, result_id/artifact reference/hash, параметры и краткая summary | Воспроизводимость без копирования сырых рядов в каждый event. |
| Методика | algorithm/version, rule_id/version, code/deployment revision | Историческое объяснение выполненного расчёта. |
| Время | occurred_at (если известно), observed_at/recorded_at, raw_ts + quality для миграции | Не подменять неизвестное время события сегодняшним. Порядок задавать sequence. |
| Проекция | status + reason/count с source_event_id/context_id; watermark; validity | Прозрачное происхождение каждого поля и применимость к текущим данным. |

Не все поля обязательны у каждого типа. Для каждого event_type определить проверяемую JSON-схему и уровень доказательности: `server_result`, `client_observation`, `user_decision`, `operational`. UI-map сохранять как client observation с версиями контекста и источниками результатов; не принуждать сервер повторно рассчитывать все профили.

### 8.2. Цель, восстановление и инвалидирование

- Ввести единый reducer effective target для session/run/mentor/report: choice + reset/invalidation. Событие сброса должно иметь null/new target, origin/reset_reason и контекст до/после. Допустим dedicated `target_column_cleared` или versioned `target_column_changed`; выбор зависит от legacy-валидации типов.
- Restore явно объявляет режим `raw` и создаёт новую ревизию/контекст. Исторические действия остаются видимыми; их результаты не считаются проверенными для нового входа.
- Происхождение цели восстанавливать из согласованных метаданных либо исторического choice/reset reducer. Legacy отсутствие source трактовать user только в согласованных пределах прежнего контракта; повреждённую историю не выдавать за подтверждённого человека.
- Не выполнять повторный авто-выбор как замену восстановлению: иначе появляется другое решение вместо сохранённого.
- Статус completion и validity разделить. Например, «Просмотрено на revision=3; текущая revision=4, результат не пересчитан». Это сохраняет достижения и не обещает актуальность.
- Смена цели/временной структуры инвалидирует зависящие от них результаты. Список зависимостей выводить из реестра узлов, а не разбрасывать reset по компонентам.

### 8.3. Доставка и порядок

Best-effort оставить явно обозначенным режимом навигационной телеметрии. Для утверждения «операция документирована» нужен receipt/watermark и наблюдаемый статус доставки.

Выбрать авторитетный ledger и транзакционную границу. Практический вариант: durable запись domain event + update run в одной транзакции, затем асинхронная проекция Redis/панели с повтором. Если научная операция завершается в сессионном слое, нужен outbox/журнал обязательства в том же устойчивом хранилище; простая дополнительная запись после response не создаёт атомарность.

Сбой записи нельзя решать безусловным HTTP rollback после уже применённого изменения DataFrame: это даст ложное обещание отката. Обозначить отдельно «операция выполнена, документирование ожидает доставки» и обеспечить повтор по operation_id. До реализации устойчивого хранения такой гарантии не заявлять.

Идемпотентность:

1. Клиент формирует report_id и привязывает run/context; сервер отклоняет чужой/устаревший контекст до первой записи.
2. Повтор одного report_id даёт прежний receipt, а не новые события.
3. Новый содержательный расчёт получает новый operation/result_id, даже если status/count совпали.
4. Projection обновляется из полного ledger либо checkpoint+tail по watermark; cap UI-трассы ограничивает только отображаемый список.
5. Все потребители используют одинаковый канонический порядок. Не сортировать один и тот же корпус по append в одном месте и ts в другом.
6. Memory реализует те же дедуп/порядок, что Postgres; startup/health показывает фактический backend. Для обязательного durable режима тихий fallback недопустим.

Redis CAS уже имеется. Его наличие не создаёт транзакции с ResearchRunStore и не гарантирует доставку факта после конфликта: ошибку нужно учитывать и восстанавливать, а не заменять CAS бездумным last-write-wins.

### 8.4. Разделение представлений

Проекции панели, наставника и отчёта должны быть читателями одной версии истории с известным watermark. Каждая цифра/причина ссылается на породивший её факт; не переносить count прежнего warning на новый done без маркировки.

Текст отчёта должен различать «автоматически выбрано», «выбрано аналитиком», «результат показан», «коррекция применена», «нарушения остаются», «исторически выполнено». Новые Modeling-типы получают шаблоны и сохраняют параметры/исходы.

Операционные логи связывать с ledger через request/operation/event/run/context ids. Логи могут иметь другие retention/sampling правила, но sampling не должен применяться к обязательным исследовательским фактам. Не сохранять сырые ряды и секреты в обычном лог-сообщении; использовать артефактные ссылки и безопасные summaries.
