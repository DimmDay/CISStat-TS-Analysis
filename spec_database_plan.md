### Архитектурные решения плана (фиксация до кода)

1) Реестр коннекторов app/data/db_connectors.py — единственная точка знания о СУБД: DbConnectorSpec {id, label, aliases, mode: server|embedded, dialect/URL-builder, native-client (только ClickHouse), default_port, test_sql (sqlalchemy.text()), ssl_support, vendor-детекция}; 6 записей, PostgreSQL и Postgres Pro — ОДНА запись с alias'ами (протокол совместим, вендор различается по SELECT version()). 
2) SQLAlchemy 2.0 — универсальный слой (postgresql+psycopg, mysql+pymysql, mssql+pyodbc, sqlite://, duckdb://); clickhouse-connect — нативный клиент CH (как в legacy); фикс D1 (text()) — в реестре каждая запись несёт готовый text()-объект тестового запроса. 
3) Два профиля подключения — discriminated union в API-схемах: ServerDbCredentials {host, port, database, user, password, ssl} для 4 серверных СУБД и EmbeddedDbSource {path} для DuckDB/SQLite; DuckDB дополнительно умеет прямой SELECT по Parquet/CSV-файлу. 
4) Безопасность ядра из находок аудита D2-D6 обязательна ДО открытия эндпоинтов в общем контуре: read-only guard (только SELECT/WITH, запрет мультистейтментов и DML/DDL-ключевых слов), принудительный row_limit (env UPLOAD_DB_ROW_LIMIT, дефолт 1 000 000) + chunksize-стриминг, ssl-флаги по СУБД (PG sslmode, MySQL ssl, MSSQL Encrypt/TrustServerCertificate, CH secure/verify), централизованное маскирование секретов в исключениях, host-whitelist (env, off в песочнице). 
5) Контракт результата = контракт файла: POST /v1/upload/db/load возвращает Тот ЖЕ UploadResponse (preview/columns_info/quality/parse_warnings) через переиспользование _compute_column_info/_compute_quality_teaser/_compute_parse_warnings (apps/api/upload_common.py) → SessionStore → БД-датасет проходит существующий 5-остановочный пайплайн «Загрузки» без новых типов событий трассы. 
6) Одна реализация семантики: legacy app.py в конце эпика переключается на общий реестр (UPLOAD-DB-10), дублирование init_db_connection-логики запрещено.

### Скоуп-решения (вынесено на контроль тимлиду)

- S1: драйвер PG — psycopg v3 (диалект postgresql+psycopg; psycopg[binary]>=3.1 УЖЕ есть в apps/api для research_runs — одна зависимость на два назначения) + psycopg2-binary в корневых requirements для legacy-совместимости прототипа; альтернатива — единый psycopg2-binary. 
ОТВЕТ ТИМЛИДА: драйвер PG — psycopg v3.
- S2: драйвер MSSQL — pyodbc + msodbcsql18 (официальная поддержка Microsoft, тянет системный слой в Dockerfile) vs pymssql (чистый pip, легче, less official); рекомендация pyodbc, fallback pymssql. 
ОТВЕТ ТИМЛИДА: pyodbc, fallback pymssql.
- S3: DuckDB/SQLite v1 — путь на серверной ФС (доверенная среда корпоративного сервера); загрузка .duckdb/.parquet файлов через drag-and-drop — вне v1 (аддитивное расширение после отладки). 
ОТВЕТ ТИМЛИДА: загрузка .duckdb/.parquet файлов через drag-and-drop — вне v1
- S4: row_limit дефолт 1 000 000 строк (env UPLOAD_DB_ROW_LIMIT), таймауты 10с/60с env-переопределяемые. 
ОТВЕТ ТИМЛИДА: row_limit дефолт 1 000 000 строк, таймауты 10с/60с.
- S5: whitelist-режим — off в песочнице, решение об on в проде после утверждения сетевой топологии (наследуется из UPLOAD-DB-AUDIT-1).
ОТВЕТ ТИМЛИДА: ок.

### Оценка рисков плана

RP1 (средний): psycopg v3 vs psycopg2 — различия в дефолтных таймаутах/sslmode-поведении; закрывается интеграционными тестами стенда UPLOAD-DB-8 на реальном PG. RP2 (средний): msodbcsql18 в Docker требует внешнего apt-репозитория Microsoft — пин версии и прокси-доступность в CI; fallback pymssql снимает риск. RP3 (низкий): duckdb-engine dialect совместим с sqlalchemy>=2.0 (проверить пин при UPLOAD-DB-3 RED-фазой). RP4 (низкий): мультистейтмент-guard эвристический (лексический) — серверная защита остаётся на read-only пользователе БД; документируется в UPLOAD-DB-9 (рекомендация развертывания с read-only кредами). RP5 (нулевой): контракты «Прогресса»/статусы остановок не меняются (БД-датасет идёт пайплайном файла) — регресс-база jest/pytest стабильна. RP6 (низкий): 10 задач эпика — риск расползания скоупа; каждая задача имеет DoD и поставку, изменение матрицы СУБД = правка реестра одной записи.
