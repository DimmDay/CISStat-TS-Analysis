Ступенчатые объёмные скидки (стандартный\n  enterprise-паттерн) — явный follow-up (§10), реализуется как\n  отдельная таблица `SEAT_PRICING_TIERS`, не меняющая эту формулу, а\n  подменяющая множитель.\n- **Квота потребления (CU)** — пулится на уровне Account и\n  масштабируется от seats, а не делится поровну на участника:\n  ```\n  compute_unit_pool_per_cycle(account) = PLAN_DEFINITIONS[account.plan].cu_per_seat × account.seats\n  ```\n  Обоснование пулинга, а не индивидуальных квот на участника — в\n  реальной команде нагрузка асимметрична (один аналитик гоняет\n  tuning/backtest, остальные просматривают Обзоры) — индивидуальные\n  квоты гарантированно создают ситуацию «моя квота кончилась, хотя я её\n  не тратил», что противоречит идее самообслуживания без ручного\n  вмешательства поддержки.\n\n### 3.3 Пересчёт при изменении состава\n\nИзменение `seats` (добавление/удаление участника) должно:\n- немедленно обновить `compute_unit_pool_per_cycle` (пропорционально,\n  без ожидания следующего расчётного периода — иначе владелец,\n  добавивший участника, не получит немедленно доступную для команды\n  квоту);\n- передать новое значение `quantity` в биллинг-провайдера (см. §8) для\n  proration — списание/зачисление разницы стоимости за оставшийся\n  период текущего цикла, а не постфактум в конце месяца.\n\n## 4. Compute Unit (CU) — единица учёта\n\n### 4.1 Почему не токены (кратко, полная аргументация — в обсуждении, зафиксирован вывод)\n\nПлатформа генерирует результаты гетерогенных численных алгоритмов, чья\nстоимость на одинаковом объёме входных данных различается на порядки\n(простая статистика vs CWT vs PELT vs backtest/tuning с комбинаторным\nростом от `trials × folds`). Единица «токен» у LLM работает, потому что\nпредельная стоимость обработки токена в фиксированной архитектуре\nмодели примерно постоянна — у нашей платформы такой однородности\nфизически нет, поэтому буквальный перенос «input/output tokens»\nсистематически исказил бы цену: либо демпинг тяжёлых операций, либо\nпереплата за тривиальные.\n\nЧто переносится из LLM-биллинга **по паттерну**, а не по единице\nизмерения:\n- непрерывный метеринг с балансом/списанием вместо грубых лимитов;\n- дифференциация цены **по типу операции** (у LLM — по модели, здесь —\n  по алгоритму), а не единая ставка на всё;\n- раздельный учёт «подготовки данных» (обычно дешевле) и «тяжёлого\n  расчёта» (обычно дороже) как отдельных компонент формулы, а не как\n  токенов символьного потока.\n\n### 4.2 Формула\n\n```python\n# apps/api/billing/compute_units.py\n\ndef compute_cu(\n    operation: OperationType,\n    rows: int,\n    columns: int,\n    repetitions: int = 1,   # folds × trials для tuning/backtest, иначе 1\n) -> float:\n    coef = ALGORITHM_COEFFICIENTS[operation]  # калибруется эмпирически\n    data_volume = rows * columns\n    return coef.base * data_volume ** coef.exponent * repetitions\n```\n\n`ALGORITHM_COEFFICIENTS` — таблица по типу операции, источник истины\nпо аналогии с `PLAN_DEFINITIONS`:\n\n| Операция (`OperationType`) | `base` | `exponent` | Комментарий |\n|---|---|---|---|\n| `basic_stats` / `smoothing` | низкий | ~1.0 | линейно от объёма |\n| `stl_decomposition` | средний | ~1.0–1.1 | |\n| `spectral_periodogram` | средний | ~1.1 | |\n| `cwt` | высокий | ~1.2–1.3 | масштабы CWT учитываются как множитель в `repetitions`, не в `columns` |\n| `structural_breaks_pelt` | высокий, зависит от бюджета сетки | ~1.2 | переиспользует существующий бюджет-параметр PELT (см. §4.3) |\n| `model_backtest` | высокий | ~1.0 | `repetitions = folds` |\n| `model_tuning` | самый высокий | ~1.0 | `repetitions = trials × folds` |\n\nКонкретные числовые значения `base`/`exponent` — **не фиксируются в этой\nспецификации** (открытый вопрос §10, требует калибровки по реальным\nзамерам, не по догадке).\n\n### 4.3 Ключевое архитектурное решение: переиспользование, не новая инфраструктура\n\nПлатформа уже располагает инфраструктурой измерения стоимости операций:\n- бюджетирование PELT-сетки (фикс HTTP 502 в «Структурных сдвигах»,\n  Task 76) — уже связывает объём данных с вычислительным бюджетом;\n- диагностика исполнения тюнинга (`TuningPlanExecution`, Task 99) — уже\n  фиксирует фактическое число trials/folds на исполнение.\n\n`compute_cu(...)` не дублирует эти измерения, а **читает уже\nсуществующие величины** (бюджет PELT-сетки, число trials/folds из\n`TuningPlanExecution`) как входные параметры формулы — это одна и та же\nточка данных, используемая сегодня для защиты от таймаута/502 и теперь\nдополнительно для метеринга CU. Первая задача Этапа 1 (§11) — аудит\nэтих двух мест кода, чтобы `compute_cu` не переизобретал их, а\nпараметризовался ими напрямую.\n\n### 4.4 Где считается и списывается\n\n```python\n# apps/api/auth.py — расширение require_capability\n\ndef require_capability(capability: str, operation: OperationType | None = None):\n    def dependency(principal: AuthenticatedPrincipal = Depends(get_current_principal)):\n        if not getattr(principal.capabilities, capability):\n            raise HTTPException(403, ...)\n        if operation is not None:\n            # резервируем CU ДО выполнения тяжёлой операции (не после)\n            reserve_compute_units(principal.account_id, operation)\n        return principal\n    return dependency\n```\n\nПринципиальное решение: **CU резервируется до выполнения операции**, а\nне списывается по факту после — иначе тяжёлая операция (например,\ntuning на грани лимита) успеет отработать и создать реальную\nинфраструктурную стоимость даже при исчерпанном пуле, что подрывает\nсаму цель метеринга (защита пула = защита инфраструктурного бюджета\nrender.com, не только бухгалтерия). При недостатке пула — `402 Payment\nRequired`/аналог, а не «пусть досчитается, потом запретим следующий\nзапрос».\n\nПосле фактического выполнения — точная фиксация факта (`rows`,\n`repetitions` могли отличаться от оценки на входе, например, tuning\nзавершился раньше по early-stopping) — резерв корректируется до\nфактического значения, не обязан совпадать один в один с оценкой.\n\n## 5. Доступ к этапам исследования по тарифу (Stage Gating)\n\n### 5.1 Мотивация и охват\n\nПо прямому продуктовому решению **демонстрационный тариф покрывает все\nшесть этапов основного исследовательского пайплайна** (Загрузка →\nВалидация → Предобработка → EDA → Моделирование → Прогнозирование,\n`apps/api/session_store.py::STAGES`) — это уже согласуется с духом\n`can_upload_own_data=True`/лимитов demo из `ROLES_AND_PLANS_SPEC.md §3`.\nНо платформа декларирует ещё **четыре прикладных модуля** за пределами\nэтого пайплайна (`packages/ui/lib/navigator-stops.ts`, id `scenario` /\n`causal` / `decision` / `monitoring` — сейчас помечены `soon: true`,\nв активной разработке, ещё не отдельные страницы): Сценарный анализ,\nПричинный анализ, Поддержка принятия решений, Мониторинг. Продуктовое\nрешение: эти четыре модуля **не входят** в демонстрационный тариф ни в\nкаком виде; доступны начиная со «Стартового» и выше.\n\nЭто не новая независимая ось прав, а расширение уже существующего\nмеханизма `Capabilities`, резолвящегося через `account.plan` (§2.1) —\nто же единственное место, где сегодня резолвятся `can_train_models`/\n`can_use_api` и т.д. — переиспользуется, не дублируется.\n\n### 5.2 Расширение `Capabilities` (`ROLES_AND_PLANS_SPEC.md`)\n\n```python\n# apps/api/plans.py (расширение Capabilities из ROLES_AND_PLANS_SPEC.md,\n# по тому же принципу, что и account_id/account_role добавлены\n# к AuthenticatedPrincipal в §2.1 этого документа -- расширение поля\n# существующей модели, не создание параллельного контракта)\n\nclass Capabilities(BaseModel):\n    # ... существующие поля без изменений ...\n    restricted_stage_ids: frozenset[str] = frozenset()\n```\n\n`restricted_stage_ids` — множество id модулей, к которым план **не**\nдаёт доступа. Пусто по умолчанию (ничего не ограничено): тариф явно\nперечисляет запрещённое, а не разрешённое — добавление нового модуля\nв будущем не требует правки существующих тарифов, если он не должен\nбыть платным барьером специально.\n\n**Единый словарь id.** Значения `restricted_stage_ids` — те же\nстроковые id, что уже используются в `packages/ui/lib/navigator-stops.ts`\n(`scenario`, `causal`, `decision`, `monitoring`) — отдельный enum на\nбэкенде не заводится. Тот же принцип уже действует в проекте между\n`STAGE_DEFS` (frontend) и `STAGES` (`session_store.py`, backend) —\nid совпадают 1:1 между двумя языками по контракту, а не дублируются\nнезависимо (см. комментарий в самом `navigator-stops.ts`).\n\n### 5.3 Расширение `PLAN_DEFINITIONS`\n\n| Тариф | `restricted_stage_ids` |\n|---|---|\n| `demo` | `{"scenario", "causal", "decision", "monitoring"}` |\n| `starter` | `{}` (не ограничено) |\n| `professional` | `{}` |\n| `enterprise` | `{}` |\n| `internal` (см. §2.2) | `{}` |\n\nОграничение введено **только** для `demo` — по прямому продуктовому\nрешению этой задачи. Открытый вопрос, должен ли `starter` тоже\nограничиваться — см. §10, новый п.7 (не решается в одностороннем\nпорядке здесь).\n\n### 5.4 Точка проверки\n\nАналог `require_capability`, но для доступа к **этапу**, а не к\nконкретному действию — разные по природе проверки не смешиваются в\nодну функцию:\n\n```python\n# apps/api/auth.py (расширение)\n\ndef require_stage_access(stage_id: str):\n    """id должен совпадать с packages/ui/lib/navigator-stops.ts."""\n    def dependency(principal: AuthenticatedPrincipal = Depends(get_current_principal)):\n        if stage_id in principal.capabilities.restricted_stage_ids:\n            raise HTTPException(\n                status_code=402,\n                detail=STAGE_UPGRADE_MESSAGES.get(stage_id, DEFAULT_STAGE_UPGRADE_MESSAGE),\n            )\n        return principal\n    return dependency\n```\n\n`402 Payment Required`, не `403 Forbidden` — тот же код статуса, что уже\nвыбран в §4.4 для недостатка пула CU: причина отказа по смыслу одна и\nта же — «это решается оплатой тарифа», а не «у вас в принципе нет прав»\n(`403` в контракте платформы означает и должен означать именно\nпоследнее — эти два кода не взаимозаменяемы в этой архитектуре).\n\n### 5.5 Формулировка сообщения — вежливо, конкретно, с указанием пути апгрейда\n\n```python\n# apps/api/billing/messages.py (новый модуль; либо в plans.py, если\n# billing/ к моменту реализации ещё не заведён, см. Этап 1 §11)\n\nDEFAULT_STAGE_UPGRADE_MESSAGE = (\n    "Этот раздел доступен на платных тарифах. Демонстрационный тариф "\n    "открывает полный цикл исследования — от загрузки данных до прогноза "\n    "с доверительными интервалами; сценарный анализ, причинный анализ, "\n    "поддержка принятия решений и мониторинг входят в тарифы «Стартовый» "\n    "и выше. Посмотреть тарифы можно в разделе «Тарифы»."\n)\n\nSTAGE_UPGRADE_MESSAGES: dict[str, str] = {\n    "scenario": (\n        "Сценарный анализ (What-if) доступен на платных тарифах — "\n        "начиная со «Стартового». Демонстрационный тариф даёт полный "\n        "доступ к анализу и прогнозированию; для моделирования "\n        "гипотез «что если» перейдите на платный тариф."\n    ),\n    "causal": (\n        "Причинный анализ доступен на платных тарифах — начиная со "\n        "«Стартового». Перейдите на платный тариф, чтобы выявлять "\n        "причинно-следственные связи между рядами."\n    ),\n    "decision": (\n        "Поддержка принятия решений доступна на платных тарифах — "\n        "начиная со «Стартового». Перейдите на платный тариф для "\n        "сравнения альтернатив и рекомендательных правил."\n    ),\n    "monitoring": (\n        "Мониторинг прогноза доступен на платных тарифах — начиная со "\n        "«Стартового». Перейдите на платный тариф для непрерывного "\n        "контроля точности прогноза по мере поступления новых данных."\n    ),\n}\n```\n\nТон закреплён явно, не оставлен на усмотрение реализации: сообщение не\nзвучит как отказ («вам запрещено»), а как приглашение («это доступно на\nтарифе X, вот как перейти») — тот же тон, которого придерживается\nостальная часть платформы (Наставник, `spec_progress.md`: не отчитывает\nпользователя, а подсказывает следующий шаг).\n\n### 5.6 Frontend — архитектурное наблюдение для будущей реализации\n\n`packages/ui/lib/navigator-stops.ts` уже сегодня помечает эти четыре\nмодуля флагом `soon: true` («модуль в активной разработке») — но это\n**другая** причина недоступности («ещё не построено»), не «недоступно\nвашему тарифу». Когда эти модули будут реализованы, `soon: true` должен\nлибо смениться на новый, отдельный флаг (например, `requiresPlan?:\nPlanName`), либо оба состояния должны сосуществовать как разные поля —\nиначе UI не сможет корректно различить «скоро появится у всех» и «уже\nесть, но не на вашем тарифе». Это наблюдение фиксируется здесь как\nтребование к будущей фронтенд-реализации, не решается этим документом —\nдоработка самого `navigator-stops.ts` вне охвата этой спецификации.\n\n### 5.7 Обнаруженное противоречие с таблицей `ROLES_AND_PLANS_SPEC.md` — требует решения тимлида\n\nПри переносе требования «демо покрывает все этапы, кроме этих четырёх»\nв конкретный механизм обнаружено прямое расхождение с уже опубликованной\nтаблицей возможностей (`ROLES_AND_PLANS_SPEC.md §3`): `can_train_models`\nдля `demo` — `❌`, то есть по буквальному смыслу существующей таблицы\nдемо не может обучать модели вообще — а Моделирование является одним\nиз шести этапов ОСНОВНОГО пайплайна, который по формулировке этой\nзадачи демо должен покрывать полностью. Это реальное противоречие\nмежду двумя явно сформулированными требованиями, а не надуманное.\n\nНе редактируется в одностороннем порядке этим документом (таблица\nживёт в `ROLES_AND_PLANS_SPEC.md`, не в этом файле), но фиксируется как\nрешение, требующее подтверждения тимлидом. Рекомендация (не решение)\nэтой спецификации: вероятнее всего `can_train_models=False` для demo\nизначально имелось в виду **уже**, чем «доступ к вкладке Моделирование»\nцеликом — скорее всего относилось к тюнингу гиперпараметров\n(`model_tuning` — самая дорогая операция по таблице\n`ALGORITHM_COEFFICIENTS`, §4.2) или к обучению кастомных конфигураций,\nа не к базовому бэктесту уже реализованных моделей на демо-датасете.\nЕсли это верное прочтение — стоит переименовать поле в\n`ROLES_AND_PLANS_SPEC.md` (например, в `can_tune_hyperparameters`) для\nоднозначности, либо явно развести «бэктест/базовый прогноз» (доступно\ndemo) и «тюнинг» (недоступно demo) двумя разными флагами. Если это НЕ\nверное прочтение и демо действительно не должен видеть Моделирование\nвообще — тогда формулировка задачи («все этапы, кроме четырёх») сама\nтребует уточнения тимлидом, так как противоречит уже принятой таблице.\nВнесено как открытый вопрос №6 (§10).\n\n## 6. Frontend-зеркало (`packages/ui/lib/plans.ts`)\n\nРасширяется теми же сущностями (`Account`, `AccountType`, `AccountRole`,\n`compute_unit_pool_balance`) — используется **только для UX** (баннер\n«осталось N CU», кнопка приглашения участника видна только `OWNER`,\nпереключатель моно→мульти в настройках) — реальная проверка баланса и\nрезервирование остаются исключительно на бэкенде, как и зафиксировано\nв исходном документе для `Capabilities` (§5 `ROLES_AND_PLANS_SPEC.md`\nпро фронтенд-зеркало распространяется и на этот контракт). Тем же\nпринципом зеркалится и `restricted_stage_ids` (§5.2) — фронтенд читает\nего только для UX (см. §5.6: как именно совместить с уже существующим\n`soon: true` в `navigator-stops.ts` — решается отдельно, не здесь),\nреальная проверка при переходе на `/scenario`, `/causal` и т.д. — тоже\nисключительно на бэкенде через `require_stage_access(...)` (§5.4).\n\n## 7. Тестовая стратегия (TDD)\n\n- **`Account`/`AccountMembership` — модельный уровень:**\n  - создание `MONO`-аккаунта фиксирует `seats == 1`, попытка изменить\n    `seats` для `MONO` — отклоняется на уровне валидации модели;\n  - Пользователь регистрируется → создаётся `Account(account_type=MONO, seats=1)`,\n   он же становится `AccountMembership(account_role=OWNER)`.\n2. В любой момент из настроек аккаунта пользователь может переключить\n   `account_type → MULTI` — это **не создаёт новый Account**, а\n   переводит существующий (сохраняя историю анализов/сессий,\n   привязанных к `account_id`, а не к отдельному принципалу — важное\n   архитектурное следствие: история анализов **уже должна быть**\n   собственностью Account, а не Principal, иначе при переходе moно→мульти\n   данные владельца «потеряются» для остальных участников команды).\n3. В режиме MULTI владелец (`AccountRole.OWNER`) приглашает\n   участников по email — каждое принятое приглашение создаёт нового\n   `Principal` + `AccountMembership(account_role=MEMBER)` и увеличивает\n   `Account.seats` на 1.\n4. Удаление участника — `seats -= 1`, немедленно.\n\n### 3.2 Автоматический расчёт цены\n\nДве **независимые** формулы, которые нельзя смешивать:\n\n- **Цена** — определяется числом seats, не фактическим потреблением:\n  ```\n  price(account) = PLAN_DEFINITIONS[account.plan].base_price × account.seats\n  ```\n  Линейная модель — намеренный выбор для v1: пользователь может\n  посчитать свою цену в уме до того, как начал пользоваться платформой,\n  без обращения в поддержку. Ступенчатые объёмные скидки (стандартный\n  enterprise-паттерн) — явный follow-up (§10), реализуется как\n  отдельная таблица `SEAT_PRICING_TIERS`, не меняющая эту формулу, а\n  подменяющая множитель.\n- **Квота потребления (CU)** — пулится на уровне Account и\n  масштабируется от seats, а не делится поровну на участника:\n  ```\n  compute_unit_pool_per_cycle(account) = PLAN_DEFINITIONS[account.plan].cu_per_seat × account.seats\n  ```\n  Обоснование пулинга, а не индивидуальных квот на участника — в\n  реальной команде нагрузка асимметрична (один аналитик гоняет\n  tuning/backtest, остальные просматривают Обзоры) — индивидуальные\n  квоты гарантированно создают ситуацию «моя квота кончилась, хотя я её\n  не тратил», что противоречит идее самообслуживания без ручного\n  вмешательства поддержки.\n\n### 3.3 Пересчёт при изменении состава\n\nИзменение `seats` (добавление/удаление участника) должно:\n- немедленно обновить `compute_unit_pool_per_cycle` (пропорционально,\n  без ожидания следующего расчётного периода — иначе владелец,\n  добавивший участника, не получит немедленно доступную для команды\n  квоту);\n- передать новое значение `quantity` в биллинг-провайдера (см. §8) для\n  proration — списание/зачисление разницы стоимости за оставшийся\n  период текущего цикла, а не постфактум в конце месяца.\n\n## 4. Compute Unit (CU) — единица учёта\n\n### 4.1 Почему не токены (кратко, полная аргументация — в обсуждении, зафиксирован вывод)\n\nПлатформа генерирует результаты гетерогенных численных алгоритмов, чья\nстоимость на одинаковом объёме входных данных различается на порядки\n(простая статистика vs CWT vs PELT vs backtest/tuning с комбинаторным\nростом от `trials × folds`). Единица «токен» у LLM работает, потому что\nпредельная стоимость обработки токена в фиксированной архитектуре\nмодели примерно постоянна — у нашей платформы такой однородности\nфизически нет, поэтому буквальный перенос «input/output tokens»\nсистематически исказил бы цену: либо демпинг тяжёлых операций, либо\nпереплата за тривиальные.\n\nЧто переносится из LLM-биллинга **по паттерну**, а не по единице\nизмерения:\n- непрерывный метеринг с балансом/списанием вместо грубых лимитов;\n- дифференциация цены **по типу операции** (у LLM — по модели, здесь —\n  по алгоритму), а не единая ставка на всё;\n- раздельный учёт «подготовки данных» (обычно дешевле) и «тяжёлого\n  расчёта» (обычно дороже) как отдельных компонент формулы, а не как\n  токенов символьного потока.\n\n### 4.2 Формула\n\n```python\n# apps/api/billing/compute_units.py\n\ndef compute_cu(\n    operation: OperationType,\n    rows: int,\n    columns: int,\n    repetitions: int = 1,   # folds × trials для tuning/backtest, иначе 1\n) -> float:\n    coef = ALGORITHM_COEFFICIENTS[operation]  # калибруется эмпирически\n    data_volume = rows * columns\n    return coef.base * data_volume ** coef.exponent * repetitions\n```\n\n`ALGORITHM_COEFFICIENTS` — таблица по типу операции, источник истины\nпо аналогии с `PLAN_DEFINITIONS`:\n\n| Операция (`OperationType`) | `base` | `exponent` | Комментарий |\n|---|---|---|---|\n| `basic_stats` / `smoothing` | низкий | ~1.0 | линейно от объёма |\n| `stl_decomposition` | средний | ~1.0–1.1 | |\n| `spectral_periodogram` | средний | ~1.1 | |\n| `cwt` | высокий | ~1.2–1.3 | масштабы CWT учитываются как множитель в `repetitions`, не в `columns` |\n| `structural_breaks_pelt` | высокий, зависит от бюджета сетки | ~1.2 | переиспользует существующий бюджет-параметр PELT (см. §4.3) |\n| `model_backtest` | высокий | ~1.0 | `repetitions = folds` |\n| `model_tuning` | самый высокий | ~1.0 | `repetitions = trials × folds` |\n\nКонкретные числовые значения `base`/`exponent` — **не фиксируются в этой\nспецификации** (открытый вопрос §10, требует калибровки по реальным\nзамерам, не по догадке).\n\n### 4.3 Ключевое архитектурное решение: переиспользование, не новая инфраструктура\n\nПлатформа уже располагает инфраструктурой измерения стоимости операций:\n- бюджетирование PELT-сетки (фикс HTTP 502 в «Структурных сдвигах»,\n  Task 76) — уже связывает объём данных с вычислительным бюджетом;\n- диагностика исполнения тюнинга (`TuningPlanExecution`, Task 99) — уже\n  фиксирует фактическое число trials/folds на исполнение.\n\n`compute_cu(...)` не дублирует эти измерения, а **читает уже\nсуществующие величины** (бюджет PELT-сетки, число trials/folds из\n`TuningPlanExecution`) как входные параметры формулы — это одна и та же\nточка данных, используемая сегодня для защиты от таймаута/502 и теперь\nдополнительно для метеринга CU. Первая задача Этапа 1 (§11) — аудит\nэтих двух мест кода, чтобы `compute_cu` не переизобретал их, а\nпараметризовался ими напрямую.\n\n### 4.4 Где считается и списывается\n\n```python\n# apps/api/auth.py — расширение require_capability\n\ndef require_capability(capability: str, operation: OperationType | None = None):\n    def dependency(principal: AuthenticatedPrincipal = Depends(get_current_principal)):\n        if not getattr(principal.capabilities, capability):\n            raise HTTPException(403, ...)\n        if operation is not None:\n            # резервируем CU ДО выполнения тяжёлой операции (не после)\n            reserve_compute_units(principal.account_id, operation)\n        return principal\n    return dependency\n```\n\nПринципиальное решение: **CU резервируется до выполнения операции**, а\nне списывается по факту после — иначе тяжёлая операция (например,\ntuning на грани лимита) успеет отработать и создать реальную\nинфраструктурную стоимость даже при исчерпанном пуле, что подрывает\nсаму цель метеринга (защита пула = защита инфраструктурного бюджета\nrender.com, не только бухгалтерия). При недостатке пула — `402 Payment\nRequired`/аналог, а не «пусть досчитается, потом запретим следующий\nзапрос».\n\nПосле фактического выполнения — точная фиксация факта (`rows`,\n`repetitions` могли отличаться от оценки на входе, например, tuning\nзавершился раньше по early-stopping) — резерв корректируется до\nфактического значения, не обязан совпадать один в один с оценкой.\n\n## 5. Доступ к этапам исследования по тарифу (Stage Gating)\n\n### 5.1 Мотивация и охват\n\nПо прямому продуктовому решению **демонстрационный тариф покрывает все\nшесть этапов основного исследовательского пайплайна** (Загрузка →\nВалидация → Предобработка → EDA → Моделирование → Прогнозирование,\n`apps/api/session_store.py::STAGES`) — это уже согласуется с духом\n`can_upload_own_data=True`/лимитов demo из `ROLES_AND_PLANS_SPEC.md §3`.\nНо платформа декларирует ещё **четыре прикладных модуля** за пределами\nэтого пайплайна (`packages/ui/lib/navigator-stops.ts`, id `scenario` /\n`causal` / `decision` / `monitoring` — сейчас помечены `soon: true`,\nв активной разработке, ещё не отдельные страницы): Сценарный анализ,\nПричинный анализ, Поддержка принятия решений, Мониторинг. Продуктовое\nрешение: эти четыре модуля **не входят** в демонстрационный тариф ни в\nкаком виде; доступны начиная со «Стартового» и выше.\n\nЭто не новая независимая ось прав, а расширение уже существующего\nмеханизма `Capabilities`, резолвящегося через `account.plan` (§2.1) —\nто же единственное место, где сегодня резолвятся `can_train_models`/\n`can_use_api` и т.д. — переиспользуется, не дублируется.\n\n### 5.2 Расширение `Capabilities` (`ROLES_AND_PLANS_SPEC.md`)\n\n```python\n# apps/api/plans.py (расширение Capabilities из ROLES_AND_PLANS_SPEC.md,\n# по тому же принципу, что и account_id/account_role добавлены\n# к AuthenticatedPrincipal в §2.1 этого документа -- расширение поля\n# существующей модели, не создание параллельного контракта)\n\nclass Capabilities(BaseModel):\n    # ... существующие поля без изменений ...\n    restricted_stage_ids: frozenset[str] = frozenset()\n```\n\n`restricted_stage_ids` — множество id модулей, к которым план **не**\nдаёт доступа. Пусто по умолчанию (ничего не ограничено): тариф явно\nперечисляет запрещённое, а не разрешённое — добавление нового модуля\nв будущем не требует правки существующих тарифов, если он не должен\nбыть платным барьером специально.\n\n**Единый словарь id.** Значения `restricted_stage_ids` — те же\nстроковые id, что уже используются в `packages/ui/lib/navigator-stops.ts`\n(`scenario`, `causal`, `decision`, `monitoring`) — отдельный enum на\nбэкенде не заводится. Тот же принцип уже действует в проекте между\n`STAGE_DEFS` (frontend) и `STAGES` (`session_store.py`, backend) —\nid совпадают 1:1 между двумя языками по контракту, а не дублируются\nнезависимо (см. комментарий в самом `navigator-stops.ts`).\n\n### 5.3 Расширение `PLAN_DEFINITIONS`\n\n| Тариф | `restricted_stage_ids` |\n|---|---|\n| `demo` | `{"scenario", "causal", "decision", "monitoring"}` |\n| `starter` | `{}` (не ограничено) |\n| `professional` | `{}` |\n| `enterprise` | `{}` |\n| `internal` (см. §2.2) | `{}` |\n\nОграничение введено **только** для `demo` — по прямому продуктовому\nрешению этой задачи. Открытый вопрос, должен ли `starter` тоже\nограничиваться — см. §10, новый п.7 (не решается в одностороннем\nпорядке здесь).\n\n### 5.4 Точка проверки\n\nАналог `require_capability`, но для доступа к **этапу**, а не к\nконкретному действию — разные по природе проверки не смешиваются в\nодну функцию:\n\n```python\n# apps/api/auth.py (расширение)\n\ndef require_stage_access(stage_id: str):\n    """id должен совпадать с packages/ui/lib/navigator-stops.ts."""\n    def dependency(principal: AuthenticatedPrincipal = Depends(get_current_principal)):\n        if stage_id in principal.capabilities.restricted_stage_ids:\n            raise HTTPException(\n                status_code=402,\n                detail=STAGE_UPGRADE_MESSAGES.get(stage_id, DEFAULT_STAGE_UPGRADE_MESSAGE),\n            )\n        return principal\n    return dependency\n```\n\n`402 Payment Required`, не `403 Forbidden` — тот же код статуса, что уже\nвыбран в §4.4 для недостатка пула CU: причина отказа по смыслу одна и\nта же — «это решается оплатой тарифа», а не «у вас в принципе нет прав»\n(`403` в контракте платформы означает и должен означать именно\nпоследнее — эти два кода не взаимозаменяемы в этой архитектуре).\n\n### 5.5 Формулировка сообщения — вежливо, конкретно, с указанием пути апгрейда\n\n```python\n# apps/api/billing/messages.py (новый модуль; либо в plans.py, если\n# billing/ к моменту реализации ещё не заведён, см. Этап 1 §11)\n\nDEFAULT_STAGE_UPGRADE_MESSAGE = (\n    "Этот раздел доступен на платных тарифах. Демонстрационный тариф "\n    "открывает полный цикл исследования — от загрузки данных до прогноза "\n    "с доверительными интервалами; сценарный анализ, причинный анализ, "\n    "поддержка принятия решений и мониторинг входят в тарифы «Стартовый» "\n    "и выше. Посмотреть тарифы можно в разделе «Тарифы»."\n)\n\nSTAGE_UPGRADE_MESSAGES: dict[str, str] = {\n    "scenario": (\n        "Сценарный анализ (What-if) доступен на платных тарифах — "\n        "начиная со «Стартового». Демонстрационный тариф даёт полный "\n        "доступ к анализу и прогнозированию; для моделирования "\n        "гипотез «что если» перейдите на платный тариф."\n    ),\n    "causal": (\n        "Причинный анализ доступен на платных тарифах — начиная со "\n        "«Стартового». Перейдите на платный тариф, чтобы выявлять "\n        "причинно-следственные связи между рядами."\n    ),\n    "decision": (\n        "Поддержка принятия решений доступна на платных тарифах — "\n        "начиная со «Стартового». Перейдите на платный тариф для "\n        "сравнения альтернатив и рекомендательных правил."\n    ),\n    "monitoring": (\n        "Мониторинг прогноза доступен на платных тарифах — начиная со "\n        "«Стартового». Перейдите на платный тариф для непрерывного "\n        "контроля точности прогноза по мере поступления новых данных."\n    ),\n}\n```\n\nТон закреплён явно, не оставлен на усмотрение реализации: сообщение не\nзвучит как отказ («вам запрещено»), а как приглашение («это доступно на\nтарифе X, вот как перейти») — тот же тон, которого придерживается\nостальная часть платформы (Наставник, `spec_progress.md`: не отчитывает\nпользователя, а подсказывает следующий шаг).\n\n### 5.6 Frontend — архитектурное наблюдение для будущей реализации\n\n`packages/ui/lib/navigator-stops.ts` уже сегодня помечает эти четыре\nмодуля флагом `soon: true` («модуль в активной разработке») — но это\n**другая** причина недоступности («ещё не построено»), не «недоступно\nвашему тарифу». Когда эти модули будут реализованы, `soon: true` должен\nлибо смениться на новый, отдельный флаг (например, `requiresPlan?:\nPlanName`), либо оба состояния должны сосуществовать как разные поля —\nиначе UI не сможет корректно различить «скоро появится у всех» и «уже\nесть, но не на вашем тарифе». Это наблюдение фиксируется здесь как\nтребование к будущей фронтенд-реализации, не решается этим документом —\nдоработка самого `navigator-stops.ts` вне охвата этой спецификации.\n\n### 5.7 Обнаруженное противоречие с таблицей `ROLES_AND_PLANS_SPEC.md` — требует решения тимлида\n\nПри переносе требования «демо покрывает все этапы, кроме этих четырёх»\nв конкретный механизм обнаружено прямое расхождение с уже опубликованной\nтаблицей возможностей (`ROLES_AND_PLANS_SPEC.md §3`): `can_train_models`\nдля `demo` — `❌`, то есть по буквальному смыслу существующей таблицы\nдемо не может обучать модели вообще — а Моделирование является одним\nиз шести этапов ОСНОВНОГО пайплайна, который по формулировке этой\nзадачи демо должен покрывать полностью. Это реальное противоречие\nмежду двумя явно сформулированными требованиями, а не надуманное.\n\nНе редактируется в одностороннем порядке этим документом (таблица\nживёт в `ROLES_AND_PLANS_SPEC.md`, не в этом файле), но фиксируется как\nрешение, требующее подтверждения тимлидом. Отдельная ось от Role (кто) и Plan (что можно).\n    Не путать AccountRole.OWNER с платформенной Role.ADMIN — это разные оси."""\n    OWNER = "owner"    # управляет составом seats и биллингом\n    MEMBER = "member"  # использует возможности плана, не управляет биллингом\n\nclass Account(BaseModel):\n    id: UUID\n    account_type: AccountType\n    plan: PlanName                      # тариф назначен АККАУНТУ, не принципалу\n    seats: int = Field(ge=1)            # для MONO жёстко зафиксировано в 1\n    plan_expires_at: datetime | None\n    billing_cycle_anchor: datetime\n    compute_unit_pool_balance: float    # текущий остаток пула CU на цикл\n    compute_unit_pool_reset_at: datetime\n\nclass AccountMembership(BaseModel):\n    account_id: UUID\n    principal_id: UUID\n    account_role: AccountRole\n    joined_at: datetime\n```\n\n`AuthenticatedPrincipal` из `ROLES_AND_PLANS_SPEC.md` не удаляется и не\nпереписывается концептуально — он приобретает ссылку на аккаунт:\n\n```python\nclass AuthenticatedPrincipal(BaseModel):\n    id: UUID\n    role: Role                    # без изменений — кто\n    account_id: UUID              # НОВОЕ — ссылка на биллинговый аккаунт\n    account_role: AccountRole     # НОВОЕ — права внутри аккаунта\n    capabilities: Capabilities    # без изменений по форме, но теперь\n                                   # резолвится через account.plan,\n                                   # а не через principal.plan напрямую\n```\n\nВажно: поле `plan` **уходит с уровня принципала на уровень аккаунта**.\n`Capabilities` для конкретного запроса резолвятся как\n`PLAN_DEFINITIONS[account.plan]` — сам паттерн `require_capability(...)`\nиз `auth.py` не меняется ни на строчку, меняется только то, откуда\nберётся план при резолве принципала (`get_current_principal` подтягивает\n`account_id` → `account.plan`, вместо `principal.plan` напрямую). Это\nнамеренно минимальная точка изменения — весь остальной код платформы,\nуже написанный против `Capabilities`, не требует правок.\n\n### 2.2 `internal_analyst`/`admin` и Account\n\nДля `embedded`-режима (`admin`, `internal_analyst`) вопрос моно/мульти\nне имеет смысла — им, как и сегодня, назначается служебный Account с\nполным доступом без биллинга (`plan` не применяется, как и в исходном\nдокументе). Явное решение: завести отдельный псевдо-план\n`PlanName.INTERNAL` без цены и без CU-лимитов (`compute_unit_pool_balance`\nне расходуется/не проверяется для такого Account), чтобы не городить\nусловную логику «если admin — пропустить биллинг» по всему коду, а\nостаться в рамках того же единого механизма резолва через\n`Capabilities`.\n\n## 3. Моно / Мульти доступ\n\n### 3.1 Выбор пользователем при регистрации/апгрейде\n\nSelf-service флоу:\n1. Пользователь регистрируется → создаётся `Account(account_type=MONO, seats=1)`,\n   он же становится `AccountMembership(account_role=OWNER)`.\n2. В любой момент из настроек аккаунта пользователь может переключить\n   `account_type → MULTI` — это **не создаёт новый Account**, а\n   переводит существующий (сохраняя историю анализов/сессий,\n   привязанных к `account_id`, а не к отдельному принципалу — важное\n   архитектурное следствие: история анализов **уже должна быть**\n   собственностью Account, а не Principal, иначе при переходе moно→мульти\n   данные владельца «потеряются» для остальных участников команды).\n3. В режиме MULTI владелец (`AccountRole.OWNER`) приглашает\n   участников по email — каждое принятое приглашение создаёт нового\n   `Principal` + `AccountMembership(account_role=MEMBER)` и увеличивает\n   `Account.seats` на 1.\n4. Удаление участника — `seats -= 1`, немедленно.\n\n### 3.2 Автоматический расчёт цены\n\nДве **независимые** формулы, которые нельзя смешивать:\n\n- **Цена** — определяется числом seats, не фактическим потреблением:\n  ```\n  price(account) = PLAN_DEFINITIONS[account.plan].base_price × account.seats\n  ```\n  Линейная модель — намеренный выбор для v1: пользователь может\n  посчитать свою цену в уме до того, как начал пользоваться платформой,\n  без обращения в поддержку. Ступенчатые объёмные скидки (стандартный\n  enterprise-паттерн) — явный follow-up (§10), реализуется как\n  отдельная таблица `SEAT_PRICING_TIERS`, не меняющая эту формулу, а\n  подменяющая множитель.\n- **Квота потребления (CU)** — пулится на уровне Account и\n  масштабируется от seats, а не делится поровну на участника:\n  ```\n  compute_unit_pool_per_cycle(account) = PLAN_DEFINITIONS[account.plan].cu_per_seat × account.seats\n  ```\n  Обоснование пулинга, а не индивидуальных квот на участника — в\n  реальной команде нагрузка асимметрична (один аналитик гоняет\n  tuning/backtest, остальные просматривают Обзоры) — индивидуальные\n  квоты гарантированно создают ситуацию «моя квота кончилась, хотя я её\n  не тратил», что противоречит идее самообслуживания без ручного\n  вмешательства поддержки.\n\n### 3.3 Пересчёт при изменении состава\n\nИзменение `seats` (добавление/удаление участника) должно:\n- немедленно обновить `compute_unit_pool_per_cycle` (пропорционально,\n  без ожидания следующего расчётного периода — иначе владелец,\n  добавивший участника, не получит немедленно доступную для команды\n  квоту);\n- передать новое значение `quantity` в биллинг-провайдера (см. §8) для\n  proration — списание/зачисление разницы стоимости за оставшийся\n  период текущего цикла, а не постфактум в конце месяца.\n\n## 4. Compute Unit (CU) — единица учёта\n\n### 4.1 Почему не токены (кратко, полная аргументация — в обсуждении, зафиксирован вывод)\n\nПлатформа генерирует результаты гетерогенных численных алгоритмов, чья\nстоимость на одинаковом объёме входных данных различается на порядки\n(простая статистика vs CWT vs PELT vs backtest/tuning с комбинаторным\nростом от `trials × folds`). Единица «токен» у LLM работает, потому что\nпредельная стоимость обработки токена в фиксированной архитектуре\nмодели примерно постоянна — у нашей платформы такой однородности\nфизически нет, поэтому буквальный перенос «input/output tokens»\nсистематически исказил бы цену: либо демпинг тяжёлых операций, либо\nпереплата за тривиальные.\n\nЧто переносится из LLM-биллинга **по паттерну**, а не по единице\nизмерения:\n- непрерывный метеринг с балансом/списанием вместо грубых лимитов;\n- дифференциация цены **по типу операции** (у LLM — по модели, здесь —\n  по алгоритму), а не единая ставка на всё;\n- раздельный учёт «подготовки данных» (обычно дешевле) и «тяжёлого\n  расчёта» (обычно дороже) как отдельных компонент формулы, а не как\n  токенов символьного потока.\n\n### 4.2 Формула\n\n```python\n# apps/api/billing/compute_units.py\n\ndef compute_cu(\n    operation: OperationType,\n    rows: int,\n    columns: int,\n    repetitions: int = 1,   # folds × trials для tuning/backtest, иначе 1\n) -> float:\n    coef = ALGORITHM_COEFFICIENTS[operation]  # калибруется эмпирически\n    data_volume = rows * columns\n    return coef.base * data_volume ** coef.exponent * repetitions\n```\n\n`ALGORITHM_COEFFICIENTS` — таблица по типу операции, источник истины\nпо аналогии с `PLAN_DEFINITIONS`:\n\n| Операция (`OperationType`) | `base` | `exponent` | Комментарий |\n|---|---|---|---|\n| `basic_stats` / `smoothing` | низкий | ~1.0 | линейно от объёма |\n| `stl_decomposition` | средний | ~1.0–1.1 | |\n| `spectral_periodogram` | средний | ~1.1 | |\n| `cwt` | высокий | ~1.2–1.3 | масштабы CWT учитываются как множитель в `repetitions`, не в `columns` |\n| `structural_breaks_pelt` | высокий, зависит от бюджета сетки | ~1.2 | переиспользует существующий бюджет-параметр PELT (см. §4.3) |\n| `model_backtest` | высокий | ~1.0 | `repetitions = folds` |\n| `model_tuning` | самый высокий | ~1.0 | `repetitions = trials × folds` |\n\nКонкретные числовые значения `base`/`exponent` — **не фиксируются в этой\nспецификации** (открытый вопрос §10, требует калибровки по реальным\nзамерам, не по догадке).\n\n### 4.3 Ключевое архитектурное решение: переиспользование, не новая инфраструктура\n\nПлатформа уже располагает инфраструктурой измерения стоимости операций:\n- бюджетирование PELT-сетки (фикс HTTP 502 в «Структурных сдвигах»,\n  Task 76) — уже связывает объём данных с вычислительным бюджетом;\n- диагностика исполнения тюнинга (`TuningPlanExecution`, Task 99) — уже\n  фиксирует фактическое число trials/folds на исполнение.\n\n`compute_cu(...)` не дублирует эти измерения, а **читает уже\nсуществующие величины** (бюджет PELT-сетки, число trials/folds из\n`TuningPlanExecution`) как входные параметры формулы — это одна и та же\nточка данных, используемая сегодня для защиты от таймаута/502 и теперь\nдополнительно для метеринга CU. Первая задача Этапа 1 (§11) — аудит\nэтих двух мест кода, чтобы `compute_cu` не переизобретал их, а\nпараметризовался ими напрямую.\n\n### 4.4 Где считается и списывается\n\n```python\n# apps/api/auth.py — расширение require_capability\n\ndef require_capability(capability: str, operation: OperationType | None = None):\n    def dependency(principal: AuthenticatedPrincipal = Depends(get_current_principal)):\n        if not getattr(principal.capabilities, capability):\n            raise HTTPException(403, ...)\n        if operation is not None:\n            # резервируем CU ДО выполнения тяжёлой операции (не после)\n            reserve_compute_units(principal.account_id, operation)\n        return principal\n    return dependency\n```\n\nПринципиальное решение: **CU резервируется до выполнения операции**, а\nне списывается по факту после — иначе тяжёлая операция (например,\ntuning на грани лимита) успеет отработать и создать реальную\nинфраструктурную стоимость даже при исчерпанном пуле, что подрывает\nсаму цель метеринга (защита пула = защита инфраструктурного бюджета\nrender.com, не только бухгалтерия). При недостатке пула — `402 Payment\nRequired`/аналог, а не «пусть досчитается, потом запретим следующий\nзапрос».\n\nПосле фактического выполнения — точная фиксация факта (`rows`,\n`repetitions` могли отличаться от оценки на входе, например, tuning\nзавершился раньше по early-stopping) — резерв корректируется до\nфактического значения, не обязан совпадать один в один с оценкой.\n\n## 5. Доступ к этапам исследования по тарифу (Stage Gating)\n\n### 5.1 Мотивация и охват\n\nПо прямому продуктовому решению **демонстрационный тариф покрывает все\nшесть этапов основного исследовательского пайплайна** (Загрузка →\nВалидация → Предобработка → EDA → Моделирование → Прогнозирование,\n`apps/api/session_store.py::STAGES`) — это уже согласуется с духом\n`can_upload_own_data=True`/лимитов demo из `ROLES_AND_PLANS_SPEC.md §3`.\nНо платформа декларирует ещё **четыре прикладных модуля** за пределами\nэтого пайплайна (`packages/ui/lib/navigator-stops.ts`, id `scenario` /\n`causal` / `decision` / `monitoring` — сейчас помечены `soon: true`,\nв активной разработке, ещё не отдельные страницы): Сценарный анализ,\nПричинный анализ, Поддержка принятия решений, Мониторинг. Продуктовое\nрешение: эти четыре модуля **не входят** в демонстрационный тариф ни в\nкаком виде; доступны начиная со «Стартового» и выше.\n\nЭто не новая независимая ось прав, а расширение уже существующего\nмеханизма `Capabilities`, резолвящегося через `account.plan` (§2.1) —\nто же единственное место, где сегодня резолвятся `can_train_models`/\n`can_use_api` и т.д. — переиспользуется, не дублируется.\n\n### 5.2 Расширение `Capabilities` (`ROLES_AND_PLANS_SPEC.md`)\n\n```python\n# apps/api/plans.py (расширение Capabilities из ROLES_AND_PLANS_SPEC.md,\n# по тому же принципу, что и account_id/account_role добавлены\n# к AuthenticatedPrincipal в §2.1 этого документа -- расширение поля\n# существующей модели, не создание параллельного контракта)\n\nclass Capabilities(BaseModel):\n    # ... существующие поля без изменений ...\n    restricted_stage_ids: frozenset[str] = frozenset()\n```\n\n`restricted_stage_ids` — множество id модулей, к которым план **не**\nдаёт доступа. Пусто по умолчанию (ничего не ограничено): тариф явно\nперечисляет запрещённое, а не разрешённое — добавление нового модуля\nв будущем не требует правки существующих тарифов, если он не должен\nбыть платным барьером специально.\n\n**Единый словарь id.** Значения `restricted_stage_ids` — те же\nстроковые id, что уже используются в `packages/ui/lib/navigator-stops.ts`\n(`scenario`, `causal`, `decision`, `monitoring`) — отдельный enum на\nбэкенде не заводится. Тот же принцип уже действует в проекте между\n`STAGE_DEFS` (frontend) и `STAGES` (`session_store.py`, backend) —\nid совпадают 1:1 между двумя языками по контракту, а не дублируются\nнезависимо (см. комментарий в самом `navigator-stops.ts`).\n\n### 5.3 Расширение `PLAN_DEFINITIONS`\n\n| Тариф | `restricted_stage_ids` |\n|---|---|\n| `demo` | `{"scenario", "causal", "decision", "monitoring"}` |\n| `starter` | `{}` (не ограничено) |\n| `professional` | `{}` |\n| `enterprise` | `{}` |\n| `internal` (см. §2.2) | `{}` |\n\nОграничение введено **только** для `demo` — по прямому продуктовому\nрешению этой задачи. Открытый вопрос, должен ли `starter` тоже\nограничиваться — см. §10, новый п.7 (не решается в одностороннем\nпорядке здесь).\n\n### 5.4 Точка проверки\n\nАналог `require_capability`, но для доступа к **этапу**, а не к\nконкретному действию — разные по природе проверки не смешиваются в\nодну функцию:\n\n```python\n# apps/api/auth.py (расширение)\n\ndef require_stage_access(stage_id: str):\n    """id должен совпадать с packages/ui/lib/navigator-stops.ts."""\n    def dependency(principal: AuthenticatedPrincipal = Depends(get_current_principal)):\n        if stage_id in principal.capabilities.restricted_stage_ids:\n            raise HTTPException(\n                status_code=402,\n                detail=STAGE_UPGRADE_MESSAGES.get(stage_id, DEFAULT_STAGE_UPGRADE_MESSAGE),\n            )\n        return principal\n    return dependency\n```\n\n`402 Payment Required`, не `403 Forbidden` — тот же код статуса, что уже\nвыбран в §4.4 для недостатка пула CU: причина отказа по смыслу одна и\nта же — «это решается оплатой тарифа», а не «у вас в принципе нет прав»\n(`403` в контракте платформы означает и должен означать именно\nпоследнее — эти два кода не взаимозаменяемы в этой архитектуре).\n\n### 5.5 Формулировка сообщения — вежливо, конкретно, с указанием пути апгрейда\n\n```python\n# apps/api/billing/messages.py (новый модуль; либо в plans.py, если\n# billing/ к моменту реализации ещё не заведён, см. Этап 1 §11)\n\nDEFAULT_STAGE_UPGRADE_MESSAGE = (\n    "Этот раздел доступен на платных тарифах. Демонстрационный тариф "\n    "открывает полный цикл исследования — от загрузки данных до прогноза "\n    "с доверительными интервалами; сценарный анализ, причинный анализ, "\n    "поддержка принятия решений и мониторинг входят в тарифы «Стартовый» "\n    "и выше. Посмотреть тарифы можно в разделе «Тарифы»."\n)\n\nSTAGE_UPGRADE_MESSAGES: dict[str, str] = {\n    "scenario": (\n        "Сценарный анализ (What-if) доступен на платных тарифах — "\n        "начиная со «Стартового». Демонстрационный тариф даёт полный "\n        "доступ к анализу и прогнозированию; для моделирования "\n        "гипотез «что если» перейдите на платный тариф."\n    ),\n    "causal": (\n        "Причинный анализ доступен на платных тарифах — начиная со "\n        "«Стартового».
