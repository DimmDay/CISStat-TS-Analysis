## 1. Разграничение: Authentication vs Authorization

Важно зафиксировать явно, потому что оба предыдущих документа уже
вплотную подошли к этой границе, но не пересекали её:

- **Authorization** (кто/что можно/за что заплатили) — уже спроектирована
  целиком: `Role` → `Account.plan` → `Capabilities` →
  `require_capability(...)`. Эта модель принимает на вход уже готовый
  `AuthenticatedPrincipal` и не знает, откуда он взялся.
- **Authentication** (эта спецификация) — отвечает **только** на вопрос
  «как система убеждается, что запрос действительно от заявленного
  принципала», и заканчивается ровно в точке, где на свет появляется
  `AuthenticatedPrincipal` со связанным `account_id`. Дальше в дело
  вступает уже готовый контракт из двух предыдущих документов
  **без единой правки**.

Это разграничение — не формальность: оно означает, что данная
спецификация может меняться (например, добавить OAuth-провайдера или
сменить алгоритм хэширования пароля) вообще не касаясь `plans.py`, и
наоборот — калибровка `ALGORITHM_COEFFICIENTS` не касается этой
спецификации. Три документа — три независимо эволюционирующих слоя.

## 2. Текущее состояние (что заменяется)

`ROLES_AND_PLANS_SPEC.md`, п.7.1, прямо фиксирует: сейчас `auth.py`
парсит API-ключи из переменной окружения
(`CISSTAT_API_KEYS="key1:external_user:starter,..."`) — единственный
существующий механизм аутентификации на платформе, пригодный только для
разработки. Полноценного логина (пароль/OAuth/сессии), self-service
регистрации, приглашения участников команды (нужного согласно
`spec_billing_accounts.md` §3.1) и хранения ключей в БД — нет вообще.
Эта спецификация закрывает пробел целиком.

## 3. Аутентификационные контексты платформы

Платформа обслуживает три принципиально разных контекста
(зафиксированы уже в `ROLES_AND_PLANS_SPEC.md` §2), и у каждого —
свой, осознанно **разный** механизм входа. Унифицировать их в один
флоу было бы ошибкой: у embedded-сотрудника CISStat и у внешнего
клиента-самообслуживания принципиально разные модели доверия.

| Контекст | Кто | Метод аутентификации |
|---|---|---|
| `embedded` | `admin`, `internal_analyst` | Внутренний механизм CISStat (см. §3.1) |
| `standalone` — полноценный аккаунт | `external_user` (mono/multi, любой план кроме demo) | Email+пароль или OAuth, JWT-сессия (см. §4–5) |
| `standalone` — демо | `external_user`, `plan=demo` | Лёгкая passwordless-регистрация по email (см. §3.2) |
| API-доступ (программный) | `external_user` с `can_use_api=True` | Долгоживущий API-ключ, отдельный от сессии (см. §6) |

### 3.1 Embedded-контекст — открытый вопрос, не решение по умолчанию

Для `admin`/`internal_analyst` эта спецификация **намеренно не
проектирует новый механизм с нуля** — сотрудники CISStat, вероятно, уже
проходят аутентификацию через внутреннюю инфраструктуру компании (SSO/
корпоративный IdP), о которой у меня нет данных. Предлагаемое
архитектурное решение — не встраивать логику паролей для этого
контекста в `apps/api/auth/` вообще, а зарезервировать точку
расширения:

```python
def resolve_embedded_principal(request: Request) -> AuthenticatedPrincipal | None:
    """Точка интеграции с внутренним IdP CISStat.
    Реализация — предмет отдельного решения тимлида (см. §11, вопрос 1)."""
```

Это осознанно вынесено в открытый вопрос (§11), а не додумано — риск
спроектировать несовместимое с уже существующей внутренней
инфраструктурой компании выше, чем польза от преждевременного решения.

### 3.2 Демо — passwordless email, не отдельный флоу

`ROLES_AND_PLANS_SPEC.md` §4 уже фиксирует: демо выдаётся «по
временному API-ключу/сессии без полноценной регистрации (или с лёгкой —
email без пароля)». Архитектурное решение здесь — **не изобретать
отдельный демо-специфичный механизм**, а переиспользовать один и тот же
passwordless email-флоу (magic link / одноразовый код, §5.3) как для
входа в демо, так и как один из способов входа в полноценный аккаунт.
Это прямое переиспользование инфраструктуры между контекстами,
согласованное с общим принципом платформы «не дублировать реализацию
между сценариями» (тот же принцип, что уже применялся при
проектировании Soft Pillow и Compute Unit).

Демо-принципал при первом обращении по email автоматически получает
`Account(account_type=MONO, plan=PlanName.DEMO, seats=1)` — без
дополнительного экрана регистрации; создание `Account` при первом входе
переиспользует ту же фабрику, что и обычная self-service регистрация
(§5.1), с той лишь разницей, что `plan` предзадан как `demo`, а не
выбирается пользователем.

## 4. Модель данных

Новая сущность `Credential`, отделённая от `Principal` (уже описанного
в `spec_billing_accounts.md`) — один принципал может иметь несколько
способов входа (пароль **и** OAuth), без необходимости редизайна при
добавлении нового способа в будущем:

```python
# apps/api/auth/models.py

class CredentialType(str, Enum):
    PASSWORD = "password"
    OAUTH_GOOGLE = "oauth_google"
    MAGIC_LINK = "magic_link"     # используется и для демо, и как обычный логин
    API_KEY = "api_key"

class Credential(BaseModel):
    id: UUID
    principal_id: UUID
    credential_type: CredentialType
    secret_hash: str | None        # для PASSWORD/API_KEY — хэш, не сам секрет
    provider_subject: str | None   # для OAuth — id пользователя у провайдера
    created_at: datetime
    last_used_at: datetime | None
    revoked_at: datetime | None

class RefreshToken(BaseModel):
    id: UUID
    principal_id: UUID
    token_hash: str                # хранится хэш, не сырой токен
    issued_at: datetime
    expires_at: datetime
    rotated_from: UUID | None      # цепочка ротации, см. §5.4
    revoked_at: datetime | None
```

`Principal` (из `spec_billing_accounts.md`) не меняется по форме — он
уже ссылается на `account_id`; эта спецификация лишь добавляет вокруг
него таблицы `Credential`/`RefreshToken`, не трогая сам контракт
`AuthenticatedPrincipal`.

## 5. Флоу для standalone (self-service)

### 5.1 Регистрация (моно, владелец нового Account)

1. Email + пароль **или** OAuth (Google — самый низкий барьер входа для
   self-service, приоритет для v1, см. §11).
2. Создаётся `Principal` + `Credential` + `Account(account_type=MONO,
   plan=PlanName.DEMO, seats=1)` **той же фабрикой**, что и демо-вход
   (§3.2) — стартовый план по умолчанию demo, апгрейд на платный —
   отдельное действие пользователя (оплата), не часть флоу
   аутентификации.
3. Подтверждение email обязательно перед выдачей полноценной сессии
   (JWT) — снижает риск накрутки демо-лимитов одноразовыми email
   (частичная мера, полная защита от накрутки демо — открытый вопрос
   §11, вне периметра одной только аутентификации).

### 5.2 Приглашение участника (мульти-доступ)

Прямая реализация флоу, уже описанного в `spec_billing_accounts.md`
§3.1, п.3 — эта спецификация детализирует именно аутентификационную
часть:

1. `OWNER` аккаунта отправляет приглашение на email.
2. Генерируется подписанный, короткоживущий `invite_token` (JWT с
   `account_id`, `invited_email`, `exp` — не хранится в БД как отдельная
   таблица, самодостаточен и проверяется по подписи, аналогично паттерну
   email-верификации §5.1).
3. Переход по ссылке → если у `invited_email` уже есть `Principal` на
   платформе — просто создаётся `AccountMembership(account_role=MEMBER)`
   для существующего принципала (без дублирования аккаунта). Если
   принципала ещё нет — короткая форма (пароль/OAuth), затем то же
   самое.
4. Успешное принятие инкрементирует `Account.seats` — эта часть уже
   специфицирована в `spec_billing_accounts.md`, здесь только точка
   вызова.

### 5.3 Passwordless (magic link / одноразовый код)

Общий механизм для входа без пароля (используется и для демо, §3.2, и
как альтернативный способ входа для обычного аккаунта — многие
self-service SaaS-платформы делают его основным способом именно из-за
низкого порога входа):

1. Пользователь вводит email.
2. Backend генерирует короткоживущий (≈15 минут), одноразовый токен,
   хранит **хэш** токена (не сырое значение) с TTL, отправляет ссылку
   (или 6-значный код, если ссылка неудобна для мобильного контекста) на
   email.
3. Переход по ссылке/ввод кода → сверка хэша → выдача полноценной
   JWT-сессии (§5.4). Токен одноразовый, использование инвалидирует
   его немедленно (защита от повторного использования перехваченной
   ссылки).

Инфраструктура отправки email — **аудит перед реализацией** (см. §12,
Этап 1): если в проекте уже есть механизм отправки писем (например, для
уведомлений/экспорта отчётов), passwordless и приглашения участников
(§5.2) должны переиспользовать именно его, не заводить параллельный
email-провайдер.

### 5.4 Сессии: JWT access + refresh, с ротацией

```
POST /v1/auth/login          → { access_token, refresh_token }
POST /v1/auth/refresh        → { access_token, refresh_token }  (ротация)
POST /v1/auth/logout         → инвалидирует refresh_token
```

- **Access token** — короткоживущий (рекомендация: 15 минут), JWT,
  содержит **только** `principal_id` и `iat`/`exp`. **Принципиально не
  содержит** `role`/`plan`/`capabilities`/`account_id` в теле токена —
  это прямое следствие уже принятого в `ROLES_AND_PLANS_SPEC.md`
  требования, что план резолвится **на каждый запрос** заново (открытый
  пункт 3 того документа: «нужно подтвердить это поведение тестом»).
  Если закэшировать план/возможности в JWT — апгрейд/даунгрейд плана
  или изменение состава `seats` (`spec_billing_accounts.md` §3.3,
  «немедленно, без ожидания цикла») не вступит в силу до истечения
  токена, что напрямую нарушает уже данное обещание платформы. Поэтому
  `get_current_principal` **всегда** делает lookup в БД по
  `principal_id` из токена, а не доверяет клэймам токена для
  авторизационных решений.
- **Refresh token** — долгоживущий (дни/недели), хранится как httpOnly
  cookie (не в `localStorage` — снижает риск кражи через XSS), в БД
  хранится только его хэш. **Ротация при каждом использовании**:
  `refresh` выдаёт новую пару и немедленно инвалидирует использованный
  refresh-токен, записывая цепочку через `rotated_from`. Повторное
  предъявление уже использованного (отозванного) refresh-токена —
  сигнал компрометации: инвалидируются **все** токены цепочки
  принципала (reuse-detection, стандартный паттерн защиты refresh-flow).

### 5.5 Кросс-доменное взаимодействие Vercel ↔ render.com

Важный архитектурный нюанс, специфичный именно для текущего
деплоя платформы: standalone-фронтенд (`ts-standalone.vercel.app`) и
API (render.com) — **разные домены**. httpOnly cookie с refresh-токеном
в таком случае требует `SameSite=None; Secure` и явного
`Access-Control-Allow-Credentials: true` + точного (не wildcard)
`Access-Control-Allow-Origin` на стороне FastAPI — иначе браузер
просто не отправит cookie межсайтовым запросом. Это нужно явно
аудировать в текущей CORS-конфигурации `apps/api` на Этапе 1 (§12) —
не факт, что она уже готова к аутентификации с cookie (сегодня, при
одних API-ключах в заголовке, эта проблема не проявлялась вообще).

Альтернатива, которую стоит рассмотреть на ревью (§11, вопрос 2) —
Next.js API routes как BFF (Backend-for-Frontend): фронтенд общается с
собственным доменом (`/api/auth/*` внутри Next.js на Vercel), который
уже сам делает server-to-server запрос к render.com — тогда cookie
живёт на домене Vercel без кросс-доменных сложностей вообще, а токен
для render.com пробрасывается сервер-сервер. Это более надёжный
паттерн для продакшена, но требует дополнительного слоя в
standalone-приложении, отсутствующего сегодня — компромисс явно
выносится на решение тимлида, а не решается по умолчанию в одну
сторону.

## 6. API-ключи (программный доступ)

Отдельный от сессии механизм, для `Capabilities.can_use_api=True`
(зависит от `Account.plan` — не выдаётся принципалам демо-плана, что
уже согласовано с `ROLES_AND_PLANS_SPEC.md` §4, `can_use_api=False` для
demo).

- Формат: `cisstat_live_<32 случайных байта в base62>` — префикс сразу
  идентифицирует тип credential в логах/грепе без расшифровки.
- Хранение: **только SHA-256 хэш** в `Credential.secret_hash`, сырое
  значение показывается пользователю **один раз** в момент создания и
  не восстановимо (стандартная практика — если утерян, только новый
  ключ, не «показать снова»).
- Привязан к `principal_id`, не напрямую к `account_id` — при
  использовании ключа `Capabilities` всё равно резолвятся через
  `principal.account_id → account.plan`, то есть отзыв/истечение плана
  аккаунта мгновенно обесценивает ключ без отдельной синхронизации.
- Ключ независим от сессии — отзыв (logout, истечение refresh-токена)
  не затрагивает API-ключи; отзыв самого ключа — отдельное действие
  (`revoked_at`), доступное владельцу через настройки аккаунта.
- Rate limiting и метеринг Compute Unit (`spec_billing_accounts.md`
  §4.4) считаются **на ключ**, а не на сессию — конкретный API-ключ
  можно точечно ограничить/отозвать, не затрагивая веб-сессию того же
  принципала.

## 7. Хранение секретов и защита

- **Пароли** — `argon2id` (текущая рекомендация OWASP, устойчивее к
  GPU-перебору, чем bcrypt при сопоставимых параметрах) — конкретные
  параметры (memory/time cost) — предмет калибровки под инфраструктуру
  render.com (компромисс между стойкостью и латентностью логина на
  бесплатном/младшем тарифе хостинга), не фиксируются жёстко здесь.
- **Токены (magic link, invite, API-ключи)** — хэшируются `SHA-256`
  перед сохранением (для высокоэнтропийных случайных токенов
  `SHA-256` достаточен и дешевле `argon2`, в отличие от
  низкоэнтропийных паролей, которым нужна намеренно медленная функция).
- **Constant-time сравнение** при проверке хэшей — защита от
  timing-атак (стандартная практика, явно фиксируется как требование к
  реализации, не деталь, оставляемая на усмотрение разработчика).
- **Rate limiting на попытки входа** — по `(email, ip)` для
  пароля/passwordless, отдельно по API-ключу для программного доступа;
  конкретный порог — предмет Этапа 1, но сам механизм обязателен с
  первой реализации, не post-factum добавление после инцидента.
- **CSRF** — при выборе cookie-based refresh-токена (§5.4) обязателен
  анти-CSRF механизм для state-changing эндпоинтов (double-submit
  cookie или `SameSite=Strict` там, где кросс-доменность не требуется,
  например embedded-контекст в §3.1, где фронтенд и API могут быть на
  одном домене в отличие от standalone).

## 8. Интеграция с уже спроектированными слоями

Единственная точка соприкосновения с `ROLES_AND_PLANS_SPEC.md`/
`spec_billing_accounts.md` — реализация `get_current_principal`:

```python
# apps/api/auth.py — get_current_principal, после этой спецификации

def get_current_principal(
    access_token: str = Depends(oauth2_scheme),      # для сессий (§5.4)
    api_key: str | None = Depends(api_key_header),    # для API-ключей (§6)
) -> AuthenticatedPrincipal:
    if api_key:
        principal_id = resolve_api_key(api_key)       # НОВОЕ (эта спецификация)
    else:
        principal_id = decode_and_verify_jwt(access_token)  # НОВОЕ (эта спецификация)

    principal = load_principal(principal_id)           # существующая логика
    account = load_account(principal.account_id)        # spec_billing_accounts.md
    capabilities = PLAN_DEFINITIONS[account.plan]        # ROLES_AND_PLANS_SPEC.md — без изменений
    return AuthenticatedPrincipal(..., capabilities=capabilities)
```

Всё, что «ниже» этой функции по стеку вызовов (`require_capability`,
резервирование Compute Unit, роутеры) — **не меняется ни единой
строкой**. Это прямое следствие трёхслойного разграничения из §1.

## 9. Тестовая стратегия (TDD)

- **Пароли/хэширование:** verify(hash(x), x) == True; verify не
  чувствителен к timing (косвенная проверка — использование
  библиотечной constant-time функции, не самописного сравнения строк).
- **JWT access-токен:** не проходит валидацию после `exp`; не содержит
  полей `role`/`plan`/`capabilities` (contract-тест на состав клэймов —
  явная защита от повторного проникновения кэшированных прав в токен в
  будущих правках).
- **Refresh-ротация:** повторное предъявление уже использованного
  refresh-токена инвалидирует всю цепочку принципала (reuse-detection,
  §5.4) — тест на сценарий «украли refresh, оригинальный владелец далее
  всё равно не может им воспользоваться, потому что предыдущий уже был
  отозван честной ротацией, а не наоборот».
- **Passwordless:** токен одноразовый — повторное использование той же
  ссылки после успешного логина отклоняется.
- **Приглашение участника:** переход по `invite_token` для email, уже
  имеющего `Principal`, не создаёт дублирующий `Principal` — только
  новый `AccountMembership`.
- **API-ключ:** отзыв плана аккаунта (даунгрейд с `can_use_api=True`
  на план без этой возможности) немедленно обесценивает существующий
  ключ на следующий запрос — без отдельного действия по отзыву самого
  ключа (прямое следствие §6 — план резолвится через account, не
  кэшируется в ключе).
- **Демо-автосоздание аккаунта:** первый passwordless-вход по новому
  email создаёт ровно один `Account(plan=demo)`; повторный вход тем же
  email не создаёт второй.
- **Кросс-доменные cookie (§5.5):** интеграционный тест на реальную
  конфигурацию CORS/`SameSite`, а не только на логику токенов — риск
  из §5.5 непосредственно связан не с бизнес-логикой, а с
  инфраструктурной конфигурацией, которая тестами на уровне unit не
  ловится.

## 10. Риски и меры

| Риск | Мера |
|---|---|
| JWT с закэшированными правами не отражает мгновенный апгрейд/даунгрейд плана | Access-токен принципиально не содержит прав, `get_current_principal` всегда делает свежий lookup (§5.4, §8) |
| Кража refresh-токена (XSS/утечка) | httpOnly cookie (не localStorage), ротация с reuse-detection (§5.4) |
| Накрутка демо через одноразовые email | Обязательное подтверждение email перед выдачей сессии (§5.1) — частичная мера, полная защита вне периметра одной аутентификации (см. §11, вопрос 3) |
| Кросс-доменные cookie не работают между Vercel и render.com из-за CORS/SameSite | Явный аудит конфигурации на Этапе 1, альтернатива — BFF-прокси в Next.js (§5.5, вопрос тимлиду §11) |
| Пароль медленно хэшируется на слабом инстансе render.com, логин ощутимо тормозит | Параметры `argon2id` калибруются под реальную инфраструктуру, не берутся из дефолтов библиотеки не глядя (§7) |
| Дублирование email-инфраструктуры (passwordless и приглашения заводят каждый свой отправитель) | Единая точка отправки, аудит существующего перед реализацией (§5.3) |
| Embedded-аутентификация спроектирована несовместимо с реальным внутренним IdP CISStat | Не проектируется в этой спецификации — явная точка расширения и открытый вопрос (§3.1, §11) |

## 11. Открытые вопросы к тимлиду

1. Каким механизмом сегодня аутентифицируются сотрудники CISStat во
   внутренних системах (SSO/корпоративный IdP)? Без этого ответа
   embedded-контекст (§3.1) не может быть спроектирован предметно, а
   не как точка расширения.
2. Cookie напрямую между Vercel и render.com (с настройкой
   `SameSite=None`) или BFF-прокси через Next.js API routes (§5.5)? Это
   решение стоит принять до Этапа 1, оно определяет форму `RefreshToken`
   и клиентского кода сессий.
3. Приемлемый уровень защиты демо от накрутки одноразовыми email —
   только подтверждение email (текущее предложение, §5.1) или
   дополнительно телефон/капча/платёжная привязка без списания (более
   тяжёлые меры, обычно приберегаемые для повторных злоупотреблений, а
   не первого демо-входа)?
4. OAuth-провайдеры для v1 — только Google, или сразу закладывать
   несколько (GitHub чаще уместен для API-ориентированной аудитории
   платформы, учитывая наличие `can_use_api`)?
5. Существует ли уже в проекте инфраструктура отправки email — прежде
   чем Этап 1 заведёт свой email-провайдер с нуля (§5.3).

## 12. Поэтапный роллаут

1. **Этап 0 (эта спецификация).** Ревью тимлидом, в первую очередь —
   вопросы 1 и 2 из §11 (они определяют форму токенов и клиентского
   кода, остальное можно уточнять параллельно с разработкой).
2. **Этап 1 — фундамент.** `Credential`, `RefreshToken` в БД;
   email+пароль флоу (регистрация/логин/логоут); JWT access+refresh с
   ротацией (§5.4); аудит существующей CORS-конфигурации под
   кросс-доменные cookie (§5.5) — до, а не после написания кода сессий.
3. **Этап 2 — passwordless + демо.** Magic link/код (§5.3), автосоздание
   `Account(plan=demo)` при первом входе (§3.2) — переиспользует
   фабрику Этапа 1, не отдельная ветка кода.
4. **Этап 3 — мульти-доступ.** Приглашение участников (§5.2),
   интеграция с `Account.seats` из `spec_billing_accounts.md`.
5. **Этап 4 — API-ключи.** Выпуск/отзыв/хэширование (§6), привязка
   метеринга Compute Unit к ключу, а не к сессии.
6. **Этап 5 — OAuth.** Google (и, по решению §11 вопрос 4, дополнительные
   провайдеры).
7. **Embedded-контекст** — отдельный этап, стартует только после ответа
   на вопрос 1 из §11, не блокирует Этапы 1–6 (standalone и embedded
   развиваются независимо, точка расширения из §3.1 это уже
   закладывает).
