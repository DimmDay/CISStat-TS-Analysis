## Механизм обратной связи и контроля качества

Контроль качества жестко разделяется на два уровня в зависимости от этапа пайплайна:

### 1. Hard Blockers (Автоматическая блокировка пайплайна)
Применяется **только на этапе Валидации**. Если `DQ Score < порога` (настраивается в `AppState.rules`), переход к Предобработке **автоматически блокируется**.
- **Визуальный:** Красный индикатор качества, кнопка "Перейти к Предобработке" неактивна (`disabled`).
- **Текстовый:** "Качество данных недостаточно для начала трансформаций. Необходимо исправить критические ошибки валидации."

### 2. Soft Warnings (Рекомендации к возврату в UI)
Применяется на этапах **Feature Store, EDA и Моделирования**. Пайплайн **никогда не блокируется автоматически** (пользователь всегда может нажать "Проджить несмотря на предупреждение"), но система генерирует явные рекомендации вернуться на шаг назад, если выявлены специфические триггеры (см. таблицу ниже).
- **Визуальный:** Желтый/Оранжевый баннер с иконкой ⚠️ и кнопкой "Вернуться к [Предыдущий этап]".
- **Текстовый:** "Обнаружены признаки низкого качества [указать причину]. Рекомендуется пересмотреть параметры [этапа]."

### Триггеры Soft Warnings (Критерии «низкого качества» по этапам)

Чтобы избежать субъективности, каждый модуль вычисляет свой специфический метрический триггер, который устанавливает флаг `AppState.{stage}_quality_warning = True`:

| Этап | Триггер (Условие срабатывания ⚠️) | Рекомендуемое действие (Куда возвращаться) |
|---|---|---|
| **Feature Store** | **Низкая информативность:** Более 70% сгенерированных признаков имеют метрику IH-анализа $R(Y|X) < 0.05$ (или близкую к нулю дисперсию). | → **Предобработка** (пересмотреть трансформации, стабилизацию дисперсии) |
| **EDA** | **Скрытые паттерны / Мультиколлинеарность:** <br>1. Отсутствие значимых сезонных периодов (для TS) при включенном `ts_mode_active`.<br>2. Жесткая мультиколлинеарность (VIF > 10) для >50% признаков, без возможности их удаления. | → **Feature Store** (отбор признаков) или **Предобработка** (PCA, изменение лагов) |
| **Моделирование** | **Несходимость / Переобучение:** <br>1. Все модели из каталога исключены из-за несходимости (см. раздел "Обработка ошибок").<br>2. Разрыв метрик Train/Test > 50% (жесткое переобучение).<br>3. $R^2 < 0.2$ или $MAPE > 50\%$ на тестовой выборке для всех моделей. | → **EDA** (проверить экзогенные переменные, причинность) или **Предобработка** (изменить горизонт, агрегацию) |

**Техническая реализация:** 
Флаги предупреждений (`features_quality_warning`, `eda_quality_warning`, `modeling_quality_warning`) хранятся в `AppState` и считываются UI-слоем (`app/ui/tabs/...`) для рендеринга желтых баннеров. Пользователь может игнорировать их (кроме роли `_partner`, которой эти вкладки доступны только для чтения).

## Обработка ошибок и Graceful Degradation
**Цель:** Обеспечить устойчивость пайплайна к сбоям и понятную обратную связь для пользователя (особенно для роли `_partner`, которая не должна видеть технические детали).

### Принципы обработки ошибок
1. **Атомарность этапов:** Если этап не завершился успешно, состояние `AppState.datasets.{stage}` **не обновляется**. Пользователь остается на предыдущей успешной стадии.
2. **Явная классификация ошибок:**
   - **Критические (Critical):** Пайплайн не может продолжаться (например, отсутствие данных, несовместимость типов). Блокировка с четким сообщением.
   - **Предупреждения (Warning):** Пайплайн может продолжаться, но с ограничениями (например, часть entity исключена из Panel). Пользователь видит уведомление.
   - **Информационные (Info):** Не влияют на работу (например, модель не сошлась, но есть альтернативные). Логируется в `AppState.error_log`.
3. **Graceful Degradation:** Если тяжелая операция не выполнилась (STL, FFT, GARCH), пайплайн **не падает**, а переходит к упрощенной стратегии (например, без декомпозиции, без спектральных признаков).

### Сценарии обработки ошибок
#### 1. **Сбой на этапе Предобработки**
- **STL-декомпозиция на коротком ряде** (< 2 сезонных циклов):
  - **Действие:** Пропустить STL, использовать аддитивную декомпозицию или сглаживание (LOWESS).
  - **Сообщение пользователю:** "Ряд слишком короткий для STL-декомпозиции. Применено упрощенное сглаживание."
  - **Логирование:** `AppState.error_log.append({'stage': 'preprocessing', 'error': 'STL failed', 'fallback': 'LOWESS'})`

#### 2. **Сбой на этапе Моделирования**
- **Модель не сходится** (ARIMA, GARCH, ML с высокой сложностью):
  - **Действие:** Исключить модель из списка кандидатов, перейти к следующей.
  - **Сообщение пользователю:** "Модель {model_name} не смогла обучиться. Причина: {reason}. Исключена из сравнения."
  - **Fallback:** Если все модели не сошлись, предложить упрощенные модели (Naive, Moving Average).
  - **Логирование:** `AppState.error_log.append({'stage': 'modeling', 'model': 'ARIMA', 'error': 'Non-convergence', 'action': 'excluded'})`

#### 3. **Частичный сбой в Panel Data**
- **Часть entity не прошли валидацию** (недостаточно наблюдений, пропуски > 50%):
  - **Действие:** Исключить проблемные entity из анализа, продолжить с оставшимися.
  - **Сообщение пользователю:** "Entity {entity_list} исключены из анализа. Причина: {reason}. Анализ продолжен для {n_remaining} entity."
  - **Требование:** Если исключено > 30% entity, блокировать переход к Моделированию с предупреждением.
  - **Логирование:** `AppState.error_log.append({'stage': 'panel_preprocessing', 'excluded_entities': [...], 'reason': 'insufficient_data'})`

#### 4. **Сбой на этапе Прогнозирования**
- **Обратное преобразование невозможно** (отсутствуют `transform_params`):
  - **Действие:** Вернуть прогноз в масштабированной шкале с предупреждением.
  - **Сообщение пользователю:** "Обратное преобразование невозможно. Прогноз представлен в масштабированной шкале."
  - **Логирование:** `AppState.error_log.append({'stage': 'forecasting', 'error': 'inverse_transform_failed', 'fallback': 'scaled_output'})`

#### 5. **Сбой на этапе Мониторинга**
- **Фактические данные не загружены** (пользователь не предоставил для сравнения):
  - **Действие:** Пропустить сравнение "Прогноз vs Факт", показать только анализ дрифта прогнозов.
  - **Сообщение пользователю:** "Фактические данные не предоставлены. Сравнение с фактом недоступно."

#### 6. **Сбой при финальном переобучении в Прогнозировании (Forecasting Fallback)**
**Ситуация:** Модель (например, ARIMA, GARCH) успешно обучилась на тренировочной выборке (`modeling/`), но не сходится при попытке переобучения на полном наборе данных ($Train \cup Test$) в `forecasting/` (например, из-за нарушения стационарности на добавленных точках или взрыва дисперсии).
**Действие:** 
1. Перехватить исключение сходимости.
2. **Автоматический откат (Fallback):** Использовать объект модели и гиперпараметры, уже сохраненные в `AppState.best_model` (то есть модель, обученную *только* на тренировочной выборке).
3. Сформировать прогноз на горизонт $h$, используя исторические данные до конца $Train$ (или $Test$, если модель позволяет экстрополировать состояние).
**Сообщение пользователю:** "⚠️ Финальное переобучение модели на полном наборе данных не удалось (причина: {reason}). Используется модель, обученная на тренировочной выборке. Прогноз сгенерирован, но его точность может быть незначительно снижена."
**Логирование:** `AppState.error_log.append({'stage': 'forecasting', 'error': 'RetrainFailedOnFullData', 'fallback': 'UsedTrainOnlyModel', 'reason': str(e)})`

## Dataset Lifecycle (Жизненный цикл данных)

## Структура `AppState.datasets` (DatasetManager)
Вместо перезаписи `AppState.df` на каждом этапе, состояния управляются через `DatasetManager`. Он хранит историю версий и автоматически освобождает память (Garbage Collection), 
предотвращая OOM при работе с большими данными (>1GB).

```python
# app/core/datasets.py
class DatasetManager:
    # Хранит словари списков версий: {'raw': [v1, v2], 'validated': [v1], ...}
    # Автоматически удаляет старые версии из памяти при превышении max_versions (по умолчанию 3)
    # Предоставляет методы: add_version(), get_version(), get_latest(), get_memory_usage()

```markdown
> ⚠️ **ИНВАРИАНТ BACKEND-AGNOSTIC GC:**
> `DatasetManager` **не знает и не должен знать**, какой именно движок (Pandas, Dask, Polars) используется под капотом. 
> Метод `get_memory_usage()` должен опираться на полиморфный вызов `version.get_memory_footprint()`. 
> Garbage Collection (удаление старых версий из `max_versions`) работает с **ссылками на вычислительные графы**, что позволяет корректно освобождать память как для in-memory (Pandas), так и для out-of-core (Dask) фреймов без утечек.

### Правила инициализации в Streamlit (Критично!)
Streamlit перезапускает скрипт при каждом взаимодействии. Чтобы `DatasetManager` не пересоздавался (что приведет к потере версий) и не дублировался в памяти, его инициализация должна быть строго завязана на `st.session_state`:

```python
# app/core/state.py или app/main.py
if 'datasets_manager' not in st.session_state:
    st.session_state.datasets_manager = DatasetManager(max_versions=3)

# В самом AppState (через property или явное присваивание при старте сессии)
AppState.datasets = st.session_state.datasets_manager

## Стратегия кэширования (Caching Strategy)

**Цель:** Избежать пересчета тяжелых операций при каждом ререндере Streamlit.

### Типы кэша

#### 1. `@st.cache_data` — для вычислений на данных
**Применяется к:** функциям, которые возвращают данные (DataFrame, dict, list)
**Инвалидация:** при изменении входных данных (хэш df + параметры)
**TTL:** 1 час (3600 секунд)
**max_entries:** 100

**Функции для кэширования:**
- `calculate_ts_passport(df_hash, ts_mode)` → паспорт свойств v1_0/v1_1/v1_2
- `compute_stl_decomposition(df_hash, period, seasonal)` → STL-декомпозиция
- `compute_fft(df_hash, n_fft)` → FFT анализ
- `compute_acf_pacf(df_hash, nlags)` → автокорреляция
- `train_model(df_hash, model_type, params)` → обучение модели
- `compute_granger_causality(df_hash, max_lag)` → Granger тест
- `compute_dtw_distance(series1_hash, series2_hash)` → DTW расстояние
- `compute_rolling_statistics(df_hash, window, stat_type)` → скользящие статистики

#### 2. `@st.cache_resource` — для тяжелых ресурсов и статических артефактов
**Применяется к:** объектам, которые создаются один раз и переиспользуются (статические конфиги, схемы, подключения, модели).
**Инвалидация:** только при перезапуске приложения или явном вызове `.clear()`.
**Примеры:**

- `load_model(model_path)` → загрузка обученной модели (pickle)

## Уровни доступа: Read (Чтение) vs Execute (Исполнение)

Для обеспечения безопасности и воспроизводимости (Dataset Lifecycle) права доступа жестко разделяются на два уровня:

1. **READ (Чтение/Аудит/Верификация):** 
   - Просмотр данных, паспортов свойств, метрик, графиков.
   - Просмотр примененных параметров (`transform_params`, `model_params`).
   - Экспорт артефактов (в рамках разрешенных стадий).
   - *Не подразумевает возможности запускать вычисления или менять состояние.*

2. **EXECUTE (Исполнение/Модификация):**
   - Запуск вкладок и пайплайнов (нажатие кнопок "Обучить", "Применить", "Запустить валидацию").
   - Изменение параметров (выбор гиперпараметров, настройка правил валидации).
   - Мутация состояния `AppState.datasets` и `AppState.model_registry`.

**Золотое правило:** Внешний пользователь (`_partner`) имеет **исключительно READ-доступ**. Он наблюдатель и аудитор, но не оператор пайплайна.

**Уровень доступа: СТРОГО READ ONLY (Только чтение)**

**Доступ к данным (READ):**
- ✅ **Валидация:** Просмотр `validated` данных и отчета Data Quality.
- ✅ **Feature Store:** Просмотр `features` и реестра признаков (чтобы понять, какие факторы учтены).
- ✅ **Моделирование:** Просмотр `model_params`, метрик качества на тестовой выборке, истории моделей (Model Registry).
- ✅ **Прогнозирование:** Просмотр финального `forecast`, доверительных интервалов, методологии.
- ✅ **Задачи:** Экспорт разрешенных артефактов (validated, features, forecast, отчеты).

- ❌ **Классификация и Предобработка:** Полный доступ закрыт (включая чтение `transformed`).
- ❌ **Запуск вычислений:** Все кнопки запуска ("Обучить модель", "Применить трансформацию", "Запустить EDA") **заблокированы (disabled)** или скрыты.

**Обоснование:**

## Стратегия работы с большими данными и защита от OOM

⚠️ **КРИТИЧЕСКОЕ ОГРАНИЧЕНИЕ СКОУПА (MVP vs FUTURE):**
Реализация Out-of-Core вычислений (Dask/Polars) и автоматического переключения бэкендов **КАТЕГОРИЧЕСКИ ИСКЛЮЧЕНА из Этапов 1–10**. 
Библиотеки спектрального анализа (`scipy`), статистического моделирования (`statsmodels`) и специфичные паттерны Panel Data (`df.groupby().transform()`) требуют in-memory массивов. Их адаптация под out-of-core движки требует написания отдельных дублирующих модулей, что нецелесообразно на этапе стабилизации архитектуры.

### 1. Реальность Этапов 1–10: Strict In-Memory Pandas + OOM Protection
**Цель:** Обеспечить стабильную работу пайплайна с датасетами, помещающимися в RAM, и гарантированно предотвратить падение приложения (OOM).

**Архитектурный принцип (MVP):** 
- `DatasetManager` и весь пайплайн (Feature Store, EDA, Modeling) работают **исключительно** с `pandas.DataFrame`.
- **Защита от OOM:** На этапе загрузки (`app/data/loader.py`) система оценивает размер файла. Если размер превышает жесткий лимит (например, 1.5 ГБ) или порог доступной RAM, загрузка **блокируется** с понятным сообщением для пользователя: *"Размер данных превышает лимиты текущей конфигурации. Пожалуйста, используйте агрегированные данные или обратитесь к администратору"*.
- Garbage Collection (`max_versions=3`) работает со ссылками на Pandas DataFrame, гарантируя своевременное освобождение RAM.

### 2. Архитектурный резерв: Out-of-Core (Этап 11+ / Post-MVP)
*Данный подраздел описывает видение развития системы. Он не блокирует релиз MVP и запускается только после полной стабилизации Pandas-пайплайна.*

**Цель:** Обеспечить обработку датасетов, превышающих RAM (10 ГБ+), без изменения бизнес-логики UI.

**Архитектурный принцип (Future):** `DatasetManager` станет **backend-agnostic** оркестратором. Он будет управлять версиями независимо от того, является ли базовый DataFrame "тяжелым" (Pandas) или "ленивым" (Dask / Polars LazyFrame).

**План внедрения (когда будет запущен):**
1. **Автоматический триггер движка (Auto-Switching):** В `loader.py` файлы > X ГБ будут маршрутизироваться на `dask.dataframe` или `polars.LazyFrame`. Данные будут читаться чанками, а вычислительный граф строиться без загрузки в RAM.
2. **Полиморфизм DatasetVersion:** Инкапсуляция движка внутри `DatasetVersion` с методом `get_memory_footprint()`, корректно оценивающим мета-данные ленивых фреймов для работы GC.
   ```python
   # Пример кода для будущего этапа:
   @dataclass
   class DatasetVersion:
       id: str
       stage: str
       _df: Any  # pd.DataFrame | dd.DataFrame | polars.LazyFrame
       backend: str # 'pandas' | 'dask' | 'polars'
       
       def get_memory_footprint(self) -> int:
           if self.backend == 'pandas':
               return self._df.memory_usage(deep=True).sum()
           else:
               return estimate_out_of_core_footprint(self._df)

   - Лаги (lag-1, lag-7, lag-30, lag-365)
   - Скользящие окна (rolling mean, std, min, max)
   - Календарные признаки (день недели, месяц, квартал)

2. **Спектральные признаки** (spectral.py)
   - FFT energy (энергия частотных компонент)
   - Wavelet scales (вейвлет-коэффициенты)
   - Доминирующие частоты

   - Макроэкономические индикаторы

   - Метаданные (название, тип, параметры создания)
   - Версионирование признаков
   - Lineage (какие признаки использовались для какой модели)
   - Отбор признаков (feature selection)

6. **Панельные признаки** (panel.py) — *Критично для Panel Data*
   - **Жесткое правило:** Все временные операции (лаги, скользящие окна) выполняются **строго внутри каждой сущности** (`df.groupby(entity_col).transform(...)`).
   - **Защита от Data Leakage:** Сквозные вычисления по всему датасету (`df['target'].shift(1)`) **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНЫ**, чтобы избежать утечки данных из будущего одной страны/региона в прошлое другой.
   - *Within-entity features:* Лаги и скользящие статистики внутри каждой панели.
   - *Between-entity features:* Кросс-секционные признаки в момент времени `t` (например, отклонение значения сущности от среднего по всей панели в этот же момент).

- **Random Effects Model** (GLS — Generalized Least Squares)
- **Hierarchical/Multilevel Models** (Bayesian hierarchical)
- **Dynamic Panel Data Models** (Arellano-Bond GMM)
- **Pooled OLS** (если homogeneity test проходит)

**Для Multivariate panel (дополнительно):**
- **Panel VARX** (с экзогенными переменными)
- **Common Correlated Effects (CCE)** — Pesaran
- **Augmented Mean Group (AMG)** — Pesaran
- **Mean Group (MG)** — Pesaran

**Субмодули:**
1. **Семейство доступных моделей**
   - Выбор моделей из доступных для тестирования
2. **Обучающая и тестовая выборки + масштабирование**
   - Split на train/test (в масштабированной шкале)
3. **Обучение моделей**
   - Обучение моделей на train_scaled   
4. **Подбор гиперпараметров**   
   - Grid Search (сеточный поиск)
   - Random Search (случайный поиск)
   - Bayesian Optimization (байесовская оптимизация)
   - Автоматический подбор для ARIMA (через AIC/BIC)
   - Кросс-валидация временных рядов (Time Series CV)
   - Сравнение результатов с разными гиперпараметрами
   - ⚠️ **Атомарная фиксация:** В момент завершения подбора и выбора модели с лучшей метрикой, происходит одновременная запись `AppState.best_model` и `AppState.model_params`.
   Промежуточные параметры в `AppState` не сохраняются (только в `experiment_log`).
   - Визуализация влияния гиперпараметров на метрики
5. **Построение прогнозов**
   - Прогнозы выбранных моделей на test_scaled → forecast_scaled  
6. **Метрики качества** (RMSE, MAE, MAPE) ← в масштабированной шкале
   - Оценка качества моделей, рекомендации, таблица результатов (скачать csv, excel)
7. **Обратное преобразование**
   - Обратное преобразование forecast_scaled → forecast_orig
8. **График прогноза**
   - Построение сравнительного графика: "Прогноз vs Факт" ← в ИСХОДНОЙ шкале
   (скачать png, jpeg, pdf)
9. **История моделей** (Model Registry — `app/modeling/registry.py`)
   - Просмотр всех обученных моделей
   - Сравнение метрик версий
   - Откат к предыдущей версии
   - Экспорт истории (CSV, JSON)
10. **Модели волатильности** (volatility.py)
    - ARCH (Autoregressive Conditional Heteroskedasticity)
    - GARCH (Generalized ARCH) — стандарт для кластеризации волатильности
    - EGARCH (Exponential GARCH) — учитывает асимметрию (leverage effect)
    - TGARCH (Threshold GARCH) — пороговый GARCH
    - GJR-GARCH — аналог EGARCH для финансовых данных
    - Прогноз волатильности на горизонт h
    - Расчет VaR (Value at Risk) и CVaR (Conditional VaR)
    - Визуализация прогноза волатильности с доверительными интервалами
11. **Лог экспериментов** (Experiment Log)
    - Запись каждого прогона: гиперпараметры, метрики, параметры трансформаций, timestamp, user
    - Сравнение экспериментов между сессиями (таблица с фильтрацией по тегам/датам)
    - Воспроизведение эксперимента по ID (загрузка параметров и повторный запуск)
    - Гибридное хранение с гарантией целостности (Manifest-based Storage): 
      Метаданные (метрики, гиперпараметры, теги) хранятся в локальной **SQLite БД** для быстрого поиска. 
      Тяжелые артефакты (модели в `pickle`, датасеты в `Parquet`) хранятся в файловой системе (`artifacts/{exp_id}/`).
      Механизм атомарности и синхронизации:
      1. В папке эксперимента создается файл-манифест `manifest.json`, содержащий метаданные и **SHA-256 хэши** всех тяжелых артефактов (`model.pkl`, `data.parquet`).
      2. Запись в SQLite (индексация эксперимента) происходит **только после** успешной записи всех файлов и верификации их хэшей через манифест.
      3. При загрузке/воспроизведении эксперимента по ID система сначала читает манифест, вычисляет хэши файлов на диске и сверяет их. Если хэш не совпадает или файл отсутствует — эксперимент помечается как `CORRUPTED` и блокируется для воспроизведения.
    - Загрузка предыдущих экспериментов при старте новой сессии (чтение индекса из SQLite)
    - Привязка к `AppState.datasets.features` (какой датасет использовался)

## Вкладка 7: ПРОГНОЗИРОВАНИЕ
**Цель:** Генерация прогнозов и визуализация результатов.

**Входные данные из Моделирования:**
- `AppState.best_model` → выбранная лучшая модель (тип + архитектура)
- `AppState.model_params` → оптимальные гиперпараметры (из Model Registry)
- `AppState.volatility_results` → прогнозы волатильности (для доверительных интервалов)

**Входные данные из Предобработки:**
- `AppState.datasets.transformed.df` → трансформированный DataFrame (после математических преобразований)
- `AppState.transform_params` → параметры трансформаций
- `AppState.ts_props_v1_2` → паспорт свойств после предобработки
→ Базовые данные для создания признаков

**Ключевое правило:** forecasting/ НЕ выполняет подбор гиперпараметров и сравнение моделей — это ответственность modeling/

1. Попытка обучения финальной модели на ВСЕХ данных (Train ∪ Test, scaled).
⚠️ Graceful Degradation: Если переобучение на полном наборе данных вызывает ошибку сходимости (нестационарность, взрыв дисперсии и т.д.), система автоматически откатывается к использованию модели, уже обученной на тренировочной выборке (из AppState.best_model), с явным предупреждением пользователя (см. раздел «Сценарии обработки ошибок», п. 6).
2. Прогноз на горизонт h → сохраняется в `AppState.forecast_future_scaled`
3. Обратное преобразование → сохраняется в `AppState.forecast_future_orig`
4. Формирование метаданных прогноза → сохраняется в `AppState.forecast_results` (горизонт, параметры модели, метрики на тесте, timestamp)
5. Финальный датасет с прогнозом (дата, прогноз, доверительные интервалы) → сохраняется в `AppState.datasets.forecast`
6. Расчет доверительных интервалов для каждого прогнозного значения
7. Анализ чувствительности к изменению параметров
8. Автоматическое выявление аномалий в прогнозных значениях
9. **Прогноз волатильности**
   - Интеграция прогнозов GARCH-моделей с прогнозами значений
   - Динамические доверительные интервалы (на основе прогноза волатильности)
   - Расчет VaR/CVaR для риск-менеджмента
10. Финальный отчет для заказчика:
   - Документирование параметров модели и условий прогнозирования
   - Визуализация результатов (график фактических данных, линия прогноза, верхняя/нижняя границы доверительного интервала, точки прогноза)
   - Метрики качества модели на исторических данных (из Model Registry: RMSE, MAE, MAPE на test set)
   - Описание методологии и параметров модели
   - Визуализация результатов (график фактических данных + линия прогноза + доверительные интервалы)
11. Экспорт результатов (CSV, Excel-файлы с прогнозными значениями, графики PNG/PDF, JSON-структуры с метриками качества, Отчет PDF)

### Вкладка 8: МОНИТОРИНГ
**Цель:** Ретроспективный анализ качества прогнозов и обнаружение деградации модели.

**Входные данные:**
- `AppState.forecast_results` → метаданные о прогнозе (горизонт, параметры модели, метрики на тесте, timestamp)
- `AppState.datasets.forecast` → финальный датасет с прогнозом (для сравнения с фактом)
- `AppState.best_model` → обученная модель
- `AppState.model_params` → параметры модели
- `AppState.transform_params` → параметры трансформаций

**Входные данные от Пользователя:**
- Загрузка фактических значений (CSV, Excel) для сравнения с прогнозами

**Субмодули:**

1. **Сравнение прогнозов с фактом**
   - Загрузка фактических данных
   - Расчет метрик качества (MAE, MAPE, RMSE) на реальных данных
   - Визуализация "Прогноз vs Факт"
   - Таблица отклонений (скачать csv, excel)

2. **Анализ дрифта данных** (Data Drift)
   - Сравнение распределения новых данных с обучающей выборкой
   - Статистические тесты (KS-test, PSI - Population Stability Index)
   - Визуализация изменений распределения
   - Уведомление о значительных изменениях

3. **Анализ дрифта прогнозов** (Prediction Drift)
   - Мониторинг распределения прогнозных значений во времени
   - Обнаружение аномальных прогнозов
   - Визуализация тренда прогнозов

4. **Деградация модели** (Model Decay)
   - Тренд ошибок во времени (скользящее окно)
   - Определение точки, когда модель нужно переобучить
   - Рекомендации по переобучению

5. **Анализ смещения прогнозов** (Forecast Bias)
   - Систематическое завышение/занижение прогнозов
   - Анализ остатков (автокорреляция, гетероскедастичность)
   - Визуализация распределения ошибок

6. **Алерты и уведомления**
   - Пороговые значения для метрик качества
   - Автоматические уведомления о деградации
   - История алертов (скачать csv, excel)

**Результат:**
- AppState.monitoring_results → метрики качества, дрифт, алерты
- Отчет о качестве модели (скачать pdf, excel)
- Рекомендации по переобучению

### Архитектурное примечание для сценарного анализа (What-if / iDSS)
Для подмодулей **3 (Сценарный анализ what-if)** и **4 (iDSS)** создается отдельный изолированный пакет `app/scenarios/`. 
**Правило:** Сценарный анализ **никогда** не мутирует основное состояние `AppState.datasets.features`. 
Вместо этого `app/scenarios/` клонирует текущий `features` в оперативную память, применяет шоковые воздействия (например, "рост цены на нефть на 20%") и считает локальные прогнозы. Это гарантирует, что "песочница" What-if не сломает основной пайплайн и не потребует пересчета кэша для базовых моделей.

## Ключевые сущности
- `AppState.df` — **Read-Only свойство (Fallback для Legacy)**. Жестко указывает на `AppState.datasets.validated.df` (если валидация пройдена),
  либо на `AppState.datasets.raw.df` (если валидация еще не запускалась). **НЕ является "активным датасетом вкладки" и НЕ переключается динамически.**

- `AppState.forecast_future_orig` — финальный прогноз в исходной шкале (после обратного преобразования). Используется для экспорта и визуализации.

  ⚠️ **Жесткий инвариант:** Эта сущность обновляется атомарно вместе с `best_model`. Никогда не содержит параметры промежуточных/тестируемых моделей.

## Ключевые правила рефакторинга
1. Не менять наблюдаемое поведение без явного указания
2. Сначала выносим бизнес-логику в `core/`, потом UI в `ui/tabs/`
3. Все изменения состояния проходят через типизированный `AppState`
4. Сохраняем обратную совместимость через wrapper в `app.py`
5. Логика вкладок строится следующим образом: классификация → валидация → предобработка → анализ → моделирование → прогнозирование
6. Система ролей определяет доступ к модулям и функциям
7. Строгое разделение READ/EXECUTE и Матрица доступа: 
   Заказчик (`_partner`) имеет строго **READ-доступ** к результатам анализа (Валидация, Feature Store, Прогнозирование) для верификации методологии и обеспечения воспроизводимости. 
   Ему **категорически запрещен EXECUTE-доступ** (запуск вычислений, изменение параметров) и доступ к сырым/трансформированным данным (вкладки «Классификация», «Предобработка», «Мониторинг» скрыты или заблокированы). 
   **Матрица доступа** является единственным источником истины для определения видимости вкладок и стадий данных для каждой роли.
8. EDA передаёт конкретные параметры в Моделирование (информативные признаки, сезонные периоды)
9. EDA поддерживает переключение "До/После" предобработки для сравнения свойств данных
10. **Устранение неявного глобального состояния (`AppState.df`):**
    - `AppState.df` **никогда не переключается** в зависимости от активной вкладки UI. Это жесткий Read-Only алиас на `validated` (или `raw`), служащий "точкой входа" для старого кода.
    - **Запрещено:** Использовать `AppState.df` в любых новых функциях, классах и вкладках.
    - **Миграция Legacy:** Вместо прямой передачи `AppState.df` в старые функции, создаются **Legacy Wrappers** с явным указанием стадии:
      ```python
      # ПЛОХО (неявное состояние):
      def legacy_eda(df=AppState.df): ...
      
      # ХОРОШО (явный wrapper):
      def legacy_eda_wrapper(stage: str = 'validated'):
          df = get_dataset_for_stage(stage) # Явное получение из Dataset Lifecycle
          return legacy_eda(df)
      ```
11. **Четкое разделение modeling/ и forecasting/:**
    modeling/ — только выбор модели (обучение на train, подбор гиперпараметров, сравнение, возврат best_model).
    forecasting/ — применение выбранной модели. Пытается переобучить модель на всех данных (Train ∪ Test) для максимизации истории. Если переобучение падает — использует модель из modeling/ (обученную на Train). Генерирует прогноз на горизонт 
    h, считает доверительные интервалы и формирует отчет.
    forecasting/ КАТЕГОРИЧЕСКИ НЕ ДОЛЖЕН содержать логику подбора гиперпараметров (GridSearch, B ayesian) или выбора другой архитектуры. Он работает строго с тем, что вернул modeling/.
12. **Матрица доступа = источник истины** — каждая вкладка UI проверяет матрицу 
    доступа перед показом данных. Если роль не имеет доступа к стадии, вкладка 
    показывает заглушку: "Эта стадия данных недоступна для вашей роли".
13. **Разделение Read/Execute в UI:** 
    - Если `AppState.user_role == 'partner'`, все интерактивные элементы управления (кнопки `st.button`, слайдеры, поля ввода параметров)  на вкладках, доступных для чтения, должны рендериться с флагом `disabled=True`.
    - Рядом с заблокированными элементами должна отображаться иконка/бейдж: 🔒 *"Режим аудита: просмотр результатов, запуск вычислений недоступен"*.
    - Это предотвращает случайное изменение состояния `AppState` внешним пользователем.

14. **Принцип явной адресации данных (Explicit Data Addressing):**
    Любая функция бизнес-логики (`core/`, `eda/`, `modeling/` и т.д.) **обязана** принимать данные либо явно через аргументы (`def compute_fft(df: pd.DataFrame)`), либо через явный запрос к состоянию (`df = AppState.datasets.validated.df`). Запрещено опираться на "контекст вкладки" или "последний измененный датасет". Это гарантирует воспроизводимость и корректную работу `@st.cache_data`.

15. **Защита от Data Leakage в Panel Data:**
    - Любая функция в `app/features/` и `app/preprocessing/`, генерирующая временные признаки (лаги, diff, rolling), **обязана** принимать аргумент `entity_col: str`.
    - Внутри функции операции должны выполняться исключительно через `df.groupby(entity_col).transform(...)` или `df.groupby(entity_col).shift(...)`.
    - Использование "плоских" сдвигов (`df.shift()`) для панельных данных блокируется на уровне unit-тестов и линтеров.

16. **Обязательная обработка ошибок и Graceful Degradation:**
    - Каждая функция бизнес-логики **обязана** иметь блок `try-except` для критических операций (обучение моделей, декомпозиция, обратное преобразование).
    - При сбое функция **не должна** падать с traceback. Вместо этого:
      1. Логировать ошибку в `AppState.error_log` с указанием `stage`, `severity`, `error_type`, `message`.
      2. Применить fallback-стратегию (если определена в разделе "Обработка ошибок").
      3. Вернуть пользователю понятное сообщение через UI (не технический текст).
    - **Запрещено:** Использовать "голый" `except Exception as e: pass` — все ошибки должны быть залогированы.
    - **Требование:** Unit-тесты для сценариев сбоев (короткие ряды, несходимость моделей, частичные сбои в Panel) обязательны.
17. **Атомарное обновление состояния лучшей модели (Atomic Model State Update):**
    - `AppState.best_model` и `AppState.model_params` представляют собой **единый логический узел**.
    - **Запрещено:** Использовать `AppState.model_params` для хранения параметров промежуточных моделей во время циклов подбора гиперпараметров (GridSearch, Bayesian Optimization). Для промежуточных параметров использовать локальные переменные функций или запись в `AppState.experiment_log`.
    - **Разрешено:** Запись в `AppState.model_params` происходит **строго в один момент (атомарно)** с записью в `AppState.best_model` — в момент фиксации победителя кросс-валидации.
    - **Обоснование:** Нарушение этого инварианта приведет к «франкенштейн-прогнозу», когда модуль `forecasting/` применит параметры от модели X к архитектуре Y, что сделает воспроизводимость невозможной.
18. **Разделение Session Memory (RAM) и Persistent Artifacts (Disk):**
    - `DatasetManager` управляет **исключительно** оперативной памятью текущей сессии. Его Garbage Collection (`max_versions=3`) безвозвратно удаляет старые версии из RAM. **Никакой скрытой сериализации на диск при GC не происходит.**
    - **Воспроизводимость экспериментов** обеспечивается механизмом **Data Snapshotting** в `experiment_log`. При сохранении эксперимента датасет-источник *обязан* быть сохранен на диск (`artifacts/{exp_id}/data.parquet`) и зафиксирован в `manifest.json`. Это и есть механизм "закрепления" (pinning) данных.
    - **Роль `_partner` (Аудитор):** Партнер не зависит от того, какие версии данных сейчас в RAM у оператора `_user`. Партнер всегда читает артефакты напрямую из персистентного хранилища, загружая их в изолированный временный `DatasetManager` для верификации.
