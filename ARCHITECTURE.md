## Потоки данных
1. **Загрузка** → `AppState.df`, `col_types`, `ts_mode_active`
2. **Классификация** → `AppState.data_classification` тип данных (TS/Non-TS, univariate/multivariate) → все последующие модули
3. **Валидация** → `AppState.val_results` (результаты проверки качества), `AppState.validation_ready` (флаг готовности)→ все последующие модули
4. **Предобработка** → `AppState.df`,`AppState.transform_params`, `AppState.ts_props_v12` → Feature | → [качество низкое] → Валидация
5. **Features** → `AppState.feature_store` (признаки + метаданные) → EDA, Моделирование | → [качество низкое] → Предобработка
6. **EDA** → `AppState.eda_results.informative_features`, `AppState.eda_results.seasonal_periods`, `AppState.eda_results.multicollinear_features`, `AppState.eda_results.causality_results`, `AppState.eda_results.similarity_results` → Моделирование, Прогнозирование | → [качество низкое] → Features → Предобработка → Валидация
7. **Моделирование** → `AppState.best_model` → `AppState.volatility_results` → `AppState.model_registry`(сохранение версии) → `AppState.experiment_log`(запись эксперимента) → Прогнозирование | → [качество низкое] → EDA → Предобработка → Валидация
8. **Прогнозирование** → Мониторинг | → [аномалии] → Моделирование → выбор другой модели
9. **Мониторинг** → `AppState.monitoring_results` (метрики качества, дрифт, алерты) → Задачи | → [деградация] → Прогнозирование → Моделирование → переобучение
10. **Для Single-series TS:**
Загрузка → Классификация → Валидация → Предобработка → Feature Store → EDA → Моделирование → Прогнозирование
11. **Для Panel data:**
Загрузка → Классификация → Валидация → **Panel Preprocessing** → **Panel Feature Store** → **Panel EDA** → **Panel Modeling** → **Panel Forecasting**
12. **Для Multivariate panel:**
Загрузка → Классификация → Валидация → **Multivariate Panel Preprocessing** → **Multivariate Feature Store** → **Multivariate EDA** → **Multivariate Modeling** → **Multivariate Forecasting**

## Dataset Lifecycle (Жизненный цикл данных)
**Цель:** Разделение Data Pipeline и Analysis Pipeline для обеспечения воспроизводимости, контроля версий и безопасного экспорта по ролям.

### Структура `AppState.datasets`
Вместо перезаписи `AppState.df` на каждом этапе, состояния хранятся в словаре версий:
```python
AppState.datasets = {
    'raw':         DatasetVersion,   # После загрузки (сырые данные)
    'validated':   DatasetVersion,   # После валидации (пропуски/выбросы исправлены)
    'transformed': DatasetVersion,   # После предобработки (стационарность, масштабирование)
    'features':    DatasetVersion,   # После Feature Engineering (лаги, скользящие окна)
    'forecast':    DatasetVersion    # Финальный датасет с прогнозом
}

### Инвариант неизменности сырых данных

**Правило:** `AppState.datasets.raw.df` — **неизменяемая копия** исходных данных после загрузки.

**Запрещено:**
- Модифицировать `AppState.datasets.raw.df` на любом этапе
- Использовать `AppState.df` как источник истины в новых модулях

**Разрешено:**
- Читать `AppState.datasets.raw.df` для сравнения и отладки
- Использовать `AppState.df` только в legacy-коде (до полной миграции)

**Обоснование:**
- Воспроизводимость: всегда можно вернуться к исходным данным
- Отладка: можно сравнить результат трансформации с оригиналом
- Аудит: партнер может проверить, что исходные данные не были изменены

## Стратегия кэширования (Caching Strategy)

**Цель:** Избежать пересчета тяжелых операций при каждом ререндере Streamlit.

### Типы кэша

#### 1. `@st.cache_data` — для вычислений на данных
**Применяется к:** функциям, которые возвращают данные (DataFrame, dict, list)
**Инвалидация:** при изменении входных данных (хэш df + параметры)
**TTL:** 1 час (3600 секунд)
**max_entries:** 100

**Функции для кэширования:**
- `calculate_ts_passport(df_hash, ts_mode)` → паспорт свойств v1.0/v1.1/v1.2
- `compute_stl_decomposition(df_hash, period, seasonal)` → STL-декомпозиция
- `compute_fft(df_hash, n_fft)` → FFT анализ
- `compute_acf_pacf(df_hash, nlags)` → автокорреляция
- `train_model(df_hash, model_type, params)` → обучение модели
- `compute_granger_causality(df_hash, max_lag)` → Granger тест
- `compute_dtw_distance(series1_hash, series2_hash)` → DTW расстояние
- `compute_rolling_statistics(df_hash, window, stat_type)` → скользящие статистики

#### 2. `@st.cache_resource` — для тяжелых ресурсов
**Применяется к:** объектам, которые создаются один раз и переиспользуются
**Инвалидация:** только при перезапуске приложения
**Примеры:**
- `init_db_connection()` → подключение к БД
- `load_model(model_path)` → загрузка обученной модели (pickle)
- `load_rules_template(template_name)` → загрузка YAML-шаблона

### Ключи инвалидации

**Формат ключа:** `{data_hash}_{computation_type}_{params_hash}`

**Интеграция с Dataset Lifecycle:**

- ✅ Все вкладки (Классификация, Валидация, Предобработка, EDA, Моделирование, Прогнозирование, Задачи)

- ✅ Настройка правил валидации
- ✅ Просмотр логов и отладочной информации

#### 2. Пользователь (`_user`) — внутренний аналитик
**Настраиваемый доступ по модулям:**
- ✅ Доступ к модулям настраивается администратором
- ✅ По умолчанию: Классификация, Валидация, Предобработка, EDA, Моделирование, Прогноз
- ✅ Экспорт данных (сырые данные, паспорта, отчеты) настраивается администратором
- ❌ Нет доступа к управлению пользователями

#### 3. Заказчик (_partner) — внешний пользователь
**Настраиваемый доступ к результатам:**
- ✅ Доступ к модулям настраивается администратором
- ✅ По умолчанию: Классификация, Валидация, Предобработка, EDA, Моделирование, Прогноз
- ✅ Экспорт данных (сырые данные, паспорта, отчеты) настраивается администратором
- ❌ Нет доступа к управлению пользователями
- ❌ Нет доступа к логам
**Обоснование:** Заказчик должен иметь возможность воспроизвести результат прогноза, проверить методологию и убедиться в корректности анализа. Это обеспечивает прозрачность и научную обоснованность результатов.

Позволяет сравнивать свойства данных до и после трансформаций

**Субмодули:**
1. **Корреляционный анализ числовых признаков**
   - Тепловая карта корреляции Пирсона
   - Выявление мультиколлинеарности
   - Передача в Моделирование: список признаков для PCA/регуляризации

2. **Причинно-следственный анализ (Causality Analysis)**
   - Granger Causality (направленное влияние с лагом)
   - Cointegration (долгосрочная связь для нестационарных рядов)
   - Cross-correlation CCF (корреляция с лагами)
   - Передача в Моделирование: список экзогенных переменных для SARIMAX/ML, оптимальные лаги влияния

3. **Анализ сходства рядов** (Similarity Analysis)
   - DTW (Dynamic Time Warping) — нелинейное выравнивание временных рядов
   - Soft-DTW — дифференцируемая версия DTW для оптимизации
   - Euclidean Distance — базовое покомпонентное расстояние
   - Cosine Similarity — сходство паттернов (без учета амплитуды)
   - Матрица сходства между всеми рядами
   - Поиск k-ближайших похожих рядов (k-NN search)
   - Визуализация: тепловая карта сходства, топ-N похожих рядов
   - Передача в Задачи: список похожих стран/регионов для сравнительного анализа

4. **Спектральный анализ временного ряда**
   - ACF/PACF (автокорреляционный анализ)
   - FFT (быстрое преобразование Фурье)
   - Периодограмма (спектральная плотность мощности)
   - Вейвлет-преобразование (CWT)
   - Передача в Моделирование: сезонные периоды (параметр m для SARIMA)

5. **IH-анализ** (Information-Entropy Analysis)
   - Оценка информативности признаков через теорию информации Шеннона
   - Метрика R(Y|X) = I(X;Y) / H(Y)
   - Анализ синергии пар признаков
   - Передача в Моделирование: список информативных признаков для отбора фич
6. Рекомендации по моделям (20 моделей, таблица → Доступны/С ограничениями/Не доступны).

3. **Обучение моделей**
   - Обучение моделей на train_scaled   
4. **Подбор гиперпараметров**   
   - Grid Search (сеточный поиск)
   - Random Search (случайный поиск)
   - Bayesian Optimization (байесовская оптимизация)
   - Автоматический подбор для ARIMA (через AIC/BIC)
   - Кросс-валидация временных рядов (Time Series CV)
   - Сравнение результатов с разными гиперпараметрами
   - Визуализация влияния гиперпараметров на метрики
5. **Построение прогнозов**
   - Прогнозы выбранных моделей на test_scaled → forecast_scaled  
6. **Метрики качества** (RMSE, MAE, MAPE) ← в масштабированной шкале
   - Оценка качества моделей, рекомендации, таблица результатов (скачать csv, excel)

   - Обратное преобразование forecast_scaled → forecast_orig
8. **График прогноза**
   - Построение сравнительного графика: "Прогноз vs Факт" ← в ИСХОДНОЙ шкале
   (скачать png, jpeg, pdf)
9. **История моделей** (Model Registry)
   - Просмотр всех обученных моделей
   - Сравнение метрик версий
   - Откат к предыдущей версии
   - Экспорт истории (CSV, JSON)
10. **Модели волатильности** (volatility.py)
    - ARCH (Autoregressive Conditional Heteroskedasticity)
    - GARCH (Generalized ARCH) — стандарт для кластеризации волатильности
    - EGARCH (Exponential GARCH) — учитывает асимметрию (leverage effect)
    - TGARCH (Threshold GARCH) — пороговый GARCH
    - GJR-GARCH — аналог EGARCH для финансовых данных
    - Прогноз волатильности на горизонт h
    - Расчет VaR (Value at Risk) и CVaR (Conditional VaR)
    - Визуализация прогноза волатильности с доверительными интервалами
11. **Лог экспериментов** (Experiment Log)
    - Запись каждого прогона: гиперпараметры, метрики, параметры трансформаций, timestamp, user
    - Сравнение экспериментов между сессиями (таблица с фильтрацией по тегам/датам)
    - Воспроизведение эксперимента по ID (загрузка параметров и повторный запуск)
    - Файловое хранение: автосохранение в JSON/Parquet при каждом прогоне
    - Загрузка предыдущих экспериментов при старте новой сессии
    - Привязка к `AppState.datasets.features` (какой датасет использовался)

3. Все изменения состояния проходят через типизированный `AppState`

5. Логика вкладок строится следующим образом: классификация → валидация → предобработка → анализ → моделирование → прогнозирование
6. Система ролей определяет доступ к модулям и функциям
7. Заказчик имеет доступ ко всем модулям для воспроизводимости результата
8. EDA передаёт конкретные параметры в Моделирование (информативные признаки, сезонные периоды)
9. EDA поддерживает переключение "До/После" предобработки для сравнения свойств данных
10. Запрет на мутацию `AppState.df` — все новые модули должны использовать явную адресацию через `AppState.datasets.{stage}.df` вместо `AppState.df`. `AppState.df` сохраняется только для обратной совместимости с legacy-кодом.
11. Четкое разделение modeling/ и forecasting/:
    - `modeling/` — только выбор модели (обучение на train, подбор гиперпараметров, сравнение, возврат `best_model`)
    - `forecasting/` — только применение выбранной модели (переобучение на всех данных, генерация прогноза на горизонт h, доверительные интервалы, отчет)
    - `forecasting/` НЕ должен содержать логику подбора гиперпараметров и сравнения моделей
