## ФИЛОСОФИЯ ПЛАТФОРМЫ: БАЛАНС АНАЛИТИКИ И DSS (60/40)

⚠️ **СТРАТЕГИЧЕСКИЙ ИНВАРИАНТ:**
Заявленная цель платформы — «глубокое исследование временных рядов и выявление закономерностей». Чтобы избежать превращения системы в «калькулятор прогнозов», архитектура жестко фиксирует баланс:
**60% Аналитическая платформа** (Data Pipeline, EDA, Modeling) + **40% Система Поддержки Принятия Решений (DSS)**.

### 60% — Аналитический Фундамент (Как устроены данные?)
Обеспечивает надежность, воспроизводимость и математическую строгость:
- **Dataset Lifecycle & OOM Protection:** Версионирование, защита от утечек памяти.
- **Data Quality & Validation:** Жесткие контракты данных (Data Contracts), валидация по стандартам DAMA/ISO.
- **Feature Engineering & Panel Data:** Защита от Data Leakage, строгая работа с панельными данными.
- **Modeling & Forecasting:** Каталог моделей, кросс-валидация, прогнозирование, мониторинг дрифта.

### 40% — Интеллектуальный DSS-Слой (Почему это происходит и что делать?)
Превращает сырые прогнозы в бизнес-инсайты и управленческие решения:
1. **Causal Discovery (Причинный анализ):** Переход от корреляций к причинности. Тесты Грейнджера, коинтеграция (Йохансен), CCF. Выявление истинных драйверов процессов.
2. **Explainability (Интерпретируемость / XAI):** Раскрытие «черного ящика». Глобальный и локальный SHAP, PDP/ICE. **Системная интерпретация (MTS):** функции импульсного отклика (IRF) и декомпозиция дисперсии (FEVD) для понимания каскадных эффектов.
3. **Scenario Analysis (Сценарное моделирование / What-if):** Движок распространения шоков (Shock Propagation Engine). Позволяет накладывать бизнес-гипотезы («Цена сахара +20%») и автоматически пересчитывать прогнозы через причинные графы и IRF-матрицы.
4. **Recommendation Engine (Рекомендательная система):** Динамический подбор моделей и признаков на основе эволюции паспортов свойств ряда (v1_0 → v1_1 → v1_2). Система сама подсказывает аналитику, если данные нестационарны или признаки неинформативны.
5. **Knowledge Base (Институциональная память / Post-MVP):** Накопление бизнес-знаний. Агрегация причинно-следственных связей и проверенных гипотез across all experiments. Переход от «разовых отчетов» к «базе знаний предприятия».

1. **Загрузка** → `AppState.datasets.raw`, `col_types`, `ts_mode_active`
2. **Классификация** → `AppState.data_classification` тип данных (TS/Non-TS, univariate/multivariate) → все последующие модули
3. **Валидация** → `AppState.val_results` (результаты проверки качества), `AppState.validation_ready` (флаг готовности)→ все последующие модули
4. **Предобработка** → `AppState.df`,`AppState.transform_params`, `AppState.ts_props_v1_2` → Feature | → [⚠️ UI-рекомендация: низкое качество признаков] → Валидация
5. **Features** → `AppState.feature_store` (признаки + метаданные) → EDA, Моделирование | → [⚠️ UI-рекомендация: низкое качество признаков] → Предобработка
6. **EDA** → `AppState.eda_results.informative_features`, `AppState.eda_results.seasonal_periods`, `AppState.eda_results.multicollinear_features`, `AppState.eda_results.causality_results`, `AppState.eda_results.similarity_results` → Моделирование, Прогнозирование | → [⚠️ UI-рекомендация: низкое качество данных/паттернов] → Features → Предобработка → Валидация
7. **Моделирование** → `AppState.best_model` → `AppState.volatility_results` → `AppState.model_registry`(сохранение версии) → `AppState.experiment_log`(запись эксперимента) → Прогнозирование | → [⚠️ UI-рекомендация: низкая предсказательная способность] → EDA → Предобработка → Валидация
8. **Прогнозирование** → `AppState.datasets.forecast`, `AppState.forecast_results`, `AppState.forecast_future_orig` → Мониторинг | → [⚠️ UI-рекомендация: аномалии в прогнозе] → Моделирование → выбор другой модели
9. **Интерпретируемость (XAI)** → `AppState.xai_results` (SHAP, PDP, IRF, FEVD) → Задачи (экспорт отчетов для верификации) | → [⚠️ UI-рекомендация: модель опирается на шум] → Features → EDA
10. **Мониторинг** → `AppState.monitoring_results` (метрики качества, дрифт, алерты) → Задачи | → [деградация] → Прогнозирование → Моделирование → переобучение
11. **Для Single-series TS:**
Загрузка → Классификация → Валидация → Предобработка → Feature Store → EDA → Моделирование → Прогнозирование
12. **Для Panel data:**
Загрузка → Классификация → Валидация → **Panel Preprocessing** → **Panel Feature Store** → **Panel EDA** → **Panel Modeling** → **Panel Forecasting**
13. **Для Multivariate panel:**
Загрузка → Классификация → Валидация → **Multivariate Panel Preprocessing** → **Multivariate Feature Store** → **Multivariate EDA** → **Multivariate Modeling** → **Multivariate Forecasting**
14. **Цикличность и Обратные связи (Feedback Loops)**
Пайплайн не является строго линейным. Архитектура UI и `AppState` должна поддерживать следующие явные циклы возврата (откаты аналитика):
  1. **EDA ↔ Feature Store:** 
   - *Вперед:* EDA передает список информативных признаков и сезонных периодов в Feature Store для генерации.
   - *Назад:* Если в EDA выявлена сильная мультиколлинеарность или неинформативность, аналитик возвращается в Feature Store для отбора/удаления признаков, либо в Preprocessing для изменения лагов.
  2. **Modeling ↔ Feature Store:**
   - *Вперед:* Modeling обучается на сгенерированных признаках.
   - *Назад:* Если модели показывают низкое качество (переобучение), аналитик возвращается в Feature Store (меняет окна, убирает шумовые признаки) или в EDA (ищет нелинейные зависимости).
  3. **Forecasting ↔ Modeling:**
   - *Вперед:* Forecasting применяет `best_model` для прогноза на горизонт `h`.
   - *Назад:* Если прогноз содержит аномалии или доверительные интервалы неадекватны, аналитик возвращается в Modeling для смены архитектуры модели или гиперпараметров.
  4. **Monitoring ↔ Modeling (Production Loop):**
   - *Вперед:* Monitoring сравнивает прогноз с фактом.
   - *Назад:* При обнаружении Data Drift или Model Decay, система инициирует переобучение (возврат в Modeling с новыми данными).
  5. **XAI ↔ Modeling / Feature Store (Interpretability Loop):**
   - *Вперед:* Modeling передает обученную модель в XAI.
   - *Назад:* Если XAI показывает, что модель опирается на "мусорные" признаки (например, артефакты сбора данных) или игнорирует критически важные экзогенные переменные (Permutation Importance ≈ 0), аналитик возвращается в **Feature Store** (чтобы переделать признак) или в **EDA** (чтобы проверить причинность).

> **Правило UI:** На каждой вкладке должна быть кнопка/ссылка **"↩️ Вернуться к настройкам [Название этапа]"**, которая явно переводит пользователя на нужную вкладку и сбрасывает (инвалидирует) downstream-состояния в `AppState`.

## Итеративная природа анализа и Каскадная инвалидация (Human-in-the-Loop)

⚠️ **АРХИТЕКТУРНЫЙ ИНВАРИАНТ:** Процесс анализа временных рядов является **циклическим**, а не линейным. Аналитик имеет право в любой момент вернуться на любой предыдущий этап (например, из `Forecasting` в `Feature Store` или `EDA`), изменить параметры и перезапустить пайплайн.

**Механизм поддержки итераций:**
1. **Сохранение истории (Experiment Log):** Каждый "прогон" (итерация) фиксируется в `experiment_log`. Аналитик может сравнивать результаты разных итераций, не теряя предыдущие удачные эксперименты.
2. **DatasetManager (Версионирование):** При возврате назад и изменении параметров создается *новая версия* датасета (например, `features_v2`), а не перезаписывается старая. Это позволяет безопасно "откатываться" к предыдущим состояниям.

**Правило Каскадной Инвалидации (Downstream Invalidation):**
Если аналитик изменяет состояние на этапе `N`, все downstream-этапы (`N+1`, `N+2`...) **автоматически инвалидируются** в `AppState`.
- *Пример 1:* Изменены параметры в `Preprocessing` (создан `transformed_v2`) → `features`, `best_model`, `forecast_results` помечаются как `stale` (устаревшие) и сбрасываются в `None`.
- *Пример 2:* В `Feature Store` отключен генератор признаков → `best_model` сбрасывается.
- *Реализация в UI:* При переходе на вкладку с инвалидированным состоянием UI показывает баннер: *"⚠️ Параметры на предыдущем этапе были изменены. Результаты текущего этапа устарели. Пожалуйста, перезапустите вычисления."* и блокирует кнопку "Экспорт/Применение" до повторного запуска.

## Механизм обратной связи и контроля качества

Контроль качества жестко разделяется на два уровня в зависимости от этапа пайплайна:

### 1. Hard Blockers (Автоматическая блокировка пайплайна)
Применяется **только на этапе Валидации**. Если `DQ Score < порога` (настраивается в `AppState.rules`), переход к Предобработке **автоматически блокируется**.
- **Визуальный:** Красный индикатор качества, кнопка "Перейти к Предобработке" неактивна (`disabled`).
- **Текстовый:** "Качество данных недостаточно для начала трансформаций. Необходимо исправить критические ошибки валидации."

### 2. Soft Warnings (Рекомендации к возврату в UI)
Применяется на этапах **Feature Store, EDA и Моделирования**. Пайплайн **никогда не блокируется автоматически** (пользователь всегда может нажать "Проджить несмотря на предупреждение"), но система генерирует явные рекомендации вернуться на шаг назад, если выявлены специфические триггеры (см. таблицу ниже).
- **Визуальный:** Желтый/Оранжевый баннер с иконкой ⚠️ и кнопкой "Вернуться к [Предыдущий этап]".
- **Текстовый:** "Обнаружены признаки низкого качества [указать причину]. Рекомендуется пересмотреть параметры [этапа]."

### Триггеры Soft Warnings (Критерии «низкого качества» по этапам)

Чтобы избежать субъективности, каждый модуль вычисляет свой специфический метрический триггер, который устанавливает флаг `AppState.{stage}_quality_warning = True`:

| Этап                                         | Триггер (Условие срабатывания ⚠️)                                 | Рекомендуемое действие (Куда возвращаться) |
|----------------------------------------------|-------------------------------------------------------------------|---------------------------------------------|
| **Feature Store**                            | **Низкая информативность:** Более 70% сгенерированных признаков имеют метрику IH-анализа $R(Y|X) < 0.05$ (или близкую к нулю дисперсию). | → **Предобработка** (пересмотреть трансформации, стабилизацию дисперсии) |
| **EDA** | **Скрытые паттерны / Мультиколлинеарность:** <br>1. Отсутствие значимых сезонных периодов (для TS) при включенном `ts_mode_active`.<br>2. Жесткая мультиколлинеарность (VIF > 10) для >50% признаков, без возможности их удаления. | → **Feature Store** (отбор признаков) или **Предобработка** (PCA, изменение лагов) |
| **Моделирование** | **Несходимость / Переобучение:** <br>1. Все модели из каталога исключены из-за несходимости (см. раздел "Обработка ошибок").<br>2. Разрыв метрик Train/Test > 50% (жесткое переобучение).<br>3. $R^2 < 0.2$ или $MAPE > 50\%$ на тестовой выборке для всех моделей. | → **EDA** (проверить экзогенные переменные, причинность) или **Предобработка** (изменить горизонт, агрегацию) |

**Техническая реализация:** 
Флаги предупреждений (`features_quality_warning`, `eda_quality_warning`, `modeling_quality_warning`) хранятся в `AppState` и считываются UI-слоем (`app/ui/tabs/...`) для рендеринга желтых баннеров. Пользователь может игнорировать их (кроме роли `_partner`, которой эти вкладки доступны только для чтения).

## Обработка ошибок и Graceful Degradation
**Цель:** Обеспечить устойчивость пайплайна к сбоям и понятную обратную связь для пользователя (особенно для роли `_partner`, которая не должна видеть технические детали).

### Принципы обработки ошибок
1. **Атомарность этапов:** Если этап не завершился успешно, состояние `AppState.datasets.{stage}` **не обновляется**. Пользователь остается на предыдущей успешной стадии.
2. **Явная классификация ошибок:**
   - **Критические (Critical):** Пайплайн не может продолжаться (например, отсутствие данных, несовместимость типов). Блокировка с четким сообщением.
   - **Предупреждения (Warning):** Пайплайн может продолжаться, но с ограничениями (например, часть entity исключена из Panel). Пользователь видит уведомление.
   - **Информационные (Info):** Не влияют на работу (например, модель не сошлась, но есть альтернативные). Логируется в `AppState.error_log`.
3. **Graceful Degradation:** Если тяжелая операция не выполнилась (STL, FFT, GARCH), пайплайн **не падает**, а переходит к упрощенной стратегии (например, без декомпозиции, без спектральных признаков).

### Сценарии обработки ошибок
#### 1. **Сбой на этапе Предобработки**
- **STL-декомпозиция на коротком ряде** (< 2 сезонных циклов):
  - **Действие:** Пропустить STL, использовать аддитивную декомпозицию или сглаживание (LOWESS).
  - **Сообщение пользователю:** "Ряд слишком короткий для STL-декомпозиции. Применено упрощенное сглаживание."
  - **Логирование:** `AppState.error_log.append({'stage': 'preprocessing', 'error': 'STL failed', 'fallback': 'LOWESS'})`

#### 2. **Сбой на этапе Моделирования**
- **Модель не сходится** (ARIMA, GARCH, ML с высокой сложностью):
  - **Действие:** Исключить модель из списка кандидатов, перейти к следующей.
  - **Сообщение пользователю:** "Модель {model_name} не смогла обучиться. Причина: {reason}. Исключена из сравнения."
  - **Fallback:** Если все модели не сошлись, предложить упрощенные модели (Naive, Moving Average).
  - **Логирование:** `AppState.error_log.append({'stage': 'modeling', 'model': 'ARIMA', 'error': 'Non-convergence', 'action': 'excluded'})`

#### 3. **Частичный сбой в Panel Data**
- **Часть entity не прошли валидацию** (недостаточно наблюдений, пропуски > 50%):
  - **Действие:** Исключить проблемные entity из анализа, продолжить с оставшимися.
  - **Сообщение пользователю:** "Entity {entity_list} исключены из анализа. Причина: {reason}. Анализ продолжен для {n_remaining} entity."
  - **Требование:** Если исключено > 30% entity, блокировать переход к Моделированию с предупреждением.
  - **Логирование:** `AppState.error_log.append({'stage': 'panel_preprocessing', 'excluded_entities': [...], 'reason': 'insufficient_data'})`

#### 4. **Сбой на этапе Прогнозирования**
- **Обратное преобразование невозможно** (отсутствуют `transform_params`):
  - **Действие:** Вернуть прогноз в масштабированной шкале с предупреждением.
  - **Сообщение пользователю:** "Обратное преобразование невозможно. Прогноз представлен в масштабированной шкале."
  - **Логирование:** `AppState.error_log.append({'stage': 'forecasting', 'error': 'inverse_transform_failed', 'fallback': 'scaled_output'})`

#### 5. **Сбой на этапе Мониторинга**
- **Фактические данные не загружены** (пользователь не предоставил для сравнения):
  - **Действие:** Пропустить сравнение "Прогноз vs Факт", показать только анализ дрифта прогнозов.
  - **Сообщение пользователю:** "Фактические данные не предоставлены. Сравнение с фактом недоступно."

#### 6. **Сбой при финальном переобучении в Прогнозировании (Forecasting Fallback)**
**Ситуация:** Модель (например, ARIMA, GARCH) успешно обучилась на тренировочной выборке (`modeling/`), но не сходится при попытке переобучения на полном наборе данных ($Train \cup Test$) в `forecasting/` (например, из-за нарушения стационарности на добавленных точках или взрыва дисперсии).
**Действие:** 
1. Перехватить исключение сходимости.
2. **Автоматический откат (Fallback):** Использовать объект модели и гиперпараметры, уже сохраненные в `AppState.best_model` (то есть модель, обученную *только* на тренировочной выборке).
3. Сформировать прогноз на горизонт $h$, используя исторические данные до конца $Train$ (или $Test$, если модель позволяет экстрополировать состояние).
**Сообщение пользователю:** "⚠️ Финальное переобучение модели на полном наборе данных не удалось (причина: {reason}). Используется модель, обученная на тренировочной выборке. Прогноз сгенерирован, но его точность может быть незначительно снижена."
**Логирование:** `AppState.error_log.append({'stage': 'forecasting', 'error': 'RetrainFailedOnFullData', 'fallback': 'UsedTrainOnlyModel', 'reason': str(e)})`

### Механизм логирования ошибок
**Структура `AppState.error_log`:**

## СТРУКТУРА `AppState.datasets` (DatasetManager)
Вместо перезаписи `AppState.df` на каждом этапе, состояния управляются через `DatasetManager`. Он хранит историю версий и автоматически освобождает память (Garbage Collection), 
предотвращая OOM при работе с большими данными (>1GB).

```python
# app/core/datasets.py
class DatasetManager:
    # Хранит словари списков версий: {'raw': [v1, v2], 'validated': [v1], ...}
    # Автоматически удаляет старые версии из памяти при превышении max_versions (по умолчанию 3)
    # Предоставляет методы: add_version(), get_version(), get_latest(), get_memory_usage()
```

```markdown
> ⚠️ **ИНВАРИАНТ BACKEND-AGNOSTIC GC:**
> `DatasetManager` **не знает и не должен знать**, какой именно движок (Pandas, Dask, Polars) используется под капотом. 
> Метод `get_memory_usage()` должен опираться на полиморфный вызов `version.get_memory_footprint()`. 
> Garbage Collection (удаление старых версий из `max_versions`) работает с **ссылками на вычислительные графы**, что позволяет корректно освобождать память как для in-memory (Pandas), так и для out-of-core (Dask) фреймов без утечек.
```

### Правила инициализации в Streamlit (Критично!)
Streamlit перезапускает скрипт при каждом взаимодействии. Чтобы `DatasetManager` не пересоздавался (что приведет к потере версий) и не дублировался в памяти, его инициализация должна быть строго завязана на `st.session_state`:

```python
# app/core/state.py или app/main.py
if 'datasets_manager' not in st.session_state:
    st.session_state.datasets_manager = DatasetManager(max_versions=3)

# В самом AppState (через property или явное присваивание при старте сессии)
AppState.datasets = st.session_state.datasets_manager
```

## СТРАТЕГИЯ КЭШИРОВАНИЯ (Caching Strategy)

**Цель:** Избежать пересчета тяжелых операций при каждом ререндере Streamlit.

### Типы кэша

#### 1. `@st.cache_data` — для вычислений на данных
**Применяется к:** функциям, которые возвращают данные (DataFrame, dict, list)
**Инвалидация:** при изменении входных данных (хэш df + параметры)
**TTL:** 1 час (3600 секунд)
**max_entries:** 100

**Функции для кэширования:**
- `calculate_ts_passport(df_hash, ts_mode)` → паспорт свойств v1_0/v1_1/v1_2
- `compute_stl_decomposition(df_hash, period, seasonal)` → STL-декомпозиция
- `compute_fft(df_hash, n_fft)` → FFT анализ
- `compute_acf_pacf(df_hash, nlags)` → автокорреляция
- `train_model(df_hash, model_type, params)` → обучение модели
- `compute_granger_causality(df_hash, max_lag)` → Granger тест
- `compute_dtw_distance(series1_hash, series2_hash)` → DTW расстояние
- `compute_rolling_statistics(df_hash, window, stat_type)` → скользящие статистики

#### 2. `@st.cache_resource` — для тяжелых ресурсов и статических артефактов
**Применяется к:** объектам, которые создаются один раз и переиспользуются (статические конфиги, схемы, подключения, модели).
**Инвалидация:** только при перезапуске приложения или явном вызове `.clear()`.
**Примеры:**
- `init_db_connection()` → подключение к БД
- `load_model(model_path)` → загрузка обученной модели (pickle)
- `load_rules_template(template_name)` → загрузка YAML-шаблона правил
- `load_rules_schema()` → **загрузка JSON Schema для валидации YAML-шаблонов** (статический артефакт уровня приложения, не должен храниться в AppState)

### Ключи инвалидации

**Формат ключа:** `{data_hash}_{computation_type}_{params_hash}`

**Интеграция с Dataset Lifecycle:**
```python
# Кэш привязан к версии датасета
cache_key = f"{dataset_version.id}_{computation_type}_{params_hash}"

# Пример:
@st.cache_data(ttl=3600)
def compute_stl_decomposition(dataset_version_id: str, period: int) -> STLResult:
    # Явное получение версии через DatasetManager (stage нужен для поиска)
    version = AppState.datasets.get_version(stage='transformed', version_id=dataset_version_id)
    df = version.df
```

## УРОВНИ ДОСТУПА: Read (Чтение) vs Execute (Исполнение)

Для обеспечения безопасности и воспроизводимости (Dataset Lifecycle) права доступа жестко разделяются на два уровня:

1. **READ (Чтение/Аудит/Верификация):** 
   - Просмотр данных, паспортов свойств, метрик, графиков.
   - Просмотр примененных параметров (`transform_params`, `model_params`).
   - Экспорт артефактов (в рамках разрешенных стадий).
   - *Не подразумевает возможности запускать вычисления или менять состояние.*

2. **EXECUTE (Исполнение/Модификация):**
   - Запуск вкладок и пайплайнов (нажатие кнопок "Обучить", "Применить", "Запустить валидацию").
   - Изменение параметров (выбор гиперпараметров, настройка правил валидации).
   - Мутация состояния `AppState.datasets` и `AppState.model_registry`.

**Золотое правило:** Внешний пользователь (`_partner`) имеет **исключительно READ-доступ**. Он наблюдатель и аудитор, но не оператор пайплайна.

**ЗАПРЕЩЕНО (Отсутствие EXECUTE):**
- ❌ **Классификация и Предобработка:** Полный доступ закрыт (включая чтение `transformed`).
- ❌ **Запуск вычислений:** Все кнопки запуска ("Обучить модель", "Применить трансформацию", "Запустить EDA") **заблокированы (disabled)** или скрыты.
- ❌ **Изменение параметров:** Партнер не может менять гиперпараметры, правила валидации или выбирать другие модели. Он видит только то, что было зафиксировано 
внутренним аналитиком (`_user` или `_admin`).
- ❌ **Мониторинг:** Закрыт (внутренний инструмент эксплуатации).

**Обоснование:** 
Разделение `_user` (оператор) и `_partner` (аудитор) гарантирует, что пайплайн является "черным ящиком" с прозрачными результатами для заказчика, но защищенным от 
внешнего вмешательства. Воспроизводимость достигается тем, что партнер может *скачать* зафиксированные параметры и данные, но не может *перезаписать* их своей сессией.

# app/core/auth.py

    Используется внутри UI-компонентов для динамического скрытия/блокировки элементов.

    # Обращение к Матрице доступа (источнику истины)
    return ACCESS_MATRIX.get(role, {}).get(stage, False)

# Пример использования во Вкладке EDA (app/ui/tabs/eda.py):
role = AppState.user_role

# Динамическая проверка: показывать ли переключатель "До/После предобработки"

**Воспроизведение для роли `_partner` (Аудитор):**
- Партнер не работает с "сырыми" версиями данных. Партнер работает с **Реестром Экспериментов** (`experiment_log`).
- При запросе на аудит, партнер выбирает конкретный `Experiment` из списка.

  связку: *"Вот эти данные + вот эти признаки + вот эта модель = вот этот прогноз"*.


## СТРАТЕГИЯ РАБОТЫ С БОЛЬШИМИ ДАННЫМИ И ЗАЩИТА ОТ OOM

⚠️ **КРИТИЧЕСКОЕ ОГРАНИЧЕНИЕ СКОУПА (MVP vs FUTURE):**
Реализация Out-of-Core вычислений (Dask/Polars) и автоматического переключения бэкендов **КАТЕГОРИЧЕСКИ ИСКЛЮЧЕНА из Этапов 1–10**. 
Библиотеки спектрального анализа (`scipy`), статистического моделирования (`statsmodels`) и специфичные паттерны Panel Data (`df.groupby().transform()`) требуют in-memory массивов. Их адаптация под out-of-core движки требует написания отдельных дублирующих модулей, что нецелесообразно на этапе стабилизации архитектуры.

### 1. Реальность Этапов 1–10: Strict In-Memory Pandas + OOM Protection
**Цель:** Обеспечить стабильную работу пайплайна с датасетами, помещающимися в RAM, и гарантированно предотвратить падение приложения (OOM).

**Архитектурный принцип (MVP):** 
- `DatasetManager` и весь пайплайн (Feature Store, EDA, Modeling) работают **исключительно** с `pandas.DataFrame`.
- **Защита от OOM:** На этапе загрузки (`app/data/loader.py`) система оценивает размер файла. Если размер превышает жесткий лимит (например, 1.5 ГБ) или порог доступной RAM, загрузка **блокируется** с понятным сообщением для пользователя: *"Размер данных превышает лимиты текущей конфигурации. Пожалуйста, используйте агрегированные данные или обратитесь к администратору"*.
- Garbage Collection (`max_versions=3`) работает со ссылками на Pandas DataFrame, гарантируя своевременное освобождение RAM.

### 2. Архитектурный резерв: Out-of-Core (Этап 11+ / Post-MVP)
*Данный подраздел описывает видение развития системы. Он не блокирует релиз MVP и запускается только после полной стабилизации Pandas-пайплайна.*

**Цель:** Обеспечить обработку датасетов, превышающих RAM (10 ГБ+), без изменения бизнес-логики UI.

**Архитектурный принцип (Future):** `DatasetManager` станет **backend-agnostic** оркестратором. Он будет управлять версиями независимо от того, является ли базовый DataFrame "тяжелым" (Pandas) или "ленивым" (Dask / Polars LazyFrame).

**План внедрения (когда будет запущен):**
1. **Автоматический триггер движка (Auto-Switching):** В `loader.py` файлы > X ГБ будут маршрутизироваться на `dask.dataframe` или `polars.LazyFrame`. Данные будут читаться чанками, а вычислительный граф строиться без загрузки в RAM.
2. **Полиморфизм DatasetVersion:** Инкапсуляция движка внутри `DatasetVersion` с методом `get_memory_footprint()`, корректно оценивающим мета-данные ленивых фреймов для работы GC.
   ```python
   # Пример кода для будущего этапа:
   @dataclass
   class DatasetVersion:
       id: str
       stage: str
       _df: Any  # pd.DataFrame | dd.DataFrame | polars.LazyFrame
       backend: str # 'pandas' | 'dask' | 'polars'
       
       def get_memory_footprint(self) -> int:
           if self.backend == 'pandas':
               return self._df.memory_usage(deep=True).sum()
           else:
               return estimate_out_of_core_footprint(self._df)
   ```

### 3. Инвариант воспроизводимости и «Закрепленные артефакты» (Pinned Artifacts)

⚠️ **КРИТИЧЕСКОЕ ПРАВИЛО:** `DatasetManager` управляет **только** оперативной памятью (RAM). Он **не гарантирует** сохранность данных после завершения сессии или вытеснения версии из RAM (GC).

**Механизм «Закрепления» (Pinning) для воспроизводимости:**
1. В момент успешного завершения эксперимента в `modeling/` или `forecasting/`, система **обязана** сериализовать исходный датасет (версию, на которой обучалась модель) на диск в формате `artifacts/{exp_id}/data.parquet`.
2. Файл `manifest.json` жестко привязывает `exp_id` к хэшу этого `data.parquet`.
3. **Эксперимент считается «Закрепленным» (Pinned) на диске**, даже если соответствующая версия была удалена из RAM сборщиком мусора (`DatasetManager`).

**Воспроизведение для роли `_partner` (Аудитор):**
- Партнер **никогда** не обращается к `DatasetManager` оператора `_user`.
- При запросе на воспроизведение/аудит, система читает `manifest.json`, находит `data.parquet` на диске и загружает его в **изолированный, временный экземпляр** `DatasetManager` в сессии партнера.
- Это гарантирует, что партнер может проверить методологию спустя дни/недели, независимо от того, какие данные сейчас в RAM у внутреннего аналитика.

## СЛОЙ МНОГОМЕРНОГО АНАЛИЗА (Multivariate Analytics Layer)

⚠️ **КОНЦЕПТУАЛЬНОЕ РАЗГРАНИЧЕНИЕ:**
Архитектура жестко разделяет три типа многомерности:
1. **Single-series + Exogenous:** 1 целевая переменная + внешние факторы (SARIMAX, ML). Факторы экзогенны (не зависят от целевой).
2. **Panel Data:** $N$ сущностей, 1 (или мало) переменных. Фокус на гетерогенности сущностей (Fixed/Random Effects).
3. **Multivariate Time Series (MTS):** 1 система, $N$ эндогенных переменных (например: Цена, Урожайность, Осадки, Температура). Фокус на **внутренней динамике системы**, равновесии и перекрестном влиянии.

Для полноценного анализа MTS (аграрные системы, макроэкономика) вводится специализированный слой `Multivariate Analytics`.

### 1. Multivariate EDA (Системный анализ)
*Модули:* `app/eda/multivariate.py`, `app/eda/cointegration.py`
- **Проверка стационарности системы:** Расширенный тест Дики-Фуллера (ADF) и КПСС для каждого ряда.
- **Тест на коинтеграцию (Johansen Test):** Критически важно для нестационарных рядов. Определяет наличие долгосрочного равновесия между переменными (например, Цена и Урожайность не могут уходить в бесконечность друг относительно друга).
- **Определение порядка лагов системы:** Критерии AIC/BIC/HQIC для VAR-моделей.
- **Граф причинности системы:** Матрица тестов Грейнджера (Granger Causality Matrix) $N \times N$ для выявления направленных связей внутри системы.

### 2. Multivariate Modeling (Системное моделирование)
*Модули:* `app/modeling/var.py`, `app/modeling/vecm.py`, `app/modeling/dfm.py`
- **VAR (Vector Autoregression):** Базовая модель для стационарных систем. Все переменные трактуются как эндогенные.
- **VECM (Vector Error Correction Model):** Применяется *только* если тест Йохансена показал коинтеграцию. Моделирует как краткосрочную динамику, так и скорость возврата к долгосрочному равновесию (Error Correction Term).
- **Dynamic Factor Models (DFM) / PCA для TS:** Выделение общих скрытых факторов (например, "общий макроэкономический шок" или "погодный индекс"), которые движут всеми $N$ переменными одновременно.

### 3. Multivariate Diagnostics & Interpretation (Интерпретация системы)
*Модули:* `app/explainability/system_xai.py`
Это ключевое отличие MTS от ML. Интерпретация идет не через SHAP, а через математические свойства системы:
- **IRF (Impulse Response Functions / Функции импульсного отклика):** Как шок в переменной $A$ (Осадки) влияет на переменную $B$ (Урожайность) и $C$ (Цена) на горизонтах $t+1, t+2 ... t+h$.
- **FEVD (Forecast Error Variance Decomposition):** Доля дисперсии ошибки прогноза переменной $A$, объясняемая шоками в переменной $B$ (например, "30% колебаний цены зерна объясняются шоками урожайности").
- **Historical Decomposition:** Разложение исторического поведения ряда на вклад конкретных структурных шоков.

### Интеграция с AppState и What-if (Синергия слоев)
Результаты MTS-слоя сохраняются в `AppState.mts_results`:
```python
@dataclass
class MTSResults:
    cointegration_rank: int          # Ранг коинтеграции (для VECM)
    optimal_lag: int                 # Оптимальный лаг системы
    irf_matrix: np.ndarray           # Матрица импульсных откликов (N x N x horizon)
    fevd_table: pd.DataFrame         # Таблица декомпозиции дисперсии

```

**АРХИТЕКТУРНЫЙ ИНВАРИАНТ ДВУХ ТРЕКОВ ОБУЧЕНИЯ (Dual-Track Modeling):**
Модуль `modeling/` работает с двумя принципиально разными источниками данных. Чтобы `model_registry` и `experiment_log` могли корректно обеспечить воспроизводимость, каждая обученная модель фиксируется с указанием `source_stage`:

- **Track A (ML & Feature-based):** Модели (XGBoost, LightGBM, Random Forest, Panel ML) обучаются на признаках.
  - *Источник:* `AppState.datasets.features.df`
  - *Фиксация в Registry/Experiment:* `source_stage='features'`, `dataset_version_id=features.version_id`, `features_version_id=features.version_id`.
- **Track B (Classical TS & Transform-based):** Классические модели (ARIMA, SARIMA, Prophet, Exponential Smoothing) обучаются на трансформированных рядах, минуя Feature Store (им не нужны лаги/rolling).
  - *Источник:* `AppState.datasets.transformed.df`
  - *Фиксация в Registry/Experiment:* `source_stage='transformed'`, `dataset_version_id=transformed.version_id`, `features_version_id=None`.

**Железное правило:** `model_registry` и `experiment_log` **никогда** не делают жестких предположений о наличии `features_version_id`. Они всегда опираются на пару `(source_stage, dataset_version_id)`.

**Для Single-series TS:**

**Субмодули:**
1. **Семейство доступных моделей**

3. **Обучение моделей**

   - Автоматический подбор для ARIMA (через AIC/BIC)
   - Кросс-валидация временных рядов (Time Series CV)
   - Сравнение результатов с разными гиперпараметрами
   - ⚠️ **Атомарная фиксация:** В момент завершения подбора и выбора модели с лучшей метрикой, происходит одновременная запись `AppState.best_model` и `AppState.model_params`.

   - Просмотр всех обученных моделей
   - Сравнение метрик версий
   - Откат к предыдущей версии
   - Экспорт истории (CSV, JSON)
10. **Модели волатильности** (volatility.py)
    - ARCH (Autoregressive Conditional Heteroskedasticity)
    - GARCH (Generalized ARCH) — стандарт для кластеризации волатильности
    - EGARCH (Exponential GARCH) — учитывает асимметрию (leverage effect)
    - TGARCH (Threshold GARCH) — пороговый GARCH
    - GJR-GARCH — аналог EGARCH для финансовых данных
    - Прогноз волатильности на горизонт h
    - Расчет VaR (Value at Risk) и CVaR (Conditional VaR)
    - Визуализация прогноза волатильности с доверительными интервалами
11. **Лог экспериментов** (Experiment Log)
    - Запись каждого прогона: гиперпараметры, метрики, параметры трансформаций, timestamp, user
    - Сравнение экспериментов между сессиями (таблица с фильтрацией по тегам/датам)
    - Воспроизведение эксперимента по ID (загрузка параметров и повторный запуск)
    - Гибридное хранение с гарантией целостности (Manifest-based Storage): 
      Метаданные (метрики, гиперпараметры, теги) хранятся в локальной **SQLite БД** для быстрого поиска. 
      Тяжелые артефакты (модели в `pickle`, датасеты в `Parquet`) хранятся в файловой системе (`artifacts/{exp_id}/`).
      Механизм атомарности и синхронизации:
      1. В папке эксперимента создается файл-манифест `manifest.json`, содержащий метаданные и **SHA-256 хэши** всех тяжелых артефактов (`model.pkl`, `data.parquet`).
      2. Запись в SQLite (индексация эксперимента) происходит **только после** успешной записи всех файлов и верификации их хэшей через манифест.
      3. При загрузке/воспроизведении эксперимента по ID система сначала читает манифест, вычисляет хэши файлов на диске и сверяет их. Если хэш не совпадает или файл отсутствует — эксперимент помечается как `CORRUPTED` и блокируется для воспроизведения.
    - Загрузка предыдущих экспериментов при старте новой сессии (чтение индекса из SQLite)
    - Привязка к источнику данных через универсальный контракт: `(source_stage, dataset_version_id)`. Для ML-моделей `source_stage='features'`, для классических TS-моделей — `source_stage='transformed'` (см. раздел «Инвариант Двух Треков Обучения»).

### Вкладка 8: ИНТЕРПРЕТИРУЕМОСТЬ (XAI)
**Цель:** Раскрытие «черного ящика» моделей. Объяснение того, как и почему модель формирует прогнозы, для верификации методологии и принятия бизнес-решений.
Эта вкладка является ключевой для роли _partner (Аудитор/Заказчик), так как предоставляет обоснование прогнозов.

**Входные данные:**
`AppState.best_model` → обученная модель (для извлечения нативных важностей или применения SHAP).
`AppState.datasets.features.df` → датасет с признаками (для расчета фоновых распределений и PDP).
`AppState.forecast_results` → метаданные прогноза.
`AppState.model_params` → параметры модели.
`AppState.mts_results` → результаты многомерного анализа (матрицы IRF, FEVD, ранг коинтеграции) для системной интерпретации (активируется только для режима Multivariate TS).

**Субмодули:**
1. **Глобальная интерпретируемость** (Global XAI - "Как модель работает в целом?")
   - SHAP Summary Plot: Матрица важности признаков (какие фичи сильнее всего сдвигают прогноз).
   - Permutation Importance: Модель-агностик оценка (насколько упадет качество, если случайно перемешать признак). Критично для сравнения с нативными важностями бустингов.
   - Feature Contribution (Global): Суммарный вклад групп признаков (Лаги vs Календарные vs Экзогенные vs Макро).
2. **Локальная интерпретируемость** (Local XAI - "Почему прогноз ИМЕННО ТАКОЙ в этой точке?")
   - SHAP Waterfall / Force Plots: Разложение конкретного прогноза (например, "Базовое значение + Лаг_1 дал +2% + Шок цены дал -1% = Итог 4%").
   - Выбор точки: Пользователь может выбрать любую точку на горизонте прогноза (или историческую точку) и посмотреть "анатомию" этого предсказания.
3. **Временная интерпретируемость** (Temporal XAI - Специфика TS)
   - Decomposition of Forecast: Визуализация вклада тренда, сезонности и остатка в итоговый прогноз.
   - Lag Impact Analysis: Как значения в моменты t−1,t−7,t−30 влияют на прогноз в момент t+h.
   - Exogenous Shock Response: Если в модель поданы экзогенные переменные, график "Импульсной реакции" (как изменение цены на нефть на 10% влияет на прогноз ВВП).
4. **Зависимости признаков** (PDP & ICE)
   - Partial Dependence Plots (PDP): Маржинальный эффект признака на прогноз (например, "При росте ключевой ставки выше 8% прогноз инфляции выходит на плато").
   - Individual Conditional Expectation (ICE): PDP для каждой сущности (в Panel Data). Показывает, одинаково ли реагируют разные страны/регионы на один и тот же фактор.
5. **Системная интерпретируемость** (System-level Interpretation - Специфика Multivariate TS)
   - Impulse Response Functions (IRF): Графики импульсного отклика, показывающие, как шок в одной переменной системы (например, "Осадки") распространяется на другие переменные ("Урожайность", "Цена") на горизонтах t+1,t+2...t+h. Критично для понимания каскадных эффектов в аграрных и макроэкономических системах.
   - Forecast Error Variance Decomposition (FEVD): Таблицы декомпозиции дисперсии ошибки прогноза. Показывают, какой процент волатильности целевой переменной объясняется шоками в других переменных системы (например, "30% колебаний цены зерна объясняется шоками урожайности").
   - Historical Decomposition: Разложение исторического поведения ряда на вклад конкретных структурных шоков.

### Архитектурное примечание для сценарного анализа (What-if / iDSS)
Для подмодулей **3 (Сценарный анализ what-if)** и **4 (iDSS)** создается отдельный изолированный пакет `app/scenarios/`. 
**Правило:** Сценарный анализ **никогда** не мутирует основное состояние `AppState.datasets.features`. 
Вместо этого `app/scenarios/` клонирует текущий `features` в оперативную память, применяет шоковые воздействия (например, "рост цены на нефть на 20%") и считает локальные прогнозы. Это гарантирует, что "песочница" What-if не сломает основной пайплайн и не потребует пересчета кэша для базовых моделей.
### Движок распространения шоков (Shock Propagation Engine)
Для поддержки полноценного DSS (в частности, аграрной и макроэкономической аналитики) модуль `app/scenarios/` реализует механизм каскадного распространения шоков (What-If Scenario Generation).

**Проблема:** В ML и TS-моделях нельзя просто "сдвинуть" целевую переменную. Чтобы оценить влияние шока (например, "Цена сахара +20%") на зависимый ряд ("Цена свеклы"), система должна сгенерировать *будущий трейл* экзогенных переменных.

**Архитектура What-If пайплайна в `app/scenarios/`:**
1. **Shock Definition (Задание шока):** Пользователь задает точку вмешательства (intervention point) и тип шока (абсолютное значение, процент, волатильность, структурный сдвиг).
2. **Causal Graph Routing (Маршрутизация через граф причинности):** Движок обращается к `AppState.eda_results.causality_results` (Granger, CCF) и `AppState.eda_results.similarity_results`. Если переменная A (Сахар) является Granger-причиной для B (Свекла) с лагом $k$, шок применяется к A.
3. **Exogenous Trail Generation (Генерация трейлов):** 
   - Для VAR/VECM моделей: Используется математический аппарат *Impulse Response Functions (IRF)* для расчета отклика всей системы.
   - Для ML/SARIMAX: Движок генерирует синтетический будущий трейл для переменной-шока (например, "Цена сахара = текущий тренд + 20% на горизонте h"), чтобы использовать его как `exog` / `future_covariates` при прогнозировании целевой переменной (Свеклы).
4. **Scenario Comparison (Сравнение сценариев):** Построение "веера" прогнозов (Baseline vs Shock Scenario) с расчетом дельты в абсолютном и процентном выражении.

**Аграрные пресеты (Agrarian DSS Presets):**
В `app/scenarios/presets.py` зашиты шаблоны комплексных шоков:
- *Погодный шок:* Засуха (падение урожайности X% -> рост цены Y% -> изменение экспортных пошлин).
- *Логистический шок:* Рост цен на удобрения/топливо (сдвиг себестоимости).
- *Регуляторный шок:* Введение квот или субсидий.

## КЛЮЧЕВЫЕ СУЩНОСТИ
- `AppState.df` — **Read-Only свойство (Fallback для Legacy)**. Реализовано как `@property` с ленивой загрузкой (lazy evaluation). 
  Жестко указывает на `AppState.datasets.validated.df` (если валидация пройдена), либо на `AppState.datasets.raw.df` (если валидация еще не запускалась). 
  **Важно для Фазы 1:** Свойство не хранит данные в себе, а забирает их из `DatasetManager` по запросу. Это предотвращает дублирование DataFrame в памяти (OOM) при параллельной работе legacy и нового кода.
  **НЕ является "активным датасетом вкладки" и НЕ переключается динамически.** В новых модулях использование СТРОГО ЗАПРЕЩЕНО (см. Правило 10).
- `AppState.datasets.raw` — неизменяемая сырая копия (после загрузки)
- `AppState.datasets.validated` — очищенный DataFrame (после валидации, пропуски/выбросы исправлены)
- `AppState.datasets.transformed` — трансформированный DataFrame (после предобработки)
- `AppState.datasets.features` (**Data Payload**) — расширенный `DataFrame` (версия в `DatasetManager`), содержащий исходные данные + все сгенерированные колонки-признаки. 
    Это физический датасет, который передается в `modeling/` для обучения.
- `AppState.datasets.forecast` — финальный датасет с прогнозом (DataFrame: дата, прогноз, доверительные интервалы)

Хранит ранг коинтеграции (тест Йохансена), оптимальный лаг системы (VAR/VECM), матрицу импульсных откликов (IRF), таблицу декомпозиции дисперсии (FEVD) и матрицу тестов    Грейнджера. Используется вкладкой «Интерпретируемость (XAI)» для системного анализа и вкладкой «Задачи» (What-if) как математический движок для каскадного распространения шоков (Shock Propagation).

    артефакты на диске (`model_artifact_path`, `forecast_artifact_path`), 
    гиперпараметры (`model_params`) и метрики (`metrics`).
    **Роль:** Является "ключом" к полной воспроизводимости. Если `Experiment` сохранен,

- `AppState.eda_results.similarity_results` — результаты анализа сходства (матрица сходства, k-ближайшие соседи, метрики DTW/Euclidean/Cosine)

## КЛЮЧЕВЫЕ ПРАВИЛА РЕФАКТОРИНГА
1. Не менять наблюдаемое поведение без явного указания
2. Сначала выносим бизнес-логику в `core/`, потом UI в `ui/tabs/`
3. Все изменения состояния проходят через типизированный `AppState`
4. Сохраняем обратную совместимость через wrapper в `app.py`
5. Логика вкладок строится следующим образом: классификация → валидация → предобработка → анализ → моделирование → прогнозирование
6. Система ролей определяет доступ к модулям и функциям
7. Строгое разделение READ/EXECUTE и Матрица доступа: 
   Заказчик (`_partner`) имеет строго **READ-доступ** к результатам анализа (Валидация, Feature Store, Прогнозирование) для верификации методологии и обеспечения воспроизводимости. 
   Ему **категорически запрещен EXECUTE-доступ** (запуск вычислений, изменение параметров) и доступ к сырым/трансформированным данным (вкладки «Классификация», «Предобработка», «Мониторинг» скрыты или заблокированы). 
   **Матрица доступа** является единственным источником истины для определения видимости вкладок и стадий данных для каждой роли.
8. EDA передаёт конкретные параметры в Моделирование (информативные признаки, сезонные периоды)
9. EDA поддерживает переключение "До/После" предобработки для сравнения свойств данных
10. **Устранение неявного глобального состояния (`AppState.df`):**
    - `AppState.df` **никогда не переключается** в зависимости от активной вкладки UI. Это жесткий Read-Only алиас на `validated` (или `raw`), служащий "точкой входа" для старого кода.
    - **Запрещено:** Использовать `AppState.df` в любых новых функциях, классах и вкладках.
    - **Миграция Legacy:** Вместо прямой передачи `AppState.df` в старые функции, создаются **Legacy Wrappers** с явным указанием стадии:
      ```python
      # ПЛОХО (неявное состояние):
      def legacy_eda(df=AppState.df): ...
      
      # ХОРОШО (явный wrapper):
      def legacy_eda_wrapper(stage: str = 'validated'):
          df = get_dataset_for_stage(stage) # Явное получение из Dataset Lifecycle
          return legacy_eda(df)
      ```
11. **Четкое разделение modeling/ и forecasting/:**
    modeling/ — только выбор модели (обучение на train, подбор гиперпараметров, сравнение, возврат best_model).
    forecasting/ — применение выбранной модели. Пытается переобучить модель на всех данных (Train ∪ Test) для максимизации истории. Если переобучение падает — использует модель из modeling/ (обученную на Train). Генерирует прогноз на горизонт 
    h, считает доверительные интервалы и формирует отчет.
    forecasting/ КАТЕГОРИЧЕСКИ НЕ ДОЛЖЕН содержать логику подбора гиперпараметров (GridSearch, Bayesian) или выбора другой архитектуры. Он работает строго с тем, что вернул modeling/.
12. **Матрица доступа = источник истины** — каждая вкладка UI проверяет матрицу 
    доступа перед показом данных. Если роль не имеет доступа к стадии, вкладка 
    показывает заглушку: "Эта стадия данных недоступна для вашей роли".
13. **Разделение Read/Execute в UI:** 
    - Если `AppState.user_role == 'partner'`, все интерактивные элементы управления (кнопки `st.button`, слайдеры, поля ввода параметров)  на вкладках, доступных для чтения, должны рендериться с флагом `disabled=True`.
    - Рядом с заблокированными элементами должна отображаться иконка/бейдж: 🔒 *"Режим аудита: просмотр результатов, запуск вычислений недоступен"*.
    - Это предотвращает случайное изменение состояния `AppState` внешним пользователем.

14. **Принцип явной адресации данных (Explicit Data Addressing):**
    Любая функция бизнес-логики (`core/`, `eda/`, `modeling/` и т.д.) **обязана** принимать данные либо явно через аргументы (`def compute_fft(df: pd.DataFrame)`), либо через явный запрос к состоянию (`df = AppState.datasets.validated.df`). Запрещено опираться на "контекст вкладки" или "последний измененный датасет". Это гарантирует воспроизводимость и корректную работу `@st.cache_data`.

15. **Защита от Data Leakage в Panel Data:**
    - Любая функция в `app/features/` и `app/preprocessing/`, генерирующая временные признаки (лаги, diff, rolling), **обязана** принимать аргумент `entity_col: str`.
    - Внутри функции операции должны выполняться исключительно через `df.groupby(entity_col).transform(...)` или `df.groupby(entity_col).shift(...)`.
    - Использование "плоских" сдвигов (`df.shift()`) для панельных данных блокируется на уровне unit-тестов и линтеров.

16. **Обязательная обработка ошибок и Graceful Degradation:**
    - Каждая функция бизнес-логики **обязана** иметь блок `try-except` для критических операций (обучение моделей, декомпозиция, обратное преобразование).
    - При сбое функция **не должна** падать с traceback. Вместо этого:
      1. Логировать ошибку в `AppState.error_log` с указанием `stage`, `severity`, `error_type`, `message`.
      2. Применить fallback-стратегию (если определена в разделе "Обработка ошибок").
      3. Вернуть пользователю понятное сообщение через UI (не технический текст).
    - **Запрещено:** Использовать "голый" `except Exception as e: pass` — все ошибки должны быть залогированы.
    - **Требование:** Unit-тесты для сценариев сбоев (короткие ряды, несходимость моделей, частичные сбои в Panel) обязательны.
17. **Атомарное обновление состояния лучшей модели (Atomic Model State Update):**
    - `AppState.best_model` и `AppState.model_params` представляют собой **единый логический узел**.
    - **Запрещено:** Использовать `AppState.model_params` для хранения параметров промежуточных моделей во время циклов подбора гиперпараметров (GridSearch, Bayesian Optimization). Для промежуточных параметров использовать локальные переменные функций или запись в `AppState.experiment_log`.
    - **Разрешено:** Запись в `AppState.model_params` происходит **строго в один момент (атомарно)** с записью в `AppState.best_model` — в момент фиксации победителя кросс-валидации.
    - **Обоснование:** Нарушение этого инварианта приведет к «франкенштейн-прогнозу», когда модуль `forecasting/` применит параметры от модели X к архитектуре Y, что сделает воспроизводимость невозможной.
18. **Разделение Session Memory (RAM) и Persistent Artifacts (Disk):**
    - `DatasetManager` управляет **исключительно** оперативной памятью текущей сессии. Его Garbage Collection (`max_versions=3`) безвозвратно удаляет старые версии из RAM. **Никакой скрытой сериализации на диск при GC не происходит.**
    - **Воспроизводимость экспериментов** обеспечивается механизмом **Data Snapshotting** в `experiment_log`. При сохранении эксперимента датасет-источник *обязан* быть сохранен на диск (`artifacts/{exp_id}/data.parquet`) и зафиксирован в `manifest.json`. Это и есть механизм "закрепления" (pinning) данных.
    - **Роль `_partner` (Аудитор):** Партнер не зависит от того, какие версии данных сейчас в RAM у оператора `_user`. Партнер всегда читает артефакты напрямую из персистентного хранилища, загружая их в изолированный временный `DatasetManager` для верификации.
19. **Поддержка циклических откатов (No Hard Locks):**
    - Запрещено блокировать переход на предыдущие вкладки (например, скрывать вкладку `EDA`, если уже запущено `Modeling`). Аналитик должен иметь возможность вернуться назад в любой момент.
    - Переход назад не удаляет данные из `DatasetManager` (они остаются в истории версий), но **обнуляет** downstream-объекты в `AppState` (`best_model`, `forecast_results`), чтобы предотвратить рассинхронизацию (см. Правило Каскадной Инвалидации).
20. **Single Source of Truth (SSOT) для состояния и защита от Documentation Drift:**
    - Python-датакласс `AppState` (в `app/core/state.py`) является **единственным источником истины** для состояния приложения.
    - Раздел «КЛЮЧЕВЫЕ СУЩНОСТИ» в `ARCHITECTURE.md` является **производным**. 
    - **Железное правило:** Любое добавление нового поля в `AppState` (например, `mts_results`, `scenarios_results`) **обязано** сопровождаться синхронным обновлением раздела «КЛЮЧЕВЫЕ СУЩНОСТИ» в документации. 
    - **Автоматизация (Post-MVP):** На этапе стабилизации (Этап 11) рекомендуется написать простой скрипт `scripts/generate_state_docs.py`, который парсит `app/core/state.py` и автоматически генерирует/обновляет раздел «КЛЮЧЕВЫЕ СУЩНОСТИ» в Markdown, полностью исключая человеческий фактор и рассинхронизацию.

## KNOWLEDGE LAYER (Слой знаний и Институциональная память)
⚠️ **АРХИТЕКТУРНЫЙ РЕЗЕРВ (Post-MVP / Этап 11+):**
Реализация полноценного семантического слоя отложена до стабилизации базового пайплайна (Этапы 1-10). Однако **схема хранения данных (SQLite) и контракты интерфейсов закладываются уже сейчас**, чтобы избежать болезненной миграции в будущем.

**Цель:** Переход от "Фактологического слоя" (Experiment Log) к "Семантическому слою" (Knowledge Base). Превращение разрозненных 1000+ моделей и 5000+ признаков в структурированные бизнес-знания.

### Что хранит Knowledge Layer (в отличие от Experiment Log):
1. **Causal Graph (Граф причинности):** Агрегированные результаты EDA (Granger, CCF) across all experiments. 
   *Пример:* "Сахар → Свекла (лаг 2 мес.)" — *Статус: Подтверждено (p-value < 0.05 в 85% запусков).*
2. **Hypothesis Registry (Реестр гипотез):** Фиксация того, что аналитик *проверял*, даже если модель не сошлась. Защита от повторной проверки отвергнутых гипотез.
3. **Feature Consensus (Консенсус признаков):** Агрегированная важность признаков (SHAP / Permutation) по всем успешным моделям. Выявление "железобетонных" драйверов процесса.
4. **Business Insights (Бизнес-выводы):** Семантические теги и текстовые резюме, которые аналитик (или LLM-агент в будущем) привязывает к конкретным сценариям (What-if).

### Интеграция с ролями (Role-Based Knowledge):
- **`_partner` (Аудитор/Заказчик):** Имеет **полный READ-доступ** к Knowledge Layer. Для партнера это главный интерфейс: он видит не "сырые метрики MAPE", а готовые бизнес-инсайты, причинно-следственные графы и подтвержденные гипотезы.
- **`_user` / `_admin`:** Имеют **EXECUTE-доступ** для добавления новых гипотез, тегирования инсайтов и экспорта знаний в корпоративную базу.

### Техническая реализация (Контракт для Этапа 11):
- Хранение: Отдельная SQLite-таблица `knowledge_graph` и `hypotheses` (связь Many-to-Many с `experiments`).
- Автоматическое обогащение: При успешном завершении `Experiment`, триггер в `experiment_log.py` будет вызывать `knowledge/graph.py` для инкрементального обновления весов ребер в графе причинности.
