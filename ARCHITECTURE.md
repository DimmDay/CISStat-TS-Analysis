## Потоки данных
1. **Загрузка** → `AppState.df`, `col_types`, `ts_mode_active`
2. **Классификация** → `AppState.data_classification` тип данных (TS/Non-TS, univariate/multivariate) → все последующие модули
3. **Валидация** → `AppState.val_results` (результаты проверки качества), `AppState.validation_ready` (флаг готовности)→ все последующие модули
4. **Предобработка** → `AppState.df`,`AppState.transform_params`, `AppState.ts_props_v12` → все последующие модули | → [качество низкое] → Валидация
5. **EDA** → `AppState.eda_results.informative_features`, `AppState.eda_results.seasonal_periods`, `AppState.eda_results.multicollinear_features`  → все последующие модули | → [качество низкое] → Предобработка → Валидация
5. **Моделирование** → `AppState.best_model` → Прогнозирование | → [качество низкое] → EDA → Предобработка → Валидация
6. **Прогнозирование** → Задачи | → [аномалии] → Моделирование → выбор другой модели

## Система ролей и доступа

### Формат токена доступа
`{базовый_пароль}_{роль}`

### Роли и уровни доступа

#### 1. Администратор (`_admin`)
**Полный доступ ко всем модулям:**
- ✅ Все вкладки (Классификация, Валидация, Предобработка, EDA, Моделирование, Прогнозирование, Задачи)
- ✅ Управление пользователями и ролями
- ✅ Экспорт всех данных (сырые данные, паспорта, отчеты)
- ✅ Настройка правил валидации
- ✅ Просмотр логов и отладочной информации

#### 2. Пользователь (`_user`) — внутренний аналитик
**Настраиваемый доступ по модулям:**
- ✅ Доступ к модулям настраивается администратором
- ✅ По умолчанию: Классификация, Валидация, Предобработка, EDA, Моделирование, Прогноз
- ✅ Экспорт данных (сырые данные, паспорта, отчеты) настраивается администратором
- ❌ Нет доступа к управлению пользователями

#### 3. Заказчик (_partner) — внешний пользователь
**Настраиваемый доступ к результатам:**
- ✅ Доступ к модулям настраивается администратором
- ✅ По умолчанию: Классификация, Валидация, Предобработка, EDA, Моделирование, Прогноз
- ✅ Экспорт данных (сырые данные, паспорта, отчеты) настраивается администратором
- ❌ Нет доступа к управлению пользователями
- ❌ Нет доступа к логам
**Обоснование:** Заказчик должен иметь возможность воспроизвести результат прогноза, проверить методологию и убедиться в корректности анализа. Это обеспечивает прозрачность и научную обоснованность результатов.

   - Точечный график, гистограмма, KDE
   - Статистики распределения
   - Авто-детект типа распределения

### Вкладка 2: ВАЛИДАЦИЯ
**Цель:** Комплексная проверка качества данных по 12 критериям (DAMA DMBOK, ISO 8000-61, TDQM).

**Входные данные из Классификации:**
- AppState.df → основной DataFrame (сырые данные после загрузки)
- AppState.col_types → типы колонок {num, cat, date}
- AppState.ts_mode_active → флаг активации режима временных рядов
- AppState.primary_date_col → временная колонка

→ Определяет, какие проверки применять (TS-специфичные vs общие)

**Входные данные из Управления правилами:**
- AppState.rules → правила валидации из YAML-шаблона или автогенерации
→ Содержит: диапазоны значений, regex-паттерны, справочники, пороги

**Входные данные из предыдущего запуска (если есть):**
- AppState.val_results → предыдущие результаты валидации (для сравнения)
- AppState.validation_ready → флаг готовности предыдущей валидации
→ Позволяет отслеживать эволюцию качества данных

**Субмодули:**
1. Проверка типов данных (data types)

3. Обработка выбросов (outlier treatment)
4. Проверка форматов (regex)
5. Проверка диапазонов значений (value ranges)
6. Проверка логики и хронологии (consistency) 
7. Проверка уникальности (uniqueness checks)
8. Проверка принадлежности (inclusion/lookup)
9. Проверка ссылочной целостности (referential integrity)
10. Проверка качества текста (text quality)
11. Проверка регулярности временного шага (regularity)
12. Проверка достаточности наблюдений (sufficiency of observations)

**Результат:**

### Вкладка 4: РАЗВЕДОЧНЫЙ EDA
**Цель:** Глубокий исследовательский анализ данных для понимания структуры и паттернов.

**Входные данные из Классификации:**
- AppState.data_classification → тип данных (TS/Non-TS, univariate/multivariate, regular/irregular)
→ Определяет режим визуализации (общий анализ vs временные ряды)

**Входные данные из Валидации:**
- AppState.df → очищенный DataFrame (после исправления пропусков/выбросов)
- AppState.val_results → результаты проверки качества
- AppState.validation_ready → флаг готовности
- AppState.ts_props_v11 → паспорт свойств после валидации
→ Используется для анализа "До предобработки"

**Входные данные из Предобработки:**
- AppState.df → трансформированный DataFrame (после математических преобразований)
- AppState.transform_params → параметры трансформаций (для понимания примененных методов)
- AppState.ts_props_v12 → паспорт свойств после предобработки
→ Используется для анализа "После предобработки"

**Переключатель "До/После предобработки":**
✅ До предобработки — анализ исходных данных (после валидации)
✅ После предобработки — анализ трансформированных данных
Позволяет сравнивать свойства данных до и после трансформаций

**Субмодули:**
1. **Корреляционный анализ числовых признаков** 
   - Тепловая карта корреляции Пирсона
   - Выявление мультиколлинеарности
   - Передача в Моделирование: список признаков для PCA/регуляризации

2. **Вариативная визуализация** 
   - Интерактивная фильтрация по категориям и временным периодам
   - Динамическое переключение между общим анализом и TS-визуализацией
   - Графики: столбчатая, линейная, площадь, точечная, box plot, гистограмма

3. **Спектральный анализ временного ряда**
   - ACF/PACF (автокорреляционный анализ)
   - FFT (быстрое преобразование Фурье)
   - Периодограмма (спектральная плотность мощности)
   - Вейвлет-преобразование (CWT)
   - Передача в Моделирование: сезонные периоды (параметр m для SARIMA)

4. **IH-анализ** (Information-Entropy Analysis)
   - Оценка информативности признаков через теорию информации Шеннона
   - Метрика R(Y|X) = I(X;Y) / H(Y)
   - Анализ синергии пар признаков
   - Передача в Моделирование: список информативных признаков для отбора фич
5. Рекомендации по моделям (20 моделей, таблица → Доступны/С ограничениями/Не доступны).

### Вкладка 5: МОДЕЛИРОВАНИЕ
**Цель:** Обучение и оценка моделей прогнозирования на основе классификации, предобработки и EDA.

**Входные данные из Классификации:**
- AppState.data_classification → тип данных (TS/Non-TS, univariate/multivariate)
→ Определяет класс моделей (ARIMA только для TS, ML для любых)

**Входные данные из Валидации:**
- AppState.val_results → результаты проверки качества
- AppState.validation_ready → флаг готовности
- AppState.ts_props_v11 → паспорт свойств после валидации
→ Влияет на доступность моделей (если DQ Score низкий, некоторые модели недоступны)

**Входные данные из Предобработки:**
- AppState.df → трансформированный DataFrame
- AppState.transform_params → параметры трансформаций (для обратного преобразования прогноза)
- AppState.ts_props_v12 → паспорт свойств после предобработки
→ Влияет на обучение моделей и интерпретацию результатов

**Входные данные из EDA:**
- AppState.eda_results.informative_features → отбор признаков
- AppState.eda_results.seasonal_periods → параметр m для SARIMA
- AppState.eda_results.multicollinear_features → PCA/регуляризация
→ Влияет на отбор признаков и параметры моделей

**Субмодули:**
1. **Семейство доступных моделей**
   - Выбор моделей из доступных для тестирования
2. **Обучающая и тестовая выборки + масштабирование**
   - Split на train/test (в масштабированной шкале)
3. **Обучение моделей**
   - Обучение моделей на train_scaled   
4. **Подбор гиперпараметров**   
   - Grid Search (сеточный поиск)
   - Random Search (случайный поиск)
   - Bayesian Optimization (байесовская оптимизация)
   - Автоматический подбор для ARIMA (через AIC/BIC)
   - Кросс-валидация временных рядов (Time Series CV)
   - Сравнение результатов с разными гиперпараметрами
   - Визуализация влияния гиперпараметров на метрики
5. **Построение прогнозов**
   - Прогнозы выбранных моделей на test_scaled → forecast_scaled  
6. **Метрики качества** (RMSE, MAE, MAPE) ← в масштабированной шкале
   - Оценка качества моделей, рекомендации, таблица результатов (скачать csv, excel)
7. **Обратное преобразование**
   - Обратное преобразование forecast_scaled → forecast_orig
8. **График прогноза**
   - Построение сравнительного графика: "Прогноз vs Факт" ← в ИСХОДНОЙ шкале
   (скачать png, jpeg, pdf)

## Вкладка 6: ПРОГНОЗИРОВАНИЕ
**Цель:** Генерация прогнозов и визуализация результатов.

**Входные данные:**
- AppState.best_model → лучшая модель
- AppState.model_params → параметры модели
- AppState.scaling_params → параметры масштабирования (для обратного преобразования)
- AppState.transform_params → параметры трансформаций (для обратного преобразования)

1. Обучение финальной модели на ВСЕХ данных (scaled)
2. Прогноз на горизонт h → forecast_future_scaled

7. Финальный отчет для заказчика:
   - Документирование параметров модели и условий прогнозирования
   - Визуализация результатов (график фактических данных, линия прогноза, верхняя/нижняя границы доверительного интервала, точки прогноза)
   - Детальная статистика по прогнозным показателям (MAE, MSE, MAPE)

## Ключевые правила рефакторинга
1. Не менять наблюдаемое поведение без явного указания
2. Сначала выносим бизнес-логику в `core/`, потом UI в `ui/tabs/`
3. Все изменения состояния проходят через типизированный `AppState`
4. Сохраняем обратную совместимость через wrapper в `app.py`
5. Логика вкладок строится следующим образом: классификация → валидация → предобработка → анализ → моделирование → прогнозирование
6. Система ролей определяет доступ к модулям и функциям
7. Заказчик имеет доступ ко всем модулям для воспроизводимости результата
8. EDA передаёт конкретные параметры в Моделирование (информативные признаки, сезонные периоды)
9. EDA поддерживает переключение "До/После" предобработки для сравнения свойств данных
