## 0. Как две части этой спецификации связаны друг с другом

Приведённые принципы описывают, на первый взгляд, две разные вещи с двумя разными «ядрами»:

1. **Часть I** («обучающая и обучаемая исследовательская платформа») — ядро объявлено как **база знаний**.
2. **Часть II** («саморазвивающаяся платформа TS») — ядро объявлено как **квант обучения** `Q` (diff между ожидаемым и наблюдаемым событием), движок — **diff состояний Q**, то есть `ΔQ`.

Это не конкурирующие архитектуры, а два слоя одной системы, и именно так они спроектированы ниже:

- **Часть I строит статический контур**: база знаний, справка по `'?'`, обучающие стеки, RAGFlow, база лучших практик, курс «Прогнозный аналитик». Principle Б этой части («обслуживание базы знаний не занимает много времени, так как процесс автоматизирован») — **декларация требования**, не механизм.
- **Часть II — это и есть механизм**, реализующий Principle Б. `Q`/`ΔQ` — не отдельная фича рядом с базой знаний, а измерительный контур, который решает, какую статью пора пересмотреть, какое правило Наставника пересчитать, какую модель дообучить, какой RAGFlow-документ переиндексировать — **без участия человека, кроме финального решения**, где оно по продукту требуется (например, публикация статьи).

Схема связи одним предложением: **база знаний — это то, ЧТО автоматизировано поддерживается; квант обучения `Q` и его дифференциал `ΔQ` — это КАК именно это поддержание происходит, не создавая нового алгоритма, а переиспользуя уже существующий в платформе детектор структурных сдвигов (PELT, Task 76) в применении не к пользовательским рядам, а к рядам самой платформы.**

# Часть I — Обучающая платформа: база знаний, встроенная в работу

## 1. Ядро: модель данных базы знаний

```python
# apps/api/knowledge/models.py (новый модуль)

@dataclass
class KnowledgeArticle:
    article_id: str
    stage_id: str          # см. §1.1 -- тот же словарь id, что и везде на платформе
    node_id: str | None      # конкретный узел стадии, None -- статья уровня всей стадии
    directions: frozenset[str]  # см. §3 -- тематические "направления", не то же самое, что stage_id
    title: str
    body_md: str              # markdown, тот же формат, что уже используют METRICS_DESCRIPTION-константы
    sources: list["Citation"]   # см. §7.1 -- официальные источники, авторитетные издания
    status: str                 # "draft" | "published" | "needs_review" (см. Часть II)
    last_reviewed_at: str | None
    superseded_constant: str | None  # см. §1.1 -- откуда мигрировано, для аудита миграции

@dataclass
class Citation:
    kind: str      # "book" | "paper" | "official_docs"
    label: str      # "Hyndman & Athanasopoulos, Forecasting: Principles and Practice, 3rd ed."
    url: str | None
```

### 1.1 Единый словарь id — не новый параллельный, а тот же самый

`stage_id`/`node_id` — **буквально те же строки**, что уже используются в трёх местах платформы одновременно (контракт, установленный ещё в `spec_progress.md §2` и переиспользуемый здесь без изменений):

| Источник id | Что уже содержит |
|---|---|
| `apps/api/session_store.py::STAGES` | 6 основных этапов пайплайна |
| `validation/rule_resolver.py::CHECK_IDS`, `apps/api/routers/session.py::PREPROCESSING_CHECK_IDS`, `apps/api/model_readiness.py::MODELING_STAGE_IDS` | узлы внутри каждого этапа |
| `packages/ui/lib/navigator-stops.ts` | 4 будущих прикладных модуля (`scenario`/`causal`/`decision`/`monitoring`) |

**Ключевая находка при проектировании (не гипотеза — проверено чтением кода репозитория на `952653e`).** У платформы уже есть прообраз контекстной справки — не отдельная фича, которую предстоит изобрести с нуля: каждый `TsAnalysis*.tsx` (EDA, Preprocessing, Modeling, Validation) уже хранит захардкоженные строковые константы по каждому узлу — `DESCRIPTIVE_METRICS_DESCRIPTION`, `DESCRIPTIVE_PIPELINE_DESCRIPTION`, и один общий `EDA_HELP` на весь модуль (`packages/ui/components/TsAnalysisEDA.tsx`, состояние `descriptionSection`, метод `handleHelpClick`). Это **уже почти** база знаний — только: (а) она в коде, а не в управляемом хранилище, (б) содержимое привязано к конкретному .tsx-файлу, недоступно для RAGFlow/курса/аналитики использования, (в) `EDA_HELP` — на уровне всего модуля, а не на уровне узла, как того явно требует задача («справки по контексту **всех этапов**»).

`KnowledgeArticle` не заменяет этот механизм с нуля, а **промотирует** его: каждая существующая `{CHECK}_METRICS_DESCRIPTION`/`{CHECK}_PIPELINE_DESCRIPTION`-константа мигрирует в `KnowledgeArticle` с сохранением `(stage_id, node_id)` и полем `superseded_constant` для аудита («эта статья заменила такую-то константу в таком-то файле»), а компонент вместо строкового литерала запрашивает статью по тому же ключу. Frontend-код для отображения не переписывается — меняется только источник данных.

## 2. Principle А: база знаний встроена в повседневную работу

### 2.1 Контекстная справка через `'?'` — на уровне узла, не модуля

Новый компонент `ContextHelpButton.tsx` — маленькая кнопка `'?'` рядом с **каждым** узлом (не только рядом с заголовком модуля, как сейчас `handleHelpClick`), открывающая всплывающую панель `KnowledgeArticleView.tsx` с содержимым `KnowledgeArticle` для `(stage_id, node_id)` текущего узла.

```
GET /v1/knowledge/articles?stage_id={stage}&node_id={node}
  → KnowledgeArticle | null (null -- ещё не мигрировано/не написано;
    ЧЕСТНЫЙ 404 с понятным сообщением, не фиктивная заглушка --
    тот же принцип платформы "no fabricated results", что уже применяется
    везде в Моделировании: если статьи нет, интерфейс должен явно
    сказать "справка готовится", не показать пустое окно)
```

Не отдельная система — переиспользует уже существующий паттерн раскрывающейся панели (`EventsLogDrawer.tsx`/`ProgressDrawer.tsx` из `spec_progress.md §6` — тот же визуальный контракт: закрывается кликом вне/крестиком).

### 2.2 Кастомные обучающие стеки по направлениям

Два независимых, ортогональных измерения тегирования статьи — не одно и то же:

- **`stage_id`/`node_id`** — «где в пайплайне» (обязательно, это и есть контекстная привязка §2.1).
- **`directions`** — «про что тематически», пересекает стадии (например, направление «Работа с сезонностью» затрагивает узлы и в Предобработке — STL-декомпозиция, — и в EDA — сезонность, — и в Моделировании — ETS/TBATS с несколькими периодами).

Стартовый набор направлений (не окончательный, требует ревью тимлида — вынесено в §15): `Работа с сезонностью`, `Работа с выбросами и пропусками`, `Интервальное прогнозирование`, `Волатильность финансовых рядов`, `Многомерные модели (VAR/VECM)`, `Модели на деревьях/бустинге`, `Нейросетевые модели`, `Методология и валидация (бэктест, утечки данных)`.

```
POST /v1/learning/track
  { "directions": ["seasonality", "intervals"] }
  → LearningStack: упорядоченный список KnowledgeArticle (по stage_id,
    в порядке пайплайна) + релевантные модули курса (§7), отфильтрованные
    по выбранным directions -- чекбоксы дают МНОЖЕСТВО направлений,
    порядок статей внутри стека всегда идёт по пайплайну (не по порядку
    выбора чекбоксов) -- личная траектория, но не хаотичная.
```

### 2.3 Курс «Прогнозный аналитик» встроен, не отдельный LMS

Подробности учебного плана — §7. Здесь фиксируется архитектурный принцип: модули курса **используют те же `KnowledgeArticle`**, что и контекстная справка (курс — это КБ, упорядоченная в линейный учебный план, плюс контрольные точки/тесты, а не параллельный контент). Пройденный урок курса — то же самое действие, что открытие статьи по `'?'` в реальном исследовании; платформа не поддерживает два экземпляра одного и того же объяснения ARIMA — один в справке, другой в курсе.

## 3. Principle Б: автоматизация обслуживания — анонс, механизм в Части II

Декларация: редактор базы знаний **не обязан** вручную отслеживать, какая статья устарела, какая не помогает пользователям, какая формулировка Наставника перестала быть точной. Это не достигается регламентом/чек-листом «раз в квартал проверять статьи» — принцип прямо требует автоматизации. Механизм — квант обучения `Q` и его дифференциал `ΔQ`, целиком описан в Части II (§8–9); здесь фиксируется **контракт**, который Часть I обязана предоставлять Части II, чтобы автоматизация вообще была возможна:

- каждая `KnowledgeArticle` обязана иметь измеримый сигнал «помогла или нет» (см. §8.2, строка «KB-статья») — без этого `ΔQ` нечего вычислять для статей;
- статус `needs_review` (§1) выставляется **не человеком**, а движком Части II — человек только подтверждает или отклоняет пересмотр (см. §9.2).

## 4. RAGFlow — надстройка над алгоритмическим Наставником, не замена

### 4.1 Что индексируется

RAGFlow не работает с сырыми данными пользователя (ряды, датасеты) — только с текстовым корпусом, который уже прошёл курирование:

| Источник | Курирование перед индексацией |
|---|---|
| `KnowledgeArticle` (§1), статус `published` | Уже прошли ревью по построению (§1) |
| База лучших практик (§6) | Человеческое ревью перед публикацией (§6.2) |
| Курс «Прогнозный аналитик» (§7) | Тот же контент, что и статьи — не отдельный проход курирования |
| Обработанные ответы техподдержки (§5) | ETL: анонимизация → курирование → только после этого индексация |

### 4.2 Контракт с Наставником — RAGFlow не решает, ЧТО рекомендовать

`spec_progress.md §7` уже спроектировал Наставника как правило-движок без LLM в реальном времени, и `§8` того документа уже зафиксировал точку расширения:

```python
class MentorTextRenderer(Protocol):
    def render(self, rule: MentorRule, context: dict[str, Any]) -> str: ...
```

RAGFlow-подключаемый ИИ-помощник — это **конкретная реализация именно этого протокола**, не новый, отдельный компонент архитектуры:

```python
class RagflowMentorTextRenderer(MentorTextRenderer):
    """Правило-движок уже решил rule_id/recommended_action/severity (§7
    spec_progress.md) -- эта реализация только переформулирует уже
    принятое решение человеческим языком, используя RAGFlow retrieval
    по тому же rule_id/stage_id как контекст для генерации. Не имеет
    доступа к сырым данным пользователя, не выбирает rule_id сама."""
    def render(self, rule: MentorRule, context: dict[str, Any]) -> str: ...
```

Это ограничение — не техническая деталь, а сознательное продолжение уже принятого в `spec_progress.md` принципа: LLM не является источником истины ни для рекомендации, ни для факта, ни здесь.

### 4.3 ИИ-помощник для открытых вопросов — единственное реальное расширение возможностей

В отличие от §4.2 (переформулировка уже готовой рекомендации Наставника), у ИИ-помощника есть одна дополнительная роль, которой у алгоритмического Наставника нет в принципе: отвечать на **открытые вопросы пользователя вне заранее написанных правил** («почему ETS дал такой широкий интервал именно на этом шаге горизонта?») — генеративный ответ по RAGFlow retrieval над корпусом §4.1 плюс факты текущего исследования (`ForecastRun`, `ModelCard`, уже посчитанные метрики — те же данные, что доступны Наставнику, см. `spec_progress.md §9.3, п.4`). Ограничение то же: ИИ-помощник **читает** уже посчитанные факты, не пересчитывает и не выдумывает числа.

## 5. Пополнение RAGFlow из ответов техподдержки

### 5.1 ETL-конвейер (не автоматическая индексация напрямую)

```
Обращение в техподдержку
  → захват (вопрос пользователя + финальный ответ оператора)
  → анонимизация (PII, идентичность пользователя, сырые данные ряда --
     тот же принцип "trace_events обезличиваются по построению",
     spec_progress.md §9)
  → курирование человеком (оператор техподдержки или выделенный
     редактор помечает: это общий кейс, годный для базы знаний, или
     разовый частный случай, не годный)
  → публикация как KnowledgeArticle (status="published", stage_id
    проставляется курирующим человеком по контексту вопроса)
  → индексация в RAGFlow (§4.1)
```

Явный отказ от прямой индексации сырых обращений техподдержки без курирования: необработанный текст поддержки почти всегда содержит либо приватные детали, либо ошибочные ad hoc советы конкретному контексту — курирование обязательно, не опционально.

### 5.2 Связь с квантом обучения

Каждое обращение в техподдержку **после** того, как пользователь уже видел справку `'?'` или ответ ИИ-помощника по тому же вопросу — это отрицательный сигнал `Q` для той статьи/того ответа (см. §8.2). Именно эта связь и обеспечивает то, что база знаний со временем действительно улучшается, а не просто растёт в объёме.

## 6. База лучших практик по завершённым исследованиям

### 6.1 Критерии отбора кандидатов — эвристика, не выбор LLM

Продолжает и уточняет то, что уже было намечено в `spec_progress.md §9`: отбор кандидатов **алгоритмический** (`run.status == "completed"`, финальный бэктест-скор выше порога, малое число `warning`-узлов, малое число сработавших sanity-предупреждений Наставника §7.2 того документа) — не LLM решает, что является «лучшей практикой».

### 6.2 Курирование и публикация — тот же паттерн, что и в §5.1

Кандидат не публикуется автоматически: он попадает в очередь ревью (человек — методолог/аналитик команды CISStat) → одобренный кандидат становится записью базы практик (материал: связка «профиль ряда → выбранная модель/семейство → построенный прогноз → фактическое покрытие интервала», уже описанная в `spec_progress.md §9.3, п.5`) → индексируется в RAGFlow (§4.1) и становится доступен как пример в курсе (§7).

### 6.3 Использование за пределами RAGFlow

Записи базы практик доступны напрямую (не только через ИИ-помощника) как раздел «Примеры исследований» — перекрёстные ссылки из `KnowledgeArticle` соответствующих узлов («вот как эту же проблему решили в похожем исследовании»).

## 7. Курс «Прогнозный аналитик»

### 7.1 Структура — зеркалит пайплайн платформы, не собственная программа

| Модуль курса | `stage_id` | Опорные источники (официальные/авторитетные) |
|---|---|---|
| 0. Введение в анализ временных рядов | — | Hyndman & Athanasopoulos, *Forecasting: Principles and Practice* (3rd ed., открытый учебник, [otexts.com/fpp3](https://otexts.com/fpp3/)) |
| 1. Загрузка и структура данных | `upload` | — |
| 2. Валидация ряда | `validation` | — |
| 3. Предобработка (пропуски/выбросы/регулярность/декомпозиция/сглаживание) | `preprocessing` | Hyndman & Athanasopoulos, гл. STL |
| 4. Разведочный анализ | `eda` | — |
| 5.1 Модели: ETS, Theta | `modeling` | Hyndman & Athanasopoulos, гл. Exponential smoothing |
| 5.2 Модели: ARIMA | `modeling` | Box, Jenkins, Reinsel, Ljung — *Time Series Analysis: Forecasting and Control* |
| 5.3 Модели: Prophet, TBATS | `modeling` | Taylor & Letham, *Forecasting at Scale* (Prophet); De Livera, Hyndman, Snyder — оригинальная статья TBATS |
| 5.4 Модели: деревья/бустинг (RF/XGBoost/LightGBM/CatBoost) | `modeling` | Официальная документация библиотек + Makridakis et al., M4/M5 competition papers (практический бенчмаркинг) |
| 5.5 Волатильность (GARCH/EGARCH) | `modeling` | Tsay, *Analysis of Financial Time Series* |
| 5.6 Многомерные модели (VAR/VECM) | `modeling` | Hamilton, *Time Series Analysis* |
| 5.7 Нейросетевые модели (LSTM/GRU/N-BEATS/N-HiTS/TFT) | `modeling` | Оригинальные статьи архитектур (см. `docs/modeling_task_list.md`, Task 137+) |
| 6. Прогнозирование и интервалы | `forecasting` | `spec_forecasting2.md §4` (уже сформулированная на платформе методология трёх методов интервалов) |
| 7+. Будущие модули по мере реализации | `scenario`/`causal`/`decision`/`monitoring` | Добавляются по мере готовности самих модулей — не пишутся заранее для несуществующего функционала |

Модуль курса — это **упорядоченное подмножество** `KnowledgeArticle` того же `stage_id` плюс контрольные вопросы (см. §7.3), не отдельный контент.

### 7.2 Доступ — бесплатно, вне тарифной сетки

Курс **не гейтится** через `Capabilities`/`PLAN_DEFINITIONS` (`spec_billing_accounts.md §5`) — по прямому определению задачи («бесплатного обучающего курса»). Это не противоречие со Stage Gating демо-тарифа: Stage Gating ограничивает доступ к **прикладным модулям исследования** (`scenario`/`causal`/`decision`/`monitoring`), курс — это не этап исследования, а образовательный материал, доступный независимо от `account.plan`, в том числе анонимным посетителям standalone-приложения (лёгкая регистрация — email без пароля, только для сохранения прогресса, — та же модель, что уже описана для демо-режима в `ROLES_AND_PLANS_SPEC.md §4`, но без 14-дневного и количественного лимитов демо, т.к. курс не расходует вычислительный бюджет платформы, только чтение статей).

### 7.3 Прогресс курса — тот же `TraceEvent`, не отдельная таблица

```python
# новый event_type в уже существующем каноническом TraceEvent
# (spec_progress.md §4.1) -- не новая сущность:
event_type = "course_module_completed"  # payload: module_id, quiz_score (если есть)
```

Курс не заводит собственную систему прогресса — переиспользует ту же трассу событий, которая уже покрывает весь остальной пайплайн; «Прогресс исследования TS» (`spec_progress.md`) и «Прогресс курса» — одна и та же панель, курс — просто ещё один `stage`-подобный контур в том же журнале.

# Часть II — Движок саморазвития: квант обучения

## 8. Формализация: `Q` — квант обучения

### 8.1 Определение

Для любого места платформы, где существует **ожидание** (`E`, expectation — прогноз, рекомендация, предположение) и позднее — **наблюдение** (`O`, observation — факт, действие пользователя, исход):

```
Q := diff(E, O)
```

`Q` — не абстракция ради абстракции: это ровно то же самое измерение, которое платформа **уже делает** для моделей временных рядов пользователя (прогноз `E` vs факт `O` = ошибка бэктеста) — здесь оно применяется рефлексивно, ко ВСЕЙ платформе, а не только к пользовательским прогнозам.

### 8.2 Конкретные инстанциации `Q` по подсистемам — не одна формула на всё, а разные по природе диффы, как и в остальной архитектуре платформы (ср. `spec_forecasting2.md §4`: «интервалы — методологический выбор по семейству модели, а не единый метод» — тот же принцип: `Q` — методологический выбор по типу сущности)

| Подсистема | `E` (ожидание) | `O` (наблюдение) | `Q` |
|---|---|---|---|
| Модель прогнозирования | `ForecastPoint.value` | Фактическое значение ряда, ставшее известным позже | `\|E - O\|` (уже существующая метрика ошибки прогноза) |
| Наставник — «Следующий шаг» (`spec_progress.md §7.1`) | `recommended_action` правила | Реальное следующее действие пользователя (`TraceEvent.event_type`) | 1, если действие ≠ рекомендации; 0, если совпало |
| Наставник — sanity-предупреждение (§7.2 того же документа) | Предупреждение показано | Пользователь применил исправление без изменений после предупреждения | 1 (предупреждение проигнорировано без пользы); 0 (скорректировал) |
| `KnowledgeArticle` | Статья показана по `'?'` | Пользователь обратился в техподдержку по тому же `stage_id`/`node_id` в течение короткого окна после | 1 (не помогла); 0 (не потребовалось эскалации) |
| RAGFlow-ответ ИИ-помощника | Ответ показан | Эскалация в техподдержку по тому же вопросу | Аналогично строке выше |
| База лучших практик | Практика помечена «лучшей» (§6.1) | Фактический результат при повторном похожем профиле ряда (fact покрытия интервала задним числом, `spec_forecasting2.md §4.3`) | `\|ожидаемое покрытие − фактическое покрытие\|` |
| Курс — контрольный вопрос | Правильный ответ | Ответ пользователя | 1/0 (неверно/верно) |
| Спецификация/тариф (см. находку `spec_billing_accounts.md §5.7`) | Задекларированное правило (`can_train_models=False` для demo) | Фактическое продуктовое требование («демо покрывает все этапы») | Расхождение обнаружено вручную в этом случае — но именно такой класс расхождений `Q` умеет обнаруживать автоматически на будущее, если оба факта (декларация и фактическое использование) логируются как события |

Все эти `Q` — **не новая структура хранения**, а производные из пар уже существующих (или тривиально добавляемых) `TraceEvent` (`spec_progress.md §4.1`): `event_type="expectation_set"` и `event_type="observation_recorded"` с общим `correlation_id`, вычисляются batch-джобом, не в реальном времени на каждый запрос.

## 9. Движок: `ΔQ` — дифференциал состояний `Q`

### 9.1 Формализация и ключевое архитектурное решение

```
ΔQ(t) := Q(t) − Q(t−1)  (для одной и той же сущности: одна модель,
                          одно правило Наставника, одна статья и т.д.)
```

На практике интересен не единичный `ΔQ`, а **тренд/структурный сдвиг** в последовательности `Q(t)` для конкретной сущности во времени — то есть **временной ряд** `Q(1), Q(2), ..., Q(n)`, в котором нужно обнаружить момент, когда его поведение статистически значимо изменилось.

**Платформа уже решает ровно эту задачу** — это не новый алгоритм, который нужно спроектировать и реализовать, а **прямое переиспользование PELT (`apps/api/eda_structural_breaks.py`, Task 76)**, уже реализованного и сертифицированного детектора структурных сдвигов для временных рядов. Разница только в том, ЧТО является «рядом»: для пользователя это его данные; для `ΔQ` — это последовательность `Q(t)` конкретной модели/правила/статьи платформы. Один и тот же движок применяется дважды: один раз пользователем к своим данным (стадия EDA, узел `structural`), второй раз платформой к самой себе.

```python
# apps/api/self_tuning/drift.py (новый модуль -- тонкая обёртка,
# НЕ новая реализация детектора)
from apps.api.eda_structural_breaks import detect_structural_breaks

def detect_q_drift(entity_id: str, q_series: list[float]) -> list[int]:
    """Переиспользует уже сертифицированный PELT-детектор Task 76.
    Возвращает индексы обнаруженных структурных сдвигов в последовательности
    Q(t) конкретной сущности (модель/правило/статья/RAGFlow-ответ)."""
    return detect_structural_breaks(q_series)
```

Это решение — не техническая экономия усилий, а содержательное продолжение принципа, установленного во всех трёх спецификациях этой сессии («не изобретаем второй, конкурирующий механизм» — `spec_forecasting2.md`, `spec_progress.md`, `spec_billing_accounts.md`), доведённое до предельного случая: движок саморазвития платформы **буквально тот же код**, что уже проверяет данные пользователей.

### 9.2 Что происходит при обнаружении сдвига — конкретные действия по подсистемам

Обнаружение `ΔQ`-сдвига **не действует автоматически на продакшн** без человеческого подтверждения там, где это критично (тот же принцип, что уже применён к базе практик, §6.2, и к техподдержке, §5.1) — движок помечает, человек подтверждает:

| Сущность | Действие при обнаруженном сдвиге |
|---|---|
| Модель прогнозирования | Флаг «требует пере-тюнинга» на Model Card (не автоматический ретрейн без подтверждения — вычислительно дорого, см. Compute Unit, `spec_billing_accounts.md §4`) |
| Правило Наставника | `status="needs_review"` для правила — методолог пересматривает `condition`/`explanation_template` |
| `KnowledgeArticle` | `status="needs_review"` (§1) — ровно то, что обещано в §3 как автоматизация Principle Б |
| RAGFlow-ответ/индекс | Сигнал на переиндексацию конкретного документа, не всего корпуса |
| Курс, контрольный вопрос | Флаг «вопрос систематически даёт неожиданно много неверных ответов» → пересмотр формулировки методологом |

### 9.3 Связь с будущим модулем «Мониторинг» — тот же принцип, два разных потребителя

`packages/ui/lib/navigator-stops.ts` уже называет будущий прикладной модуль `monitoring` с описанием «Мониторинг: прогноз vs факт… Смещение распределения данных и прогнозов во времени» — это **пользовательское** приложение ровно того же принципа `Q`/`ΔQ`, который здесь применяется к самой платформе. Не два разных алгоритма: один и тот же PELT-движок (§9.1), применённый один раз к ряду «прогноз минус факт» ПОЛЬЗОВАТЕЛЯ (модуль «Мониторинг», когда он будет реализован), и рефлексивно — к ряду `Q(t)` самой платформы (эта спецификация). Реализация модуля «Мониторинг» и реализация движка Части II могут и должны переиспользовать один и тот же код `detect_structural_breaks`, не два похожих, но разных.

## 10. RL-дообучение ИИ-помощника — источник сигнала подкрепления: `Q`

### 10.1 Модель вознаграждения выводится из `Q`, не задаётся отдельно

Задача явно требует «дообучения ИИ-помощника методом обучения с подкреплением» — источник reward-сигнала не изобретается отдельно, а **берётся напрямую из строк таблицы §8.2**, относящихся к RAGFlow-ответам и переформулировкам Наставника: ответ, после которого пользователь НЕ обратился в техподдержку и продолжил исследование (`Q=0`) — положительное вознаграждение; ответ, после которого потребовалась эскалация (`Q=1`) — отрицательное. Не нужен отдельный размеченный датасет предпочтений на старте — сигнал уже собирается как побочный продукт нормальной работы техподдержки (§5) и трассы событий (`spec_progress.md §4`).

### 10.2 Офлайн, батчами — не в реальном времени

Дообучение — периодический офлайн-процесс (еженедельно/ежемесячно, не на каждый запрос) — та же позиция, что уже занята в `spec_progress.md §8` относительно LLM в целом («без LLM в реальном времени» для самого Наставника). RL-дообучение не меняет поведение системы «на лету» посреди сессии пользователя — только на границе явно версионированных обновлений модели ИИ-помощника.

### 10.3 Явная граница: RL меняет ретривер/рендерер текста, не решения Наставника

Дообучение методом RL применяется **только** к компонентам с ролью «переформулировать»/«ответить на открытый вопрос» (§4.2–4.3) — `RagflowMentorTextRenderer` и retrieval-ранжирование RAGFlow. RL **не применяется** к правило-движку Наставника (`MentorRule.condition`, `spec_progress.md §7`) — те пересматриваются методологом-человеком по сигналу `needs_review` (§9.2), не переобучаются градиентно. Это разделение — прямое продолжение архитектурной границы, уже проведённой в `spec_progress.md §8`: LLM (и теперь RL поверх LLM) — рендерер и ответчик на открытые вопросы, никогда не источник истины о том, что правильно рекомендовать.

## 13. Тестовая стратегия (TDD)

- **База знаний:** миграция константы → статьи не меняет отображаемый текст (снапшот-тест на паритет до/после миграции — риск случайно потерять уже написанный, проверенный методологический текст при промоушене в новую систему хранения).
- **Обучающие стеки:** выбор пересекающихся направлений не дублирует статьи в итоговом стеке; порядок статей в стеке всегда следует порядку `stage_id` в `STAGES`, а не порядку выбора чекбоксов пользователем.
- **RAGFlow-контракт:** `RagflowMentorTextRenderer.render(...)` не вызывается до того, как `MentorRule.condition` уже вернул `True` — regression-тест на то, что порядок «сначала правило, потом текст» не инвертирован по ошибке.
- **`Q`/`ΔQ`:** `detect_q_drift(...)` — тот же тестовый набор, что уже покрывает `detect_structural_breaks` (Task 76), плюс тест на то, что функция не переопределяет и не дублирует логику PELT (импорт, не копипаста).
- **Курирование (§5, §6):** запись не попадает в `published`/RAGFlow-индекс без явного события подтверждения человеком — тест на «нет прямого пути от `draft`/кандидата к индексации, минуя ревью».
- **RL-граница (§10.3):** regression-тест, что обновление весов RAGFlow-ретривера не изменяет ни один `MentorRule.condition`/`recommended_action` — эти данные лежат в разных, не пересекающихся хранилищах по конструкции.

## 14. Риски и меры

| Риск | Мера |
|---|---|
| Миграция контента из хардкода в БД потеряет уже проверенный методологами текст | Снапшот-тест на паритет (§13), ручное построчное сравнение перед удалением старых констант, не одновременно с их вводом |
| `Q` для статей/RAGFlow-ответов слишком редкий сигнал на старте (мало трафика — мало эскалаций в техподдержку) | `ΔQ`-детекция не запускается на короткие/разрежённые ряды — тот же порог `min_observations`, что уже используется PELT в Task 76, не новый порог специально для этого случая |
| RL-дообучение незаметно «дрейфует» в сторону формально более безопасных, но менее полезных ответов (reward hacking через избегание любых конкретных чисел) | Периодическая ручная выборочная проверка методологом перед выкаткой новой версии — offline-процесс (§10.2), не автоматический деплой по метрике |
| Курирование техподдержки/базы практик становится узким местом (человеческий ревью не поспевает за объёмом) | Осознанный компромисс: без ревью — не публикуется, не индексируется; масштабирование ревью — операционная, не архитектурная задача |
| Два независимых измерения тегирования (`stage_id` и `directions`) на практике редко используются согласованно редакторами | Обязательное поле `stage_id` при создании статьи, `directions` — опционально, с постепенным наполнением, не блокирует публикацию |

## 15. Открытые вопросы к тимлиду

1. Финальный список «направлений» (§2.2) — приведённый список стартовый, требует подтверждения продуктовой командой, не окончательный.
2. Технология хранения `KnowledgeArticle`/курс/база практик — по умолчанию предполагается та же СУБД, что и `research_runs` (`spec_progress.md §5`, там же открытый вопрос №1) — если выбор БД там изменится, синхронизировать здесь.
3. Порог/окно для «эскалация в техподдержку после статьи = отрицательный `Q`» (§8.2) — сколько времени между просмотром статьи и обращением считается «по той же причине», а не совпадением — калибровочный вопрос, не архитектурный.
4. Кто именно выполняет роль курирующего редактора техподдержки/базы практик (§5.1, §6.2) — выделенная роль/штатная единица или ротация среди аналитиков команды — организационный вопрос, не технический.
5. Периодичность RL-дообучения (§10.2, «еженедельно/ежемесячно») — не зафиксирована окончательно, зависит от фактического объёма накопленных `Q`-сигналов после запуска.
6. Наследуемое из `spec_billing_accounts.md §5.7`: расхождение `can_train_models=False` для demo vs «демо покрывает все шесть этапов» — не решено там, влияет и на курс (§7.1, модуль 5 про Моделирование должен показывать пользователю то, что демо-тариф реально позволяет делать самому, не только читать).

5. **Этап 4 — конвейеры пополнения (§5, §6).** ETL техподдержки, отбор кандидатов базы практик — требуют уже накопленного объёма реальных исследований и обращений, не запускаются раньше него.
6. **Этап 5 — квант обучения `Q`/`ΔQ` (Часть II).** `detect_q_drift`, автоматическая простановка `needs_review` — требует уже накопленного объёма `TraceEvent`-пар «ожидание/наблюдение» от Этапов 1–4, наиболее поздний по зависимости этап.
7. **Этап 6 — RL-дообучение ИИ-помощника (§10).** Требует уже работающего RAGFlow-ответчика (Этап 3) и уже накопленного `Q`-сигнала (Этап 5) — самый поздний этап по построению, не может быть запущен раньше.
