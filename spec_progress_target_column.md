## 1. Сценарий и симптом

Аналитик загружает демо-датасет `forecast_monitor_synthetic_n150.csv`, открывает «Прогресс». Шапка панели:

> Датасет: forecast_monitor_synthetic_n150.csv · Признак: — · 08.10.2026
> Запуск: RUN-CBCAFBCF · Начат 2 мин назад

Исследуемый признак показан как «—», хотя в датасете одна числовая колонка (`value`), то есть выбор однозначен.

## 2. Вопрос и решение

**Вопрос.** Нужно ли обязательное ручное подтверждение исследуемого признака кнопкой «Подтвердить», или достаточно автодетекта числовых колонок?

**Решение.** Обязательной кнопки «Подтвердить» нет. Принимается модель из трёх частей:

1. **Однозначный случай** (ровно одна подходящая числовая колонка) — система выбирает признак сама и фиксирует это как факт с источником `auto`.
2. **Неоднозначный случай** (две и более подходящих колонки) — тихого выбора нет на ОБЕИХ сторонах: бэкенд не фиксирует (п.1), фронтенд-хук не выполняет авто-POST рекомендации (снятие тихого авто-POST — PROGR-25-B, обязательная правка R1 акта); панель показывает «не выбран» и ведёт к существующему селектору, `suggested_column` остаётся отображаемой рекомендацией; ручной выбор фиксируется с источником `user`.
3. **Отображение** — шапка панели всегда показывает актуальное значение с пометкой происхождения («value (авто)» / «value») либо честное «не выбран».

**Обоснование.**
- Ключевая идея сервиса: автоматические решения по системным правилам — тоже факты (`spec_progress_v1.1.md`, контрольная формулировка). Авто-выбор без фиксации этому противоречит; обязательное подтверждение — лишний клик без пользы в однозначном случае.
- Прецедент платформы для колонки даты: «доверяем осознанному выбору, confidence — только предупреждение» (`confidentDateCol`), а не обязательное подтверждение.
- Блокирующее подтверждение породило бы вопрос о судьбе остановок «Предобработки»/EDA до подтверждения (блокировать — ломает автозаполнение степпера; не блокировать — подтверждение формально).

### PROGR-25-A — авто-фиксация признака на бэкенде при загрузке

**Проблема:** фиксация зависит от монтирования вкладки с хуком (закрывает Г1).

**Решение:**
- После успешной загрузки датасета бэкенд применяет детерминированное правило: если среди кандидатов ровно одна числовая колонка — это исследуемый признак. **Кандидаты = числовые колонки фрейма − `session.date_column` − колонки реестра производных `derived_columns_in_frame`** (канон PROGR-24: исключение по факту реестра, НЕ по суффиксу имени; правка R4 акта). Имя-исключение date-подобных заменяется факт-вычетами: колонка `year` без зарегистрированной даты — полноценный кандидат (неоднозначность → честное «не выбран»).
- **Точки фиксации (правка R2 акта):** единый хелпер вызывается из `handle_upload` (`upload_common.py:166`) И из demo-эндпоинта `POST /v1/session/demo` (`session.py:594`). Путь restore (`progress.py:1146`) НЕ меняется — он восстанавливает `run.target_column` своим путём, двойной фиксации нет. Сам `set_dataset` не правится (иначе заденет restore).
- **Механизм события (правка R3 акта):** в точке фиксации — программный посев `make_trace_event` (`target_column_changed`, payload `{target_column, source: "auto"}`, `stage="validation"`, `node_id=None` — атрибуция маршрута, не вкладки) по прецедентам PROGR-16-A / restore `run_resumed`; фиктивный вызов POST-маршрута запрещён.
- Две и более кандидатов — признак не фиксируется; панель покажет «не выбран».
- Правило живёт на бэкенде в одном месте (источник истины): хелпер размещается рядом с `_suggest_target_column` (`session.py:3979`) и используется и для фиксации, и для рекомендации — вторая реализация запрещена.

**Контракты:**
- Событие `target_column_changed`: аддитивное поле payload `source ∈ {"auto","user"}`; отсутствие поля трактуется как `user` (обратная совместимость со старым корпусом).
- Белый список `payload_keys` в `TRACE_ROUTES` дополняется `source`.
- Ответ `POST /target-column` и `GET /current` отдают `target_column_source` (опционально).
- Ответ `GET /v1/progress/trace` (`ProgressTraceResponse`, `routers/progress.py:247`) дополняется полями `target_column`, `target_column_source` (Optional) — носитель для шапки задачи B; все бэкенд-расширения сосредоточены в A, B остаётся чисто фронтендовой.
- Все расширения схем (`TargetColumnResponse` / `SessionStateResponse`, `schemas.py:2772/2748`, и `ProgressTraceResponse`) — аддитивные Optional-поля; тест «ровно 7 полей» движка не затрагивается (payload — не поле `PipelineNodeState`).

**TDD (RED сначала):**
- одна числовая колонка → после загрузки `target_column` заполнен, событие `source=auto`;
- две числовые колонки → не заполнен, события нет;
- ручной выбор после авто → `source=user`, last-wins;
- старый корпус без `source` читается как `user`;
- явная приманка: колонка с «производным» именем в файле не исключается по суффиксу (канон PROGR-24);
- демо-путь: `POST /v1/session/demo` применяет то же правило (R2): для встроенного `sales_demo.csv` (две числовые) — фиксации/события нет, для датасета с единственной числовой — `source=auto`;
- restore: `target_column` восстанавливается из `run.target_column`, второго события фиксации нет (R2);
- колонка из реестра производных исключается из кандидатов; производноподобная ИСХОДНАЯ (вне реестра) остаётся кандидатом — решает реестр, не имя (R4);
- `session.date_column` исключается даже без date-подобного имени (R4).

**Приёмка:** сценарий «upload → `/current`» без захода на какую-либо вкладку даёт заполненный признак с `target_column_source="auto"` (одна числовая); demo-эндпоинт применяет то же правило — встроенный `sales_demo.csv` имеет ДВЕ числовые (sales, profit) и даёт честное «не выбран», датасет с единственной числовой — авто-фиксацию (уточнение реализации PROGR-25-A: первоначальная формулировка «кнопка демо даёт заполненный признак» неточно описывала встроенный демо-датасет).

### PROGR-25-B — шапка панели «Прогресс»: актуальное значение и происхождение

**Проблема:** «—» при загруженном датасете (закрывает Г2).

**Решение:**
- При каждом открытии панели шапка берёт `target_column` из того же ответа, что и трасса (`GET /v1/progress/trace`; поля вводятся задачей A — см. её контракты) — один источник, без зависимости от устаревшего контекста.
- **Снятие тихого авто-POST хука (правка R1 акта, обязательная).** Хук `useTargetColumn` (`useTargetColumn.ts:139-160`) перестаёт выполнять авто-POST рекомендации полностью: авто-фиксация — исключительная компетенция бэкенда (задача A). `suggested_column` остаётся отображаемой рекомендацией селектора; фиксация — только ручная (`POST /target-column`, `source=user`). Альтернатива «ограничить авто-POST однозначным случаем» отклонена: фронту потребовалась бы собственная реализация правила кандидатов, запрещённая задачей A («вторая реализация запрещена»). Выкат снятия — только после A (§5).
- Состояния шапки: «Признак: value (авто)» / «Признак: value» / «Признак: не выбран — выбрать» (ссылка на селектор).
- Прочерк «—» остаётся только при отсутствии датасета.

**TDD:**
- ответ с `source=auto` → «(авто)»;
- ответ с `source=user` → без пометки;
- датасет есть, признака нет → «не выбран» и ссылка;
- датасета нет → «—»;
- смена признака на другой вкладке и повторное открытие панели → новое значение без перезагрузки страницы;
- монтирование любой вкладки с хуком само по себе не создаёт `target_column_changed` (ни при одной, ни при нескольких числовых) — авто-POST снят (R1);
- при неоднозначности рекомендация отображается в селекторе, тихой фиксации нет.

**Приёмка:** шапка не показывает «—» при загруженном датасете ни в одном порядке действий.

### PROGR-25-C — Наставник и `reason` узла учитывают происхождение выбора

**Решение:**
- `phase_text` стадии Загрузка: при `source=auto` — «Исследуемый признак выбран автоматически: value» (без просьбы выбрать); при `user` — прежний текст; при отсутствии признака — просьба выбрать (как сейчас).
- `status_reason` узла `validation/sufficiency` (PROGR-21): «Целевой признак: value (авто)» при `source=auto`.
- Условия читают уже посчитанные факты (движок `node_status.py`), нового I/O нет. Носители (сертификация, R5): `phase_text` — условия `STAGE_PHASE_TEXT_RULES` (`mentor_rules.py:1104-1130`) получают `(summary, events)` и читают `source` из payload события после аддитивного расширения `payload_keys`; `status_reason` — `_stage_level_reason_updates` (`node_status.py:345-354`), носитель `(validation, sufficiency)` — `TARGET_REASON_STAGE_NODE:285`. Нюанс: событие авто-фиксации всегда несёт `stage="validation"` (атрибуция маршрута, не вкладки) — правила C не опираются на вкладку возникновения события.

**TDD:** по одному кейсу на каждое состояние (auto / user / нет признака) для `phase_text` и для `status_reason`; регресс: прежние тесты PROGR-15-B и PROGR-21 остаются зелёными без правок.

**Приёмка:** Наставник не просит выбрать признак, если он уже выбран автоматически.

## 6. Осознанные границы

- Кнопка «Подтвердить» как обязательный шаг не вводится. Если появится требование явного подтверждения (например, для регуляторной отчётности), оно оформляется отдельным необязательным событием без блокировки остановок.
- Авто-выбор не применяется при неоднозначности: платформа предпочитает честное «не выбран» тихому угадыванию (принцип честной маркировки).
- Ранжирование кандидатов не вводится: рекомендация = первая колонка множества кандидатов по стабильному порядку фрейма (как сегодня — «первая не-date-подобная»). Унификация хелпера (R4) меняет только МНОЖЕСТВО кандидатов (вычеты `date_column` и реестра производных), не порядок обхода.
- Колонки реестра производных исключаются из кандидатов (канон `spec_status_original_series.md`).
- Авто-фиксация — исключительная компетенция бэкенда: фронтенд-хук фиксацию не выполняет (снятие авто-POST, R1) — один исполнитель правила, один источник истины.
- Сессии, загруженные до внедрения A (legacy), авто-фиксацию не получают: панель честно показывает «не выбран», работает ручной выбор (`source=user`); миграция старых сессий не делается.
- Restore сохраняет собственное восстановление `run.target_column` и не дублирует фиксацию.

## 7. Критерии приёмки спецификации

- Демо `forecast_monitor_synthetic_n150.csv`: сразу после загрузки панель показывает «Признак: value (авто)».
- Файл с несколькими числовыми колонками: панель показывает «не выбран»; ручной выбор отображается без пометки «(авто)»; тихой фиксации нет ни на бэкенде, ни в хуке (рекомендация остаётся в селекторе).
- Кнопка «Попробовать на демо-данных» (`POST /v1/session/demo`) применяет то же правило (R2): встроенный `sales_demo.csv` (две числовые: sales, profit) → честное «не выбран», фиксации/события нет; датасет с единственной числовой → «Признак: value (авто)». (Уточнение реализации PROGR-25-A: первоначальная формулировка «даёт тот же результат: value (авто)» не учитывала состав встроенного демо-датасета.)
- Restore запуска восстанавливает `target_column` из `run` без второго события фиксации.
- Событие `target_column_changed` несёт `source`; старые события без поля не ломают чтение.
- Регресс: сертификационные оракулы и мутации `PROGR-1…24-CERT` остаются зелёными; расширение полей аддитивно.
