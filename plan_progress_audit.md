## 1. Цель и условия выполнения

Сделать «Прогресс» основой документирования исследования: факт имеет идентичность, происхождение, контекст и проверяемый результат; панель, Наставник и отчёт используют согласованную историю; доставка различает принятый запрос, выполненную операцию и сохранённое свидетельство.

План разворачивает направления AUDIT-1…AUDIT-8 из аудита в **16 отдельно сдаваемых задач**. Дополнительные AUDIT-0/S/C — подготовка и общие контракты; буквы A/B/C делят крупные направления. Идентификатор журнальной записи `PROGR-AUDIT-1` относится к уже выполненному исследованию, а не к выполнению задачи `AUDIT-1a` настоящего плана.

**Обязательные правила.**

- Следовать `AGENTS.md`: изучить текущий код, выбрать точки изменений, оценить риски, RED→GREEN, регрессия и сборка для реализации, ZIP только файлов текущей задачи, запись в worklog9.
- Не выполнять commit/push в `DimmDay/CISStat-TS-Analysis/main`. Синхронизация — только по прямому указанию тимлида. Перед задачей записывать фактический HEAD и состояние рабочего дерева, сохранять изменения предыдущих задач.
- Использовать настоящие пути: `apps/api/upload_common.py`, `app/core/node_status.py`, `app/core/mentor_rules.py`; standalone — `apps/standalone`. Пути из ранних планов могут быть устаревшими.
- Сохранять канон TraceEvent, legacy-чтение, единственное backend-правило выбора цели и общие реестры узлов. Новый контекст не создавать догадками фронтенда.
- Не менять молча принятые смыслы: EDA done = результат показан/просмотрен по UI-контракту; raw restore не обещает восстановление промежуточного DataFrame; рекомендация не равна выбору.
- Не подменять отсутствие доказательства значением «всё корректно». Неизвестное происхождение, устаревший результат и недоставленное событие имеют явные состояния.

**За пределами работ:** пересмотр статистических алгоритмов всех модулей, neural runtime, PROGR-23 кэп/«Исправлено», пересчёт stale-производных, полноценный replay checkpoint-DataFrame, новый сервис авторизации и инфраструктурные backup/retention политики. Инвалидирование зависимых результатов входит; исправление их математических алгоритмов — отдельные задачи.

## 2. Исходные доказательства и критерий завершения

Аудит получил 25 локальных наблюдений P01…P25 и 92 passed существующих тестов. Это **не** E2E-подтверждение Render/Vercel. H26…H30 пока открыты. Нельзя превращать их в объявленные production-дефекты или считать устранёнными без проверки.

`progress_audit_readonly.py` содержит assertions текущего поведения, включая дефекты. Исполнитель сохраняет исходный JSON как доказательство базы, а новые acceptance-тесты проверяют исправленное поведение. Не менять старый протокол на «зелёный» и не удалять найденный сценарий ради прохождения.

Финальная приёмка требует:

1. Свежая загрузка, reset цели, смена цели/даты, применённая коррекция и raw restore дают согласованный текущий контекст.
2. Карта старого run/context не меняет новый; повтор того же report_id не создаёт новые факты.
3. Проекции не зависят от cap=1000, сортировки по часам, порядка объединения источников и временной недоступности UI seed.
4. Причины/цифры имеют источник и применимость; старое достижение не удостоверяет новые данные.
5. В заявленном required-контуре запись подтверждается durable receipt; повтор доставки не повторяет научную операцию.
6. Отчёт различает вычисление, показ, выбор человека, auto-решение и исторический результат.
7. Закрытые и открытые гипотезы перечислены с доказательствами; непроверенный production отдельно обозначен.

## 7. AUDIT-6A — атомарный ledger и одинаковые хранилища

**Точки:** `apps/api/research_runs.py`, новая аддитивная SQL-миграция в `apps/api/migrations/`; `test_research_runs.py`, `test_research_runs_postgres.py`. Номер миграции выбрать по актуальному каталогу, существующую `0001` не переписывать.

**Состав.**

- Ввести единый `commit_event_batch` или эквивалент: проверка expected context, обновление run, запись событий, регистрация idempotency key и receipt в **одной DB-транзакции**.
- Полная карта десяти узлов — один batch, не десять независимых commit.
- Назначать sequence транзакционно с сериализацией по run. Сам по себе BIGSERIAL не удостоверяет порядок commit конкурентных транзакций и не гарантирует непрерывный committed prefix.
- Receipt содержит operation/report_id, run/context, принятые event ids, committed watermark. Повтор того же ключа/тела возвращает прежний receipt; тот же ключ с другим телом — конфликт без записи.

**RED:** P08/P10/P20 по исправленному контракту; падение на середине batch оставляет ноль событий и прежние метаданные; два concurrent batch имеют один порядок; retry после потерянного receipt не дублирует; stale context отклонён до commit.

**GREEN/приёмка:** DB rollback атомарен; одинаковые contract tests проходят Memory и Postgres; миграция применима к старому корпусу. Если live PostgreSQL недоступен, соответствующая приёмка остаётся открытой.

**Граница:** Redis и изменение DataFrame пока не включены в эту транзакцию. Не объявлять P09 и весь контур доставки устранёнными этой задачей.

## 9. AUDIT-1a — цель: choice, reset, source и restore

**Точки:** `apps/api/target_column_rule.py`, conversion/target handlers в `apps/api/routers/session.py`, `trace_events.py`, `trace_hook.py`, `research_runs.py`, `routers/progress.py::restore_run`, `node_status.py`, `mentor_rules.py`.

**Состав.**

- Посеять reset в реальной точке сброса цели после успешной коррекции; обеспечить только одну запись.
- Один effective-target reducer обрабатывает choice/reset. Его используют session/run metadata, reason, Наставник и документ.
- При сбросе очистить актуальную цель и origin; прежний выбор сохранить исторически.
- Restore восстанавливает согласованную пару target/source; старый payload без source читается как user по legacy-контракту, повреждённое происхождение — unknown.

**Точки:** transaction/store слой AUDIT-6A, `trace_hook.py`, session mutation boundary, DatasetFileStore/артефакты, recovery worker/служебный runner — новый модуль по паттернам проекта.

**Риск/граница:** это крупнейшая архитектурная задача. Не завершать её только заменой порядка двух вызовов или переносом хука перед response. Не обещать гарантированное документирование для unmigrated handlers.

## 20. Проверки, совместимость и порядок поставки

### 20.1. Проверки исполнителя

Команды выполнять из корня репозитория после установки соответствующих зависимостей.

```bash
python -m pytest tests/api/test_trace_events.py tests/api/test_node_status_engine.py -q
python -m pytest tests/api tests/integration -q
npx jest --runInBand
npm run typecheck:all
npm run build:all
```

Первый прогон — минимальный контроль исходного ядра; адресные suites определяются карточкой задачи. Полный API/integration и UI регресс — перед сдачей функциональной поставки. При изменении requirements/startup/storage добавить сборку образа `apps/api/Dockerfile` и импорт/запуск полного API с нужными runtime dependencies; deployment не требуется для build-проверки.

Новые live-Postgres contract tests не заменять mock-строкой SQL. Прогон в среде с неполным Modeling runtime, где main не импортируется, маркировать компонентным; readiness gate не отключать ради «зелёного» общего результата. Старые показатели 92/25 не являются результатом текущей реализации.

### 20.2. Legacy и миграции

1. Сначала readers v2 и аддитивная DB-миграция, затем producers/receipt, затем strict context-write.
2. Старый корпус не пересортировывать по invented timestamps; backfill новой metadata — отдельный журналируемый процесс с raw/quality.
3. У legacy отсутствующие source трактуются по принятому target-контракту; отсутствующие revision/result доказательства остаются unknown.
4. Во время rollout старого UI context-guard может быть ограничен compatibility mode. До его отключения нельзя заявить полное закрытие P24/H26. План завершения/дата или release-marker режима обязательны.
5. Rebuild проекции делать повторяемо; сохранять прежнюю экспортную форму и возможность сравнения corpus ids. Не удалять ledger для «починки прогресса».
6. Изменение старого exact-output теста допустимо только как явное обновление versioned-контракта с доказательством сохранённой legacy-ветки. Не переписывать оракулы дефектов под реализацию.

### 20.3. Definition of Done каждой задачи

- Записаны исходный HEAD, границы, зависимости и риски.

## Донастройка плана:

- (а) по AUDIT-0: target_column_cleared и горячая дорожка F02/F17
Часть 1. Решение по сбросу цели: выделенный тип, не перегрузка target_column_changed
Рекомендация: утверждать выделенный канонический тип target_column_cleared (stage=validation, node_id=None — по образцу target_column_changed), а не «versioned» пустой target в существующем типе.

Почему не «пустой target в changed»
Решающий аргумент даёт код: дешевизна Option B — иллюзия. Сегодня семантика «пустой target = сброс» существует только в одном потребителе из четырёх:

Потребитель
Поведение при пустом target сегодня
Редьюсер reason (node_status.py:358–360)	пустая строка → сброс своего reason; мусор → не факт
_target_confirmed (mentor_rules.py:1058)	any-семантика: пустые пропускаются, сброс не снимает подтверждение
_target_origin (mentor_rules.py:1077)	last-wins только по непустым; сброс не сбрасывает origin
_phase_event_text_facts (mentor_rules.py:1196+)	last-wins по непустым; текст держит старую колонку

То есть при Option B правки Наставника всё равно нужны те же, что и при Option A, — но вдобавок контракт «пусто = сброс» придётся задокументировать и поддерживать в каждом потребителе отдельно, а payload одного типа начнёт смешивать две разные схемы (выбор и сброс). Я это уже сертифицировал в C-CERT с другой стороны: смешение семантик в payload порождает ровно тот класс багов (Mapping-щит, мусор-vs-пусто), от которого §4.1 аудита требует различать утверждения.

Почему Option A закрывает класс, а не случай
F02 возник потому, что сигнал сброса ушёл вне канала цели: конвертация типов (session.py:3952–3961) чистит session.target_column/source, но флаг target_column_reset=true путешествует в correction_applied/correction_previewed узла data_types (trace_hook.py:143, спецификация маршрута :219–223), который подсистема цели не читает. Выделенный тип делает сброс первоклассным фактом с собственным контрактом — исчезает сам соблазн «сигнализировать сброс боковым флагом».

Форма контракта (внести в docs/progress_audit_contract.md)
Реестр: аддитивная запись в _STAGE_EVENT_TYPES["validation"] (trace_events.py:86–104). Это v1-совместимое расширение: неизвестные типы у всех читателей деградируют честно («событие мимо фактов, не 500»), legacy-корпус типа не содержит → миграция не нужна. Важная оговорка для AUDIT-0: «добавление ТИПА события не ждёт AUDIT-S; добавление ПОЛЕЙ envelope — ждёт». Это решение разблокирует горячую дорожку.
Payload: {target_column: null, reset_reason: str, source: "system"|"auto", before_target: str|null}. Мусор в полях — деградация, не 500 (щит из C-CERT). Строгое whitelisting — событие сеется кодом, а не через TRACE_ROUTES, поэтому таблица маршрутов и _CORRECTION_PAYLOAD_KEYS не трогаются.
Семантика origin после сброса — тонкость, которую обязательно зафиксировать в контракте: после cleared происхождение = unknown/пусто, а НЕ «user». Дефолт _target_origin = "user" легитимен только для отсутствия поля у legacy-ВЫБОРА; после сброса «user» фабриковал бы человеческий выбор, которого не было.
Разделение маршрутов: POST /target-column остаётся маршрутом выбора с 422 на пустой (граница PROGR-25-C); сброс — только серверный producer. Не объединять.
Канон R3: cleared сеется двухслойно (слой 1 + зеркало слоя 2, общий event_id) в точке решения — по образцу auto_fix_and_seed; correction_applied хука приходит после — хронология «сброс → исход коррекции» согласована с каноном «фиксация → upload_completed».
Часть 2. Горячая дорожка: ДА, но разной глубины для F02 и F17
Оба дефекта достижимы штатными действиями пользователя (конвертация типов — стандартный шаг валидации; повторный GET — remount/refetch), оба дают видимую ложь интерфейса — Наставник утверждает выбор, которого нет, EDA-узел регрессирует из done в running. Фундамент (S→C→6A→5B) — это недели; оставлять честностные нарушения живыми противоречит канону, который PROGR-25 только что построил. Но дорожка должна идти строго после AUDIT-0 (контракт типа фиксируется документом решений) и быть жёстко ограничена.

F02 — горячий фикс = первый инкремент AUDIT-1a (без выброса)
Объём: 4 точки, ~1 день.

trace_events.py: регистрация типа (см. выше).
session.py, convert_types (:3952–3961): посев target_column_cleared двухслойно + upsert_run с target_column=None, target_column_source=None (паттерн merge-dict есть в restore_run progress.py:1194–1203). Сейчас run-метаданные не обновляются вовсе — это и есть половина P03.
node_status.py: ветка редьюсера для cleared — тот же эффект, что существующая пустая ветка (:358–360).
mentor_rules.py: тройка (_target_confirmed/_target_origin/_phase_event_text_facts) становится reset-aware: cleared снимает подтверждение и текущую колонку. После сброса условия правил честно падают в fallback «Подтвердите целевой признак…» — это и есть ожидание P03.
Это не выброс: редьюсер и тройка — ровно «один effective-target reducer» из карточки AUDIT-1a; горячая дорожка доставляет его первую инкрементацию, AUDIT-1a позже расширит его на restore/origin. Единственное, что осознанно НЕ делается: restore (F03), контекст, origin-восстановление.

RED/GREEN: тесты на HEAD до правки (сброс-событие в /trace, run.target_column=None, Наставник просит, reason снят) — 4 RED; затем GREEN. Регресс обязателен адресный: test_progress_progr25a/progr25c, интеграционные D1/D2 (их путь reset не задевает — должны остаться зелёными), мои оракулы progr25ccert (корпуса не содержат cleared → все пины §4-C/«(авто)» остаются валидными; новое поведение аддитивно).

F17 — горячий фикс узкий, с маркировкой «interim»
Рекомендация: монотонность только для profile_viewed, только в редьюсере статусов. Правило: profile_viewed устанавливает running только из pending/отсутствия; узел, достигший done, им не понижается. Точка — derive-функция рядом со статической картой (node_status.py:69), не сама карта.

Почему это безопасно вопреки опасению «заморозим устаревание»: легитимный путь переоткрытия узла существует отдельно от profile_viewed — карта eda-checks (progress.py:744) несёт статусы через PAYLOAD_STATUS и может поставить pending после коррекции. Гипотетическая липкость done при смене контекста (H28) не ухудшается: done из UI-карты и сегодня клиентское наблюдение; правило лишь убирает ложный регресс от GET. Обязательная маркировка в коде и в поставке: «interim до AUDIT-3, заменяется на контекст-ключевую монотонность» — ~10 строк выброса против недель ожидания, сделка оправдана.

Чего НЕ делать: глобальную монотонность на все события — она сделает H28 неисправимым молча.
