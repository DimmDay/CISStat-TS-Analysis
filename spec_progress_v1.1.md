# spec_progress_v1.1.md — Сверка с основной идеей сервиса + план исправления

Статус: предложение к утверждению тимлидом. Дополняет `spec_progress.md` (v3)
и `spec_progress_review_and_v4_addendum.md` (v4). Синхронизация кода на
момент написания — `main@c164e95` (Task PROGR-15-B).

**Контрольная формулировка, с которой сверяется реализация** (зафиксирована
тимлидом): *«Сеются все факты прохождения всех фаз, этапов и шагов
исследования, в том числе те, которые проводит система автоматически на
основе системных правил. Ручные операции аналитика фиксируются в трассе и
также являются фактом. Все факты имеют эргономичное и понятное отображение
в панели «Прогресс». Наставник подробным образом комментирует текущее
состояние и предлагает следующий шаг.»*

---

## 0. Итоговый вердикт

Архитектурное ядро (§2–§5, §7 `spec_progress.md`: единый граф узлов, единый
движок статусов `node_status.py`, панель как потребитель уже посчитанного
состояния, а не отдельный опрос) реализовано образцово и строго следует
контрольной формулировке на уровне механики. Но по охвату — **что именно
становится фактом** и **насколько подробно Наставник комментирует
состояние** — реализация является курируемым, явно задокументированным
подмножеством идеи, а не её полной реализацией. Ниже — пять категорий
расхождений, по каждой — решение (закрыть сейчас / закрыть позже / принять
как осознанный компромисс с фиксацией в тексте спецификации).

## 1. Категория A — не все изменяющие действия трассируются

### Диагноз
§4.2 (v3) предполагал механизм, не требующий ручной поддержки списка
маршрутов («единая точка интеграции… не требует правки каждого роута
вручную»). По факту реализации (`PROGR-3`) — это fail-closed **allowlist**
`TRACE_ROUTES` (44 записи), который требует явного добавления строки на
каждый новый факт. Сертификация `PROGR-3-CERT` (R-2) перечислила
непротрассированные мутирующие эндпоинты: `validation-rules`,
`type-schema`, `stage/{stage}`; Моделирование — `compare`,
`selection/evaluate`, **`candidates`**, `baselines`, `backtest/exclude`,
`tuning/skip`×2, `jobs`×3, `diagnostics`×2, `feature-regressors`.

`candidates` — ключевой случай: это прямое попадание в формулировку
«факт, который система формирует автоматически на основе системных
правил» (applicability-движок `modeling.yaml`), и он сейчас не оставляет
следа в трассе вовсе.

### Решение
Allowlist-архитектура **остаётся** (это осознанный выбор платформы — см.
§12 п.7/sпрецедент `rules/mentor.yaml`: калибруемые/контрактные константы
не хардкодятся произвольно, а явно перечисляются и проверяются на
импорте — тот же принцип "fail-closed, не fail-open" применён и здесь,
замена на «ловить всё подряд» снизила бы, а не повысила качество фактов:
не всякий мутирующий вызов содержательный факт исследования, часть —
служебные/идемпотентные операции).

Вместо отказа от allowlist — **плановое расширение по приоритету**:

| Приоритет | Эндпоинт | Обоснование включения |
|---|---|---|
| P0 | `POST /v1/models/candidates` | Прямой пример из формулировки идеи — факт системного правила (applicability) |
| P0 | `POST .../selection/evaluate`, `model_selected`-соседи | Решение аналитика о выборе модели — тот же класс, что уже трассируемый `model_selected` |
| P1 | `POST .../compare` | Факт сравнения моделей — содержательное решение аналитика |
| P1 | `POST .../diagnostics` (×2) | Факт запуска диагностики — пара к уже трассируемому `backtest_run` |
| P2 | `tuning/skip`×2, `jobs`×3 | Служебные операции долгого job-контура — оценить по факту, не дублируют ли уже `tuning_trial_completed` |
| Не включать | `validation-rules`, `type-schema` | Конфигурационные правки до запуска проверки, не факт прохождения исследования — предлагается явно зафиксировать как осознанное исключение, не пробел |

Задача: **`PROGR-20`** — расширение `STAGE_EVENT_TYPES` + `TRACE_ROUTES` по
таблице выше (P0 обязательно, P1/P2 — по решению тимлида), с тем же
TDD-циклом, что и исходная таблица (`PROGR-3`).

## 2. Категория B — узловой факт-контур есть не у всех этапов

### Диагноз
`PROGR-16-A` закрыл класс «нет носителя факта прохождения» только для
**Валидации** (`validation_check_status`, зеркало `upload_stop_status`).
Для **Предобработки** тот же класс дефекта зафиксирован как «сознательно
вне границы» в самой записи `PROGR-16-A`. Для **EDA** аналогичного
отчётного контура не было никогда — узлы EDA не достигают `done` от
самого модуля.

### Решение
Закрыть оба пробела тем же, уже трижды проверенным паттерном
(`upload_stop_status` → `validation_check_status` → …), не изобретая
новый механизм:

- **`PROGR-17`** — `preprocessing_check_status`: `POST
  /v1/progress/preprocessing-checks`, зеркало `/validation-checks`
  буквально (fail-closed all-or-nothing, карта по 10 остановкам
  `PREPROCESSING_CHECK_IDS`, отчёт на изменение снапшота степпера).
- **`PROGR-18`** — `eda_check_status`: тот же паттерн для 10 исследований
  EDA (`eda_checks.json`, уже общий реестр с `PROGR-2`). Для EDA нужно
  решить один методологический вопрос заранее (не откладывать на
  реализацию): что считается «статусом» исследования, у которого
  исторически нет pass/fail-семантики (EDA — не проверка качества, а
  анализ) — рекомендация: статус `done`/`pending` по факту «аналитик
  открыл и просмотрел результат», `warning` не вводить (ложная тревога
  там, где нет критерия ошибки).

## 3. Категория C — Наставник комментирует подробно только одну стадию из шести

### Диагноз
Самое свежее расхождение. `PROGR-15-B` сделал `phase_text`
факт-обусловленным **только для `upload`**:

```python
if stage != "upload":
    return PHASE_TEXT_TEMPLATES.get(stage, _PHASE_TEXT_FALLBACK)
```

Для остальных пяти стадий `phase_text` — статический шаблон, не читающий
`statuses`/`events`, хотя `summary` того же ответа `next-step` уже
содержит реальные посчитанные цифры по узлам этой стадии — то же самое
«самопротиворечие одного JSON» (которое `PROGR-15-B` устранил для
Загрузки), просто не найденное вживую на остальных стадиях, потому что
расследование `PROGR-15-REPRO` тестировало именно Загрузку.

### Решение
Не копировать `upload`-ветвление ещё пять раз (ручная конструкция
«if/elif» на шесть стадий, предложенная PROGR-15-B как узкий фикс одной
находки, не рассчитана на тиражирование — превратится в нечитаемый
монолит). Вместо этого — **обобщение контракта**, задача **`PROGR-19`**:

- Декларативная таблица `STAGE_PHASE_TEXT_RULES: dict[str, list[PhaseTextRule]]`
  в `app/core/mentor_rules.py`, где `PhaseTextRule` — `(condition:
  Callable[[stage_node_summary, events], bool], template: str)`, в порядке
  приоритета; первое совпавшее правило — текст; ни одно — текущий
  статический `PHASE_TEXT_TEMPLATES[stage]` как fallback (обратная
  совместимость с `phase_text(stage)` без аргументов сохраняется дословно
  — то же требование, что уже было в `PROGR-15-B`).
- Источник условий — **уже посчитанный** `stage_node_summary`
  (`done_count`/`total_nodes`/`warning_nodes`, тот же объект, что уже
  есть в ответе) — ноль нового I/O, тот же принцип «пересказ уже
  вычисленного», что и раньше.
- Перенос текущей upload-логики (`_UPLOAD_STRUCTURE_DONE_*`) в этот же
  реестр как частный случай — не два параллельных механизма.
- Минимальный набор правил для v1.1 (по одному на стадию, не копия
  детализации upload): «Валидация: N/10 проверок, найдены проблемы» /
  «Предобработка: N/10 этапов обработано» / «EDA: N/10 исследований
  просмотрено» / «Моделирование: кандидаты сформированы, backtest не
  запускался» / «Прогнозирование: прогноз не строился» — то есть
  **каждая стадия получает хотя бы один факт-обусловленный вариант**,
  вместо нуля сейчас.

Отдельно — §7.1 «конечный список из 8 правил, тишина если ничего не
сработало» — это признаётся осознанным, не патчится в рамках `PROGR-19`
(расширение правил `NEXT_STEP_RULES` — отдельная, открытая, растущая
работа по категории B исходного `spec_progress.md §11`, не разовая
задача).

## 4. Категория D — решения Наставника не попадают в видимую трассу

### Диагноз
`MentorObservation` (`PROGR-8`) — сознательно отдельная от `trace_events`
сущность; срабатывания sanity-правил и next-step-рекомендаций не видны
ни в панели, ни в «Развернуть трассу» — только в закрытой
admin-аналитике.

### Решение
**Принять как осознанный архитектурный компромисс, зафиксировать явно в
тексте спецификации**, не переносить в пользовательскую трассу. Обоснование
(дословно сохраняется из `PROGR-8`): рекомендации и предупреждения — это
**советы**, а не **факты исследования** в смысле §2 (они не меняют
состояние датасета/модели/прогноза, их повторный вызов идемпотентен и
не детерминирован частотой открытия панели). Смешение в один журнал
обесценило бы и трассу (шум от каждого открытия Наставника), и телеметрию
(пользовательский шум против корпусной аналитики).

Формальное действие: добавить в `spec_progress.md` §3.1 новый подпункт
(по аналогии с уже существующим разведением `session.stages`/
`pipeline_graph.py`) — **«§3.2 Советы Наставника — не факты»** с этим
обоснованием. Задача не кодовая, а документационная — часть
`PROGR-19` deliverable.

## 5. Категория E — не все факты трассы подняты на визуальный слой узла/стадии

### Диагноз
`N-2`/`N-3` (`PROGR-10`): stage-level факты (`mode_changed`,
`target_column_changed`, `checkpoint_saved`, `run_*`) не влияют на свод
статуса узла/стадии — видны только в плоском логе «Развернуть трассу».

### Решение
Частично принять, частично закрыть:

- **Принять** для run-level фактов (`checkpoint_saved`, `run_paused`,
  `run_resumed`) — они и не должны влиять на свод узла/стадии по
  определению (это факты уровня запуска, не узла, §2); отображение в
  логе — корректно и достаточно. Зафиксировать явно, не как открытый
  N-пункт, а как решённый вопрос.
- **Закрыть** для `mode_changed`/`target_column_changed` — это узловые
  по смыслу решения аналитика (смена режима проверки конкретной
  остановки, выбор целевого признака конкретно для Загрузки), которые
  сейчас не подсвечиваются на карточке. Задача **`PROGR-21`**: добавить
  `mode_changed` и `target_column_changed` как источник `reason`
  (не `status`) в `derive_pipeline_node_states` — узел не меняет цвет
  статуса, но получает актуальный `status_reason` («Режим: включена
  вручную», «Целевой признак: Price») — минимальное, не ломающее
  текущий контракт расширение (поле `reason` уже существует в
  `PipelineNodeState`, PROGR-11).

## 7. Критерии приёмки v1.1

- Для каждой из 6 стадий пайплайна существует хотя бы один факт-источник
  уровня «проверка/этап пройден(а)», не только Модель/Прогноз/Загрузка/
  Валидация (сейчас — 4 из 6).
- `phase_text` в ответе `next-step` обусловлен фактами для всех 6 стадий,
  не только `upload`; вызов `phase_text(stage)` без аргументов — дословно
  прежний статический текст (обратная совместимость не нарушается).
- `TRACE_ROUTES` включает как минимум оба P0-пункта категории A.
- `spec_progress.md` содержит явный подпункт §3.2, объясняющий, почему
  `MentorObservation` не сливается с пользовательской трассой — решение
  зафиксировано как осознанное, не как открытый вопрос.
- Регресс: все существующие сертификационные оракулы/мутации
  (`PROGR-1…16-CERT`) остаются зелёными — расширение полей/реестров
  аддитивно, ни один существующий контракт не сужается.
