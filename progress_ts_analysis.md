## 1. Назначение и границы

Мега-меню «Прогресс» — единая точка входа, показывающая полный пайплайн исследования (Загрузка → Валидация → Предобработка → Разведочный EDA → Моделирование) для конкретной пары (датасет, признак), с текущим состоянием каждого узла, контрольными точками, паузой/восстановлением и трассой с логами. Вызывается пунктом «Прогресс» из главного меню; изнутри мега-меню — кнопка «Наставник» (правило-движок «Следующий шаг», см. §7).

Пять целей из брифа отображены на архитектуру так:

| Цель | Компонент архитектуры |
|---|---|
| 1. Онлайн-ориентация аналитика | Граф пайплайна + live-статус (§2–3), рендер мега-меню (§6) |
| 2. Отчёт для пользователя | Экспорт трассы в читаемый вид (§5.4) |
| 3. Данные для техподдержки | Тот же trace-log, доступ по `run_id` (§5) |
| 4. «Наставник / Следующий шаг» + обнаружение ошибок в Мастере | Правило-движок над уже посчитанными фактами (§7) |
| 5. Данные для статистики/банка кейсов/RAGFlow/дообучения | Append-only корпус трасс, офлайн-потребители (§9) |
| Admin-панель мониторинга | Агрегация по корпусу трасс, `Role.ADMIN` (§10) |

**Не входит в объём этой спецификации** (сознательно вынесено за скобки, чтобы не размывать ядро): сам движок RAGFlow, дообучение моделей, UI итогового банка кейсов — эти пункты только получают данные от сервиса, но не проектируются здесь.

## 2. Граф пайплайна — единый реестр узлов

Сервис не изобретает свой список этапов — он **агрегирует уже существующие** реестры узлов, которые платформа независимо ведёт по каждой вкладке:

| Вкладка | Существующий реестр | Кол-во узлов сейчас |
|---|---|---|
| Загрузка | нет CHECKS-массива — линейный флоу (структура → `target_column`/`date_column` → декомпозиция-бейджи) | 1 узел `upload.structure_confirmed` |
| Валидация | `validation/rule_resolver.py::CHECK_IDS` | 10 (`data_types`, `formats`, `ranges`, `consistency`, `uniqueness`, `inclusion`, `referential`, `text_quality`, `regularity`, `sufficiency`) |
| Предобработка | `apps/api/routers/session.py::PREPROCESSING_CHECK_IDS` | 11 (`missing`, `outliers`, `regularity`, `decomposition`, `variance_stab`, `smoothing`, `stationarity`, `spectral`, `feature_eng`, `scaling`, `passport`) |
| Разведочный EDA | `TsAnalysisEDA.tsx :: CHECKS` (id) | 11 (`descriptive`, `correlation`, `ih_analysis`, `seasonality`, `stationarity`, `distribution`, `structural`, `feature_select`, `validation_strategy`, `model_matrix`, `passport`) |
| Моделирование | линейный флоу (кандидаты → бэктест/тюнинг), не CHECKS-массив | 1 узел `modeling.model_selected` |

Проектируется новый, единственный источник истины для графа — **не дублирует**, а **ссылается** на перечисленные реестры (импортирует id-списки напрямую из существующих модулей, где это Python, и держит явную копию id EDA, единственно существующего только на фронтенде):

```python
# app/core/pipeline_graph.py (новый модуль)
"""Единый граф узлов пайплайна исследования -- источник истины для
сервиса «Прогресс». НЕ дублирует список остановок каждой вкладки:
для Python-реестров (Валидация, Предобработка) импортирует id
напрямую; для чисто-frontend реестра (EDA CHECKS, единственно
существующего в .tsx) держит копию id-списка с явным комментарием
"синхронизировать при изменении TsAnalysisEDA.tsx :: CHECKS" --
альтернатива (вынести EDA CHECKS в общий JSON/YAML, из которого читают
и фронтенд и бэкенд) вынесена в открытые вопросы §12."""

from validation.rule_resolver import CHECK_IDS as VALIDATION_STAGE_IDS
from apps.api.routers.session import PREPROCESSING_CHECK_IDS

STAGES = ("upload", "validation", "preprocessing", "eda", "modeling")

STAGE_NODES: dict[str, tuple[str, ...]] = {
    "upload": ("structure_confirmed",),
    "validation": VALIDATION_STAGE_IDS,
    "preprocessing": PREPROCESSING_CHECK_IDS,
    "eda": (  # см. предупреждение в докстринге модуля
        "descriptive", "correlation", "ih_analysis", "seasonality",
        "stationarity", "distribution", "structural", "feature_select",
        "validation_strategy", "model_matrix", "passport",
    ),
    "modeling": ("model_selected",),
}
```

**Важное замечание, требующее решения при реализации.** Оба CHECKS-массива (`TsAnalysisPreprocessing.tsx`, `TsAnalysisEDA.tsx`) содержат узел `"passport"` — по-видимому, дублирующийся артефакт (в `spec_passports.md` уже зафиксировано архитектурное решение: паспорт — не остановка степпера с pass/fail-статусом, а сквозная панель, и `"passport"` из `PREPROCESSING_CHECK_IDS`/`CHECKS` предложено убрать). Реестр графа пайплайна для «Прогресса» строится по факту реализации (либо после чистки `spec_passports.md`, либо с явным исключением `"passport"` из узлов графа на уровне `pipeline_graph.py`, независимо от того, вычищен ли он из UI-массивов).

## 3. Модель узла и статуса

Узел графа не изобретает новую статусную модель — переиспользует уже принятую платформой пятёрку (`done`/`warning`/`pending`/`skipped`/`running`/`error` — см. `StatusIcon.tsx`, `CheckStatus`), потому что «Прогресс» именно **агрегирует** те же статусы, которые уже возвращают эндпоинты `/dataset/*-profile` каждой остановки, а не вычисляет собственные.

```python
@dataclass
class PipelineNodeState:
    stage: str          # "validation" | "preprocessing" | "eda" | ...
    node_id: str         # "missing" | "outliers" | ...
    status: str           # CheckStatus, как в StatusIcon.tsx
    status_reason: str | None
    mode: str | None       # auto/enabled/disabled, где применимо (Валидация/Предобработка)
    last_touched_at: str | None   # ISO-timestamp последнего события по узлу (§4)
    summary_count: int | None      # то же число, что в правом бейдже узла (напр. total_missing)
```

Источник данных для КАЖДОГО узла — уже существующий endpoint профиля этого узла (`GET /dataset/missing-profile`, `GET /dataset/eda-structural-breaks`, и т.д.). Сервис «Прогресс» не пересчитывает статистику самостоятельно — **опрашивает** (или получает push-обновление, см. §4.2) те же эндпоинты, что и штатный UI остановки.

## 4. Трасса событий (Event Log / Trace)

### 4.1 Событие

```python
@dataclass
class TraceEvent:
    event_id: str            # uuid
    run_id: str               # см. §5 -- идентификатор "исследования", НЕ session_id
    ts: str                    # ISO-timestamp, сервер
    stage: str
    node_id: str
    event_type: str             # "profile_viewed" | "mode_changed" | "correction_previewed"
                                  # | "correction_applied" | "target_column_changed"
                                  # | "run_paused" | "run_resumed" | "checkpoint_saved"
    payload: dict[str, Any]       # см. ниже -- разный состав по event_type
    actor: str                     # "user" (сейчас единственный вариант; задел под "system"/"mentor")
```

`payload` не хранит сырые данные ряда (датасет может быть большим/чувствительным) — только **факты о решении и его результате**, тот же уровень детализации, что уже возвращают эндпоинты корректировок (`total_changed`, `strategy`, `method`, `rows_removed` и т.п. — переиспользуется форма ответа `DatasetXCorrectionResponse`, не изобретается заново).

### 4.2 Откуда берутся события — не полинг, а хук на запись

Полинг статусов всех ~34 узлов на каждый рендер мега-меню — избыточная нагрузка. Вместо этого:

- **Изменяющие эндпоинты** (`POST .../corrections`, `PUT .../check-modes`, `POST /target-column`) получают **общий middleware/декоратор**, пишущий `TraceEvent` при успешном ответе — единая точка интеграции, не требует правки каждого из ~25 уже существующих роутов вручную. Технически: FastAPI `Depends` или dispatch-middleware, читающий `request.url.path`/`response.status_code`, сопоставляющий путь с `(stage, node_id, event_type)` через статическую таблицу маршрутов (генерируется из `pipeline_graph.py` + соглашения об именовании путей, уже единообразного: `/dataset/{concept}-corrections`).
- **Читающие эндпоинты** (`GET .../profile`) генерируют событие `profile_viewed` реже — троттлинг (не чаще 1 раза на узел за N минут активности), т.к. цель — трасса решений и переходов, а не лог каждого клика.
- Статус узла в мега-меню (§6) при открытии — **живой опрос** актуальных profile-эндпоинтов только тех узлов, которые видны на экране/раскрыты, не всех разом.

## 5. Персистентность: `run_id` — не то же самое, что `session_id`

Это ключевое архитектурное решение, вынуждающее выйти за пределы уже существующего `SessionStore`.

**Почему нельзя просто расширить `AnalysisSession`.** `SessionStore` (`apps/api/session_store.py`) — TTL 30 дней, ключ — cookie браузера, in-memory или Redis. Это отлично подходит для целей 1 (онлайн-ориентация) и «паузы/восстановления» **в пределах одного браузера/устройства за 30 дней** — эти сценарии можно реализовать, просто добавив поле `pipeline_trace: list[TraceEvent]` в `AnalysisSession` без нового хранилища. **Но не подходит** для целей 2 («отчёт для пользователя» — должен переживать очистку cookie/смену устройства), 3 (техподдержка обращается по `run_id`, который пользователь называет голосом/в письме — не может звучать как cookie), 5 (корпус трасс для банка кейсов/RAGFlow должен агрегироваться **по всем пользователям**, а Redis-ключи разных cookie-сессий для этого не предназначены) и админ-панели (§10, требует SQL-подобных агрегаций по множеству запусков).

**Решение — два слоя, не один:**

1. **Внутрисессионный (использует существующий `SessionStore`, без изменений архитектуры):** `AnalysisSession.pipeline_trace: list[TraceEvent]` — короткий буфер последних событий текущего браузерного сеанса, для мгновенного рендера мега-меню без похода во внешнее хранилище. TTL = TTL сессии (30 дней), сбрасывается вместе с сессией.
2. **Долговременный, кросс-сессионный (новый слой, требует БД — впервые в проекте появляется постоянное хранилище за пределами Redis/памяти):** таблица `research_runs` (или документо-ориентированная коллекция, если проект тяготеет к NoSQL — решение по технологии вне объёма этой спецификации, важен контракт) с полями `run_id (PK, уникальный, показывается пользователю), session_id (последний известный, для связи с текущим браузером), dataset_fingerprint, target_column, created_at, last_active_at, status (active/paused/completed/abandoned)`, и связанная таблица/коллекция `trace_events` (append-only, `run_id` — внешний ключ). Именно сюда пишет middleware из §4.2 — **в дополнение** к внутрисессионному буферу, не вместо него.

`run_id` генерируется при первом событии исследования (по факту первой загрузки датасета) и **не привязан к аутентификации** (её на платформе сейчас нет для `/v1/session/*`, см. §10) — просто устойчивый уникальный идентификатор, который можно показать пользователю («Ваш номер обращения для техподдержки: `RUN-8F2A91`») и по которому можно восстановить сессию на другом устройстве (см. §5.3).

### 5.1 Чекпоинты

Чекпоинт — не отдельная сущность с собственной моделью, а **именованная ссылка на конкретное событие в trace_events** («на этот момент указывает контрольная точка N») + опциональный человекочитаемый комментарий аналитика («перед экспериментом с агрессивным сглаживанием»). Создаётся явно (кнопка «Сохранить контрольную точку» в мега-меню) — не автоматически на каждое событие, иначе чекпоинты обесцениваются количеством.

### 5.2 Пауза

«Пауза» не требует отдельного технического действия сверх уже происходящего: `AnalysisSession` и так переживает закрытие вкладки (Redis/TTL). «Пауза» на уровне UX — это просто **явная фиксация статуса `run.status = "paused"`** в `research_runs` с текущим timestamp, чтобы отличить «аналитик отошёл на 5 минут» от «аналитик сознательно поставил работу на паузу и вернётся позже» — второе учитывается в статистике платформы (цель 5) отдельно от брошенных (`abandoned`) сессий.

### 5.3 Восстановление на другом устройстве/после истечения cookie

`GET /v1/progress/runs/{run_id}/restore` — если предъявленный `run_id` валиден и его `research_runs.status != "completed"`, создаёт НОВУЮ `AnalysisSession` (новый cookie), **пере-загружает исходный датасет** (тут нужен физический доступ к сырому файлу — вне объёма этой спецификации: зависит от того, где вообще хранятся загруженные датасеты сейчас — если только в оперативной памяти процесса конкретного `AnalysisSession.dataframe`, восстановление возможно только с ПОВТОРНОЙ загрузкой исходного файла аналитиком; если появится персистентное хранилище файлов — восстановление станет автоматическим). Прогресс (какие узлы уже пройдены, какие решения приняты) восстанавливается из `trace_events`, но **сами промежуточные состояния DataFrame — нет**, если только каждое `apply=true`-событие также не сохраняет снапшот данных (дорого; в MVP не делается — см. §12, открытый вопрос).

### 5.4 Отчёт для пользователя (цель 2)

`GET /v1/progress/runs/{run_id}/report` (или `?format=pdf|html|md`) — рендерит `trace_events` в читаемый линейный отчёт: по каждому пройденному узлу — что нашли, что исправили, чем кончилось (переиспользует те же шаблоны текста, что уже пишутся для «Метрики и алгоритм» каждой остановки — терминология отчёта не изобретается заново). Не в объём MVP реализации, но контракт эндпоинта фиксируется здесь, чтобы модель `trace_events` проектировалась с расчётом на такой рендер (человекочитаемый `payload`, а не сырые числа без единиц).

## 6. Мега-меню — frontend

### 6.1 Точка входа

Пункт «Прогресс» в существующем главном меню (`PortalNavBar`/`ModuleNav`, `packages/ui`) открывает оверлей/модальное мега-меню (аналогично уже существующим полноэкранным паттернам платформы, напр. `TsAnalysisNavigator`) — не отдельная страница/роут, чтобы не терять контекст текущей вкладки под ним.

## 7. «Наставник» — правило-движок

Как согласовано в обсуждении: **без LLM в реальном времени**. Наставник решает ДВЕ разных по природе задачи, которые в этой спецификации сознательно разведены на два независимых потока правил с разными триггерами:

- **§7.1 «Следующий шаг»** — проактивная навигация по графу: что делать дальше, куда идти.
- **§7.2 «Обнаружение ошибок в Мастере»** — реактивная проверка результата ТОЛЬКО ЧТО совершённого действия: не ошибся ли аналитик в выборе метода/параметра.

Обе используют общий тип правила и общий текстовый рендерер (§8), но разные источники данных и разные точки вызова в UI.

### 7.1 «Следующий шаг» (навигация по графу)

```python
# app/core/mentor_rules.py (новый модуль)

@dataclass
class MentorRule:
    rule_id: str
    stage: str
    trigger: str                       # "on_demand" (§7.1) | "on_correction_result" (§7.2)
    condition: Callable[..., bool]       # чистая функция, без побочных эффектов; сигнатура
                                           # зависит от trigger -- см. §7.1/§7.2
    priority: int                         # порядок применения при нескольких сработавших правилах
    explanation_template: str              # параметризованный текст, тот же стиль,
                                              # что уже используют METRICS_DESCRIPTION-константы
    recommended_action: str | None          # deep-link на конкретный узел/вкладку, если есть

# Пример правила "Следующий шаг" (trigger="on_demand", condition: (nodes) -> bool):
MentorRule(
    rule_id="regularity_before_decomposition",
    stage="preprocessing",
    trigger="on_demand",
    condition=lambda nodes: (
        _status(nodes, "preprocessing", "regularity") == "warning"
        and _status(nodes, "preprocessing", "decomposition") in ("pending", "skipped")
    ),
    priority=10,
    explanation_template=(
        "В ряде остались нарушения регулярности временного шага. "
        "STL-декомпозиция и спектральный анализ требуют равномерной сетки дат — "
        "рекомендуем сначала исправить регулярность."
    ),
    recommended_action="preprocessing.regularity",
)
```

`GET /v1/progress/runs/{run_id}/mentor/next-step` — прогоняет текущее состояние графа (`list[PipelineNodeState]`) через отсортированный по `priority` список `trigger="on_demand"`-правил, возвращает **первое** сработавшее (не весь список — Наставник даёт ОДНУ рекомендацию за раз, не заваливает советами) + текст пояснения текущей фазы (шаблон по последнему активному `stage`) + краткую сводку уже полученных выводов (агрегация `summary_count`/`status_reason` уже пройденных узлов той же стадии — не новая аналитика, а **пересказ уже посчитанного**). Вызывается по кнопке «Наставник» в мега-меню (`MentorPanel.tsx`).

### 7.2 Обнаружение ошибок в Мастере (реактивная проверка результата)

**Мотивация.** Каждый Мастер исправления (Пропуски/Выбросы/Регулярность и далее по мере реализации остальных остановок) уже показывает блок «Прогноз влияния на статистики» на шаге «Предпросмотр» — но это просто ЧИСЛА (до→после), интерпретация которых целиком лежит на аналитике. Аналитик может не заметить, что: выбранный метод по факту ничего не исправил (неверный порог/параметр), исправление оказалось избыточно агрессивным (переглаживание, схлопывание дисперсии), или задел не ту колонку. Наставник должен уметь читать те же самые уже вычисленные числа (`stats_before`/`stats_after`, `changed_count`, `still_missing`/`still_outliers`, `rows_removed` — везде уже присутствуют в `DatasetXCorrectionResponse`) и явно предупреждать о характерных паттернах ошибки — **не запрещая действие**, а показывая предупреждение до подтверждения.

**Ключевое архитектурное решение: проверка встраивается в шаг «Предпросмотр» (`preview=true`, ДО применения), а не постфактум после `apply=true`.** Тем самым аналитик видит предупреждение прежде, чем нажмёт «Применить исправления» — тот же принцип, что уже действует в самом Мастере («preview → confirm → apply»), Наставник просто добавляет ещё один сигнал в ту же точку принятия решения, не создавая отдельный шаг.

```python
@dataclass
class SanityWarning:
    rule_id: str
    severity: str            # "info" | "warning"
    message: str
    suggested_action: str | None    # человекочитаемая подсказка ("попробуйте порог 3.0 вместо 1.5")

@dataclass
class CorrectionOutcomeSummary:
    """Нормализованная проекция того, что уже возвращает preview-ответ
    ЛЮБОГО мастера (Missing/Outliers/Regularity/...) -- не новые
    вычисления, только переупаковка уже существующих полей ответа
    в общую форму, чтобы правила §7.2 не знали про специфику
    конкретного мастера."""
    stage: str
    node_id: str
    strategy: str
    method: str | None
    affected_count_before: int          # missing_count / outlier_count / total_violations
    changed_count: int
    still_affected_count: int            # still_missing / still_outliers / total_violations_after
    rows_before: int
    rows_after: int
    stats_before: dict[str, float] | None   # mean/std/median, где применимо
    stats_after: dict[str, float] | None


def rule_no_effect(outcome: CorrectionOutcomeSummary) -> SanityWarning | None:
    """Стратегия выбрана, но по факту ничего не изменила -- типичный
    признак: порог/метод слишком мягкий, либо выборка слишком мала."""
    if outcome.affected_count_before > 0 and outcome.changed_count == 0:
        return SanityWarning(
            rule_id="no_effect",
            severity="warning",
            message="Выбранная стратегия не изменила ни одного значения.",
            suggested_action="Проверьте параметр/порог метода или попробуйте другой метод обнаружения.",
        )
    return None


def rule_over_aggressive(outcome: CorrectionOutcomeSummary) -> SanityWarning | None:
    """Стандартное отклонение после исправления схлопнулось намного
    сильнее, чем можно объяснить долей затронутых значений -- признак
    переглаживания/слишком грубой стратегии (напр. замена медианой
    большой доли выборки)."""
    if not (outcome.stats_before and outcome.stats_after):
        return None
    std_before, std_after = outcome.stats_before.get("std"), outcome.stats_after.get("std")
    if std_before and std_after is not None and std_after < std_before * 0.2:
        return SanityWarning(
            rule_id="over_aggressive",
            severity="warning",
            message="После исправления стандартное отклонение упало более чем в 5 раз — возможно, стратегия слишком агрессивна для этой доли данных.",
            suggested_action="Рассмотрите менее жёсткую стратегию (например, флаг вместо замены) или уточните порог метода.",
        )
    return None


def rule_excessive_data_loss(outcome: CorrectionOutcomeSummary) -> SanityWarning | None:
    """drop_rows/ресемплирование удалило значительную долю датасета --
    типичный признак слишком узкого порога или ошибочно выбранной колонки."""
    if outcome.rows_before == 0:
        return None
    removed_share = 1 - (outcome.rows_after / outcome.rows_before)
    if outcome.strategy == "drop_rows" and removed_share > 0.3:
        return SanityWarning(
            rule_id="excessive_data_loss",
            severity="warning",
            message=f"Стратегия удалит {removed_share:.0%} строк датасета.",
            suggested_action="Проверьте, не завышен ли порог метода, и не задета ли колонка, которую вы не собирались исправлять.",
        )
    return None
```

`POST /v1/progress/mentor/sanity-check` — принимает `CorrectionOutcomeSummary` (frontend строит его из уже полученного preview-ответа конкретного Мастера — маппинг тривиален, разный набор полей у Missing/Outliers/Regularity сводится к общим именам на клиенте перед отправкой), прогоняет через ВСЕ `trigger="on_correction_result"`-правила (в отличие от §7.1, здесь возвращается **весь список** сработавших предупреждений, а не одно — разные проблемы независимы и не взаимоисключающи), рендерит `MentorInlineWarning.tsx` над кнопкой «Применить исправления» в каждом Мастере.

**Правило "мечется" (`thrashing`) — отдельный, требующий истории `trace_events`, а не одного preview-ответа.** Если один и тот же узел за короткое окно (напр. 10 минут) многократно исправляется чередующимися стратегиями без итогового применения (несколько `correction_previewed` без единого `correction_applied`, либо применение → повторное применение другой стратегией → повторное… — паттерн «аналитик пробует всё подряд») — это не проверяется на одном preview-ответе, а требует чтения последних N событий `trace_events` того же `run_id`/`node_id`. Реализуется как `trigger="on_demand_with_history"` — третий вид триггера, вызывается не при каждом preview (дорого гонять историю на каждый клик), а при открытии мега-меню/Наставника, и предупреждение показывается уже там, а не инлайн в Мастере:

```python
MentorRule(
    rule_id="thrashing_detected",
    stage="preprocessing",  # или любая
    trigger="on_demand_with_history",
    condition=lambda recent_events: (
        len({e.payload.get("strategy") for e in recent_events if e.event_type == "correction_previewed"}) >= 3
        and not any(e.event_type == "correction_applied" for e in recent_events)
    ),
    priority=5,
    explanation_template=(
        "На этой остановке опробовано несколько разных стратегий подряд без применения ни одной. "
        "Если не уверены в выборе — посмотрите раздел «Оценка методологии» в «Метрики и алгоритм» этой остановки, "
        "или зафиксируйте промежуточный результат чекпоинтом и продолжите позже."
    ),
    recommended_action=None,  # осознанно без deep-link -- это не "куда идти", а "как решать", рекомендация другого типа
)
```

**Пороговые значения эвристик (`0.2`, `0.3`, окно `10 минут`, `3` разных стратегии) — не окончательные, требуют калибровки на реальном использовании платформы.** Вынесены в конфигурацию (не хардкод), см. §12.

## 8. Точка расширения LLM (не реализуется сейчас)

Контракт зафиксирован здесь заранее, чтобы включение LLM позже не потребовало переписывать §7:

```python
class MentorTextRenderer(Protocol):
    """Единственная точка, где мог бы появиться LLM: ПЕРЕФОРМУЛИРОВКА
    уже вычисленного правило-движком факта (rule_id + параметры шаблона),
    НЕ вычисление самого факта/рекомендации/предупреждения. Дефолтная
    реализация -- просто .format() шаблона, без сети/модели. Применимо
    одинаково и к §7.1 (следующий шаг), и к §7.2 (sanity-предупреждения)."""
    def render(self, rule: MentorRule, context: dict[str, Any]) -> str: ...
```

Если понадобится: добавляется `LLMMentorTextRenderer(MentorTextRenderer)` за фиче-флагом, вызывается ПОСЛЕ того, как правило-движок уже определил `rule_id`/`recommended_action`/`severity` — LLM никогда не выбирает рекомендацию или не решает, есть ли ошибка, и не имеет доступа к сырым данным ряда, только к уже агрегированным текстовым фактам (тот же принцип, что уже использован в позиции по паспортам: LLM — рендерер, не источник истины).

## 9. Данные для аналитики/банка кейсов/RAGFlow/дообучения (цель 5)

Всё потребляет один и тот же корпус `trace_events` (§5), офлайн, батчем — не в горячем пути аналитика:

| Потребитель | Как использует корпус |
|---|---|
| Статистика платформы | SQL/агрегация по `research_runs`/`trace_events` (какие узлы чаще всего дают `warning`, средняя длительность стадии, доля `abandoned`, частота срабатывания правил §7.2 — сигнал, какие Мастера чаще всего приводят к ошибкам аналитиков) |
| Банк кейсов | Отбор кандидатов — алгоритмическая эвристика (`run.status == "completed"`, финальный бэктест-скор выше порога, малое число `warning`-узлов и малое число сработавших `on_correction_result`-предупреждений на выходе — т.е. «чистые», без метаний, прохождения) → отобранные `run_id` идут в офлайн-процесс суммаризации трассы в читаемый кейс (**вот здесь у LLM легитимная роль уже сейчас в дизайне, но как офлайн-джоба, не часть этого сервиса** — вынесено в отдельный будущий тикет) |
| RAGFlow | Индексирует сгенерированные кейсы (не сырые `trace_events`) |
| Дообучение моделей | Отдельный офлайн-экспорт корпуса, вне объёма этой спецификации |

`trace_events` проектируются как **обезличиваемые по построению** — `payload` не содержит значений ряда, только факты о решениях (методы/стратегии/статусы), что снимает часть вопросов приватности до того, как они встанут остро.

## 10. Admin-панель мониторинга

Использует уже существующую ролевую модель (`apps/api/plans.py::Role.ADMIN`, `apps/api/auth.py::require_capability`) — **не изобретает новую систему прав**. Важное ограничение: `Role`/`require_capability` сейчас защищают `/v1/public`/`/v1/models` (API-ключ), а не `/v1/session/*` (cookie-based, без API-ключа) — микросервис «Прогресс» естественно живёт в `/v1/session/*` для аналитика, но admin-эндпоинты (`GET /v1/progress/admin/*`) должны требовать API-ключ с ролью `ADMIN`, а не cookie — то есть админ заходит другим путём, чем обычный аналитик (соответствует уже принятому на платформе разделению `internal`/`public`/`session`).

Состав панели (агрегаты по `research_runs`/`trace_events`, без раскрытия содержимого конкретных датасетов пользователей):
- Активные/приостановленные/завершённые запуски за период.
- Распределение времени по стадиям (где аналитики чаще всего застревают).
- Топ узлов с `status=warning`/`error` (какие проверки чаще всего требуют вмешательства — сигнал для приоритизации будущих улучшений методологии).
- Частота срабатывания правил «Следующий шаг» (§7.1) — какие рекомендации даются чаще всего.
- **Частота срабатывания sanity-предупреждений (§7.2) по правилу и по узлу** — прямой сигнал, где аналитики чаще всего ошибаются в выборе метода/параметра, и, соответственно, где в первую очередь стоит улучшать методические подсказки/дефолтные значения параметров в самих Мастерах.

## 11. Поэтапный план реализации

Учитывает текущее состояние платформы (Валидация — 10/10 узлов реальны; Предобработка — 6/11; EDA — большинство узлов уже реальны после последнего мержа):

1. **Этап 0 — граф + внутрисессионная трасса.** `app/core/pipeline_graph.py`, `PipelineNodeState`, расширение `AnalysisSession.pipeline_trace` (без нового хранилища), мега-меню читает только текущую сессию — уже даёт цель 1 (онлайн-ориентация) полностью, без БД.
2. **Этап 1 — долговременное хранилище.** `run_id`, `research_runs`/`trace_events`, восстановление в пределах того же браузера (§5.3 частично — без повторной загрузки файла, т.к. `AnalysisSession.dataframe` ещё жива в TTL) — даёт цели 2/3.
3. **Этап 2 — Наставник v1: «Следующий шаг» (§7.1).** `mentor_rules.py` с 5-10 правилами для уже реализованных узлов (Пропуски/Выбросы/Регулярность/Декомпозиция/Стабилизация дисперсии/Сглаживание) — даёт цель 4 (навигационная часть). Расширяется по мере появления новых остановок, не блокирует их разработку.
4. **Этап 2.1 — Наставник v1.1: sanity-предупреждения в Мастере (§7.2).** `POST /v1/progress/mentor/sanity-check` + 3-4 базовых правила (`no_effect`, `over_aggressive`, `excessive_data_loss`) для уже реализованных Мастеров, `MentorInlineWarning.tsx` в каждом из них. Правило `thrashing_detected` — после появления `trace_events` (зависит от Этапа 1).
5. **Этап 3 — офлайн-потребители.** Экспорт корпуса, отбор кандидатов в банк кейсов (эвристика, без LLM) — даёт часть цели 5.
6. **Этап 4 — admin-панель.** §10, после появления реальных данных за 2-3 недели использования (иначе агрегаты пустые/неинформативные).
7. **Этап 5 (отдельный будущий тикет, не в этой спецификации) — LLM-суммаризация кейсов и/или `LLMMentorTextRenderer`.**

## 12. Открытые вопросы (решение — за тимлидом до реализации)

1. **Технология долговременного хранилища (§5)** — SQL (Postgres) vs документная БД vs расширение существующего Redis с отдельным неистекающим namespace. Влияет на схему `research_runs`/`trace_events`, не на контракт эндпоинтов.
2. **EDA CHECKS как единственный frontend-only реестр (§2)** — стоит ли выносить в общий YAML/JSON, читаемый и `TsAnalysisEDA.tsx`, и `pipeline_graph.py`, чтобы не дублировать список id вручную (риск рассинхронизации при добавлении новых узлов EDA).
3. **Восстановление сырых данных на другом устройстве (§5.3)** — требует решения, где вообще персистентно хранятся загруженные датасеты (сейчас предположительно только в памяти процесса конкретной `AnalysisSession`); без этого «восстановление» ограничено метаданными трассы, не полным состоянием.
4. **Снапшоты DataFrame на каждый чекпоинт** — дорого по месту, но даёт настоящий откат «вернуться к состоянию на контрольной точке», а не только к списку событий. Решить, входит ли это в MVP.
5. **Очистка дублирующегося узла `"passport"`** в `PREPROCESSING_CHECK_IDS`/EDA `CHECKS` (см. §2) — синхронизировать с решением по `spec_passports.md`.
6. **Гранулярность троттлинга `profile_viewed`-событий (§4.2)** — конкретный интервал не зафиксирован, требует эмпирической настройки после первых недель эксплуатации.
7. **Пороговые значения sanity-эвристик §7.2** (`0.2` для схлопывания std, `0.3` для доли удалённых строк, окно `10 минут`/`3` стратегии для `thrashing`) — предложены как разумные дефолты по аналогии с уже принятым на платформе IQR-множителем 1.5, но не выведены эмпирически; требуют калибровки по реальному использованию и, вероятно, должны стать настраиваемыми per-node, а не глобальной константой (то, что для «Выбросов» — норма, для «Сглаживания» может быть намеренным эффектом, а не ошибкой).
8. **Должен ли `MentorInlineWarning` блокировать кнопку «Применить исправления» или только предупреждать?** Спецификация проектирует **не блокирующее** предупреждение (аналитик может осознанно продолжить — например, экстремальное сглаживание иногда осознанный выбор) — но финальное UX-решение (soft warning vs hard confirm-диалог с доп. подтверждением) — за дизайном/тимлидом.
