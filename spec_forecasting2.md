## 1. Место в архитектуре — это не новая ветка, а уже анонсированный этап

`apps/api/session_store.py::STAGES` уже содержит шестой этап:
```python
STAGES = ("upload", "validation", "preprocessing", "eda", "modeling", "forecasting")
```
«Прогнозирование» — не гипотетическое расширение, а зарезервированный, но нереализованный этап. Точка входа — уже существующий **Model Card** (`apps/api/routers/modeling_session.py::create_model_card`/`get_model_card`, `session.modeling_pipeline["model_card"]`): к моменту, когда Model Card создан, зафиксированы `model_id`, `hyperparameters` (замороженные после тюнинга), `training.preprocessing` (fold-safe цепочка трансформаций), `performance.backtest_metrics`, `traceability.comparison_signature`/`diagnostics_signature`. Прогнозирование **потребляет** эти артефакты, не создаёт собственную модель заново и не переоткрывает вопрос «какая модель лучше» — этот вопрос уже закрыт этапом «Моделирование».

Сам Model Card уже честно декларирует пробел, который закрывает эта спецификация:
```
"limitations": [..., "Prediction intervals и их coverage ещё не реализованы в production backtest."]
```

То, что `forecasting` — шестой и последний элемент кортежа `STAGES`, а не пятый (после `modeling`), не случайно и для другой, независимой от Model Card, причины: это ровно тот порядок, в котором боковая панель «Прогресс исследования TS» (§9) отрисовывает узлы блок-схемы общего пайплайна — Прогнозирование обязано быть её последним узлом уже сейчас, по факту положения в `STAGES`, без дополнительного согласования при реализации панели.

## 2. Методологическая оценка текущей цепочки Загрузка → Валидация → Предобработка → EDA → Моделирование

Коротко, по существу вопроса (детальный аудит каждой из ~35 остановок не требуется — оценивается архитектурная состоятельность цепочки как основы для прогнозирования):

**Сильные стороны, подтверждённые прочтением кода, а не только докстрингов:**
- **Leakage-safe backtest** — `FoldLocalTargetPreprocessor`/`prepare_modeling_target` (`apps/api/fold_preprocessing.py`) применяют трансформации (стабилизация дисперсии, разности, масштабирование) **внутри каждого фолда отдельно**, не на всём ряду разом — исключает утечку информации о будущем в параметры трансформации прошлого. Это методологически необходимое, но часто игнорируемое на практике условие корректного бэктеста временных рядов.
- **Точное согласование OOF** (`apps/api/modeling_comparison.py::aligned_oof`, `_point_key`) — сравнение моделей идёт по строго совпадающим точкам (fold, horizon_step, index), а не по агрегатам, которые могли бы скрыть несопоставимость выборок между моделями.
- **Сквозная трассируемость** (`apps/api/modeling_workflow.py`) — ~30 источников (каждая проверка Валидации/остановка Предобработки/анализ EDA) явно объявляют, в какие стадии Моделирования они фидят факты — само по себе методологическая гарантия, что решения на этапе Моделирования опираются на прослеживаемые основания, а не на непрозрачный чёрный ящик.
- **Разделение применимости и production-готовности модели** (Task 95) — методологически корректное разделение «эта модель статистически уместна для этих данных» и «эта модель реализована и надёжна в проде» — распространённая путаница в предметной области, которую платформа явно не допускает.
- **Diagnostics-gated сравнение** — модели сравниваются только после диагностик остатков, не по голому значению метрики.

**Единственный содержательный пробел** (не методологическая ошибка цепочки, а не законченная часть пайплайна): бэктест оценивает точность на **известном прошлом** (OOF-фолды), но ничего не говорит о неопределённости **будущего** прогноза — ни доверительных интервалов, ни рефита на полных данных для реального прогноза вперёд. Это ожидаемо (бэктест и прогноз — разные по определению задачи), и это ровно тот пробел, который закрывает данная спецификация. Иных методологических нарушений в проверенных модулях не найдено.

## 3. Ключевое архитектурное решение: финальный рефит (Final Fit), а не переиспользование фолдов

Бэктест обучает модель на **части** истории (train-фолд) и проверяет на будущих относительно фолда точках — так измеряется обобщающая способность. Для реального прогноза вперёд это неверная основа: если обучить только на train-фолде последнего окна бэктеста, часть уже известных данных (test-хвост последнего фолда) останется неиспользованной — стандартная и методологически обязательная практика (Hyndman & Athanasopoulos, гл. 5.9 — «после кросс-валидации модель переобучается на всех доступных данных перед реальным прогнозом») — переобучить модель **на всей доступной истории** с уже подобранными (замороженными на этапе тюнинга) гиперпараметрами, не переподбирая их заново.

**Новый компонент (переиспользует, а не дублирует существующую трансформационную логику):**

```python
# apps/api/final_fit.py (новый модуль)
"""Финальный рефит модели на всей доступной истории для реального
прогноза вперёд -- НЕ бэктест-фолд. Переиспользует ту же трансформацию,
что и FoldLocalTargetPreprocessor (apps/api/fold_preprocessing.py), но
применяет её ОДИН раз к полному ряду, а не по фолдам, и без повторного
подбора гиперпараметров (они уже заморожены в Model Card)."""

from apps.api.fold_preprocessing import _resolve_chain, _make_scaler, _stationarity_forward, _inverse_stationarity
from apps.api.backtesting import PRODUCTION_PREDICTORS

@dataclass
class FinalFitResult:
    model_id: str
    transformed_series: np.ndarray      # ряд после forward-трансформации, на чём реально обучалась модель
    transform_state: dict[str, Any]      # параметры инверсии (не пересчитываются -- фиксируются здесь)
    fit_metadata: dict[str, Any]          # что реально произошло при рефите (для трассы, §9)

def final_fit(series: pd.Series, model_card: dict[str, Any]) -> FinalFitResult:
    chain = _resolve_chain(model_card["training"]["preprocessing"])   # та же цепочка, что уже в Model Card
    transformed, state = chain.apply_forward(series.to_numpy())        # один раз, на всём ряду
    return FinalFitResult(
        model_id=model_card["model_id"],
        transformed_series=transformed,
        transform_state=state,
        fit_metadata={"n_observations": len(series), "refit_at": _now_iso()},
    )
```

Прогноз генерируется вызовом уже существующего `PRODUCTION_PREDICTORS[model_id]` (`apps/api/backtesting.py`) на `transformed_series` с горизонтом `h` и замороженными `hyperparameters` из Model Card — **не новый код предсказания**, тот же реестр предикторов (ETS/Theta/ARIMA/Auto-ARIMA/базовые), который уже используется бэктестом, вызывается здесь на полном ряду вместо train-фолда. Обратная трансформация — `_inverse_stationarity`/обратный `scaler` — та же функция, что уже инвертирует прогноз фолда в бэктесте, применяется здесь к финальному прогнозу.

**Важный нюанс для доверительных интервалов (не только точки прогноза):** обратная трансформация в общем случае нелинейна (`log_difference`, `seasonal_difference` и т.п. — см. `_inverse_stationarity`) — обратное преобразование **границ** интервала не сводится к применению прямой трансформации к готовому интервалу в исходной шкале. Верхняя/нижняя граница считаются в ТРАНСФОРМИРОВАННОМ пространстве (`точка ± z·SE`), и только затем **каждая граница по отдельности** проходит через ту же нелинейную `_inverse_stationarity`, что и точка прогноза — иначе для мультипликативных/логарифмических трансформаций интервал в исходной шкале будет асимметричен неправильно (или симметричен там, где не должен быть).

## 4. Доверительные интервалы — методологический выбор по семейству модели, а не единый метод

Единого способа посчитать интервал для всех моделей реестра не существует — они разной статистической природы. Решение — **три метода** (не два, см. уточнение по итогам §10, п.3), выбор автоматический по `model_id`, ни один не альтернативен другим в рамках своей группы:

### 4.1 Аналитический метод — раздельно по фактическому API каждой модели, не единой формулой
Проверено по факту вызовом на установленной версии `statsmodels==0.15.0` (закреплённой в `requirements.txt`), а не предположено по документации — три разных класса дают три разных, несовместимых API:
- **ARIMA/Auto-ARIMA** (`statsmodels.tsa.arima.model.ARIMA`, см. `apps/api/model_impls/arima.py`) — `model.fit().get_forecast(steps).summary_frame(alpha)` → `mean_ci_lower`/`mean_ci_upper`. Классический state-space Gaussian-интервал.
- **Theta** (`statsmodels.tsa.forecasting.theta.ThetaModel`, см. `apps/api/model_impls/theta.py`) — **другой метод**, `ThetaModelResults.prediction_intervals(steps, theta, alpha)`, замкнутая формула на основе IMA-выведенной дисперсии (`σ²(1+(h-1)(1+(α-1)²))`), не `get_forecast().conf_int()` — этого метода на `ThetaModelResults` не существует.
- **Prophet, TBATS** — интервалы уже встроены и подтверждены реестром `MODEL_EXECUTION_REGISTRY` (`apps/api/model_execution.py`, `supports_prediction_intervals=True` для `prophet`/`tbats`, Task 124/125) — переиспользуются напрямую, без нового кода: адаптеры `_prophet_fit_predict`/`_tbats_fit_predict` уже возвращают `(forecast, lower, upper)` на произвольный горизонт.

### 4.1a Параметрическая симуляция (ETS, ETS damped) — третий метод, не аналитический и не эмпирический
Платформа использует `statsmodels.tsa.holtwinters.ExponentialSmoothing` (классический Holt-Winters API, см. `apps/api/model_impls/ets.py`, где это явно закомментировано как сознательный выбор — не полная state-space `ETSModel`). Проверено: у `HoltWintersResults` **нет** `get_forecast`/`conf_int` — аналитического интервала из коробки не существует для этого API. Но есть `HoltWintersResults.simulate(nsteps, repetitions=N, ...)` — параметрическая (Monte-Carlo) симуляция на основе дисперсии подобранных инноваций самой модели; интервал строится как эмпирический квантиль по `N` симулированным траекториям. Это не то же самое, что метод §4.2 (эмпирический квантиль по OOF-остаткам бэктеста той же модели): здесь квантиль берётся по внутренним симуляциям одной подобранной на всём ряде модели, а не по истории её OOF-ошибок на разных фолдах — качественно иной источник неопределённости, точнее отражающий именно параметрическую неопределённость ETS.

### 4.2 Эмпирический метод на основе OOF-остатков бэктеста (обязателен для baseline-моделей без аналитической формы — naive/seasonal_naive/drift/mean)
Бэктест **уже** хранит OOF-предсказания и остатки, индексированные по `(fold, horizon_step, ...)` (`apps/api/modeling_comparison.py::_indexed_oof`). Эмпирический интервал для горизонта `h` строится по эмпирическим квантилям остатков **того же `horizon_step`** из истории бэктеста той же модели (не единая дисперсия на все шаги горизонта — неопределённость растёт с горизонтом, и это уже видно из уже собранных данных, не нужно постулировать рост аналитически):
```
interval(h) = forecast(h) + quantile(oof_residuals[model_id, horizon_step=h], [alpha/2, 1-alpha/2])
```
Не новая статистика — **переиспользование** уже посчитанных и сохранённых `oof_predictions` из Model Card/бэктеста. **Жёсткое ограничение, не мягкая рекомендация**: данные для `interval(h)` физически существуют только для `h ≤ training.horizon` (максимальный `horizon_step`, реально проверенный бэктестом) — для `h` за этой границей квантиль считать не из чего (см. §10, п.1 — это прямое следствие того же факта, что определяет порог предупреждения о горизонте).

### 4.3 Закрытие декларированного пробела Model Card: `prediction_interval_coverage`
Раз эмпирический метод уже даёт интервалы для каждой исторической OOF-точки (пересчитав интервалы «задним числом» на всех фолдах бэктеста), можно посчитать **фактическое покрытие** — долю OOF-точек, реально попавших в свой интервал, против номинального уровня (`95%` номинально → сколько на деле). Это ровно то поле, которое Model Card сейчас держит как `None` с пометкой «не реализовано» — модуль Прогнозирования его заполняет, замыкая обещание, данное на этапе Моделирования.

## 5. Требования пользователя → архитектурные решения

### 5.1 Генерация прогноза на горизонт
`FinalFitResult` (§3) → `PRODUCTION_PREDICTORS[model_id](transformed_series, horizon, period, hyperparameters)` → обратная трансформация (§3) → `ForecastPoint[]`. Горизонт по умолчанию — тот же, что использовался при тюнинге/бэктесте (Model Card уже хранит `training.horizon`); пользователь может запросить другой горизонт. Порог предупреждения — не откалиброванный эвристически множитель, а точная, уже имеющаяся в данных граница: **`horizon > training.horizon`** (запрошено больше, чем реально проверено бэктестом — это факт, а не оценка). Строгость реакции зависит от `ci_method` (§4), а не одинакова для всех моделей:
- `ci_method = "empirical_oof_quantile"` (§4.2, baseline-модели) — это не мягкое предупреждение, а функциональное ограничение: квантиль остатков для `horizon_step > training.horizon` физически не существует. Для шагов за этой границей интервал не экстраполируется молча — используется квантиль последнего валидированного шага (`horizon_step = training.horizon`) с явным флагом в `warnings` («интервал для шагов N+ — консервативная оценка по последнему проверенному шагу, не валидирован эмпирически»), чтобы прогноз не обрывался визуально без ленты неопределённости.
- `ci_method = "analytic"`/`"parametric_simulation"` (§4.1/§4.1a) — формула/симуляция математически определена на любом горизонте, здесь это действительно мягкое предупреждение (текст в `warnings`, интервал считается как обычно) — модель экстраполирует свою же структуру дальше проверенного диапазона, что расширяет, а не аннулирует её обоснованность.

### 5.2 Доверительные интервалы
§4. Уровень доверия (`alpha`) — параметр запроса, по умолчанию `0.05` (95%), не хардкод.

### 5.3 Визуализация
Один график: факт (историческая часть ряда) + линия прогноза (продолжение той же линии другим цветом/пунктиром от последней фактической точки) + закрашенная область между верхней/нижней границей интервала + точки прогноза поверх линии (маркеры на каждом шаге горизонта, для явного считывания конкретных значений при наведении). Технически — `recharts`, тот же стек, что и `TimeSeriesLineChart.tsx`/`BacktestOofChart.tsx`, уже используемые платформой для похожих составных графиков (факт+модель) — не новая библиотека, композиция `Area` (для интервала) + `Line` (факт, прогноз) + `Scatter`/`dot` (точки прогноза) в одном `ComposedChart`.

### 5.4 Детальная статистика (MAE/MSE/RMSE/MAPE)
**Методологическая оговорка, обязательная к отражению в UI, а не только здесь:** для реального будущего прогноза эти метрики **не вычисляются заново** — у будущих точек нет фактических значений для сравнения, посчитать «ошибку прогноза» до наступления будущего невозможно ни алгоритмически, ни любым другим способом. То, что показывается рядом с прогнозом — это **исторические метрики точности той же модели**, уже посчитанные на бэктесте (`model_card["performance"]["backtest_metrics"]`, где MASE уже есть, MSE ранее не хранился отдельно — добавляется как `rmse**2`, тривиально, без нового расчёта) — переиспользуются, не пересчитываются. Формулировка в UI: «Ожидаемая точность (по результатам бэктеста)», не «Точность этого прогноза» — разница принципиальна и обязана быть видна пользователю, иначе платформа неявно обещает то, что физически недостижимо.

### 5.5 Экспорт (CSV/JSON — backend; PNG/PDF — клиентски)
- `GET /v1/session/modeling/forecast/{forecast_id}/export.csv` — `date, actual (историческая часть, где есть), forecast, ci_lower, ci_upper`.
- `GET /v1/session/modeling/forecast/{forecast_id}/export.json` — весь `ForecastRun` целиком (§7), включая `model_card` ссылку, метрики, параметры — самодостаточный файл, не требующий доступа к сессии для интерпретации (важно для цели «данные для техподдержки»/отчёта).
- **PNG/PDF — без backend-роута** (проверено: в кодовой базе нет ни одного существующего механизма экспорта графика ни на клиенте, ни на сервере — `grep` по `html2canvas`/`jspdf`/`toDataURL`/PDF-библиотекам в `apps/api/requirements.txt` не дал ни одного совпадения). Экспорт реализуется целиком на клиенте в `ForecastExportMenu.tsx` (§8): PNG — сериализация уже отрисованного `<svg>` узла `ForecastChart.tsx` (`recharts` — чистый SVG) через `XMLSerializer` → `<canvas>` → `toBlob()`, без новых зависимостей, серверный рендеринг не нужен. PDF — тот же PNG плюс краткая таблица метаданных прогноза (`model_card_id`, `horizon`, `alpha`, `expected_accuracy`), собранные единственной новой лёгкой клиентской зависимостью `jspdf` (~30 КБ) — не заводится второй, серверный путь генерации PDF ради этой не критичной для сессии функции.

### 5.6 Сравнение прогнозов от разных моделей
Не отдельная сущность — тот же экран, но с несколькими `model_id` из уже существующего Model Comparison (Task 96) вместо одного: строится `FinalFitResult`/прогноз для каждой из выбранных (например, топ-3 по уже посчитанному сравнительному рейтингу), накладываются на один график разными цветами линий (интервалы — полупрозрачными областями, чтобы не перегружать). Не вводит новую логику ранжирования моделей — использует уже посчитанный `comparison_id`/ранжирование.

### 5.7 Анализ чувствительности к изменению параметров
Не произвольное варьирование параметров — **в границах уже исследованного пространства тюнинга** (`rules/modeling.yaml::param_space`, уже определяющий допустимые диапазоны для каждой модели, использованные на этапе тюнинга). Генерируется веер прогнозов при значениях гиперпараметров на границах/квартилях уже исследованного диапазона (не произвольно широкий диапазон, значения за пределами исследованного тюнингом пространства не были статистически проверены на этих данных и показывать по ним прогноз было бы неоправданным). Визуализация — тот же график §5.3, дополнительные полупрозрачные линии вариаций поверх основного прогноза.

### 5.8 Автоматическое выявление аномалий в прогнозных значениях
Не новая логика детекции — **переиспользование уже реализованного модуля** `app/preprocessing/outliers.py::detect_outlier_mask` (IQR/Z-score/MAD), применённого к объединению «исторический ряд + прогнозные точки»: если прогнозная точка регистрируется как выброс относительно статистики исторического ряда — это сигнал (не запрет), что прогноз резко расходится с предысторией, возможно, model экстраполирует неустойчиво на этом горизонте. Тот же принцип, что уже принят для sanity-правил Наставника (`progress_ts_analysis.md §7.2`) — предупреждение, не блокировка.

### 5.9 История прогнозов + документирование параметров/условий
Не отдельный, изолированный механизм — прогноз запускается как ещё один трассируемый артефакт в общей модели трассировки исследования (`TraceEvent`), которую отдельно потребляет боковая панель «Прогресс исследования TS» — её цели и UI зафиксированы тимлидом (§9), это больше не гипотетический, неопределённого статуса сервис, как трактовалось в версии 1 этой спецификации.

Каждая операция модуля Прогнозирования, видимая пользователю как отдельный шаг, порождает свой `event_type`, а не единый общий:

- `forecast_generated` — payload: `model_card_id`, `horizon`, `alpha`, `ci_method`, `forecast_id`
- `forecast_compared` — payload: `model_card_ids[]`, `forecast_ids[]` (§5.6)
- `forecast_sensitivity_computed` — payload: `forecast_id`, `varied_params` (§5.7)
- `forecast_exported` — payload: `forecast_id`, `format` (`csv`/`json`/`png`/`pdf`) (§5.5)

Дробление на 4 типа события, а не один `forecast_generated` на всё — не произвольное решение: панель «Прогресс» визуализирует не факт «прогноз где-то когда-то был сделан», а прогресс *внутри* этапа «Прогнозирование» через блок-схему с посегментным статусом (§9.2) — сравнение, анализ чувствительности и экспорт для пользователя суть отдельные, самостоятельные шаги внутри этапа и обязаны отдельно подсвечиваться как пройденные контрольные точки, а не схлопываться в одно неразличимое событие.

До реализации backend-персистентности сервиса «Прогресс» (`research_runs`/`trace_events` — сама персистентность специфицирована по UI/целям, но не по схеме хранения, это отдельная работа) — временное хранение `session.modeling_pipeline["forecasts"]: list[ForecastRun]` (тот же паттерн списка артефактов сессии, что уже используют `model_cards`), где `ForecastRun` уже содержит поле `trace_events: list[TraceEvent]` (§7) в формате, идентичном тому, что впоследствии будет читать финальный сервис — миграция сводится к смене места чтения, а не к пересборке структуры данных. Не изобретается второй, конкурирующий механизм истории.

## 6. Backend API

Роуты — в существующем `apps/api/routers/modeling_session.py`, тот же файл, что и Model Card, тот же префикс `/v1/session/modeling/*`.

```
POST /v1/session/modeling/forecast
  { "model_card_id": "...", "horizon": 12, "alpha": 0.05 }
  → ForecastRun (§7), сохраняется в session.modeling_pipeline["forecasts"]

GET  /v1/session/modeling/forecast/{forecast_id}
  → ForecastRun

GET  /v1/session/modeling/forecast/{forecast_id}/export.csv
GET  /v1/session/modeling/forecast/{forecast_id}/export.json

POST /v1/session/modeling/forecast/compare
  { "model_card_ids": ["...", "..."], "horizon": 12, "alpha": 0.05 }
  → список ForecastRun, для §5.6

POST /v1/session/modeling/forecast/{forecast_id}/sensitivity
  → веер прогнозов по границам param_space, для §5.7

GET  /v1/session/modeling/forecast/history
  → list[ForecastRun] всей сессии, для §5.9
```
Нет `export.png`/`export.pdf` роутов — сознательно (§5.5, §10 п.2): растровый/PDF-экспорт не требует обращения к backend, весь необходимый для него материал (`ForecastRun`, уже отрисованный график) уже доступен на клиенте.

## 7. Модель данных

```python
@dataclass
class ForecastPoint:
    step: int                  # 1..horizon
    date: str                   # ISO
    value: float
    ci_lower: float
    ci_upper: float
    is_anomalous: bool            # §5.8

@dataclass
class TraceEvent:
    event_type: str      # "forecast_generated" | "forecast_compared" |
                          # "forecast_sensitivity_computed" | "forecast_exported" (§5.9)
    timestamp: str        # ISO, совместим с общим форматом трассы (§9.3, п.3)
    payload: dict[str, Any]

@dataclass
class ForecastRun:
    forecast_id: str
    model_card_id: str              # обязательная ссылка на Model Card -- прогноз не существует сам по себе
    generated_at: str
    horizon: int
    alpha: float
    ci_method: str                    # "analytic" | "parametric_simulation" | "empirical_oof_quantile" (§4)
    points: list[ForecastPoint]
    expected_accuracy: dict[str, float]  # ИЗ model_card.performance.backtest_metrics, не пересчитано (§5.4)
    prediction_interval_coverage: float | None   # §4.3, если посчитано
    warnings: list[str]                # напр. "горизонт превышает проверенный бэктестом диапазон" (§5.1)
    trace_events: list[TraceEvent]      # питает панель «Прогресс» (§9) -- НЕ отдельно агрегируется панелью
```

## 9. Интеграция с боковой панелью «Прогресс исследования TS»

### 9.1 Статус и границы раздела
Функционал панели «Прогресс» (цели, UI-паттерн, точка вызова) зафиксирован тимлидом — раздел ниже фиксирует, как этап «Прогнозирование» технически в неё встраивается. Дизайн самой панели и backend-персистентность сервиса «Прогресс» (`research_runs`/`trace_events`: схема хранения, обезличивание, RAGFlow-индексация, дообучение моделей) — вне рамок этой спецификации, отдельная работа. Здесь описан только контракт **со стороны Прогнозирования**: что оно обязано поставлять, чтобы панель могла работать, когда бы её backend ни был реализован — до или после этого модуля.

### 9.2 Точка вызова и UI-паттерн (контекст; не переопределяется этой спецификацией)
- Вызывается из главного меню, справа, на месте прежней иконки «Логи событий» — глобальная навигационная замена, затрагивающая все этапы пайплайна, не только Прогнозирование.
- Раскрывается поверх текущей страницы правой боковой панелью (тот же паттерн, что и панель «Логи событий»); закрывается кликом вне панели или иконкой-крестиком в правом верхнем углу.
- Визуализация — блок-схема пайплайна с лёгким семантическим цветным фоном (пройдено/текущий шаг/впереди), статус дополнительно кодируется иконками, каждый узел сопровождается кратким поясняющим текстом.

Отсюда прямое следствие для этого модуля: `STAGES[-1] == "forecasting"` (§1) — шестой и последний узел блок-схемы. Пока в сессии нет ни одного `ForecastRun`, узел отображается как «не начат» (нейтральный фон); после первого `forecast_generated` — «в процессе», с посегментной подсветкой по `trace_events` (§5.9): построен → сравнён → проверена чувствительность → экспортирован. Точное условие перехода в статус «завершён» — открытый вопрос (см. §10, п.5), т.к. зависит от общей спецификации пайплайна, а не только от Прогнозирования.

### 9.3 Что этап «Прогнозирование» обязан поставлять — по каждой из 5 целей панели

1. **Онлайн-ориентация аналитика** — узел «Прогнозирование» в блок-схеме подсвечивается, поясняющий текст узла берётся из последнего `TraceEvent.payload` этого этапа (например: «Прогноз построен: ETS, горизонт 12, покрытие интервала 93%») — не генерируется отдельно панелью, использует уже посчитанные поля `ForecastRun` (§7).
2. **Отчёт для пользователя** — `GET .../forecast/{id}/export.json` (§5.5) уже самодостаточен; панель не обязана параллельно агрегировать те же данные — переиспользует тот же export-эндпоинт по ссылке, а не дублирует сериализацию.
3. **Данные для техподдержки** — тот же экспорт + полный список `trace_events` (§5.9, §7); важно, что `ForecastRun.generated_at` и `trace_events[].timestamp` совместимы по формату с общей таймлинией трассы «Прогресса» (паузы/восстановление сессии — атрибут сессии в целом, не специфичен для Прогнозирования), чтобы попадать в общий отчёт без конвертации форматов.
4. **Данные для «Наставника (следующий шаг)»** — Наставнику нужны текущая фаза, выводы анализа и рекомендация следующего шага. Для Прогнозирования это конкретно: `ForecastRun.warnings` (например, предупреждение о горизонте за пределами проверенного бэктестом диапазона, §5.1), `expected_accuracy`/`prediction_interval_coverage` (§4.3) как «выводы», и то, какие из действий §5.5–§5.7 (экспорт, сравнение, анализ чувствительности) ещё не выполнялись в этой сессии — прямой материал для рекомендации («прогноз построен, но не сравнивался с альтернативными моделями — рассмотрите сравнение перед экспортом»). Прогнозирование не формулирует саму рекомендацию — только поставляет сырые факты; логика рекомендации — зона ответственности Наставника, не этого модуля.
5. **Сбор данных (статистика/лучшие практики/RAGFlow/дообучение)** — `trace_events` этапа Прогнозирования обезличиваются по тому же механизму, что и остальные этапы (вне scope этой спецификации), и участвуют в тех же 4 подпотоках без специальной обработки: обезличенная статистика (какие модели/горизонты/`alpha` выбираются чаще), банк кейсов (связка «профиль ряда → выбранная модель → построенный прогноз → фактическое покрытие интервала» — материал для будущей верификации надёжности интервалов платформы), база RAGFlow (текстовые `payload`-описания узла как готовые фрагменты для ИИ-аналитика), дообучение моделей (согласие, что `trace_events` — общий источник для всех этапов; специфического технического решения для Прогнозирования здесь не вводится).

### 9.4 Явно вне рамок этого раздела
Компонент самой панели, анимации раскрытия/схлопывания, blocks-схема как таковая, backend-персистентность (`research_runs`/`trace_events`), обезличивание, RAGFlow-индексация, дообучение — отдельная спецификация. Здесь зафиксирован только контракт поставки данных со стороны Прогнозирования, чтобы (а) не блокировать реализацию этого модуля ожиданием готовности «Прогресса» и (б) не потребовать переработки уже сделанного здесь, когда «Прогресс» будет реализован.

## 10. Открытые вопросы и рекомендации

Рекомендации даны с проверкой по фактическому коду репозитория (версии библиотек, существующие адаптеры, уже принятые на платформе паттерны), а не умозрительно — там, где проверка изменила исходную формулировку вопроса, это отмечено явно.

### 1. Горизонт, существенно превышающий проверенный бэктестом (§5.1) — **решено**
Было: «точный порог не выведен эмпирически, например `2×`». Рекомендация: калибровка не нужна — порог не эвристический, а точный факт, уже хранящийся в Model Card: `horizon > training.horizon`. Это ровно та граница, на которой у эмпирического метода (§4.2) физически заканчиваются данные для квантиля, так что вопрос «когда предупреждать» и «когда данных для интервала объективно не хватает» — один и тот же вопрос, а не два независимых. Решение зафиксировано в §5.1: единый порог, разная строгость реакции по группе `ci_method`. Действие: не требуется дальнейшая калибровка перед реализацией.

### 2. PNG/PDF-экспорт графика — **решено**
Было: «нет прецедента, проверить перед реализацией». Проверено: прецедента действительно нет нигде в кодовой базе (ни клиентского, ни серверного механизма). Рекомендация: не заводить новый backend-эндпоинт и не ждать появления прецедента в другом модуле — реализовать напрямую на клиенте в `ForecastExportMenu.tsx` (SVG→canvas для PNG без новых зависимостей, `jspdf` — единственная новая лёгкая зависимость для PDF). Решение зафиксировано в §5.5/§6. Дополнительная польза: поскольку `recharts` — общий стек всей платформы (`TimeSeriesLineChart.tsx`, `BacktestOofChart.tsx` и др.), этот же SVG→PNG приём при желании тривиально переносится и в другие модули — но заводить его как общую утилиту `packages/ui` заранее, до второго реального потребителя, преждевременно (YAGNI: один потребитель — не повод строить абстракцию).

### 3. Список моделей с аналитическими интервалами `statsmodels` — **решено, с существенной поправкой к §4.1**
Было: «Theta — нужно явно проверить `ThetaModelResults` при реализации». Проверено вызовом на `statsmodels==0.15.0` (версия, закреплённая в `requirements.txt`) — результат меняет не только ответ по Theta, но и исходную классификацию §4.1, которая ошибочно объединяла ETS/ARIMA/Theta в одну группу с одним методом (`get_forecast().conf_int()`). Факт: это три разных API.
- **ARIMA/Auto-ARIMA** — да, `get_forecast(steps).summary_frame(alpha)`, ровно как предполагалось.
- **Theta** — да, но **другим методом**: `ThetaModelResults.prediction_intervals(steps, theta, alpha)`, не `get_forecast()` (такого метода на `ThetaModelResults` не существует).
- **ETS/ETS damped** — **нет**, аналитического интервала нет: платформа сознательно использует классический `statsmodels.tsa.holtwinters.ExponentialSmoothing` (см. комментарий в `apps/api/model_impls/ets.py`), а не полную state-space `ETSModel` — у `HoltWintersResults` нет ни `get_forecast`, ни `conf_int`. Есть `HoltWintersResults.simulate(nsteps, repetitions=N)` — параметрическая симуляция, третий метод (§4.1a), не аналитический и не эмпирический OOF.
- **Prophet/TBATS** — уже реализовано на уровне `MODEL_EXECUTION_REGISTRY` (Task 124/125), интервалы честные, переиспользуются как есть.

Действие: §4 переписан на три метода вместо двух (см. выше). Дальнейшая проверка перед реализацией не требуется — факты установлены по коду, а не по документации библиотеки.

### 4. Backend-персистентность сервиса «Прогресс» — **сознательно остаётся открытым, с одной конкретной рекомендацией**
Это не вопрос, который корректно закрывать в одностороннем порядке спецификацией одного модуля — архитектура `research_runs`/`trace_events` касается всех этапов пайплайна, не только Прогнозирования, и её владелец — команда «Прогресса», не этот модуль. Рекомендация как Senior-разработчика — не «подождать», а одно конкретное действие: **вынести датакласс `TraceEvent` (§7) из этой спецификации в общее место** (например, `apps/api/trace_events.py` или туда, где уже лежат общие модели сессии) **до начала реализации хотя бы одного из двух модулей** (Прогнозирование или «Прогресс», в любом порядке) — и явно предложить это как общий контракт на ревью команде «Прогресса». Причина: если каждый модуль спроектирует свой `TraceEvent` независимо «по конвенции», совместимый лишь по факту совпадения полей, при реальной интеграции почти неизбежно всплывут расхождения (разный формат `timestamp`, разная вложенность `payload`) — их дешевле исключить на уровне одного общего класса сейчас, чем находить и мигрировать постфактум. Это не решает вопрос backend-персистентности, но снимает риск, из-за которого этот вопрос вообще опасен для параллельной разработки.

### 5. Условие перехода узла «Прогнозирование» в статус «завершён» — **предложен конкретный дефолт по прецеденту, не изобретается новый механизм**
Платформа уже решает ровно такую же задачу для Моделирования — статус этапа выводится из данных, а не по явному пользовательскому действию «далее» (см. `apps/api/routers/modeling_session.py`: `session.modeling_pipeline["tuning"] = "done" if not pending_tuning else "in_progress"`, применяется многократно по всему файлу как устоявшийся паттерн). Рекомендация: не ждать общей спецификации «завершения исследования» и не вводить для Прогнозирования отдельный, новый по типу механизм («кнопка Готово») — по умолчанию считать узел «завершённым», когда в сессии есть хотя бы один `forecast_exported` (§5.9) — экспорт прогноза уже является естественным терминальным действием этого этапа, тем самым, чем «применение выбранного tuning» является для Моделирования. Если владелец общей спецификации «Прогресса» впоследствии определит иную семантику завершения для всего пайплайна — этот дефолт заменяется без структурных изменений (это derived-статус, а не жёстко закодированное правило, переопределяется в одном месте).
