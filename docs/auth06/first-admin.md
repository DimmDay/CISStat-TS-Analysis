# Первый вход администратора после AUTH-06

Учётная запись создаётся отдельной операторской процедурой AUTH-05. Деплой
AUTH-06 сам её не создаёт. Команды ниже создают логин `dimm.day`; пароль задаёт
оператор скрытым вводом. В этой поставке нет созданного production-пользователя
или заранее действующего пароля.

## Подготовка

Откройте локальный защищённый интерактивный терминал в корне репозитория с
активным Python-окружением. Ему нужен доступ к **той же рабочей PostgreSQL БД**,
которую использует API: `CISSTAT_AUTH_DATABASE_URL` либо `DATABASE_URL`.
`CISSTAT_AUTH_TEST_DSN` для этого не используется. Если терминал вне сети
сервиса, требуется доступный с него адрес той же БД. DSN/пароль БД не помещайте
в аргументы команд, чат или протоколы тестов.

Если auth-зависимости ещё не установлены:

```console
python -m pip install -r scripts/auth05/requirements.txt
```

Проверьте схему:

```console
python scripts/auth05/migrate.py --check
```

Продолжайте только при `ok: true` и нулевом exit code. Если миграции AUTH-05
ещё не применялись, оператор рабочего API выполняет
`python scripts/auth05/migrate.py --apply`, затем повторяет `--check`.
Это существующая additive-миграция до 0021; новых миграций в исправлении нет.

## Создание учётной записи

Выполните последовательно в интерактивном терминале, без перенаправления вывода:

```console
python scripts/auth05/bootstrap.py prepare
python scripts/auth05/bootstrap.py create --login dimm.day
```

Первая команда показывает одноразовый provisioning secret. Сразу выполните
вторую: secret действует 15 минут. На `Provisioning secret:` вставьте его;
на `Named admin passphrase:` задайте собственный уникальный пароль минимум
из 15 символов и повторите его. Сохраните логин/пароль в своём менеджере паролей.
Пароль не передаётся через argv и не выводится. Успешный ответ второй команды
содержит `login`, `subject_id`, `account_id` и имеет нулевой exit code.

CLI создаёт ADMIN, личный INTERNAL Account, OWNER membership и разрешение на
первую настройку MFA. Пока команды не завершились успешно, реквизиты не
считаются действующими. Если ADMIN уже существует, либо bootstrap уже
подготовлен/использован, повтор блокируется. При `bootstrap_failed` остановитесь:
не удаляйте ledger и не подменяйте пароль SQL-запросом. Нужна диагностика состояния
оператором; действующий администратор использует свой пароль/TOTP или recovery.

## Вход

Откройте https://ts-standalone.vercel.app/login?return_to=%2Fupload .
Введите `dimm.day` и заданный пароль. При первом входе настройте TOTP по
инструкции формы, подтвердите одноразовый код из своего приложения-аутентификатора
и сохраните показанные recovery codes. После завершения входа выберите файл
повторно: браузерная навигация не переносит выбранный локальный файл.

Для этого у рабочего API должны быть настроены постоянные
`CISSTAT_AUTH_MFA_KEYS` / `CISSTAT_AUTH_MFA_ACTIVE_KEY`,
`CISSTAT_AUTH_CSRF_KEY` и exact HTTPS origins в
`CISSTAT_AUTH_ALLOWED_ORIGINS` (либо `ALLOWED_ORIGINS`). Формат MFA keyring —
JSON key-id → base64 ключа из 32 байтов, active key — один из этих key-id.
Ключи сохраняются в конфигурации API; не генерируйте новые при каждом рестарте.
В Vercel соответствующей оболочке нужны server-only `API_URL` и
`CISSTAT_AUTH_PUBLIC_ORIGIN=https://ts-standalone.vercel.app`.
Подробности: `docs/auth05/design.md`, `docs/auth06/design.md`.

## Ошибки загрузки

- 401: вход отсутствует или сеанс завершился; форма предлагает ссылку на вход.
- 403: отказ в праве либо устаревшая CSRF-защита; это отдельное сообщение.
- 503: сервис недоступен; вход не предлагается как способ исправления.

Создание ADMIN обеспечивает личный вход с MFA. Подключение этой identity к
старым key-only административным API — задача AUTH-07. AUTH-06 не завершает
миграцию всех сервисов/научных прав и не обходит их действующие проверки.
