# Сценарий «Доступ запрещён — документы этого исследования недоступны вашему субъекту»: воспроизведение и разбор

**Дата:** 27 октября 2026 года, Москва. **База:** `79044e8c91195dcb54969da5b34b77dcd15941da` (AUTH-ARCHITECTURE). **Тип работы:** разбор пользовательского сценария и воспроизведение (постановка тимлида); изменения продукта НЕ входили в задачу, код/спека не менялись. **Запрещено и не выполнялось:** commit/push в main.

## 1. Постановка

Аналитик загружает демо-датасет `forecast_monitor_synthetic_n150.csv` (первая демо-карточка вкладки «Загрузка», `packages/ui/lib/demoDatasets.ts::generateForecastMonitor`), проходит весь этап «Загрузка» (подтверждает одномерный ряд в Структуре, формирует Паспорт свойств ряда), нажимает кнопку «Документы» — и все виды документов в модуле «Версии» отвечают одним и тем же: «Доступ запрещён — документы этого исследования недоступны вашему субъекту». Вопросы: прокомментировать, воспроизвести, ответить, как поступить аналитику.

## 2. Как на самом деле устроен доступ к документам (факты кода, база 79044e8)

**Субъект запроса** (`apps/api/identity.py::resolve_request_subject`): валидный API-ключ приоритетен; иначе — владелец серверной записи cookie-сессии (`owner_subject`, first-write-wins, DOCLOG-0 restore-наследование); иначе — детерминированный суррогат cookie (`subject_pseudonym`); без cookie — аноним. tenant/subject из браузерных заголовков не принимаются (§15).

**Решающая таблица** (`authorize_run_access`, R09, fail-closed): anonymous → deny; роль admin → allow; режим `dev_single_user` → allow (`dev_single_user_isolated`); bound-владелец + tenant → allow (`owner`); создавшая cookie-сессия → allow (`creator_continuity`); всё остальное → deny (`foreign_session` / `unresolved_foreign`). Причина — ТОЛЬКО в durable audit-потоке (`record_run_access_decision`), не в HTTP.

**Ключевое свойство HTTP (R09/T1/T15): отказ = uniform 404.** «Нет такого запуска» и «чужой запуск» на проводе неразличимы: знание `run_id` не является правом, существование ресурса не дисклоужается. Шлюз документации `_authorized_run_or_404` и сервис выдачи (`DocumentDeliveryService._authorized_run` → `DocumentAccessDenied`) ведут к одному и тому же 404 («Запуск не найден» / «Документ недоступен»); 403 `insufficient_scope` — только для «ресурс свой, права на действие нет» (DOCLOG-6).

**UI-маппинг** (`packages/ui/components/DocumentationWorkspace.tsx`, `loadDocuments`): `setListPhase(result.status === null ? "offline" : "forbidden")` — ЛЮБОЙ не-2xx HTTP-ответ списка (404, 403, 400, 409, 429, 5xx) показывается одной фразой «Доступ запрещён — документы этого исследования недоступны вашему субъекту». Сеть/исключение — отдельная фаза offline. То есть наблюдаемая фраза = «список документов получил HTTP-отказ», а не строго «субъект не совпал с владельцем».

**Открытие не создаёт документы** (§12.1): GET-список — только чтение; после этапа «Загрузка» реестр документов run'а честно ПУСТ, пока аналитик явно не соберёт черновик нужного вида (для Паспорта — вид D02). Это отдельное состояние «Документов пока нет…» (фаза empty), не запрет.

## 3. Воспроизведение

Скрипт `scripts/doclog_access_scenario/reproduce_analyst_scenario.py`; изолированный TestClient, disposable Memory-сторы, `CISSTAT_IDENTITY_MODE=session_scoped` (честный дефолт прод-развёртывания Render/Vercel), без DATABASE_URL/REDIS_URL/ключей. Датасет — НАСТОЯЩИЕ байты демо-генератора (дамп `dump_demo_csv.mjs`, Node 24 strip-types; 2691 байт, 150 строк, 3 пропуска). Протокол: `scripts/doclog_access_scenario/protocols/scenario.json`.

Этап «Загрузка» аналитика проходит штатно: upload 200 → target/value, date/date → passport/start (снимок паспорта создан) → trace отдаёт `run_id`.

| Ветвь | Условие | Результат | Что видит UI |
|---|---|---|---|
| S1 | Владелец открывает «Документы» (здоровый процесс) | 200, документов 0 | «Документов пока нет — соберите черновик нужного вида» (не запрет) |
| S2 | Владелец: черновик D02 → PDF → скачивание | 201 → job ready → 200, PDF 27191 байт | Документ скачивается |
| S3a | ЧУЖАЯ cookie-сессия (новый браузер/инкогнито/второй человек) на тот же `run_id` | 404 «Запуск не найден»; revision → 404 «Документ недоступен»; audit: `foreign_session` | «Доступ запрещён — …» |
| S3b | Аноним (cookie не дошла до API) | 404; audit: `anonymous` | «Доступ запрещён — …» |
| S4 | Run ПОТЕРЯН при живой сессии (симуляция рестарта/выселения free-tier инстанса при частично durable-сессии) | trace ВСЁ ЕЩЁ возвращает `run_id` (advisory-деградация `session_tail`, `projection_complete=false`), список → 404 «Запуск не найден» | «Доступ запрещён — …» — ЭКВИВАЛЕНТ наблюдаемого симптома |
| S5 | Полная потеря памяти процесса (и сессия тоже) | trace → `run_id=null` | «Исследование не выбрано — откройте раздел из исследования…» (фаза no-run, ДРУГОЕ сообщение) |
| S6 | `CISSTAT_IDENTITY_MODE=dev_single_user`, чужая сессия | 200 (`dev_single_user_isolated`) | Локальная демонстрация отказ НЕ показывает |

Durable audit-поток при этом честно различает причины: `owner` / `foreign_session` / `anonymous` / `dev_single_user_isolated`. Для S4 access-decision НЕТ вовсе: запуск не существует, 404 отдаётся до решающей таблицы.

## 4. Диагноз (комментарий)

Сообщение «Доступ запрещён — документы этого исследования недоступны вашему субъекту» означает на практике: **список документов получил HTTP-отказ для этого `run_id` из этой cookie-сессии**. Это не одно событие, а класс из трёх реальных причин, неразличимых в UI по дизайну (uniform 404):

1. **Субъект запроса — не владелец/не создатель запуска.** Другой браузер/профиль/устройство, очищенные cookie, инкогнито, второй человек, работа через ссылку с чужим `?run=RUN-…`. Защищаемое свойство платформы (T1/R09: знание run_id не право), а не дефект.
2. **Запуск потерян средой при живой сессии (S4 — точный эквивалент симптома).** Render free-тир «засыпает» при простое и рестартует на деплоях; advisory-контур без DATABASE_URL хранит runs в памяти процесса (H29). Запись сессии может вернуть `run_id` (или deep-link `?run=` принести старый идентификатор), а run-стор уже пуст → 404 → UI честно-нечестно показывает «Доступ запрещён», хотя прав никто не нарушал и исследования больше не существует в этой среде.
3. **Косвенные HTTP-отказы** (429 квота очереди, 5xx durable-слоя) UI тоже отображает этой фразой — для списка это редкость, но контракт маппинга именно такой.

Локально/в демонстрации отказ часто НЕ воспроизводится из-за `CISSTAT_IDENTITY_MODE=dev_single_user` (S6: cross-session разрешён) — отсюда типичное «а у меня работает».

Отдельно: даже при полностью здоровом доступе сразу после этапа «Загрузка» список пуст (S1, §12.1) — документы этапа появляются после явного «Создать черновик» (Паспорт свойств ряда — вид D02), и скачивание работает (S2). Пустой реестр запрещением не является и запрещение не маскирует.

## 5. Как поступить аналитику (порядок действий)

1. **Убедиться, что работа идёт в том же браузерном профиле, где выполнялась загрузка.** Не инкогнито, не другой браузер/машина, cookie `cisstat_session_id` не очищены. Субъект — производная cookie-сессии; смена носителя = смена субъекта.
2. **Открывать «Документы» из активного исследования**, а не по сохранённой ссылке: «Прогресс» → кнопка «Документы» (deep-link с текущим `run_id` формируется из свежего trace), либо пункт меню «Документы» (страница сама разрешит текущий run через `/v1/progress/trace`). Старая закладка с `?run=RUN-…` — типичный источник отказа.
3. **Если сообщение сохранилось — проверить среду:** `/health/ops` (режим identity, effective backend хранилищ). `memory` в проде означает границу free-тира: после простоя/рестарта сервиса исследования в памяти не выживают. Тогда документы именно ЭТОГО исследования восстановить нельзя (снимки привязаны к run) — сценарий повторяется в одной рабочей сессии: загрузка → Структура → Паспорт → «Документы» → «Создать черновик» нужного вида → скачивание, без длительных пауз, либо администратор переводит контур на durable-хранилища.
4. **Если аналитик — второй человек, которому нужны документы чужого исследования:** текущий контракт доступа (DOCLOG-0, session_scoped) не даёт sharing/grants — доступ имеют владелец, создавшая сессия, ADMIN. Легальный путь сейчас: владелец исследования сам выгружает документы и передаёт файлы; ожидание системного решения — контур Авторизации (AUTH-00…20: Account/membership/grants, `spec_auth_architecture.md`), доступ к чужим исследованиям появится только там.
5. **Не пытаться «подобрать» доступ по известному run_id** — это защищаемое свойство, а не баг; настоящая причина каждого отказа фиксируется в durable security-audit (`run_access_denied`, reason_code) и доступна администратору, но не клиенту.

## 6. Что платформе сделать дальше (рекомендации, вне этой задачи)

- **H29 (главное):** довести durable-миграцию до конца (`DATABASE_URL` + `CISSTAT_STORAGE_MODE=required` для runs/sessions/documents согласованно). Это устраняет класс S4/S5 «исследование исчезло после засыпания free-тира» — самую вероятную причину наблюдаемого сценария.
- **UI-честность (кандидат-задача):** когда run_id разрешён той же сессией (`resolveCurrentRun`/свежий trace) и список ответил 404, показывать состояние «исследование недоступно в этой среде (возможно, потеряно после рестарта сервиса)» с кнопкой «открыть текущее исследование» вместо безальтернативного «Доступ запрещён». Uniform-404 ослаблять нельзя (T1), но фразу на клиенте можно выбирать по КОНТЕКСТУ получения run_id (свой-resolved vs deep-link) — это не дисклоужает существование чужих ресурсов.
- **AUTH-контур:** grants/membership на исследование (AUTH-00…20) — системный ответ на сценарий «документы нужны другому субъекту».
- **Наблюдаемость:** админ-представление security-audit (reason_code по run) — чтобы инцидент «у меня запрещён» разбирался по фактической причине, а не по догадкам.

Выводы о поведении UI — из кода `DocumentationWorkspace.tsx`/`documentation-client.tsx` и jest-корпуса DOCLOG-4/E2E-RECHECK; живого браузерного прогона не было. Причины отказов в audit-потоке подтверждены чтением Memory-audit-sink в том же процессе.
