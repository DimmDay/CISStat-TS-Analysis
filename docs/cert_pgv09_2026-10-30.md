## 4. Находки

### F-P9C1 — CRITICAL: Postgres write-path печатных jobs/renditions нарушает контуры 0010; печатный контур неработоспособен на Postgres-бэкенде (production), работает только на Memory

- `request_print_rendition` создаёт `DocumentJobRecord(snapshot_id="")`;
  `complete_render` для печатной rendition ставит
  `snapshot_id=job.snapshot_id` (`""`) и `revision_id=job.revision_id`
  (= `print_revision_id`, `dprint-…`).
- Postgres-адаптер передаёт значения в INSERT как есть
  (`register_job`/`register_rendition`, пустая строка ≠ NULL).
- DDL 0010: `document_jobs.snapshot_id TEXT NOT NULL REFERENCES
  report_snapshots(snapshot_id)`; `document_renditions.snapshot_id`
  — тот же FK; `document_renditions.revision_id TEXT NOT NULL
  REFERENCES document_revisions(revision_id)`. Миграция 0017 снимает
  только NOT NULL (`DROP NOT NULL`) — **FK сохраняются**, и её
  комментарий прямо рассчитан на NULL («NULL проходит проверку
  внешнего ключа»). Код пишет `''`, а не NULL: **семантический
  разрыв код↔DDL**.
- Следствие (Postgres-бэкенд выбирается при любом `DATABASE_URL`
  либо явном `CISSTAT_DOCUMENTS_BACKEND=postgres` — production
  render-конфигурация): первая же постановка печатной job'а —
  `INSERT document_jobs (snapshot_id='')` → **FK-нарушение → 500**;
  даже без него первая печатная rendition нарушает FK
  `revision_id → document_revisions` (dprint-… отсутствует в
  document_revisions) и FK `snapshot_id → report_snapshots`.
- Латентный слой (если FK снять): `UNIQUE(snapshot_id, format,
  redaction_profile)` из 0010 с `''` — ОБЩИЙ ключ всех печатных
  ревизий; `register_rendition` использует `ON CONFLICT
  (snapshot_id, format, redaction_profile) DO UPDATE` → вторая
  печатная ревизия **молча перезаписывает чужую строку rendition**
  (перехват: rendition_id первой ревизии остаётся, content/
  print_revision_id подменяются второй). Частичный UNIQUE 0017
  `(print_revision_id, format, profile)` этой коллизии не
  предотвращает — конфликт попадает в старый индекс раньше.
- Доказательство: proof-оракулы O11
  (`tests/api/test_p9cert_oracles.py::TestO11PostgresWritePathProof`)
  — мини-модель ограничений 0010/0016/0017 в SQLite с точными
  формами INSERT Postgres-адаптера: FK-нарушения воспроизведены
  (2 оракула), перехват строки воспроизведён (1 оракул); плюс
  статический анализ DDL/кода (цитаты выше).
- Класс: F-P0C1-подобный (критерий строки §13 в durable-контуре не
  выполняется) + нарушение собственного заявления поставки
  «Memory/Postgres паритет» (docs/pgv09_jobs_renderer_integration.md
  §2, §3; worklog11 «Memory+Postgres, миграция 0017»).
- Смягчение контекста: граница автора честна — «Postgres-реестр с
  новой миграцией на живой БД не прогонялся (нет DSN в среде)»;
  parity-оракулы поставки проверяют текстовый паритет DDL, а не
  совместимость write-пути с ограничениями. Но дефект вскрывается
  статическим сопоставлением кода и DDL 0010 и не требует живой БД.

### F-P9C2 — MEDIUM (doc-vs-code): заявленный pHYs-гейт клиента не реализован

`docs/pgv09_jobs_renderer_integration.md` §2: «200 гейтится
PNG-подписью (`\x89PNG…`) **и pHYs-наличием**». В
`png_renderer_client.py` реализована только подпись
(`data.startswith(PNG_SIGNATURE)`); pHYs-чанк не проверяется.
Комментарий тестов поставки признаёт упрощение («без pHYs — подписи
достаточно: pHYs инъекция и геометрия — зона PGV-08/CERT»), но
проектный документ остался с более сильным заявлением. Граница
PGV-08 (pHYs — зона контейнера) не отменяет обязанности документа
описывать фактическое поведение клиента.

### N-P9C1 — MINOR: «ready» в отчёте worker'а при CAS-отклонённом завершении

`_process_print_job` игнорирует результат `complete_render`: при
гонке «cancel в rendering → завершение» CAS-гейт корректно НЕ
публикует байты (AC20 держится — подтверждено D9), но worker
логирует «печатный job … ready» и возвращает `report["ready"] += 1`
для оставшегося cancelled. Публикации нет (безопасность не нарушена);
это mislabel статистики цикла. Паттерн унаследован от snapshot-пути
(паритет), новых рисков не создаёт.

### N-P9C2 — MINOR: NaN вне канонического freeze даёт transient вместо terminal

`PngRendererClient.render_page` сериализует payload
`json.dumps(..., allow_nan=False)`; ValueError поймается веткой
`URLError/TimeoutError/OSError/ValueError` → `RendererUnavailable`
(transient) → requeue-цикл до исчерпания попыток вместо честного
terminal `invalid_payload`. Канонический freeze
(`canonical_json_bytes`, allow_nan=False) блокирует NaN upstream,
поэтому в обычном контуре недостижимо; риск — только обходные пути
записи артефактов.

### N-P9C3 — COVERAGE (закрыто): пробелы корпуса автора

Помимо выживших мутантов: нет авторского теста на `print_basis_unsupported`
(P01/P02 вне каталога — покрыто моим O10), на реальный TCP через
worker (мои O7/O8), на чтение готовых байтов чужим субъектом на
печатной ветке (авторский D11 покрывает — зачтено).

## 6. Границы сертификации

1. Контейнер PGV-08/Chromium/Docker в среде недоступны — контейнерная
   E2E и финальный image smoke не пересертифицировались (наследуется
   от PGV-08/08-FIX/08-CERT; требуемый gate описан в runbook PGV-08).
2. Живой Postgres отсутствует — proof F-P9C1 построен на мини-модели
   ограничений (SQLite, точные формы INSERT адаптера) и статическом
   анализе DDL 0010/0017; живой прогон миграции 0017+write-пути —
   обязательный шаг recovery.
3. TS/jest/typecheck/Next-build не применимы: поставка не меняла
   TypeScript/фронтенд (паттерн PGV-00/01/02).
4. ZIP поставки автора недоступен в среде — упаковщик проверен
   аудитом кода; побайтная сверка невозможна (граница).
5. Мои оракулы — jsdom-free Python-контур; растровая корректность
   PNG — зона PGV-08/CERT (сертификатор проверяет только PNG-гейт
   подписи и lifecycle).
