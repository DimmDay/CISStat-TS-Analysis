# AUTH-20 — Audit/operations и миграционный rollout

База: c08ee9e (AUTH-19 на VM, образы собраны). Зависимости AUTH-09/AUTH-13/AUTH-16/AUTH-18 выполнены. Задача из spec_auth_architecture.md §9: точки изменения — `security_audit, health/ops, migrations, runbooks`; критерий приёмки — «Mandatory fault не оставляет неучтённое изменение; backup/revoke reconciliation и safe rollback проверены». spec_auth.md §14: восстановление из backup не воскрешает revoked credential, consumed admission или исчерпанный budget; DB/Redis failover и восстановление проверяются на replay и counters, а не только на наличие таблиц. spec_auth_architecture.md §8: backup restore требует reconciliation отзыва/consumed codes/settled operations; при сомнении кампании и сессии закрываются до reconciliation; rollback отключает новые входы/вычисления, но не возвращает production к открытому /internal или revoked legacy keys.

## Процесс и границы

1. **Durable revocation ledger — единственное основание reconciliation.** Существующие mutation-пути (AUTH-04 revoke, AUTH-10 ключи, AUTH-13 worker services, AUTH-15/16 grants/admissions, AUTH-12 reservations, AUTH-18 orders) разбросаны по восьми таблицам, и код-центричный «пиши в ledger при каждом отзыве» нарушается молча при появлении нового пути (fail-open по построению). AUTH-20 фиксирует переходы в КОНЕЧНОЕ защищённое состояние на уровне PostgreSQL: additive 0032 создаёт `auth_ops_ledger` (append-only, hash-свободный) и восемь `AFTER UPDATE` capture-триггеров: `auth_password_credentials` active→revoked, `auth_sessions` revoked_at NULL→set, `auth_api_keys` и `auth_worker_services` revoked_at NULL→set, `auth_demo_grants` active→revoked, `auth_demo_admissions` redeemed NULL→set, `auth_reservations` →settled/released, `auth_billing_orders` pending→applied/canceled. Каждая запись несёт `row_image` (финальный образ строки, `to_jsonb(NEW)`) — ledger является replay-журналом, а не только маркером. Ротации версии, входы, продления idle и прочие нетерминальные UPDATE не capture'ятся (WHEN-условия триггеров).
2. **Restore reconciliation через out-of-band marks.** Backup rollback возвращает и ledger, и ревокации к состоянию снапшота — само по себе БД не может знать о потерянных ревокациях. Поэтому операционный контракт (docs/auth20/runbook.md): перед КАЖДЫМ backup — `scripts/auth20/reconcile.py --export` в файл на volume ВНЕ pgdata (`/var/lib/cisstat-ops-marks/`); restore = восстановление pgdata + `--reconcile --marks <файл>`. Reconcile пере-применяет события idempotentно и bounded-порциями: существующая строка в незащищённом состоянии → UPDATE до конечного состояния (с уважением существующих immutable-гвардов: auth12 требует version+1 и валидный переход pending→running→settled / →released; auth10 требует version+1; auth04-триггер сессий разрешает ревокацию только при NULL revoked_at; auth15/16/18-гварды разрешают только статусные переходы), отсутствующая строка → INSERT tombstone из row_image ТОЛЬКО для `auth_demo_grants` (status='revoked', FK-целое — кампания) с компенсацией `issued_grants+1`; для sessions/credentials/keys отсутствие строки после restore означает, что строка не resurrection'ится (она и так исчезла) — report-only. Reservations re-apply идёт БЕЗ postings/budget-дельт: restore консистентен на момент снапшота, недо-charge фиксируется в отчёте как `budget_recheck_required` (over-charge запрещён направлением операции); consumed admission, чей grant потерян (создан после снапшота), не может быть закрыт in-place (auth16-гвард требует redeemed_grant_id) — report `unrepairable_consumed` с рекомендацией pause/re-issue кампании. Повторный reconcile с тем же marks — no-op (проверка конечного состояния перед каждым UPDATE/INSERT).
3. **Mandatory audit delivery — замыкание контура AUTH-04.** `auth_audit_outbox` (0020) сегодня доставляется только вручную (`scripts/auth04/publish_audit.py`); pending не ограничены по времени и видны лишь в readiness. AUTH-20 добавляет `ops_sweeper` (in-process, паритет demo_sweeper, только storage_mode=required): bounded `publish_pending(limit=100)` каждые `CISSTAT_AUTH_AUDIT_OUTBOX_INTERVAL` секунд (по умолчанию 30, 0 = off) + prune ledger по `CISSTAT_AUTH_OPS_LEDGER_RETENTION_DAYS` (по умолчанию 180, минимум 7; prune — единственный разрешённый DELETE). Отказ доставки — warning + счётчик в health, цикл не останавливает API; mandatory-семантика не ослабляется: intent уже закоммичен в той же транзакции мутации, delivery — идемпотентная доставка (`audit_id` PK + `ON CONFLICT DO NOTHING` в PostgresAuditSink), сбой delivery не «отменяет» изменение, а удерживает его видимым до успеха.
4. **Quarantine — «при сомнении кампании и сессии закрываются до reconciliation»** (§8). `scripts/auth20/reconcile.py --quarantine --reason "…"`: одной bounded-кампанией (порции по 100 субъектов) поднимает `session_epoch` всем субъектам, ревоцирует все активные сессии, ставит все active-кампании в `paused`. Это НЕ revoke ключей API/worker (их ревокация — отдельное решение оператора штатными командами) и не lockdown: после успешного reconciliation вход снова открыт, участники кампаний получают новые admission по решению оператора. Каждая порция — mandatory `auth_ops_changed` в той же транзакции.
5. **Safe rollback — env-kill-switch `CISSTAT_AUTH_LOCKDOWN`.** Значение не из {"", "0"} включает lockdown: четыре точки входа (password `SessionService.login`, demo `DemoService.enter`, OIDC `OidcService.start`, email `EmailChallengeService.start`) отвечают 503 `auth_lockdown` ДО любой работы с БД/секретами. Существующие сессии/ключи НЕ затрагиваются (проверка только на входе), /internal и научные пути остаются под AUTH-11 guards (rollback не возвращает открытый /internal), revoked legacy keys остаются revoked (ревокация не отменяется env). Вычисления останавливаются оператором штатно: quarantine закрывает сессии — новые reservations не выдаются; существующие управляются fencing AUTH-13. Снятие — unset env + пересоздание контейнера, без DDL.
6. **health/ops — facts-only auth_ops.** Peek-семантика (не инициализирует фабрики; все пробы под try): `lockdown` (env), `audit_sweeper` (enabled/running/last_cycle: delivered/failed/at), `audit_outbox_pending` (COUNT по фактическому store), `ledger` (total + last_24h), `external_entry` (oidc/email_trial флаги конфигурации), `schema_version` (0032 checksum-проверка — проба миграционного контракта). Любое исключение → `{"state": "<state unavailable>"}` — диагностика не роняет health (паритет worker_credential/render_dependencies).
7. **Новый mandatory audit `auth_ops_changed` (каталог 37→38).** Классифицируется как изменение прав/политики (§14.1): quarantine, reconcile (каждая порция re-apply), export marks. Fail-closed: intent в `auth_audit_outbox` в той же транзакции, что и мутация; failure аудита = откат операции (существующий контракт MandatoryAuditFailure/outbox).
8. **Миграция 0032 additive, явная, вне request-path.** `auth_ops_ledger` + триггеры; checksums 0019–0031 не меняются; apply/check — `scripts/auth20/migrate.py` (паритет auth19, та же цепочка `demo_lifecycle_migrations → auth19 → 0032`). Отката DDL нет (паритет прежних задач): rollback = env/операционные действия; down -v запрещён runbook'ом.
9. **Ledger не содержит секретов.** row_image — серверные строки: token_hash/key_hash (уже hash-only по построению AUTH-04/10/13), состояние, версии, FK; cookies/пароли/OTP в ledger не попадают (там их нет в строках). Retention — настройка оператора; реальные сроки утверждает оператор (spec_auth §14), код даёт механизм, не политику.
10. **Робастность цикла sweeper.** Thread daemon, `Event.wait(interval)`, все исключения — warning (паритет demo_sweeper); статус для health ведётся атомарно; stop() с join(timeout). В advisory-режиме (dev) sweeper не стартует — durable outbox в dev не заявляется (паритет audit_outbox.publish_pending: memory sink → 503).
11. **Роуты не затронуты.** Ни одного нового HTTP-маршрута: /health/ops остаётся GET с additive-блоком в payload (inventory `ops.diagnostics` без изменений); все четыре входных пути уже inventory. Проверка — check_routes/auth00 (274 API, bindings 278 — без изменений) + policy_review дополнен политикой auth.ops (без новых записей операций).
12. **Не входит:** автоматический pg_basebackup/PITR (выбор оператора, runbook даёт контракт), Redis (в проекте нет Redis-зависимости auth-контура), кросс-региональный DR, rewriting reconcile под будущие таблицы (AUTH-21/22/23 добавят свои capture-триггеры той же функцией по тем же правилам), UI-админка reconcile (CLI-first, доступ через docker compose exec).

## Риски и проверки

- **Молчаливая потеря ревокации новым код-путём** — capture на уровне триггеров БД: любой путь, проводящий строку в конечное состояние, capture'ится; негативный оракул — UPDATE версии без ревокации не capture'ится.
- **Reconcile ломает immutable-гварды** — ревоцируются только строки в незащищённом состоянии; version+1 и валидные переходы соблюдаются; идемпотентность доказана повторным прогоном.
- **Reconcile создаёт двойной charge** — reservations re-apply без postings/budget-дельт (только terminal state), направление ошибки — недо-charge + отчёт, never over-charge.
- **Ledger как канал утечки** — только hash-only поля и серверные метаданные; row_image без cookie/пароля/OTP; retention prune; экспорт — chmod 600, tmp+rename.
- **Mandatory fault** — intent в outbox в одной транзакции с мутацией (quarantine/reconcile/export); сбой доставки НЕ отмечает delivered (crash после append до mark безопасен: audit_id-fence), отказ экспорта/порции = откат порции.
- **Lockdown lockout самого оператора** — проверяется только на 4 входах; CLI auth20 работает по DSN мимо HTTP; сессии оператора не рвутся.
- **Sweeper деградация** — все сбои warning + health-счётчик, цикл жив; в advisory не стартует (нет ложного durable).
- **Ошибка миграции** — additive, checksums 0019–0031 immutable, явные --apply/--check, native PG гейт.
- Не входит: реальный pg_basebackup/PITR прогон на VM (контракт + native-эмуляция restore в тестах), Redis, UI, IdP/SMTP (AUTH-19), ручной ввод политик retention сверх env.
