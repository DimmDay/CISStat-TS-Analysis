## 2. Модель рекомендателя v2 — гибрид

Два слоя, ОДНА рекомендация на выходе (канон §7.1 «не заваливает советами» сохраняется дословно):

- **Слой A — специфичные правила** (`NEXT_STEP_RULES`, `app/core/mentor_rules.py`). Существующие 8 правил **не переименовываются, приоритеты не меняются** (pin-таблица в канон-блоке §3.1 — гвард `tests/unit/test_mentor_next_step_spec.py`). Прогон прежний: сортировка `(priority, rule_id)`, первое сработавшее правило возвращает рекомендацию. Слой A кодирует то, что скан «жёлтого» выразить не может: методологические зависимости (`regularity_before_decomposition`) и процессные гэпы стадий без warning-семантики (`modeling_*`, `forecast_*`).
- **Слой B — fallback-скан**. Включается **только если Слой A не дал рекомендации**. Детерминированный проход по канону сканирования §3: находит первый проблемный узел (`error`, затем `warning`) на warning-способных стадиях и собирает рекомендацию из реестра объяснимости (§5, артефакт `MNS-REG-2`). Никаких эвристик, никакого I/O — только уже посчитанная проекция (`projection.node_statuses`, единая проекция AUDIT-5B — та же, что у панели и отчёта).

**Инвариант v2 (главное требование контракта):** если на warning-способной стадии существует узел со статусом `error` или `warning`, рекомендация обязана существовать (Слоем A или Слоем B). Этим устраняется задокументированное самопротиворечие текущей реализации (review §2.2(д)): панель показывает жёлтый узел, `phase_text` говорит «найдены проблемы», а `recommendation == None` рендерит «Критичных подсказок нет — исследование идёт по плану».

**Тишина честна** только в одном случае: проблемных узлов (`error`/`warning`) на warning-способных стадиях нет **и** ни одно специфичное правило Слоя A не сработало (процессные гэпы Моделирования/Прогнозирования неактуальны). Тогда ответ `recommendation == None` — и текст «исследование идёт по плану» на панели соответствует фактам.

**Порядок применения:** Слой A (сортировка прежняя) → Слой B (`error`-проход → `warning`-проход по канону §3). Канон сканирования **не** вытесняет специфичные правила: они старше по построению (сначала A), миграция правила между слоями — правка приоритета/реестра с тест-пином (§6).

## 3. Канон сканирования (ScanCanon)

### 3.1. Определение и машиночитаемый блок

Канон сканирования — **детерминированный порядок обхода узлов графа для Слоя B**: стадии в порядке `STAGES`, узлы в порядке `STAGE_NODES` соответствующей стадии, ограничено warning-способными стадиями. Порядок реестров — та же конвенция, что уже рендерит панель и степперы модулей; спека фиксирует её как **канон сканирования** (воспроизводимость и одинаковость у панели и Наставника), а не как утверждение о жёстких методологических зависимостях между соседними узлами (разведение — review §2.2(в)). Машиночитаемый канон-блок ниже — единственный источник для гварда `tests/unit/test_mentor_next_step_spec.py` (двойная запись знания: код + контракт связаны тестом; правка `STAGE_NODES`/`NEXT_STEP_RULES` без синхронной правки блока роняет сюит):

Свойства канона: (1) **детерминизм** — два вызова на одном снапшоте проекции дают один и тот же узел; (2) **полнота** — ровно 25 остановок (5 + 10 + 10), совпадает с суммой реестров кода; (3) **ноль нового I/O** — вход `projection.node_statuses` уже посчитан роутером next-step; (4) **error старше warning** — два прохода: сначала ищется первый узел со статусом `error` (проверка упала — срочнее любого замечания), затем первый узел со статусом `warning` (решение Q2); (5) **границы Q3/Q4** — `eda`, `modeling`, `forecasting` в скан не входят.

### 3.2. Семантика «проблемного узла»

Проблемный узел = узел warning-способной стадии, чей статус из единой проекции (`node_statuses`, ключ `"{stage}/{node_id}"`) принадлежит `problem_statuses` (`error`, `warning`). Источники этих статусов — уже существующие и не меняются данной спекой:

- `correction_previewed` — «Найдены нарушения: предпросмотр коррекции» (семя warning, `EVENT_NODE_STATUS` в `app/core/node_status.py`);
- отчёты модулей `upload_stop_status` / `validation_check_status` / `preprocessing_check_status` (payload-статус из `CHECK_STATUS_VALUES`, валидация fail-closed на map-эндпоинтах, AUDIT-2A);
- payload-статусный override `correction_applied` (last-wins, PROGR-23-FIX-G345) — честный статус «нарушения остались» после применения;
- `error` — падение проверки (модуль сообщил ошибку отчётом или проекция получила error-факт).

## 5. Сборка рекомендации

### 5.1. Структура (аддитивно к `MentorNextStepResponse`)

Ответ next-step сохраняет все существующие поля (`phase_text`, `summary`, `history_warnings`, `watermark`, `events_total` — контракты прежние) и рекомендацию прежней формы (`rule_id`, `stage`, `message`, `recommended_action`). Аддитивные расширения:

- для рекомендаций Слоя B поле `rule_id` — синтетический идентификатор семейства fallback (например, `fallback_error` / `fallback_warning`, константы кода, не новые специфичные правила);
- `message` собирается из реестра объяснимости с подстановкой уже посчитанных фактов узла (§5.2);
- опциональное поле объяснения (`explanation`: `status_reason` + `summary_count` + ссылка на методологию) — задача `MNS-TEXT-5`; данной спекой фиксируется требование аддитивности (существующие потребители не ломаются) и разведения советов и фактов: **объяснение — совет, в трассу не пишется** (§3.2 `spec_progress.md`, канон «советы — не факты» дословно: частота открытий панели — не телеметрия решений).

### 5.2. Объяснение «почему жёлтый» — из трёх уже посчитанных слоёв

Ноль нового I/O (тот же принцип «пересказ уже посчитанного», что §7.1/§7.2 исходной спеки):

1. `status_reason` узла — из тех же фактов (`EVENT_NODE_REASON`, `correction_reason` с числами, payload-причины отчётов модулей);
2. `summary_count` — то же число, что в бейдже узла (например, `total_missing`);
3. методология остановки — **ссылка** на статью реестра знаний (`help_entries`, решение Q7); VERBATIM-текст остаётся механизму отчёта (`run_report.py::node_methodology`).

### 5.3. Граница «куда идти vs как решать» и deep-link

Рекомендация v2 отвечает на «куда идти»: переход на конкретную остановку (`stage.node_id` deep-link — якорь/параметр степпера модуля, `MNS-LINK-3`; фолбэк — вкладка стадии, как сейчас). На «как решать» (выбор стратегии/метода/порога) Наставник не отвечает ни в Слое A, ни в Слое B — этот канон уже зафиксирован правилом «мечется» (`recommended_action=None` — «как решать», а не «куда идти») и sanity-правилами §7.2 (совет на preview Мастера, до применения). Аналитик попадает на остановку с объяснением и методологией — выбор стратегии остаётся за ним.

## 9. Критерии приёмки v2

1. Инвариант: существует узел со статусом `error`/`warning` на warning-способной стадии ⇒ `recommendation != None`; тишина честна только при отсутствии проблемных узлов и неактуальных процессных гэпах (проверяется тестами `MNS-FALLBACK-4`, сертифицируется `MNS-CERT-6`).
2. Существующие 8 правил `NEXT_STEP_RULES` не переименованы, приоритеты не изменены (гвард канон-блока).
3. Слой B детерминирован: два вызова на одном снапшоте проекции — один и тот же узел; порядок — `STAGES × STAGE_NODES`, `error` раньше `warning`.
4. Скан не добавляет I/O: вход — `projection.node_statuses` той же единой проекции AUDIT-5B.
5. Ответ next-step аддитивен: существующие поля и потребители (`MentorPanel`, телеметрия) не ломаются; объяснение в трассу не пишется.
6. Deep-link ведёт на остановку; неизвестный узел — фолбэк на вкладку стадии (Q6).
7. Регресс: все существующие тесты Наставника (`tests/api/test_mentor_rules.py` — 121) и гвардов спеки зелёные.

## 10. Риски и меры

- **Взрыв шаблонов объяснений** — реестр данных/конфига с fail-closed валидацией, не if/elif-монолит (урок PROGR-15-B → PROGR-19).
- **Дрейф терминологии против модулей** — источник текстов объяснений: существующий реестр знаний (`help_entries`), тест на совпадение заголовков «Метрики и алгоритм» (в DoD `MNS-REG-2`).
- **Миграция правил между слоями** — смена приоритета = синхронная правка канон-блока + тест-пин (гвард ловит рассинхрон).
- **UI-объём deep-link на шесть модулей** — фолбэк на вкладку стадии смягчает; первой реализуются три warning-способные стадии (`MNS-LINK-3`).
- **«Тишина» после исправлений** — инвариант гарантирует рекомендацию при проблемном узле, но не навязывает повторную рекомендацию по уже осознанно принятому предупреждению: поведение для «осознанно оставленного warning» (аналитик видел объяснение и продолжил) не меняется этой спекой — существующие каналы (sanity/thrashing/фаза) покрывают контекст; калибровка — категория B §11.

## 11. Аддендум UPLOAD-SEM-1 (2026-10-20): семантика статусов «Загрузки»

Решение тимлида (обсуждение 2026-10-20; план-отчёт `docs/upload_stop_semantics_2026-10-20.md`): модуль «Загрузка» несёт ознакомительные функции (ничего не исправляет и не преобразует), поэтому единственным содержательным «стопом» исследования является остановка «Структура» при невозможности определения структуры данных. Прежняя семантика (жёлтые факты о входных данных на 4 остановках) создавала тупик Наставника: fallback-скан (§3) вёл аналитика в модуль, где нечего делать.

Изменения (канон скана, состав 25 остановок реестра и инвариант v2 не меняются):

1. **Агентность как принцип статуса**: warning/error — только там, где у аналитика есть действие in-place.
2. **Ознакомительные остановки** `overview`/`chart`/`distribution`/`quality` — `done/pending` по факту просмотра («аналитик открыл и результат показан», паттерн EDA PROGR-18; монотонное множество в пределах датасета, смена датасета — новая вселенная; seed трассы + якорь — паттерн AUDIT-2B/3, H27/H28). Информация о данных остаётся в контенте остановок (тост/баннер parse_warnings, счётчики качества, Паспорт).
3. **«Структура»** — единственная факт-обусловленная остановка: `done` — уверенное решение (PROGR-14-A); `warning` — сомнительное угадывание конкретной колонки; **`error` (новый)** — авто-детект не нашёл ни одного правдоподобного кандидата временной колонки (реальная форма бэкенда: `selected="(не использовать)"`, все score нулевые) и аналитик ещё не сделал явного выбора. Error снимается явным выбором в селекторе (→ done/warning по PROGR-14-A) или заменой датасета — обе ветки формулы «продолжить исследования либо искать новые данные» имеют действие.
4. **Следствие для Наставника**: скан «Загрузки» может указать только на «Структуру» — место, где есть действие; реестр объяснимости несёт честные записи «warning не производит» для четырёх ознакомительных остановок; тупиковых рекомендаций «идите смотреть, где нечего делать» больше не возникает по построению.
5. **Совместимость**: эндпоинт `/upload-stops` не меняется (whitelist `CHECK_STATUS_VALUES` уже допускает `error`); движок node_status и правило last-wins без изменений; легаси-жёлтые старых трасс перезаписываются первым отчётом модуля по новой семантике (хронология решает).
