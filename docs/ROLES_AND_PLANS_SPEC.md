# Контракт "Роль / План / Возможности" (Role / Plan / Capability)

**Статус:** предложенная схема, готова к реализации. Заменяет плоскую модель `admin`/`user`/`partner` из текущего Streamlit-приложения.

---

## 1. Зачем разделять три сущности

Текущая модель Streamlit смешивает в одном атрибуте `role` три независимые оси:

1. **Кто вы** (идентичность/контекст) — сотрудник CISStat или внешний клиент
2. **Что вам разрешено** (возможности) — обучение моделей, доступ к API, лимиты
3. **За что вы заплатили** (тариф) — конкретный коммерческий план

Смешение этих осей означает: любое изменение прайсинга требует правки кода авторизации, а не только таблицы тарифов. Демо-режим для этой модели попросту не имеет естественного места — понадобится либо тайно урезать `partner`, либо заводить четвёртую роль под каждый новый тариф в будущем.

**Правило:** роль отвечает на вопрос "кто", план — на вопрос "что можно", возможности — конкретные проверяемые в коде флаги, производные от плана. Код (`require_capability(...)`) никогда не проверяет роль или название плана напрямую — только конкретную возможность.

---

## 2. Роли (`Role`)

| Роль | Кто | Контекст | Тариф |
|---|---|---|---|
| `admin` | Администратор платформы CISStat | embedded | Не применяется — полный доступ по умолчанию |
| `internal_analyst` | Сотрудник CISStat (было `user`) | embedded | Не применяется — полный доступ по умолчанию |
| `external_user` | Любой внешний клиент | standalone | **Определяется через `Plan`**, не через роль |

Для внешних пользователей остаётся **одна** роль — весь спектр возможностей (демо/стартер/профессионал/энтерпрайз) выражается через `Plan`, а не через отдельные роли на каждый тариф.

---

## 3. Тарифные планы (`PlanName`) и возможности (`Capabilities`)

| Возможность | `demo` | `starter` | `professional` | `enterprise` |
|---|---|---|---|---|
| Обучение моделей (`can_train_models`) | ❌ | ❌ | ✅ | ✅ |
| Доступ к API (`can_use_api`) | ❌ | ✅ | ✅ | ✅ |
| Сохранение истории анализов (`can_save_history`) | ❌ | ✅ | ✅ | ✅ |
| Загрузка своих данных (`can_upload_own_data`) | ✅ (с лимитом строк) | ✅ | ✅ | ✅ |
| Лимит строк на датасет | 5 000 | 50 000 | без лимита | кастомно |
| Лимит вызовов API/мес | 0 | 1 000 | 50 000 | кастомно / SLA |
| Лимит числа анализов всего | 10 | без лимита | без лимита | без лимита |
| Срок действия плана | 14 дней | бессрочно | бессрочно | бессрочно |
| Водяной знак на экспорте | ✅ | ❌ | ❌ | ❌ |

Источник истины — словарь `PLAN_DEFINITIONS` в `apps/api/plans.py`. **Новый тариф добавляется новой записью в этом словаре, без изменений в `auth.py` или роутерах.**

---

## 4. Демо-режим — не урезанная роль, а изолированный план

Демо-пользователь может не иметь полноценного аккаунта — это отдельный сценарий, не "внешний клиент с ограниченными правами":

- Выдаётся по временному API-ключу/сессии без полноценной регистрации (или с лёгкой — email без пароля).
- Жёсткая изоляция: демо-датасеты из коробки либо загрузка своих данных с жёстким лимитом (см. `max_dataset_rows`), без сохранения состояния между сессиями (`can_save_history=False`).
- `can_use_api=False` и `max_api_calls_per_month=0` — демо не даёт доступа к API вообще, только к веб-интерфейсу; это осознанное решение, чтобы не открывать вычислительно тяжёлый пайплайн (STL/wavelet/spectral) для злоупотребления бесплатным доступом.
- `trial_days=14` и `max_analyses_total=10` — двойное ограничение (по времени и по количеству), чтобы демо не превращалось в бесплатный тариф де-факто.

---

## 5. Как это проверяется в коде — по возможности, не по роли/плану

```python
# ПРАВИЛЬНО -- проверка конкретной возможности:
@router.post("/train", dependencies=[Depends(require_capability("can_train_models"))])
def train_model(...): ...

# НЕПРАВИЛЬНО -- проверка роли/плана напрямую в бизнес-коде:
def train_model(principal):
    if principal.plan != "professional" and principal.plan != "enterprise":
        raise HTTPException(403)
```

Второй вариант означает, что при появлении нового тарифа с `can_train_models=True` придётся находить и переписывать все подобные проверки по коду. Первый — работает автоматически для любого текущего и будущего плана с этой возможностью.

**Frontend** (`packages/ui/lib/plans.ts`) — точное зеркало того же контракта, но **только для UX** (скрыть кнопку "Обучить модель" для плана без этой возможности). Это удобство интерфейса, не защита — реальная проверка всегда на бэкенде.

## 7. Что осталось сделать (не реализовано, требует решения)

1. **Хранилище клиентов/ключей.** Сейчас `auth.py` парсит ключи из переменной окружения (`CISSTAT_API_KEYS="key1:external_user:starter,..."`) — годится для разработки, не для продакшена. Нужна таблица в БД: `principal_id`, `api_key_hash`, `role`, `plan`, `plan_expires_at`, счётчики использования для лимитов.
2. **Учёт использования лимитов** (`max_api_calls_per_month`, `max_analyses_total`) — сейчас определены в `Capabilities`, но нигде не инкрементируются и не проверяются по факту вызова. Нужен отдельный middleware/dependency, считающий вызовы и сверяющий с лимитом плана.
3. **Апгрейд/даунгрейд плана** — как изменение `plan` у существующего клиента отражается на уже выданном API-ключе (мгновенно на следующий запрос, ожидаемо, раз `get_current_principal` резолвит план при каждом запросе — но нужно подтвердить это поведение тестом, когда появится реальное хранилище).
4. **Единая синхронизация `plans.py` (Python) и `plans.ts` (TypeScript)** — сейчас два файла поддерживаются вручную. Рассмотреть генерацию TS-типов из Pydantic-схемы (например, через `pydantic2ts` или экспорт OpenAPI-схемы FastAPI и генерацию клиента), чтобы расхождение между бэкендом и фронтендом было невозможно физически, а не только по дисциплине разработчика.
5. **`internal_analyst`/`admin` в embedded-режиме** — сейчас `AuthenticatedPrincipal.capabilities` для них захардкожен как "всё разрешено". Нужно решить: действительно ли `admin` и `internal_analyst` должны иметь идентичные возможности, или `admin` — это отдельный набор прав (управление пользователями, доступ к системным настройкам), не связанный с `Capabilities` анализа вообще (что вероятнее).
