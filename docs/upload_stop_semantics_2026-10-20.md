# UPLOAD-SEM-1 — Семантика статусов остановок «Загрузки»: done/pending по факту просмотра, error/warning только у «Структуры»

Дата: 2026-10-20. База: `main@7556e3f` (MNS-CERT-6). Постановка тимлида (обсуждение 2026-10-20, чат): модуль «Загрузка» несёт ознакомительные функции; единственный содержательный «стоп» исследования — остановка «Структура» при невозможности определения структуры загруженных данных; статусы `done/pending` получают все остановки по факту просмотра (паттерн EDA PROGR-18), и только «Структура» несёт красный `error` и жёлтый `warning`.

---

## 1. Постановка и границы

**Противоречие, закрываемое задачей.** Наставник «Следующий шаг» v2 (спека `spec_mentor_next_step.md`, сертифицирована MNS-CERT-6) сканирует канон `SCAN_STAGES × STAGE_NODES` — «Загрузка» первая, и все её 5 узлов объявлены warning-способными (реестр `rules/mentor_stop_explanations.json`, 25 записей). Жёлтый на «Обзоре»/«Графике»/«Качестве» — факт о входных данных, а не действие: в модуле нет ни одного мастера исправлений (справка модуля: «Модуль ничего не исправляет и не преобразует»). Рекомендация Наставника «откройте остановку X модуля "Загрузка" и разберите…» ведёт в место, где аналитику нечего делать, — тупик контракта «куда идти».

**Решение (принцип агентности):** warning/error — только там, где у аналитика есть действие in-place. На «Загрузке» таких две: подтверждение/исправление структуры и замена датасета (dropzone доступна всегда). Остальные остановки — ознакомительные: `done` = «аналитик открыл и результат показан», `pending` = «не открывал».

**Границы задачи:**
- меняется СЕМАНТИКА статусов модуля «Загрузка» (фронт) и тексты semantics реестра объяснимости + §4 спеки (аддендум);
- НЕ меняются: канон скана (`SCAN_STAGES`, порядок `STAGE_NODES`), состав 25 записей реестра («ровно узлы STAGE_NODES трёх стадий»), движок node_status, эндпоинт `/upload-stops` (whitelist `CHECK_STATUS_VALUES` уже допускает `error`), 8 специфичных правил Слоя A, EDA/Валидация/Предобработка;
- без commit/push (AGENTS.md).

## 3. Проект

### 3.1 Новая формула stopStatus

| Остановка | Формула | Семантика |
|---|---|---|
| overview | `!isUploaded ? "pending" : viewed ? "done" : "pending"` | просмотр превью |
| chart | `!isUploaded ? "pending" : viewed ? "done" : "pending"` | просмотр графика (или честного объяснения, почему графика нет) |
| distribution | `!isUploaded \|\| numericCols.length === 0 ? "pending" : viewed ? "done" : "pending"` | просмотр засчитывается, только когда результат показан (EDA-правило) |
| structure | `!detection ? "pending" : dateImpossible ? "error" : confidentBoth ? "done" : "warning"` | факт-решение (PROGR-14-A сохранён) + НОВЫЙ error |
| quality | `!uploadData?.quality ? "pending" : viewed ? "done" : "pending"` | просмотр счётчиков |

Факт просмотра: остановка активна И результат показан (EDA PROGR-18); множество монотонно в пределах датасета; смена датасета (datasetId) — новая вселенная фактов.

### 3.2 Критерий error «Структуры» (консервативный)

`dateImpossible = detection && !dateColTouched && !detection.dateCol.candidates.some(c => c.score > 0)`

- авто-детект не нашёл НИ ОДНОГО правдоподобного кандидата временной колонки (реальная форма от бэкенда: `selected="(не использовать)"`, все score нулевые) И аналитик ещё не сделал явного выбора;
- снимается действием аналитика: явный выбор в селекторе (`dateColTouched`) → обычная семантика решения (явное «(не использовать)»/«(нет)» → done, сомнительная конкретная колонка → warning, PROGR-14-A);
- НЕ срабатывает: сомнительное угадывание с ненулевым score (Year@40 — жёлтый, прецедент FAO), нерегулярная сетка при уверенной дате (freq не определена, но решение уверенное → done), легитимный однорядный датасет.

Красный честно кодирует вторую ветку формулы тимлида «продолжить исследования либо искать новые данные»: рекомендация Наставника при error — «подтвердите структуру вручную или замените датасет».

### 3.3 Seed/якорь (урок H27, паттерн EDA)

Статусы перестают быть детерминированной функцией данных (становятся просмотр-зависимыми) → remount без seed'а перезаписал бы done-факты панели all-pending картой (класс H27). Зеркалится EDA: одноразовый `GET /v1/progress/trace` на вселенную; seed: узлы `upload/*` со статусом done (validity=current) → viewed («Структура» не сеется — она факт-обусловленная); якорь = снапшот записанных статусов как есть; seed не получен → отчёт удерживается, ретрай по новому просмотру. Якорь снимается при принудительном ре-посте после подтверждения структуры (`reportUploadStopsNow`) — панель обязана получить свежее наблюдение модуля (хронология решает, зеркало PROGR-13).

### 3.4 Миграция легаси-жёлтых

Старые трассы с warning на overview/chart/quality: якорь содержит recorded warning, живая формула даёт pending/done → первый снапшот отличается → доставляется как новое наблюдение (last-wins) → зеркало выравнивается на новую семантику без ручных миграций.

## 5. Риски и меры

- **R1 — потеря «жёлтого маяка»** parse_warnings/качества со степпера: информация остаётся в контенте (тост при загрузке, баннер и счётчики на остановках, Паспорт); Наставник получает те же проблемы как actionable-warning в Валидации/Предобработке, где есть мастера исправлений.
- **R2 — легаси-жёлтые в старых трассах**: last-wins + первый отчёт модуля по якорю §3.4.
- **R3 — ложный error на легитимных данных**: критерий §3.2 требует нулевых score ВСЕХ кандидатов и неактивности аналитика; сомнительное угадывание остаётся жёлтым; гвард-тесты на оба случая.
- **R4 — H27-регресс (remount перезаписывает факты)**: seed+якорь по сертифицированному паттерну EDA (AUDIT-2B/3), отчёт удерживается без seed'а.
- **R5 — рассинхрон зеркала при подтверждении структуры**: якорь снимается в `reportUploadStopsNow` — принудительный ре-пост гарантирует «панель == модуль».
