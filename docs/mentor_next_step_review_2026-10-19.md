## 2. Проверка гипотезы, п.1 — «первая ближайшая остановка с warning»

### 2.1. Что подтверждается

- Форма «нашли жёлтую остановку → объяснили → отправили на остановку» — это ровно то, что делают 6 из 8 существующих правил; гипотеза не ломает канон, а обобщает его.
- ONE-recommendation («первая ближайшая», не список) — уже зафиксированный канон §7.1, гипотеза ему соответствует.
- Единая проекция статусов (AUDIT-5B) уже даёт детерминированный снапшот всего графа на момент вызова — источник для скана есть, нового I/O не нужно.

### 2.2. Что требует поправок (частичное опровержение)

**(а) «Жёлтый» существует не на всех стадиях — только на 25 узлах из 50.** CheckStatus (`done/warning/pending/skipped/running/error`) живёт у Загрузки (5), Валидации (10), Предобработки (10). Для EDA решение тимлида зафиксировано (PROGR-18, v1.1 §2): статус `done/pending` по факту просмотра, **warning не вводится** (EDA — анализ, не проверка качества; ложная тревога там, где нет критерия ошибки). Моделирование и Прогнозирование — процессные стадии (`StageStatus pending/in_progress/done`), узлового warning у них нет по определению §3. Значит скан «первой жёлтой» определён только на стадиях `upload | validation | preprocessing`. Это не дефект, а граница применимости гипотезы, которую нужно зафиксировать явно.

**(б) Текущий порядок правил — НЕ порядок пайплайна, и это видно контрпримером.** `validation/sufficiency == warning` (стадия 2) + `preprocessing/missing == warning` (стадия 3): движок выдаст `preprocessing_missing_attention` (priority 30) раньше `validation_sufficiency_attention` (priority 40), хотя Валидация в `STAGES` стоит раньше Предобработки. Приоритеты назначались пачками по мере появления правил (10/15/20/30/40 — batches PROGR-6/v1.1), а не выводились из канона порядка; методологическая нагрузка на числа приоритетов нигде не документирована.

**(в) «Последовательность остановок подтверждена методологически» — верно наполовину.** Подтверждаю на уровне стадий: `STAGES = upload → validation → preprocessing → eda → modeling → forecasting` — инвариант с import-тестами (`test_pipeline_graph.py`, паттерн CERTIFIED_IDS), направленный ациклический граф с решением «остановка ниже по течению не может изменить статус остановки выше» (PROGR-24-ORIGIN-C, `spec_progress.md` §3.2). Частично подтверждаю внутри Предобработки: есть реальные жёсткие зависимости (регулярность → декомпозиция/спектр: STL и спектр требуют равномерной сетки — это каноническое правило §7.1). Но опровергаю универсальность: реестры Валидации (`CHECK_IDS` + `CHECK_SECTIONS`: schema → formats → ranges → …) — группировка «от структурных к содержательным», проверки гоняются пакетом независимо; порядок EDA — порядок просмотра, не зависимостей; Моделирование — явный граф с capability-статусами, «не линейный флоу» (§2). То есть **порядок реестра узлов — детерминированная презентационная конвенция, а не цепочка жёстких методологических зависимостей**. Для цели «первая ближайшая жёлтая остановка» использовать его можно — но как *канон сканирования* (детерминизм, воспроизводимость, одинаковый порядок у панели и Наставника), а не как утверждение о жёстких зависимостях между соседними узлами.

**(г) В гипотезе не упомянут `error` (красный).** `CHECK_STATUS_VALUES` включает `error` (проверка упала). Узел с `error` — более срочный, чем `warning`; ни одно из 8 правил на `error` не смотрит, и в текущем каноне красная остановка не даёт рекомендации вовсе. Скан v2 обязан различать: `error` старше `warning`.

**(д) Ключевое самопротиворечие, которое закрывает гипотеза.** Жёлтая остановка вне покрытия 8 правил (например, `validation/ranges`, `preprocessing/variance_stab`, `upload/overview` с parse-warnings) даёт: панель «Прогресс» — жёлтый узел, свод стадии `warning_nodes > 0`, `phase_text` честно говорит «найдены проблемы», а `recommendation == None` → MentorPanel показывает зелёное «Критичных подсказок нет — исследование идёт по плану». Один JSON противоречит сам себе. Инвариант v2: **есть жёлтая/красная остановка ⇒ рекомендация != None**; тишина честна только когда проблемных узлов нет вообще.

### 2.3. Вердикт по п.1

Гипотеза **принимается как целевая семантика** с четырьмя уточнениями: (1) скан ведётся по warning-способным стадиям (upload, validation, preprocessing) — EDA и процессные стадии в скан «жёлтого» не входят; (2) `error` сканируется с приоритетом над `warning`; (3) порядок — двухуровневый: специфичные методологические правила (зависимости типа «регулярность до декомпозиции») поверх детерминированного fallback-скана по канону `STAGES × STAGE_NODES`; (4) «методологическая подтверждённость» последовательности фиксируется на уровне стадий, внутри стадий порядок реестра — канон сканирования, а не жёсткая цепочка зависимостей (документируется, не перевыдумывается).

## 3. Проверка гипотезы, п.2 — «объяснить почему жёлтый и рекомендовать исправление»

### 3.1. Материал для объяснения уже посчитан — нового I/O не нужно

- `status_reason` узла — из тех же фактов: `EVENT_NODE_REASON` (`node_status.py:141`, «Найдены нарушения: предпросмотр коррекции» и т.д.), `correction_reason` с числами, payload-статусы отчётов модулей (`upload_stop_status` / `validation_check_status` / `preprocessing_check_status` с честными причинами «нарушения остались»);
- `summary_count` — то же число, что в бейдже узла (например, `total_missing`);
- методология остановки — **уже существует вербатимом**: `apps/api/knowledge/registry_data.json`, `help_entries` 78 записей (facet `metrics` — «Метрики и алгоритм» 30, `pipeline` — описание остановки 30, `stage_overview` 12, `module_help` 6) + 14 library-статей; `run_report.py::node_methodology()` уже рендерит этот текст VERBATIM («пересказ уже посчитанного», no fabricated results).

### 3.2. Чего не хватает

- Шаблоны текущих next-step-правил — статичные строки: числа и причины узла в них не подставляются (`evaluate_next_step` передаёт контекст `{"statuses": …}`, шаблоны им не пользуются).
- Рекомендация не адресует остановку точно: deep-link обрезается до вкладки стадии. Аналитик с жёлтой «Стабильностью дисперсии» попадает на верх Предобработки, а не на остановку.
- «Рекомендация по исправлению дефекта» имеет фиксированную границу по §7: Наставник говорит «куда идти» (deep-link на остановку) и «почему жёлтый» (факты + методология остановки), но **не выбирает стратегию исправления** — выбор метода/порога остаётся за аналитиком (канон правила «мечется»: «как решать», а не «куда идти»; §7.2 sanity-правила советуют уже на preview Мастера). Это границу сохраняем: рекомендация = переход на остановку + объяснение, не выбор стратегии.

### 3.3. Связь с LLM/RAGFlow

Контракт `spec_education.md` §4.2 сохраняется: решение (что жёлтое, куда идти) остаётся за правило-движком; `MentorTextRenderer` Protocol (§8) — единственная точка переформулировки текста. Ничего в гипотезе от этого не ломается; наоборот, структурированная рекомендация v2 (rule_id + узел + факты + ссылка на методологию) — готовый каркас для будущего `RagflowMentorTextRenderer`.

## 4. Экспертное заключение (сводка)

1. **Гипотеза принимается** как целевая семантика «Следующего шага» v2: детерминированная первая проблемная остановка + объяснение + адресная рекомендация. Она совместима с канонами §7.1 (ONE-recommendation), §3.2 (советы — не факты: объяснение не пишется в трассу, частота открытий панели — не телеметрия), §3.1 (`session.stages` не трогаем) и не требует пересчёта статистик — только пересказ уже посчитанного.
2. **Архитектурно правильная форма — гибрид, не замена.** Существующие специфичные правила сохраняются с приоритетами (они кодируют реальные методологические зависимости и процессные гэпы Моделирования/Прогнозирования, которые скан «жёлтого» не увидит в принципе). Добавляется общий fallback-скан: `error` раньше `warning`, далее канон порядка `STAGES × STAGE_NODES` по warning-способным стадиям. Замена движка на чистый скан опровергается: он теряет зависимости (`regularity_before_decomposition`) и процессные правила (`selected_without_backtest`, `forecast_not_compared`).
3. **Объяснение собирается из трёх уже существующих слоёв**: `status_reason` + `summary_count` (почему жёлтый, с числом), текст правила (что это значит), методология остановки из `help_entries` (что с этим делают, VERBATIM — паттерн `node_methodology`). Реестр «объяснимости» на 25 warning-способных остановок — новый декларативный артефакт с fail-closed валидацией (паттерн `upload_stops.json` / `mentor.yaml`).
4. **Deep-link доезжает до остановки**, не до вкладки: контракт `stage.node_id` уже несёт узел — не хватает фронтенд-навигации до него.
5. **Инвариант v2**: жёлтая/красная остановка ⇒ рекомендация != None. Тишина остаётся честной только при полном отсутствии проблемных узлов.
