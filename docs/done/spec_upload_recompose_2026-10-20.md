## 1. Постановка и границы

**UPLOAD-SEM-1 выразил агентность аналитика семантикой статусов, но не инструментов.** На «Структуре» действие «подтвердить структуру» декларировано (рекомендация Наставника при error: «подтвердите выбор вручную или замените датасет»), однако зелёный `done` ставится одномоментно из детекции — аналитик видит «зелёно» ещё до любого своего решения, и кнопка подтверждения как отдельное действие не существует (`handleApplyOverride` «Применить и пересчитать превью» — локальный пересчёт override, не гейт статуса). Пункт (а) закрывает этот разрыв: `done` у «Структуры» = факт явного подтверждения аналитиком, а не факт уверенного угадывания детектора.

**Пункт (б) — прозрачность маршрутизации.** Справочная схема «Определение структуры данных» (`StructuralClassSchema.tsx`, 7 правил + 2 подстроки панели) визуально перегружена: каждое правило — строка «условие → английский класс». Русскоязычных определений классов нет нигде в схеме (label'ы классов — только в карточке структурного класса). Требование: компактная табличная форма + столбец «Определение (RU)», подсветка совпадающей строки и подписи сохраняются.

**Пункт (в) — инструменты для панели.** Платформа корректно классифицирует панель (`panel_balanced`/`panel_unbalanced`/`panel_unknown`, карточка + panel-balance endpoint), но не даёт ни одного in-place действия: EDA просит «выберите одну сущность» (`apps/api/eda_correlation.py:41–49`), паспорт ряда отказывает на повторяющихся датах (`app/core/passport.py:144–147`), декомпозиция недоступна. Единственный путь к классическому пайплайну сегодня — сведение панели к одному ряду ВНЕ платформы. Противоречие с принципом агентности: у аналитика на «Структуре» должно быть действие, а его нет. Пункт (в) добавляет два микросервиса преобразования (фильтр сущности; агрегация по времени) + честную альтернативу «исследуем панель как есть» (бейдж).

**Границы задачи:**
- меняется: фронт остановки «Структура» (`TsAnalysisUpload.tsx`, `StructuralClassSchema.tsx`, `structuralClass.ts`), `POST /v1/session/date-column` (снятие искусственного гейта score≥0.7 для явного подтверждения), ДВА новых preview/apply-эндпоинта панельных преобразований, контур `upload-stops` (семантика узла structure), реестр `rules/mentor_stop_explanations.json` (semantics structure), справка модуля;
- НЕ меняются: канон скана `SCAN_STAGES × STAGE_NODES` и состав 25 записей реестра, семантика просмотров overview/chart/distribution/quality (UPLOAD-SEM-1), критерий `dateStructureImpossible` (PROGR-14-A/UPLOAD-SEM-1 §3.2), панельная проверка баланса, движок `node_status` (событие `structure_confirmed` уже в каноне `EVENT_NODE_STATUS`), сессия Валидации/Предобработки/EDA;
- панельные модели (FE/RE/Panel VAR, entity-pivot) — ВНЕ этой задачи: см. `docs/panel_models_2026-10-20.md` (PANEL-MODELS-3); бейдж «Ряд не трансформируем» честно описывает состояние до её поставки;

## 3. Проект

### 3.1 Пункт (а): подтверждение «Структуры» кнопкой

Новая формула узла `structure` (переход от факт-обусловленной к решающе-обусловленной):

| Состояние | Формула | Семантика |
|---|---|---|
| pending | `!detection \|\| (!structureConfirmed && confidentBoth && !dateStructureImpossible && !suspicious)` | детекция уверенная — ждём подтверждения (НЕ зелёный) |
| warning | `!structureConfirmed && suspicious && !dateStructureImpossible` | сомнительное угадывание (PROGR-14-A сохранён) |
| error | `!structureConfirmed && dateStructureImpossible` | авто-детект не нашёл кандидатов (UPLOAD-SEM-1 §3.2 сохранён) |
| done | `structureConfirmed` | аналитик нажал «Подтвердить структуру данных» |

- `suspicious = !(isStructureDecisionConfident(dateCol) && isStructureDecisionConfident(entityCol))` — вынесено в именованное вычисление (текущая инлайн-логика 1178).
- Кнопка «Подтвердить структуру данных» на остановке «Структура»: активна при `detection && (дата выбрана как конкретная колонка ИЛИ «(не использовать)» после явного выбора)`. Подтверждение — СВЯЗКА ДВУХ ФАКТОВ: (1) фронт: `setStructureConfirmed(true)` → done; (2) бэкенд: `POST /v1/session/date-column` с выбранным колонком (или флагом «без временной колонки») → хук трассы пишет `structure_confirmed` → узел панели `upload/structure` = done. Затем `reportUploadStopsNow()` (якорь снимается — зеркальный ре-пост, хронология решает; механизм готов с UPLOAD-SEM-1).
- Снятие искусственного гейта: в `POST /date-column` условие `score < 0.7 → 422` заменяется на «явное подтверждение аналитика»: требование остаётся — колонка существует, ≠ target, ≥2 валидных даты; НИЗКИЙ score больше не блокирует (аналитик взял ответственность — семантика PROGR-14-A «явный выбор снимает»). Параметр запроса `confirmed: bool = True` — GET-профиль детекции не затронут. Риск завала мусорной колонкой принят сознательно: выбор физически делает аналитик в селекторе; passports инвалидируются как раньше (`set_date_column` уже сбрасывает несовпадающие паспорта).
- Вселенная факта: `structureConfirmed` живёт в viewed-контуре модуля и сеется при remount из трассы (узел `upload/structure` validity=current со статусом done → `structureConfirmed=true`; UPLOAD-SEM-1 seed-механизм переиспользуется — снимается исключение «„Структура" не сеется»). Смена датасета (datasetId) — сброс в false.
- После подтверждения изменение селекторов даты/группировки/частоты сбрасывает `structureConfirmed` в false (подтверждение относится к зафиксированной конфигурации; повторное подтверждение — той же кнопкой).

### 3.2 Пункт (б): компактная таблица «Определение структуры данных»

`StructuralClassSchema.tsx` переписывается с блочного списка на компактную таблицу:

| Признаки (условие) | Класс | Определение |
|---|---|---|
| Нет даты И нет группировки | Cross-Sectional | Кросс-секционные данные: измерения без временно́й оси |
| Есть дата, ОДНА числовая колонка, нет группировки | Univariate TS | Одномерный временной ряд |
| Есть дата, МНОГО числовых колонок, нет группировки | Multivariate TS | Многомерный временной ряд: несколько рядов на общей сетке |
| Есть дата И есть группирующая колонка | Panel Data | Панельные данные: сущности × время |
| — у всех групп одинаковый набор дат | Panel Data — Balanced | Сбалансированная панель |
| — иначе | Panel Data — Unbalanced | Несбалансированная панель |
| Есть колонки координат (lat/long) + дата | Spatio-Temporal | Пространственно-временные данные |
| Обнаружена вложенная иерархия (страна → регион → …) | Hierarchical | Иерархические данные: вложенные уровни агрегации |
| Timestamp + категориальная «событие»/«действие», нерегулярный шаг, нет содержательных числовых рядов | Event Time Series | Событийный ряд: точки-события, не значения |

- Русские определения — ЕДИНЫЙ ИСТОЧНИК в `structuralClass.ts` (`RU_DEFINITION: Record<StructuralClass, string>`; для `panel_unknown` — «Панельные данные (баланс уточняется)»), схема и карточка класса читают оттуда; вторая копия строк запрещена.
- Подсветка active-строки (bg-brand + Check) и подписи сохраняются; компактность: таблица `text-xs`, строки py-1.5, заголовок-строка, панельные подстроки — с отступом; высота блока сокращается ориентировочно на треть против текущего списка.
- Тест-гарды: пин всех 9 русских определений, пин подсветки (activeClassId → класс строки), пин отсутствия изменений правил дерева (условия дословно).

### 3.3 Пункт (в): панельные микросервисы на остановке «Структура»

При `isPanelCandidate && structuralClass.id ∈ {panel_balanced, panel_unbalanced, panel_unknown}` под карточкой класса появляется блок «Панельные данные: три пути исследования» — карточка-выбор из трёх альтернатив, каждая с подробным описанием. До явного выбора показана третья (бейдж) — состояние по умолчанию.

**Микросервис 1 — «Фильтр сущности»** (свести панель к одному ряду одной сущности):
- описание (в UI): «Оставить в датасете строки только одной сущности (например, один регион). Панель превращается в обычный временной ряд — открываются декомпозиция, ACF/PACF, классические модели и прогноз. Используйте, когда исследовательский вопрос про конкретную сущность»;
- UI: селектор значения сущности (уникальные значения entity-колонки), превью результата (T наблюдений, диапазон дат, частота), кнопка «Применить»;
- бэкенд: `POST /v1/session/dataset/entity-filter` — preview/apply по сертифицированному паттерну (`payload.apply`); preview: `(n_rows_before/after, n_dates, date_min/max, frequency)`, валидации fail-closed (entity_col/date_col существуют; значение есть; после фильтра ≥ паспортный минимум точек); apply: мутация `session.dataframe` (keep строки значения), честный summary; сессия сохраняется, паспорта инвалидируются;
- после apply фронт перезапускает контур детекции модуля (re-detection) → класс становится univariate/multivariate TS → block исчезает; факты модуля = новая вселенная (см. §3.4).

**Микросервис 2 — «Агрегация по времени»** (свести панель к одному ряду агрегатом по сущностям):
- описание: «Для каждой даты усреднить (или просуммировать) значения по всем сущностям. Панель превращается в один агрегированный ряд. Используйте, когда исследовательский вопрос про совокупность целиком; суммирование — только для аддитивных величин (объёмы), для уровней (цены, индексы) — среднее»;
- UI: селектор функции агрегации (mean/sum/median/min/max), превью (число дат после агрегации, политика пропусков: даты без ни одного валидного значения отбрасываются, честный счётчик), кнопка «Применить»;
- бэкенд: `POST /v1/session/dataset/panel-aggregate` — preview/apply; группировка ТОЛЬКО по date_col (`groupby(date).agg(func)` по числовым колонкам, нечисловые — first); если entity-колонка остаётся — удаляется из результата с пометкой в summary; apply инвалидирует паспорта, возвращает summary (rows_before/after, n_dates, skipped_dates);
- после apply — тот же контур re-detection, что в микросервисе 1.

**Альтернатива 3 — бейдж «Ряд не трансформируем, исследуем панельные данные»:**
- пассивный бейдж (не кнопка): текст + пояснение «Панель сохраняется как есть. Доступно: по-сущностные проверки Валидации (регулярность, достаточность), панельная проверка баланса. Панельные модели исследования и прогноза — контур PANEL-MODELS-3 (в разработке); классические однорядные модели к панели неприменимы без сведения к одному ряду»;
- выбор альтернатив 1/2 не обязателен: бейдж — дефолтное состояние, исчезает после применения любого микросервиса (данные уже не панель);
- намеренно НЕ является третьим «действием»: платформа не выполняет от имени аналитика отказ от преобразования как операцию над данными (честность: отсутствие мутации — не мутация).

**Методологические запреты (честность, без исключений):** молчаливая агрегация НЕ выполняется нигде вне явного apply (EDA-принцип «агрегация меняет статистический объект»); агрегация по сущностям без подтверждения аналитика запрещена на уровне API (нет автоматического вызова панельных эндпоинтов из других модулей).

### 3.4 Вселенная фактов после преобразования

Apply микросервиса меняет данные при том же datasetId (lineage-файл) → факты просмотров/подтверждения валидны для ПРЕЖНЕГО содержимого. Решение: локальный счётчик `transformEpoch` модуля (0 при загрузке, +1 на каждый apply), входящий в `universeKey` (`datasetId + ':' + transformEpoch` для факт-контура) и сбрасывающий `viewedStops`/`structureConfirmed`/panelBalance к состоянию «новые данные»; после re-detection остановки снова pending, отчёт в панель — как новая вселенная (H27-безопасно: seed нового epoch берёт трассу узлов той же поставки; снапшоты разных epoch не смешиваются). Альтернатива «смена datasetId» отклонена: datasetId принадлежит файлу, не версии содержимого (дедуп поставки §12 п.4 опирается на стабильность id внутри run).
