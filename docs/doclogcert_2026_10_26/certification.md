## 1. Вердикт

**Полная сквозная сертификация по спецификации НЕ ПРОЙДЕНА.** Есть работающие, проверяемые компоненты: объектный доступ, реестры, замороженные снимки, рендеринг/выдача, lifecycle, monitoring и журналы. Но путь «обычный анализ → доступный первый документ → документ с содержательными результатами этапа» не замкнут. Предыдущий итог `PASSED WITH BOUNDARIES` нельзя распространять на этот пользовательский путь.

Блокеры: потеря run-контекста при общем переходе в «Документы», запрет создать первый документ из пустого списка, отсутствие вызовов промоушена результатов из научных handlers. Дополнительно подтверждены неправильная актуальность исторических claims, слабый смысл `complete`, неполный рецепт D04 и нарушение fail-closed при обязательном аудите создания профиля.

Это **аудит**, а не исправление. Продуктовые файлы не изменялись; пользовательские/production данные и deployment не открывались. Прежние рабочие копии с незакоммиченными изменениями сохранены. Коммит, push и deploy не выполнялись.

## 2. Что именно проверено

1. Код синхронизирован в отдельный detached worktree на заданный commit.
2. Сверены требования §6–§20 спецификации, контрактные документы DOCLOG-0…9 и прежние акты. Прошлая запись worklog не принималась за экспериментальное доказательство текущего поведения.
3. CSV получен из **штатного TypeScript-генератора** `DEMO_DATASETS[forecast_monitor_n150].generateCsv()`, а не из похожего numpy-скрипта. Файл включён в образцы; его SHA256 и версия среды — в `protocols/scenario.json`.

Данные/реестры — одноразовые Memory stores; файлы — собственный временный каталог. Никаких заранее созданных artifact/document записей в этой части опыта нет.
5. После каждого этапа проверен список документов; после коррекций — сессионный паспорт, durable artifact registry и ledger.
6. Отдельной явной командой API созданы D02/D03/D04, собраны MD/HTML/JSON/PDF, проверены права и неизменность scientific state при чтении/рендеринге. Для PDF вызван штатный worker `run_once`, фоновые workers были отключены для управляемости опыта.
7. Новые acceptance-оракулы проверяют требования, а не закрепляют ошибочное поведение как правильное. Их RED сохранён; продукт под тест не подгонялся.

Границы: это воспроизведение логики текущей базы, **не восстановление вашей конкретной сессии**. Параметры пользовательских коррекций не предоставлены; в опыте выбраны `median_mode` и IQR `cap`. Отсутствие документов и UI-тупик от выбора этих параметров не зависят. Живой браузер/Render/Vercel, production PostgreSQL, настоящие IAM/backup и нагрузочные SLA не удостоверены.

**Почему у вас ничего не появилось:** текущая реализация не создаёт document records автоматически после пройденных остановок. Она ожидает явный POST «Создать черновик». Открытие раздела только читает список — это соответствует §12.1 и само по себе не дефект. Однако способ выполнить **первую** команду из UI сломан, а данные для содержательного документа не продвигаются из исследовательского контура в artifact layer. Поэтому объяснение «надо было просто нажать кнопку» неполно и неверно для свежего исследования.

Обычный паспорт свойств в сессии и D02 «Паспорт источника» в реестре документов — разные сущности. Подтверждение структуры или расчёт паспорта не регистрирует D02 автоматически. Аналогично, событие `correction_applied` ещё не равно полному документу рецепта с исходными/конечными данными.

## 4. Подтверждённые находки

### C01 — общий переход не передаёт активный ResearchRun

**Серьёзность:** высокая для пользовательского пути. `ModuleNav.tsx` даёт `href="/documentation"`. Страница читает только `searchParams.run`; клиент передаёт его Workspace без восстановления из активного исследования. При `runId=null` Workspace показывает empty и не вызывает list API. Поэтому общий бейдж «Документы» может показать пустоту даже при существующих документах.

Ссылка из ProgressDrawer содержит `?run=...` и эту конкретную проблему обходит. Это не обход C02. Основание: `ModuleNav`, standalone `documentation/page.tsx`, `documentation-client.tsx`, `DocumentationWorkspace.loadDocuments`.

### C02 — невозможно создать первый документ через Workspace

**Серьёзность:** блокирующая. Пустой ответ переводит `listPhase` в `empty` и сбрасывает `activeKind` в null. После ручного выбора вида кнопка появляется, но имеет `disabled={creating || listPhase !== "ready"}`. `ready` получится только после наличия хотя бы одного документа — требуется предварительный документ для создания первого.

Вторая проба: deep link с `initialKind=D03` тоже не спасает — после загрузки пустого списка выбор очищается. Positive control с уже существующим document record делает создание доступным. Это не сетевой отказ, не ошибка dataset и не недостаток API-доступа.

**Доказательство:** `bootstrap.test.tsx`, первые два RED; третий независимый RED в этом файле описан в C07. Корректный контракт: разрешать создание после успешного **пустого** ответа при известном run и выбранном kind; сохранять выбор вида.

### C03 — PromotionService не подключён к результатам реального анализа

**Серьёзность:** блокирующая для научных документов/воспроизводимости. `artifact_promotion.py` реализует `promote_passport`, `promote_backtest`, `promote_model_card`, `promote_forecast`, `promote_checkpoint_data`. В продуктовом API-коде вне этого модуля не найдены вызовы этих промоутеров. В реальном сценарии после capture/validate/apply registry пуст, хотя паспорт и события в сессии/ledger существуют.

SnapshotService принципиально читает durable layer, а не сессию. Поэтому он закономерно не видит паспорт; D02 прямо пишет: «Паспорт источника не продвинут в устойчивый слой (promote не выполнялся)». Для всех трёх документов отсутствует data_ref. Это не надо «исправлять» чтением живой сессии во время скачивания: промоушен должен происходить при фиксации научного результата, с исходным context/revision, receipt и честной обработкой ошибки доставки.

Наличие helper/service API и тестов с заранее продвинутыми артефактами подтверждает инфраструктуру, но не подключение producer→artifact→document.

### C04 — исторические факты маркируются current

**Серьёзность:** высокая, §10 R07 и §11. `SnapshotService._event_claim` начинает с `VALIDITY_CURRENT` и не сравнивает `event.context_id` с контекстом снимка. Меняется статус только при неразрешённом artifact ref.

В нашем опыте **12 из 13** привязанных к событиям claims имеют другой context_id, но `claim_validity=current`: загрузка, 10 проверок до коррекций и первая коррекция. Последняя коррекция относится к текущему контексту. Исторические события действительно происходили; ошибка — в обещании актуальности их результата для последней версии данных, а не в существовании событий.

Подтверждение — `scenario.json.event_claim_validity` и RED `test_historical_event_claims_are_not_marked_current`. Нужно применять общую семантику current/stale/unknown, не отменяя исторический факт выполнения.

### C05 — complete означает только отсутствие битых ссылок

**Серьёзность:** средняя/высокая, §6/§10/§12. Сборщик ставит `complete`, если `ctx.missing_refs` пуст. Если нужный артефакт вообще не был создан и ссылка на него не добавлена, missing_refs тоже пуст.

Фактический D02 одновременно содержит «паспорт не продвинут», `data_ref=null`, `limited/missing_data_artifact` и **`completeness=complete`**. D03/D04 получают тот же флаг. Это допустимо как узкий технический показатель целостности перечисленных ссылок, но недостаточно и вводит в заблуждение как «полнота документа по виду» из спецификации. Полнота, integrity и reproducibility должны проверяться раздельно; обязательные gaps по виду документа должны быть перечислены.

RED `test_unknown_source_passport_is_not_presented_as_complete` закрепляет именно семантическое требование, а не отсутствие механической честности: текст документа и reproducibility ограничение сейчас показывают.

### C06 — D03/D04 не содержат требуемого научного протокола

**Серьёзность:** высокая для содержательной приёмки §6. D03 перечисляет статусы проверок из `client_observation`, но не сохраняет полный результат validate с правилами, порогами, знаменателями и результатными ссылками. Сам `validation_response.json` в опыте содержит подробности; они не становятся частью документа автоматически.

D04 выводит две строки: «Применена коррекция missing» и «Применена коррекция outliers». Выбранные `median_mode`, `cap`, `iqr`, изменённые 3/4 значения, входной/выходной digest и воспроизводимый порядок параметризованных операций не образуют рецепт документа. Часть информации есть в ответах/ledger, однако адаптер её не переносит. В `samples/D04.md` можно проверить это без запуска кода. RED проверки присутствия фактически выбранного метода сохранён.

Ссылки на event_id полезны, но не заменяют сам научный результат, если получателю не доступна соответствующая версия ledger/артефакта.

### C07 — ошибка явного создания черновика не показывается

**Серьёзность:** средняя, §12.3/AC17. `handleCreateDraft` снимает spinner и перечитывает список только при `result.ok`; ветки отображения ошибки нет. Проба с существующим документом и ответом create=503 не показывает alert/причину. Это отдельный RED `AC17: a failed create request is visible to the analyst`.

Здесь не утверждается, что API вашего deployment вернул 503: это контролируемая проверка поведения UI при отказе.

### C08 — обязательный audit профиля не откатывает защищённую запись

**Серьёзность:** высокая, AC11. Независимая проба с собственным MemoryOrgProfileRegistry и недоступным AuditSink: `create_profile` бросает MandatoryAuditFailure, но профиль уже создан. В `doc_profiles.py` порядок — `registry.create_profile` → `_audit`. Это подтверждение ранее известного F-D9C2, а не новая находка из пользовательского сценария.

RED `test_mandatory_profile_audit_failure_does_not_commit_policy` требует отсутствия protected write при отказе обязательного аудита и падает. Нельзя сертифицировать общий fail-closed всего сервиса только потому, что fail-closed работает на отдельных approve/publish путях.

### C09 — часть реализованных форматов не доступна из общего меню

**Серьёзность:** средняя, §7/§12.2. В `DocumentationWorkspace.BUILD_FORMATS` только MD/HTML/JSON/JSONL/CSV. Стандартный PDF, XLSX, Parquet и ZIP, которые backend уже умеет, не включены в общий селектор. DOCX/PDF-A имеют отдельный профильный контур; это не делает обычный PDF доступным тем же действием. Наш PDF создан через API.

Этот вывод — проверка каталога UI по коду, не visual-E2E. Он ограничивает оценку «все форматы реализованы для пользователя».

## 5. Что действительно работает

- Документы можно создать явной командой API из авторизованного текущего run; дальнейшая выдача готовых форматов работает в изолированной среде.
- Из трёх реальных snapshots получены 12 файлов MD/HTML/JSON/PDF. Все 3 PDF отрендерены и просмотрены: кириллица читается, обрезки/наложений на этих одностраничных образцах нет. Содержательные ограничения и ошибочные флаги **оставлены как в продукте**, а не исправлены в приложенных файлах.
- Отдельный клиент без сессии владельца не читает ревизии: HTTP 404. Это подтверждение на проверенных ресурсах, не доказательство всей production IAM-конфигурации.
- До/после сборки и чтения совпали DataFrame, target/date, context/revision и durable events. Аудит доступа может расти — он отдельно от scientific state.
- Существующие repo-сюиты проверяют metadata, staging/hash integrity, snapshot freeze, idempotency, auth/scopes, rendering, lifecycle/hold/archive, monitoring и profile validation. Большая часть этих компонентных проверок зелёная; результат не обнуляется интеграционными дефектами.

## 8. Открытые прежние находки и недоказанные свойства

- Акт DOCLOG-9-CERT в f1d6151 уже описывает F-D9C1 (ICC timestamp, PDF/A byte nondeterminism), F-D9C2 (порядок protected write/audit), F-D9C3 (failed validation evidence не читается через HTTP по job), F-D9C4/5 и bool-as-int наблюдение. **C08 перепроверен независимо; остальные здесь не объявляются повторно динамически проверенными или исправленными.** HMAC-профиль не называется юридической электронной подписью.
- Акт DOCLOG-5-CERT содержит F-D5C1: отмена в rendering может быть перезаписана завершением worker в ready. В текущих `cancel_job`/`complete_render`/worker нет явного атомарного CAS-гейта отмены перед завершением. В этой кампании race заново не запускался; закрытие находки не установлено. Предлагается вернуть сохранённый RED-пробник в обязательную приёмку fix.
- Предыдущий DOCLOG-CERT сам ограничивает PG, нагрузку, browser E2E и полную панель. Эти области и сейчас не превращаются в PASSED. Новые C01–C07 относятся к функциональному пути, доступному для проверки в этой среде, а не к отсутствию инфраструктуры.
- В прежнем `scripts/doclogcert/conftest.py` helper `seed_forecast` создаёт artifact напрямую, а `ensure_revision` вызывает сервис регистрации документа. Это допустимые компонентные фикстуры, но они обходят именно ту producer→promotion связь, которая отсутствует в пользовательском сценарии.

## 9. Минимальный порядок исправления и повторной приёмки

1. **Контекст страницы:** URL run имеет приоритет; при его отсутствии нужен разрешённый текущий run или явный выбор исследования. Пустой query не должен маскироваться под пустой реестр документов активного датасета.
2. **Первый документ и ошибки:** создать draft разрешено после успешного пустого списка; initialKind сохраняется; действие доступно и на узком экране. Отказы 404/409/422/503 показываются пользователю, повтор не теряет выбранный вид.
3. **Producer integration:** при успешном capture/check/apply/backtest/card/forecast продвигать точный результат с исходным context/revision/schema. Для DataVersion — сохранённые данные и рецепт. При сбое сохранять честный pending/receipt и восстановимую доставку; не повторять научную операцию при retry.
4. **Содержимое и валидность:** использовать единый context-validity reducer; перечень обязательных gaps по kind; D03 получает результаты правил/пороги/знаменатели, D04 — реально применённые параметры/изменения/refs и digest. Старые snapshots не переписываются; фикс создаёт новую версию.
5. **Защищённые операции/worker:** устранить C08 и проверить прежнюю race отмены. Проверка обязательного аудита должна быть согласована с commit protected state; одного исключения после записи недостаточно.
6. **Пользовательская выдача:** подключить реально поддержанные backend форматы к UI и показывать зависимость от профиля/валидатора/worker, не предлагать недоступный формат как успешный.
7. **Повторная сквозная приёмка:** чистое исследование с данным демо без предзаполненных артефактов/документов; затем ≥5 сущностей, forecast/actual revisions, отказ storage/audit/worker, рестарт durable store, две темы/узкий экран и внешняя проверка форматов. Вернуть все новые RED к GREEN с неизменённым смыслом требований.

Сначала исправляется нормальный пользовательский путь; автоматическое создание PDF после каждого клика для этого не требуется. Допустим явный пользовательский draft, если результаты уже документированы и действие действительно доступно.
