# AUTH-22 — Quote/top-up checkout и credit: проектирование

База: `7d233ad` (AUTH-21). Задача из `spec_auth_architecture.md` (строка AUTH-22: области `billing/topups, provider/inbox, UI`; критерий: «Только confirmed server payment начисляет CU; duplicate events/callback spoof/currency tamper закрыты», зависимости AUTH-21, AUTH-18). Нормативные правила — `spec_billing_accounts.md` §13.4 (quote → payment → credit), §13.8 (данные/API), §13.9 (согласование и запуск), приёмочные примеры E3/E5/E6; §12.3 spec_auth_architecture (UI «Пополнить»). Правила AGENTS.md соблюдены; commit/push/VM из сессии не выполняются.

## Объём и границы

**В объёме:** операторский каталог пакетов пополнения (trusted CLI, выключен по умолчанию — пустой каталог = контур закрыт), immutable quote с серверным снимком, durable order/outbox-сага (паритет AUTH-18: lease/fence/attempts, GET-подтверждение, Idempotence-Key), bounded inbox wake-up по существующему webhook-маршруту, атомарный кредит: переход заказа + purchased-лот (AUTH-21 `origin_order=order_id`) + обязательный аудит в одной PostgreSQL-транзакции, trusted reconcile/credit-paid recovery, три новых OWNER-эндпоинта `/v1/billing` (коллекция topups + topup-quotes + создание заказа; отдельный GET заказа избыточен — серверный статус виден в bounded-коллекции), UI-секция «Пополнение баланса CU» в обеих оболочках (пакет → quote → подтверждение → hosted checkout → серверный статус), миграция `0034_auth22_topups.sql` с защитными триггерами, гейты auth22/auth22-postgres, CI-матрица.

**Вне объёма (честные границы):** refund/dispute/chargeback как HTTP/UI — AUTH-23 (refund_hold/refund_confirmed/refund_failed лота реализованы в AUTH-21 и доступны trusted-командами); wallet/ledger READ-эндпоинты и финансовая приватность MEMBER — AUTH-24 (`GET /v1/billing/wallet`, `GET /v1/billing/ledger` не добавляются); автопополнение — запрещено v1 (§13.4); реальный прайс/запуск продаж — отдельная операторская поставка до коммерческого запуска (§13.9: кнопка покупки без провижиненного каталога честно отвечает `topup_not_configured`); MONO-кошельки остаются на operator-CLI начислениях AUTH-21 (top-up checkout — v1 только paid MULTI, паритет контура AUTH-18); live-платежи кодом запрещены (адаптер YooKassa требует `sandbox=True`, тестовый магазин — только для изолированных sandbox Account).

## Решения

**D1. Каталог пакетов — операторская таблица, не env и не клиент.** `auth_topup_packages` провижинится только trusted-командой (`manage_topups.py add-package`, reason + обязательный аудит в той же транзакции): `units` (micro-CU, 1…10^12), `price_minor` (1…10^10), `currency='RUB'` (v1, паритет cycle-config AUTH-18), `price_version`, `terms_version`, `enabled`. Пакеты immutable: UPDATE разрешает только флип `enabled true→false`, DELETE запрещён; изменение прайса = новый пакет + отключение старого (история цен сохраняется). «Цены задаются конфигурацией; конкретный курс данным документом не придумывается» (§13.4) — значения только от оператора. Клиент выбирает `package_id`, но не сумму/количество: DTO `TopupQuote` содержит `package_id` (+Command-поля), `extra="forbid"`; снимок цены копируется сервером из строки пакета.

**D2. Quote — immutable снимок.** `auth_topup_quotes(quote_id, account_id, owner_id, package_id, snapshot JSONB, digest, created_at, expires_at)`; snapshot копирует поля пакета + `account_id/owner_id/quote_id/expires_at`; `digest = sha256(canonical json(snapshot))`; `expires_at = min(now+15min, …)`. BEFORE UPDATE/DELETE запрещены (паритет auth18_quote_guard). Повторный quote того же payload/key при живом кэше — replay из `auth_team_commands` (`operation='billing-topup-quote'`, другой payload с тем же key → 409 `idempotency_conflict`, механизм `_replay/_record` AUTH-17). Rate-limit: ≤32 quote на Account за 24 ч → 429 `topup_quote_limit`. После expiry quote новый checkout не создаётся (confirm → 409 `topup_quote_expired`); уже созданный order исполняется по своему фиксированному снимку (D6).

**D3. Order — durable state machine.** `auth_topup_orders`: `pending → credited | canceled | review_required | paid_review` (§13.4 «created → pending_payment → paid/credited либо failed/cancelled/expired»; `paid_review` — деньги подтверждены, кредит требует решения оператора). Гварды строки: DELETE запрещён; привязки `(order_id, quote_id, account_id, units, created_at)` immutable; `payment_id/first_attempt_at/paid_at/credited_at` — только NULL→значение; терминальные `credited`/`canceled` неизменяемы (out-of-order «failed/pending» не отменяет уже decided — §13.4.5); `paid_review` допускает ровно один явный переход `→ credited` — только trusted `credit-paid` (D5), кодом из веба недостижим. `quote_id UNIQUE` (один order на quote — «повторный клик не создаёт повторный заказ», подтверждение того же quote возвращает тот же order), `payment_id UNIQUE`, `units NOT NULL CHECK(units>0)` копируется из снимка при confirm (не пересчитывается и не доверяется клиенту).

**D4. Кредит — только confirmed server payment, одна транзакция.** Proof — только authenticated `GET payments/{id}` после `GET /me` (merchant enabled/test shop, паритет AUTH-18; callback-поля — never proof, «Возврат браузера с success=true не начисляет CU» §13.4.3: отдельного browser-callback маршрута не существует, `/v1/billing/webhooks/yookassa` — untrusted wake-up). В `finish()` при валидном `succeeded`: state=`paid_review` → savepoint → `credit_purchased_order` (новый module-level hook в `wallet.py`: `auth_wallets FOR UPDATE` → status active → лот `purchased` с `origin_order=str(order_id)`, обязательный `auth_wallet_changed`-аудит) + order→`credited, credited_at` → commit. Crash между capture и commit — reconcile завершает ровно один раз (§13.4: «paid и credited могут быть одним атомарным доменным переходом»): invoice-состояние, не зафиксированное в БД, не существует; двойной кредит невозможен тройной защитой — терминальный state-гвард, `payment_id UNIQUE`, частичный уникальный индекс AUTH-21 `(account_id, origin_order)` (E3/E6).

**D5. Wallet отсутствует/заблокирован в момент кредита → `paid_review`, а не исключение.** Деньги получены — не теряются и не возвращаются молча; lot не создаётся; аудит фиксирует `wallet_required`. Разблокировка/возврат — явная операторская процедура: `manage_wallet.py issue-purchased --origin-order <order_id>` (AUTH-21 CLI, защищён тем же unique-индексом) → `manage_topups.py credit-paid --order-id` (CAS `paid_review→credited`, требует существование лота с этим origin_order — «reconcile credit либо контролируемый возврат, без необоснованного удержания денег и без двойного результата» §13.4.6). Отрицательный available/долг не возникает (лот не частичен).

**D6. Saga-исполнение — паритет AUTH-18.** claim: `state='pending' AND next_attempt_at<=now AND lease free … FOR UPDATE SKIP LOCKED LIMIT 1`; lease 45s/fence/attempts; worker I/O вне SQL-транзакций; backoff `15·2^n` сек (cap 900s). Create: Idempotence-Key = `order_id` (устойчив к повторам), metadata `{order_id, quote_digest}`, description «CISStat DataTime Lab CU top-up» (адаптер расширен опциональным `order["description"]`, дефолт прежний — AUTH-18 поведение байт-в-байт). Нет candidate 15 мин → `review_required`; окно create 23 ч → `review_required`; `review_required` снимается только trusted `reconcile` (API-proof обязателен, «paid flag» им не является). Shop/sandbox снимка ≠ gateway → `review_required` сразу.

**D7. Inbox/wake-up — bounded, untrusted.** Расширяется существующий `POST /v1/billing/webhooks/yookassa` (нового маршрута нет): после subscription `notify` вызывается `TopupService.notify` с той же семантикой — только известные bound payments или UUID order-hint получают wake-up; неизвестные callback'и не аллоцируют строк; максимум 3 события на bound payment (`auth_topup_inbox PK(payment_id,event)`, immutable), один unverified candidate на order; cooldown 30 s по `last_observed_at`. Wake-up не делает I/O и не меняет состояние, кроме `next_attempt_at`/`candidate_id` — proof берётся только из API-GET.

**D8. Duplicate/spoof/tamper-оракулы.** (а) duplicate events одного платежа — wake-up идемпотентен, кредит одноразовый по D4; (б) spoof — webhook без merchant-подписи не имеет authority по построению (только wake-up), подмена recipient/amount/currency/metadata ловится `validate` (снимок pins amount/currency/shop/test/metadata) → `review_required`/`candidate_invalid`, лота нет; (в) currency tamper — пакет и снимок фиксируют `RUB`, `validate` сверяет `amount` целиком; частичная подмена → `ProviderMismatch`; (г) два разных payment ID на один order — второй candidate игнорируется notify-гвардом `candidate_id`; (д) payment_id другого order — UNIQUE + metadata-binding.

**D9. Допуск к покупке (§13.3).** `can_purchase_cu` effective: personal current OWNER, paid MULTI (`account_type='multi'`, план ∉ demo/internal), Account status active, свежий login/MFA (`_fresh`, паритет confirm AUTH-18), CSRF/Origin (SafeAuthRoute), account_version CAS. **Кошелёк обязателен и активен** на quote и confirm: без строки кошелька — 403 `wallet_required` (оператор провижинит через AUTH-21 CLI), locked — 403 `wallet_locked`. MEMBER/demo/internal получают отказ без checkout-пути (сообщение ведёт к OWNER). Покупка не меняет membership/capabilities/plan/seats (E5): credited order не трогает `auth_accounts` вовсе.

**D10. Кредит — только целый purchased-лот.** `units` из снимка пакета; частичных self-service возвратов в v1 нет (AUTH-23 вернёт целый неиспользованный lot по исходному заказу, E4). Promotional/included этим контуром не создаются. Начисление не зависит от cycle/seats; purchased бессрочен (CHECK AUTH-21) и не обнуляется rollover'ом.

**D11. Аудит.** Кредит в транзакции саги: обязательный `auth_wallet_changed` (43-й каталог, AUTH-21) через `_wallet_audit`; переходы заказа — `team.audit` (`billing-topup-quote`, `billing-topup-order`, `billing-topup-credited/canceled/review_required`, `provider:yookassa`, паритет AUTH-18); операторские команды каталога/recovery — обязательный аудит с reason и `via="operator_cli"` в той же транзакции. Отказ записи аудита откатывает кредит (fail-closed, R7-паритет AUTH-21).

**D12. Роуты затронуты — 3 новых OWNER-эндпоинта.** `POST /v1/billing/{account_id}/topup-quotes`, `POST /v1/billing/{account_id}/topups`, `GET /v1/billing/{account_id}/topups` (GET возвращает каталог пакетов + последние 20 заказов с серверными состояниями — покрывает и каталог, и статус-экран §12.3 без отдельного маршрута заказа). Registry: операция `billing.topup` (service/platform, authority external) + 3 bindings; webhook остаётся `billing.provider`. Прочее — derived: inventory (--write), OpenAPI/TS (auth01 generator), proxy allowlist (274→277). Научные пути не переименованы; общее число actual API 274→277.

**D13. UI — секция «Пополнение баланса CU» (обе оболочки, только paid MULTI).** `TopupPanel.tsx` в AccountScreen рядом с BillingPanel: «Показать пакеты пополнения» → GET topups; выбор пакета → quote (CU-количество, сумма/валюта, price/terms versions, срок действия) → «Подтвердить предложение» → order view: `pending` + hosted-checkout ссылка (только `https://(yoomoney|yookassa).ru`, `safeCheckout` паритет) + явное «Возврат со страницы оплаты не подтверждает платёж; статус появится после проверки провайдером». Повторная кнопка «Подтвердить» даёт тот же order (replay). Серверные состояния заказов: `credited` (зачислено), `pending` (ожидает оплаты/сверки), `canceled`, `review_required`/`paid_review` (нужна сверка оператора). Автопополнения/redirect-циклов нет; секреты в UI не попадают. Wallet-блок баланса — AUTH-24.

**D14. Порядок блокировок (anti-deadlock).** finish: identity → account → order → (кредит) wallet → lots по `lot_id`; совпадает с направлением AUTH-18 `finish` и хуками AUTH-21 в coordinator. quote/confirm: identity → account → (order) — без циклов с wallet. Inbox-вставки — обычные INSERT без row-локов родителя (FK только).

## Миграция 0034 (аддитивная)

`0034_auth22_topups.sql`: 4 таблицы (`auth_topup_packages`, `auth_topup_quotes`, `auth_topup_orders`, `auth_topup_inbox`) + guard-функции/триггеры (package: DELETE запрет + enabled-flip only; quote: immutable; order: переходы/привязки; inbox: immutable), индекс due `WHERE state='pending'`, rate-индекс quote(account_id, created_at). Цепочка `topup_migrations.apply_migration` через `wallet_migrations` (гарантирует 0019…0033; FK — на auth_accounts/auth_identities как 0030); checksum-регистрация, repeat=false, прежние SQL/checksums не меняются. `check_schema`: колонки 4 таблиц + 4 включённых триггера. Новых обязательных env/volumes/compose-правок нет: compose-команда billing-worker сохраняет `scripts/auth18/worker.py --loop` (файл расширен аддитивно: после `SubscriptionService.step()` шагает `TopupService.step()`; deployment-тест топологии остаётся зелёным).

## Риски и снятие

| Риск | Снятие |
|---|---|
| R1: двойное начисление CU | D4: терминальный state-гвард + `payment_id UNIQUE` + `auth21_lot_order` unique; native-тесты E3/E6 (дубли webhook, два event id, retry create) |
| R2: callback spoof активирует кредит | D7/D4: webhook — wake-up only; proof только authenticated GET; native-тест «notify(succeeded) без API-GET не кредитует» |
| R3: currency/amount tamper | Снимок pins amount/currency; `validate` полное сравнение; native-тесты подмены → `review_required`, лота нет |
| R4: ломка AUTH-18 саги/адаптера | `provider.create` — только опциональный description-ключ; subscriptions.py не тронут; полный native-регресс test_auth18_saga обязателен |
| R5: line-shift evidence в policy_review (routers/billing.py, provider.py, worker.py) | Якоря известны; после правок `inventory.py --write` и адресная проверка evidence (паритет AUTH-13-HOTFIX-1) |
| R6: кредит при locked wallet теряет деньги | D5: paid_review + операторская процедура credit-paid (CAS) + native-тест |
| R7: аудит-отказ после кредита | D11: одна транзакция, fail-closed; native fault-тест |
| R8: некаталожный прайс из клиента | D1: DTO extra=forbid; снимок из строки пакета; unit-тесты |
| R9: дедлоки wallet/order | D14: единый порядок блокировок; native-конкурентные тесты |
