# AUTH-05 — MFA, bootstrap и recovery

База a7502efe349c8a3eb8f80157d9c93f1ff10bc7f1. AUTH-04 password/session authority и AUTH-03 context переиспользованы. Первый локальный фактор этой поставки: TOTP SHA1/6 digits/30s, окно ±1, 160-bit random seed. Это явно разрешённый spec fallback; WebAuthn с UV остаётся предпочтительным будущим адаптером, OIDC не реализован. NIST AAL certification не заявляется.

## Процесс и риски

TDD: primitive и SQL lifecycle tests → сохранённый RED → реализация → negative HTTP/replay/fault tests → AUTH-00/01 route gates → build → ZIP. Риски: challenge как полноценный credential, повтор OTP/кода, откат attempts вместе с ошибкой, пересечение session/action, plaintext seed, неатомарный audit, гонка bootstrap. Решения ниже проверяются на PostgreSQL wire, не memory-auth substitute.

## Контракт состояний

Пароль ADMIN не выдаёт AuthSession: только c1_ challenge purpose login (есть фактор) или enroll_start (CLI разрешил первоначальный enrollment); при завершённом reset без нового фактора — только recovery challenge. ADMIN без фактора и provisioning разрешения получает отказ. Обычный password user сохраняет AUTH-04 вход; если у identity есть фактор, он также обязателен.

POST mfa/enroll расходует enroll_start и один раз возвращает base32 secret/otpauth URI вместе с challenge enroll. POST mfa/verify подтверждает enrollment, создаёт фактор, отзывает прежние sessions/challenges через epoch, выдаёт новую s1_ сессию и десять recovery-кодов. Login challenge после OTP выдаёт только новую session. Полный context получает mfa_verified_at из серверного auth_session_mfa; arbitrary amr/boolean клиента не принимается.

Challenge SHA256-domain-separated, random 256 bits, 5 минут, purpose/target/Origin/subject/account/credential versions/epoch и при необходимости exact session. SQL bindings immutable; consumed_at terminal. Challenge c1_ не проходит s1_ parser и не попадает в cookie AuthSession. Проверки identity/status/version, credential/status/version, epoch, membership/account повторяются при каждом consume. Нет DDL, cross-request positive cache или memory fallback.

Каждая OTP/recovery попытка сначала коммитит increment (макс. 5/challenge), потом проверяет код. Subject-wide durable limiter 10/min защищает от обхода новым challenge; login отдельно ограничен AUTH-04. Успешный timestep фактора сохраняется под identity/factor lock; повтор даже в другом challenge запрещён. Все операции начинают с identity lock. Ошибка authority/key/schema — safe 503; неверный/истёкший challenge/OTP/recovery — одинаковый 401 без секретов.

Seed шифруется AES-256-GCM с уникальным 96-bit nonce и AAD subject:factor. Только ciphertext и key id в pending/active DB, не пароль или полный raw challenge. Конфигурация обязательна при seed-операциях: CISSTAT_AUTH_MFA_KEYS — JSON object key-id → стандартный base64 32-byte key; CISSTAT_AUTH_MFA_ACTIVE_KEY выбирает ключ новых seeds. Нет default. Для ротации оставить старые key ids до явного replacement всех соответствующих факторов; простая смена active key не перешифровывает старые seeds. Утеря keyring блокирует TOTP; заранее сохранить recovery codes и ключи в защищённом operator vault.

POST step-up требует полноценную session + текущий пароль, возвращает challenge step_up с allowlisted action mfa.replace / recovery.rotate / password.change. OTP verification дополнительно требует cookie именно исходной session и выдаёт proof на 5 минут. Mutation расходует proof в одной транзакции с изменением и audit. Недостаточно свежего timestamp от login, нового client boolean или proof другой action/session. MFA replacement отзывает фактор, все recovery codes и все sessions, затем возвращает enroll_start. Старые proofs/challenges fenced epoch. Password change для MFA session также расходует action password.change и отзывает все sessions; обычный пользователь без MFA сохраняет AUTH-04 current-password contract. Recovery rotation возвращает новые коды один раз, старые терминально погашены.

POST recovery требует password-authenticated login challenge и recovery code (192 random bits, r1_ prefix, domain-separated SHA256 в DB). Consume расходует только предъявленный код, отзывает фактор, sessions и challenges; возвращает только enroll_start. Остальные коды остаются для безопасного повтора recovery, если ответ потерян; при подтверждении нового фактора все старые коды погашаются. Новая проверка пароля в этом состоянии даёт лишь challenge recovery: ни password-only session, ни разрешение enrollment. Повтор восстановления требует другого ещё не использованного recovery code. Нельзя восстановлением получить password-only ADMIN session. Новое MFA enrollment обязательно. Recovery не предназначен для password reset. После replacement старые коды сразу погашены; сохраните полученный ограниченный challenge до завершения enrollment. При потере этого ответа или всех кодов — отдельная защищённая операторская процедура, публичного обхода нет.

## Операторский запуск

Установить requirements apps/api и выполнить python scripts/auth05/migrate.py --apply; --check не выполняет DDL. Миграция 0021 additive, 0019/0020 неизменны, свой checksum и transaction/advisory lock предыдущих миграций. Сервис теперь требует 0021; применить до запуска нового API. Старый код не должен работать параллельно после включения MFA (он не знает этот security contract).

В защищённом interactive terminal с auth DB env: python scripts/auth05/bootstrap.py prepare печатает единственный provisioning secret (TTL 15 минут), затем python scripts/auth05/bootstrap.py create --login <named-login> спрашивает secret и passphrase через getpass, печатает только login/subject_id/account_id для выбора активного Account. Args/env/логи не содержат password/provisioning secret. Singleton + advisory transaction lock + отсутствие любого ADMIN запрещают повторный bootstrap. Публичного bootstrap route нет. При истечении/потере secret процедура блокируется; не удалять ledger в production и не создавать default ADMIN, требуется отдельная проверенная операторская процедура. CLI создаёт именованную identity ADMIN, INTERNAL mono Account, OWNER membership, password credential и разрешение enrollment атомарно с mandatory audit. Первый login обязан завершить TOTP.

Auth HTTP — first-party HTTPS/Origin/CSRF foundation AUTH-04. Все POST требуют fresh CSRF proof и exact allowed Origin. Challenge/seed/recovery DTO — no-store, SecretStr write-only inputs, безопасные 422. После login/issue/recovery/replacement cookie binding меняется: повторно GET csrf. Challenge/proof — временное значение только в памяти будущего UI; не сохранять в browser storage. Нужны TLS и request-body/response/Set-Cookie redaction в ingress/APM. Секреты seed/URI/codes нельзя логировать/скриншотить. Нет email/SMS fallback.

## Границы и поставка

AUTH-06 реализует общий proxy/login UX; AUTH-07 подключает named MFA identity к реальным admin management APIs. Существующий key-only admin facade сохранён как временная совместимость из spec; новая MFA session не принимается им до AUTH-07. Научные object/entitlement policies не менялись. Для новых sensitive admin actions потребуется расширять allowlist и вызывать consume_step_up внутри той же UoW; текущие mfa.replace/recovery.rotate/password.change уже реально закрыты этим guard.

Audit auth_mfa_changed добавлен к существующему mandatory catalog, использует тот же безопасный record schema и outbox/replay AUTH-04, а не отдельный лог. Secret/code/token/URI не входят в audit details. Изменение authority и outbox атомарны. Rollback приложения после MFA rollout требует отдельного security review; destructive down migration не поставляется, данные MFA/sessions/ledger сохраняются.

Источники: RFC 6238 §5.2 (https://www.rfc-editor.org/rfc/rfc6238), OWASP MFA Cheat Sheet (https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html). Эти рекомендации не заменяют проектные TTL/attempt limits. Native PG16/18 CI обязателен для locking/restart; PGlite wire proof не означает native concurrency certification.
