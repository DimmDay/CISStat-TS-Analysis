## 4. Независимые оракул-тесты аудитора (свои данные)

Скрипт `scripts/task144_audit_oracle.py` (данные аудитора: свой генератор
рядов seed=144, свои профили DataProfile, свои CSV n=96/44/43 для E2E —
не переиспользуют fixtures коллеги). Итог: **250/250 GREEN**.

Ключевые группы:
- **A (движок, 24 модели × границы):** F04 срабатывает при n < effective_min и
  НЕ срабатывает при n == effective_min у всех 24 моделей (профили подобраны
  так, чтобы F01/F02/F05 не маскировали F04: var/vecm n_series=4, deepar
  n_series=6, garch/egarch financial). Границы D07-окна: tbats 49→F04 /
  50→D07 / 99→D07 / 100→D05 (не D07); tree-четвёрка 39→F04 / 40→D07.
  D07-сообщение рендерит все три числа (n, min, soft) без фигурных скобок.
- **B (матрица на своих фреймах):** n=64→initial_train=60: пять soft-моделей
  attention/conditional/shortlist + «в пределах мягкого порога» в conclusion;
  garch/egarch/var/lstm — fail/blocked. n=44→40: левая граница включительна
  (квартет attention, tbats fail). n=43→39: нижняя граница цела.
  n=104→100: все пять pass.
- **B5 (главный синхронизационный оракул):** для КАЖДОЙ из 24 моделей
  матричная history-граница (первый initial_train без blocking-fail) строго
  равна движковой F04-границе (effective_min) — расхождение двух путей
  гейтинга исключено любым изменением данных; плюс монотонность
  fail→attention→pass по всей сетке n=1..259.
- **C:** `soft_history_warning` — точный текст «Обучено на N наблюдениях при
  рекомендованном минимуме M — результат используйте с осторожностью.» на
  границах (49/50/99/100 для tbats; 39/40 для RF); None для pass/fail и для
  моделей без soft при любых n.
- **D:** валидатор: soft==min и soft>min → ValidationError; soft=0 →
  ValidationError (ge=1); soft=min-1 валиден; отсутствие поля валидно.
- **E:** `/candidates` на профиле n=64: пять soft-моделей NOT_RECOMMENDED/D07
  с непустыми actions и blocking_reason=None (для ready); NOT_APPLICABLE

## 6. Находки и замечания

- **R1 (доставка, minor — устранено в ходе сертификации).**
  `scripts/task144_mutations.py` отсутствовал в рабочем дереве: worklog
  ссылается на `scripts/task144_mutations.py`, файл ехал в ZIP только в
  корне. Воспроизводимость мутационного прогона из репозитория была нарушена.
  Исправлено аудитором: файл размещён в `scripts/` (незакоммиченным,
  по запрету commit/push).
- **R2 (робастность раннера, recommendation).** Мутационный раннер не имеет
  pre-flight проверки: (а) не убеждается, что защитная сюита зелёная ДО
  мутаций; (б) при «pattern not found» продолжает прогон вместо аварийного
  останова; (в) не защищён от старого мутированного состояния (инцидент §5).
  Рекомендация: перед циклом — прогон fast-сюиты + sha256-сверка эталонов,
  аварийный останов при отсутствии паттерна. Не блокирует: после
  восстановления дерева все 21 мутант убиты.
- **R3 (наблюдение, informational).** `worklog_summary.md` не обновлялся
  после 2026-09-14 (Task 144 там отсутствует) — саммари ведётся в
  периодическом режиме; предложить тимлиду обновить на ближайшем цикле.
- **R4 (наблюдение, informational).** В `run_modeling_backtest` предупреждение
  берётся по фактическому `len(plan.folds[0].train_indices)` — при sliding-
  стратегии с train_window текст честно отражает реальный размер первого
  train, а не initial_train из профиля. Поведение корректное; зафиксировано,
  чтобы будущие рефакторинги не «упростили» его до initial_train.
