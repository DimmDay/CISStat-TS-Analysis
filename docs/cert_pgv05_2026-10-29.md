## 2. Что сертифицировано (факты о поставке, подтверждённые корпусом)

1. **Полный контракт §8 на живых данных** (A1): snapshot-запись несёт schema_version
   `pgv.passport_history/1`, snapshot_ref/session_snapshot_id (обратная деривация из
   idempotency-ключа — верифицирована), artifact_id, stage/universe, ПОЛНЫЙ паспорт AS-IS

   target/date, stamped-контекст (context_id/data_revision — только у доказуемо созданных),
   data_ref (честный None), ДВА разных доказуемых времени: captured_at = время capture
   СНИМКА (session-факт rs-записи; НЕ checkpoint.confirmed_at capture-ответа — они расходятся
   на микросекунды, оракул пинует именно snapshot-факт), created_at = время промоушена.
2. **Два разных хэша с определёнными алгоритмами (§8)** (A1/U3): source_hash ==
   payload_sha256 реестра, алгоритм пинован `sha256(canonical_json)`; fingerprint ==
   series_fingerprint данных capture; значения РАЗЛИЧНЫ (контент vs данные) — A1+repo.
3. **XOR-конвенция «значение либо явная причина»** (U1/A3): на present-записях reason=None
   при значении; на legacy-записях (rs без артефакта) — None+legacy_unknown для ВСЕХ четырёх
   XOR-полей; captured_at при этом честен из rs-метаданных (2026-01-15T12:00:00+00:00 seed —
   не время чтения, не выдуман). Фабкация версий отсутствует: schema/calculation текущих
   captures честно legacy_unknown (repo + A3); forward-compat верифицирован ДЕЛОМ (A4):
   payload с passport_schema_version/calculation_version изВЛЕКАЕТСЯ без изменения reader'а
   — заявка честной границы №1 поставки подтверждена.
4. **Целостность — два слоя** (A5/A6): подмена ассоциации (producer_key passport:{sid},
   payload.snapshot_id чужой) → corrupt/snapshot_id_mismatch, контент скрыт; расхождение
   sha256 байтов с payload_sha256 РЕЕСТРА (байты passes content-key) → corrupt/
   payload_sha256_mismatch — ВТОРОЙ слой поверх T8 content-key. Записанный хэш остаётся
   доказуемым фактом ожидаемого контента (док поставки §3.5 честна).
5. **Изоляция run'ов** (A2/A17): чужой СУЩЕСТВУЮЩИЙ rs-ref → None; не-паспортная rs-запись
   (D01) → None; rs-запись с тамперированной зависимостью на чужой артефакт → резолв ПО
   producer-ключу СВОЕГО run (fallback честен: контент именно своего run, артефакт чужой
   отвергнут по run-принадлежности). Чужой checkpoint_id → None (A15).
6. **Траектория «на выбранное подтверждение»** (A7): stage_refs РОВНО замороженные refs
   чекпоинта; две траектории независимы (первая не переключилась на поздний exit);
   confirmed_at == payload-факт чекпоинта.
7. **Reused handoff (AC11)** (A8): подтверждённый снимок доступен под ОБОИМИ адресами
   (физический exit И путь подтверждения modeling_entry) как ОДИН объект (алиас, не копия);
   физических паспортов ровно 3; чтение не добавляет артефактов/записей/пинов (A13 — полный
   цикл чтений, счётчики идемпотентны).
8. **Честные gaps (AC12)** (A9/A12): висячие refs → gaps по ТОЧНЫМ адресам

  `artifact.refs["stage"]` — доказуемый registry-факт (reader сам использует его для битых

  corrupt-снимки выпадают из universe-фильтров списков. Унификация с пикерным подходом —
  опциональное улучшение.
- N-P5C2: §8 формулирует «target/date/entity» в составе snapshot-записи; reader не кладёт
  entity на snapshot-запись (панельная entity доказуемо живёт в context чекпоинта; для
  single-series entity неприменима). Поставка документирует границу (док §5.3); интерпретация
  принята как честная (дублирование entity фабковало бы вселенную однорядным записям).
- N-P5C3: в corrupt-ветке `_snapshot_record` причина XOR для source_hash при ОТСУТСТВИИ
  значения была бы «legacy_unknown», хотя семантически это integrity_failure — путь мёртвый

- N-P5C4: субстрат PGV-04: открытая находка F-P4C1 (панельный backfill не работает) НЕ
  ограничивает сертификацию reader'а — AC14 сертифицирован для reader'а на фактах, которые
