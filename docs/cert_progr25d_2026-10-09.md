## 4. RED-эквивалент для тестовой задачи (дельта repo-канала)

Для тестовой задачи классический RED на проде невозможен по построению:
функционал A/B/C/F1 уже в базе, поэтому любые оракулы контрактов зелёные и
до D (это подтверждено: оракулы аудитора — 23/23 — проверяют контракты
функционала, существующего с A/C). Честный эквивалент RED для тестовой
поставки — доказательство, что НОВЫЕ repo-пины закрывают РЕАЛЬНЫЕ гэпы, а не
дублируют уже покрытое. Метод сертификации: СВОИ мутанты продового кода
прогоняются через ТРИ канала — repo-DO (адресные сюиты, существовавшие до D,
на `a55caed`: progr25a/c, target_column, trace_hook, session_store,
mentor_rules, node_status_engine, progress_panel, progr17 — 400 тестов),
repo-D (только новые сюиты задачи D) и oracle (свои оракулы аудитора).
Предрегистрация EXPECTED (какой канал какой вердикт даёт) зафиксирована в
скрипте мутаций ДО прогона; grep-обоснования каждого прогноза — в акте §6.

Результат: ровно три мутанта пережили pre-D repo-канал и убиты НОВЫМИ сюитами
задачи D — **DC-4** (носитель /trace оторван от факта: 400 passed на pre-D —
репо слеп), **DC-5** (demo-точка правила выпала: 400 passed), **DC-7**
(нечестная рекомендационная ветка toast с сохранением префикса «Признак
«Price»…»: 2 pre-D фронт-сюиты зелёные). Это мутационное доказательство
добавленной ценности задачи D ровно по трём находкам сертификаций
(TM-15/TM-11/TB-8): пины не декларативны — каждый реально убивает свой класс
отказа, который прежде жил в repo-канале. Ложно-красного нет: no-op контроль
DC-0 выжил во всех каналах.
