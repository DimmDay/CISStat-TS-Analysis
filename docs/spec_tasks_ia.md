# spec_tasks_ia.md — Информационная архитектура «Задач» и стратегия роста главного меню

Статус: утверждена тимлидом (постановка в чате 2026-09-13, формулировка решения — в диалоге).
Затрагивает: `packages/ui/lib/task-stops.ts` (новый), `packages/ui/components/TaskCard.tsx` (новый),
`packages/ui/components/TasksHub.tsx` (новый), `apps/standalone/app/tasks/page.tsx` (замена
плейсхолдера), 4 плейсхолдера-маршрута задач. Верхнее меню (`ModuleNav`) НЕ меняется.

---

## 1. Контекст и постановка

Пайплайн платформы — обязательная горизонтальная последовательность из шести этапов
(`STAGES = ("upload", "validation", "preprocessing", "eda", "modeling", "forecasting")`,
`apps/api/session_store.py`; фронтенд-зеркало — `STAGE_DEFS` в `packages/ui/lib/stages.ts`).
После прогноза начинается ветвление по задачам, решаемым на его основе: сценарии, причины,
принятие решений, мониторинг прогноза. С ростом прикладных задач возникает вопрос:
как растёт главное меню и предопределено ли решение задач наличием прогноза.

Исходная гипотеза («бейдж Задачи с аккордеоном, ветвление строго после Прогнозирования»)
не выдерживает проверки зависимостями: часть задач работает без прогноза вовсе.

## 2. Ответ на центральный вопрос: зависимость задач от прогноза

**Нет — не глобально.** Прогноз — центр тяжести продукта («от файла до прогноза»), но не
универсальный турникет. Каждая задача декларирует собственный **контракт входа** —
минимальный набор артефактов сессии, без которых её исполнение невозможно:

| Задача | Минимальный вход (контракт) | Зависимость от прогноза | Обоснование |
|---|---|---|---|
| Причины (drivers, XAI) | `model_card` | **Нет** | SHAP/PDP/IRF/FEVD/Грейнджер считаются обученной моделью на исторических данных (ARCHITECTURE.md:155, 1382) |
| Сценарии (What-if) | `model_card` (+ `forecast_run` рекомендуется) | **Мягкая** | Механика шоков — IRF/FEVD модели; базовый прогноз нужен для наложения веера, не для генерации контрфактических траекторий |
| Принятие решений (iDSS) | `forecast_run` | **Жёсткая (исполнение)** | Решения оцениваются на прогнозных значениях; настройка правил в v2 сможет не требовать прогноза (расщеплённый гейт, §7) |
| Мониторинг прогноза | `forecast_run` | **Жёсткая по определению** | Сравнение факта с прогнозом существует, только если прогноз есть |

Подтверждение в существующей архитектуре: матрица `ARCHITECTURE.md:375` помечает «Задачи»
как потребителя **всех стадий**, а не только forecasting. Прогноз — один из артефактов
сессии, наряду с валидированным датасетом и Model Card.

## 3. Решение IA: формула

> **Пайплайн — конечная горизонталь (заморожена), задачи — открытая вертикаль
> (растут вниз в хабе), зависимость — не «после прогноза», а «по контракту входа
> каждой задачи».**

- **Верхняя строка меню заморожена**: 6 бейджей пайплайна (зеркало `STAGES`/`STAGE_DEFS`)
  + «О платформе» + «Задачи». Новые бейджи верхнего уровня возможны только как новый
  этап пайплайна — версионное изменение `STAGES` на бэкенде, не реакция на рост задач.
- **«Задачи» — хаб-страница, не аккордеон.** Аккордеон деградирует при 7–9 пунктах
  (точность hover, ширина вьюпорта, мобильная раскладка). Хаб масштабируется свободно:
  URL-пространство растёт (`/tasks/<id>`), меню остаётся одним бейджем.
- **Гейтинг повсезадачный**: хаб честно показывает, какая задача доступна сейчас,
  какая станет доступна после какого этапа, а какая требует прохождения пайплайна
  с нуля. Позиция бейджа «Задачи» последней в строке сохраняется (продуктовая
  метафора ветвления от прогноза), но доступ к задачам гейтится индивидуально.

## 4. Три состояния задачи (контракт хаба v1)

Источник сессии — `useAppShell().stages` (гидратация `GET /v1/session/current`,
`AppShellContext`). Слой артефактов:

```ts
type TaskArtifact = "validated" | "model_card" | "forecast_run";

// stages -> артефакты (артефакт существует, когда его этап = "done")
validated   <- stages.validation  === "done"
model_card  <- stages.modeling    === "done"
forecast_run<- stages.forecasting  === "done"
```

Состояния (`deriveTaskGateState(requires, artifacts, pipelineStarted)`):

| Состояние | Условие | Рендер | Причина (текст) |
|---|---|---|---|
| `available` | `requires ⊆ artifacts` | Кликабельная карточка-ссылка (DNA RouteCard) | — |
| `awaiting` | не `available`, но пайплайн уже начат (хотя бы один этап `done`) | Некликабельная карточка, amber-плашка | «Станет доступна после этапа {Label}» — Label этапа первого недостающего артефакта |
| `blocked` | не `available` и пайплайн не начат (свежая сессия) | Некликабельная карточка, нейтральная плашка | «Начните с этапа Загрузка — задачи работают поверх артефактов пайплайна» |

`pipelineStarted = STAGE_DEFS.some(s => stages[s.key] === "done")`.
Порядок артефактов в контракте — порядок пайплайна (validated → model_card → forecast_run),
поэтому «первый недостающий» детерминирован.

A11y: некликабельные карточки — `div role="group"` с aria-label, содержащим название
задачи и причину; кликабельные — `<a href>` (next/link). Некликабельные не являются
ссылками сознательно: навигация на нереализуемую пока задачу — ложный аффорданс.

## 5. Реестр задач v1 (`task-stops.ts`)

Источник истины — по образцу `home-stops.ts`/`navigator-stops.ts`:

| id | Заголовок | href | requires |
|---|---|---|---|
| `scenarios` | Сценарии | `/tasks/scenarios` | `["model_card"]` |
| `causes` | Причины | `/tasks/causes` | `["model_card"]` |
| `decisions` | Принятие решений | `/tasks/decisions` | `["forecast_run"]` |
| `monitoring` | Мониторинг прогноза | `/tasks/monitoring` | `["forecast_run"]` |

Для «Сценариев» `forecast_run` — рекомендуемый (не гейтящий) артефакт; подсказка
о нём — забота самой задачи в v2, не хаба.

**Предусловие входа в реестр (R6, 2026-09-15).** Каждый артефакт в `requires`
обязан быть производимым бэкендом: этап-владелец (`ARTIFACT_STAGE`) должен
выставляться в `done` хотя бы одним роутером. Свидетельства v1:
`upload` — `session_store.py:273` (`set_dataset`); `modeling` —
`modeling_session.py:3258` (создание Model Card); `forecasting` —
`forecasting_session.py:182` (завершение ForecastRun); `validation` —
`session.py::get_dataset_validate` (успешный общий запуск 10 проверок;
R6/вариант C — до этого правки этап `validation` не выставлял никто, и задача
с `requires: ["validated"]` была бы пожизненной `awaiting`-карточкой).
Семантика артефакта — «работа выполнена», не «данные чисты» (чистота — поле
`is_valid` ответа). Правило страхуется тестом `BACKEND_PRODUCIBLE_ARTIFACTS`
(`task-stops.test.ts`): новая запись реестра или новый артефакт слоя требуют
одновременного обновления свидетельств о продюсере.

## 6. Эшелоны роста (пороги без перепроектирования)

1. **≤ 8 задач** — плоская сетка карточек хаба (текущий уровень).
2. **9–15** — секции по категориям (Сценарии / Причины / Решения / Мониторинг) с якорями;
   реестр получает поле `category`.
3. **15+** — вкладки категорий или левый сайдбар ВНУТРИ `/tasks`; верхнее меню по-прежнему
   содержит один бейдж.
4. **Промоция в верхнюю строку** — исключительная, версионная: только если задача стала
   обязательным этапом для каждого аналитика (критерии: обязательность для всех,
   позиция в потоке, использование в >80% сессий, изменение `STAGES`).

Добавление одной задачи = одна запись реестра + плейсхолдер-страница. Верхнее меню,
`STAGES`, бэкенд — не затрагиваются.

## 7. Что осознанно НЕ входит в v1

- Реальное содержимое задач (What-if/iDSS/мониторинг) — отдельные вертикальные срезы;
  v1 поставляет каркас: хаб + 4 плейсхолдера-маршрута (`ModulePlaceholder`).
- Расщеплённое состояние `configurable` (настройка правил решений/порогов мониторинга
  без прогноза) — расширение контракта v2: четвёртое состояние поверх тех же данных.
- Wiring «рекомендуемых» артефактов (`recommendedWith`) в подсказки хаба.
- Embedded-оболочка: хаб общий (`packages/ui`), встраивание — отдельной задачей.
- Изменения `ModuleNav`, `STAGES`, бэкенда — запрещены этим решением.

## 8. Критерии приёмки v1

- Свежая сессия (все этапы `pending`): 4 карточки в состоянии `blocked`, ни одной ссылки.
- Сессия после Моделирования (`validation/modeling = done`): «Сценарии» и «Причины» —
  кликабельны; «Принятие решений» и «Мониторинг» — `awaiting` с причиной
  «…после этапа Прогнозирование».
- Полный пайплайн: все 4 задачи кликабельны, ведут на свои маршруты.
- Карточки-ссылки наследуют визуальную DNA RouteCard (бейдж-карточка, иконка,
  заголовок `text-base`, описание `text-sm`).
- Регресс: полный `npx jest` зелёный; сборка standalone успешна.
