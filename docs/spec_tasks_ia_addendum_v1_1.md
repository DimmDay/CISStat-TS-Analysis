## 9. Композиция хаба (v1.1): почему «4 карточки» недостаточно

### 9.1 Диагноз

Сквозной принцип платформы, установленный ещё в Валидации/Предобработке/EDA
и подтверждённый Паспортами свойств ряда (`spec_passports.md`) и панелью
«Прогресс» (`spec_progress.md`): **интерфейс показывает реально вычисленные
факты сессии, а не только статичный текст состояния**. Степпер красит
остановку зелёным только когда работа реально сделана; окно «Обзор» рисует
настоящий график, а не заглушку; паспорт показывает настоящие ADF/Hurst, а
не общие фразы про важность стационарности.

Хаб `/tasks` в реализации v1 — единственная страница пайплайна, целиком
состоящая из статичного текста и трёх состояний доступности. Аналитик,
только что видевший содержательные окна на каждом из шести этапов, получает
на «Задачах» шаг назад в информативности — притом что нужные для заполнения
данные (список Model Card через `GET /v1/session/modeling/card` — уже
существует с Task FORECAST-1, `is_valid`/DQ Score валидации, история
`ForecastRun`) уже посчитаны сессией и почти бесплатны для отображения.

### 9.2 Решение v1.1 — лента артефактов сессии

Между шапкой хаба и сеткой карточек — горизонтальная лента compact-карточек
по образцу `Metric`-карточек `DatasetPassportPanel` (переиспользование
компонента, не изобретение нового):

```
┌─────────────────────────────────────────────────────────┐
│ H1 «Задачи» + поддерживающая строка                       │
├─────────────────────────────────────────────────────────┤
│ Лента артефактов: «Датасет: 240 набл., DQ 94%» /           │
│ «Model Card: ETS, MASE 0.87» / «Прогноз: LSTM, h=12»       │
│ — рисуются ТОЛЬКО реально существующие артефакты;          │
│ отсутствующий артефакт не рисуется как «пусто» —            │
│ его просто нет в ленте (честная маркировка, не             │
│ фиктивное заполнение места)                                │
├─────────────────────────────────────────────────────────┤
│ Сетка карточек задач (текущая DNA RouteCard)               │
└─────────────────────────────────────────────────────────┘
```

Правило заполнения ленты — то же самое дерево артефактов, что уже описано в
§4 (`validated` / `model_card` / `forecast_run`), без расширения контракта
состояний карточек. Источник данных — `useAppShell().stages` (уже
используется) плюс точечный вызов `GET /v1/session/modeling/card` для
`model_card`-чипа (список карт уже отдаёт нужные поля: `model_id`,
`selection_kind`, метрика). Для `forecast_run`-чипа на v1.1 достаточно факта
наличия (`stages.forecasting === "done"`) без похода за деталями — состав
чипа детализируется вместе с v2 задачей «Мониторинг», которой эти детали
нужны предметно.

### 9.3 Решение v1.1 — содержательные карточки задач

Каждая карточка (`TaskCard.tsx`) дополняется 2–3 буллетами конкретного
обещанного результата вместо (или в дополнение к) одной строки описания —
буллеты формулируются по продукту, не по механике: «Вклад каждого фактора в
прогноз», «Сравнение сценариев на одном графике» — не «использует SHAP».

### 9.4 Решение v1.1 — замыкающая кнопка цепочки степперов

Цепочка `StepperNextModuleButton` («Перейти к →») уже тянется через все пять
степперов (Загрузка→...→Моделирование→Прогнозирование), но на
«Прогнозировании» сознательно обрывается — решение `Task FORECAST-1`:
«прогнозирование — workspace, а не степпер, кнопки «Перейти к Задачам» на
вкладке нет». Теперь, когда хаб `/tasks` существует, разумно замкнуть
цепочку: добавить такую же кнопку-приглашение в конце степпера
«Прогнозирования», ведущую на `/tasks`. Прецедент того, что целевая страница
кнопки не обязана быть степпером, уже есть — Моделирование ведёт на
Прогнозирование, которое тоже workspace.

Это единственное точечное изменение вне `packages/ui/lib/task-stops.ts` /
`TasksHub.tsx` / `TaskCard.tsx`, которое предлагает данное дополнение;
компонент `StepperNextModuleButton` уже существует и переиспользуется без
изменений (`label`/`href` — единственные входы).

### 9.5 Что v1.1 сознательно НЕ меняет

- Контракт трёх состояний (§4), логика `deriveTaskGateState`,
  `ctaStageInfo`/`awaitStageInfo`, allowlist-предусловие R6 — без изменений.
- Реестр задач (§5) — 4 записи, без добавления полей `category`/
  `recommendedWith` (это остаётся эшелоном 2/v2, §6).
- `ModuleNav`, `STAGES`, бэкенд-контракты — по-прежнему не затрагиваются
  (запрет §7 исходного документа сохраняется), кроме одной точечной вставки
  кнопки в степпер Прогнозирования (п. 9.4), которая не является «хабом
  задач» в смысле §7 и не меняет ни `STAGES`, ни `ModuleNav`.

### 10.1 Приоритет первого среза (v2): «Причины» (XAI), не «Сценарии»

Рекомендация — начинать v2 с задачи **«Причины»**, а не с логически первой в
таблице §5 «Сценарии»:

- самый простой контракт входа — только `model_card`, без `forecast_run`
  даже в мягкой форме;
- методологический движок уже назван в архитектуре (SHAP/PDP/IRF/FEVD/
  Грейнджер, `ARCHITECTURE.md:155,1382`) — не требует изобретения новой
  методологии интерфейса;
- по природе работы — «просмотр уже вычисленного» (см. §11.3), а не
  «настройка + запуск», то есть самый низкий эксплуатационный риск для
  первого среза нового раздела продукта (прецедент того же принципа —
  выбор Random Forest как первого supervised-адаптера ML-серии из-за
  простейшего контракта относительно Prophet, Task 127).

## 11. Паттерны layout для страниц задач (`/tasks/<id>`)

### 11.1 Почему не «всегда 3-колоночный степпер-паттерн»

Прямое применение степпер-паттерна (степпер / Описание+Обзор / Панель
управления) ко всем четырём задачам создало бы фиктивные состояния
прогресса там, где реальной последовательности стадий нет — платформа
последовательно отказывалась именно от такого натягивания (честные
`not_applicable` вместо натянутых значений в Предобработке; степпер не
красится done, пока работа реально не сделана). Задача, у которой нет
настоящей последовательности «шаг 1 → шаг 2 → шаг 3», не должна получать
искусственный степпер только ради визуального единообразия.

### 11.2 Три паттерна, единый набор строительных блоков

Разделение по природе задачи, с обязательным переиспользованием общих
элементов платформы независимо от паттерна (жёсткое требование ради
согласованности, а не выбор реализации):

| Строительный блок | Обязателен во всех трёх паттернах |
|---|---|
| Заголовок «Панель управления» (правая колонка/панель) | Да |
| Контракт высоты рабочего окна `468px` | Да, для любого графика/таблицы |
| `ExpandableChartPanel`/`ExpandableChartsProvider` для раскрытия графиков | Да, для любого нетривиального графика |
| `StatusIcon` + зелёный done-паттерн степпера | Только там, где есть реальная стадийность |
| Полу-бейджи «Когда использовать» / «Что нужно для запуска» (по образцу `NavigatorHero` «Для кого»/«Для чего») | Да, как методологический контекст задачи на её собственной странице |

**Паттерн A — полный степпер (3 колонки: степпер / Описание+Обзор / Панель
управления).** Для задач с настоящей последовательностью «настроить →
запустить → посмотреть результат», где промежуточные состояния осмысленны
и реально либо пройдены, либо нет:

- **Сценарии** (What-if): выбрать шок → задать параметры → построить веер
  контрфактических траекторий поверх базового прогноза;
- **Принятие решений** (iDSS): задать правила/пороги → оценить на
  прогнозных значениях → получить рекомендацию.

**Паттерн B — дашборд без степпера (2 зоны: основной чарт/лента + «Панель
управления» справа).** Для задач, представляющих живое, непрерывно
обновляемое состояние, а не последовательность шагов:

- **Мониторинг прогноза**: сравнение факта с прогнозом по мере поступления
  новых данных — концептуально ближе к панели «Прогресс» (`spec_progress.md`,
  живой поток событий), чем к степперу с состояниями «пройдено/не
  пройдено».

**Паттерн C — информационный/навигационный 3-колоночный (категория →
элемент → деталь, по образцу `AppliedTasksNavigator` на `/navigator`).**
Для задач, где аналитик не проходит стадии, а переключается между видами
уже готового объяснения:

- **Причины** (XAI): колонка методов (SHAP / PDP / Granger) → колонка
  факторов → деталь по выбранному фактору — браузинг, а не пайплайн.

### 11.3 Сводная таблица (все 4 задачи v1)

| Задача | Паттерн | Обоснование |
|---|---|---|
| Причины | C (информационный) | Просмотр уже вычисленного, переключение видов объяснения, не последовательность |
| Сценарии | A (степпер) | Настоящая последовательность: выбор шока → параметры → результат |
| Принятие решений | A (степпер) | Настоящая последовательность: правила → оценка → рекомендация |
| Мониторинг прогноза | B (дашборд) | Живое состояние, а не пройденные/непройденные шаги |

Решение о паттерне принимается для каждой задачи один раз на этапе её
проектирования (перед первым TDD-циклом реализации), не унифицируется
насильно — как и разделение `platform_status`/`level`, cohort-изоляция
`objective` и прочие случаи «честной маркировки вместо единого формата»,
уже принятые на платформе.

## 12. Открытый архитектурный риск (перекрёстная ссылка на `spec_progress.md`)

Гейтинг хаба (`deriveTaskGateState`, §4) читает `AnalysisSession.stages` —
грубую модель готовности (`pending/in_progress/done`, без узлов внутри
стадии). Спецификация панели «Прогресс» (`spec_progress.md`, §3.1)
сознательно отвергает эту же модель как источник данных для будущего
`pipeline_graph.py` — она слишком грубая для детального отображения
трассы событий.

Из этого следует не ошибка, а осознанный факт, который стоит держать в
поле зрения при переходе к v4 (§10, промоция/сведение источников): на
платформе одновременно существуют (и будут развиваться независимо) два
потребителя близкой, но не идентичной модели «готовности стадии» — хаб
задач (грубая, `session.stages`) и потенциальный Прогресс (детальная,
`pipeline_graph.py`). Рекомендация, зафиксированная также в оценке
`spec_progress.md`: в перспективе разумнее свести хаб задач на
`pipeline_graph.py` как более полный источник (у хаба уже структурно
похожий контракт `requires: [...]` на артефакты), а не наоборот. Это не
блокирует ни v1.1, ни v2 — фиксируется как решение, которое нужно принять
осознанно при появлении `pipeline_graph.py`, а не обнаружить постфактум
как расхождение двух счётчиков прогресса на экране пользователя.

## 13. Критерии приёмки дополнения

- v1.1: лента артефактов рисует только реально существующие чипы (пустая
  сессия — лента не рендерится вовсе, не «пусто»); буллеты карточек —
  конкретные обещанные результаты, не общие фразы; кнопка в конце степпера
  Прогнозирования ведёт на `/tasks`, переиспользует
  `StepperNextModuleButton` без изменения компонента.
- v1.1 не меняет ни один существующий тест контракта состояний (§4,
  `deriveTaskGateState`/`ctaStageInfo`/`awaitStageInfo`) — только
  добавляет новые сборки/тесты для ленты, буллетов и кнопки.
- Регресс: полный `npx jest` зелёный; сборка standalone успешна;
  `typecheck:all` без ошибок — как для любой задачи платформы (AGENTS.md).
