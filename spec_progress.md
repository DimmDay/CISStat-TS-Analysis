## 1. Назначение и границы

Правая боковая панель «Прогресс» — единая точка входа, показывающая полный пайплайн исследования (Загрузка → Валидация → Предобработка → Разведочный EDA → Моделирование → **Прогнозирование**) для конкретной пары (датасет, признак), с текущим состоянием каждого узла, контрольными точками, паузой/восстановлением и трассой с логами. Вызывается кнопкой «Прогресс» из главного меню (замещает «Логи событий», §6.1); из самой панели — кнопка «Наставник» (правило-движок «Следующий шаг», §7).

Пять целей из брифа отображены на архитектуру так:

| Цель | Компонент архитектуры |
|---|---|
| 1. Онлайн-ориентация аналитика | Граф пайплайна + live-статус (§2–3), рендер правой панели (§6) |
| 2. Отчёт для пользователя | Экспорт трассы в читаемый вид (§5.4) |
| 3. Данные для техподдержки | Тот же trace-log, доступ по `run_id` (§5) |
| 4. «Наставник / Следующий шаг» + обнаружение ошибок в Мастере | Правило-движок над уже посчитанными фактами (§7) |
| 5. Данные для статистики/банка кейсов/RAGFlow/дообучения | Append-only корпус трасс, офлайн-потребители (§9) |
| Admin-панель мониторинга | Агрегация по корпусу трасс, `Role.ADMIN` (§10) |

**Не входит в объём этой спецификации** (сознательно вынесено за скобки, чтобы не размывать ядро): сам движок RAGFlow, дообучение моделей, UI итогового банка кейсов — эти пункты только получают данные от сервиса, но не проектируются здесь.

## 2. Граф пайплайна — единый реестр узлов

Сервис не изобретает свой список этапов — он **агрегирует уже существующие** реестры узлов, которые платформа независимо ведёт по каждой вкладке. Таблица ниже — проверенное по коду состояние на дату этой спецификации, не предположение:

| Вкладка | Существующий реестр | Кол-во узлов сейчас |
|---|---|---|
| Загрузка | нет CHECKS-массива — линейный флоу (структура → `target_column`/`date_column` → декомпозиция-бейджи) | 1 узел `upload.structure_confirmed` |
| Валидация | `validation/rule_resolver.py::CHECK_IDS` | 10 (`data_types`, `formats`, `ranges`, `consistency`, `uniqueness`, `inclusion`, `referential`, `text_quality`, `regularity`, `sufficiency`) |
| Предобработка | `apps/api/routers/session.py::PREPROCESSING_CHECK_IDS` | 10 (`missing`, `outliers`, `regularity`, `decomposition`, `variance_stab`, `smoothing`, `stationarity`, `spectral`, `feature_eng`, `scaling`) — **без `"passport"`**, узел убран (см. шапку документа) |
| Разведочный EDA | `TsAnalysisEDA.tsx :: CHECKS` (id) | 10 (`descriptive`, `correlation`, `ih_analysis`, `seasonality`, `stationarity`, `distribution`, `structural`, `feature_select`, `validation_strategy`, `model_matrix`) — **без `"passport"`**, тот же узел убран синхронно |
| Моделирование | `apps/api/model_readiness.py::MODELING_STAGE_IDS` | **11** (`problem_definition`, `data_structure`, `constraint_mapping`, `candidate_generation`, `baseline_estimation`, `backtest`, `tuning`, `diagnostics`, `comparison`, `selection`, `model_card`) — полноценный граф с capability-статусами, не линейный флоу |
| Прогнозирование | `spec_forecasting2.md §5.9` — реестр событий, не CHECKS-массив (артефакт-ориентированный этап, не чек-лист) | 4 типа события на один `ForecastRun`: `forecast_generated`, `forecast_compared`, `forecast_sensitivity_computed`, `forecast_exported` |

**Паспорт (`spec_passports.md`) сознательно не входит в граф** ни одним узлом ни в одной вкладке — он сквозная панель, не остановка степпера с pass/fail-статусом; удаление `"passport"` из `PREPROCESSING_CHECK_IDS`/EDA `CHECKS` (см. выше) — это уже реализованное на платформе следствие того решения, а не предложение данной спецификации.

Проектируется новый, единственный источник истины для графа — **не дублирует**, а **ссылается** на перечисленные реестры (импортирует id-списки напрямую из существующих модулей, где это Python, и держит явную копию id EDA, единственно существующего только на фронтенде):

```python
# app/core/pipeline_graph.py (новый модуль)
"""Единый граф узлов пайплайна исследования -- источник истины для
сервиса «Прогресс». НЕ дублирует список остановок каждой вкладки:
для Python-реестров (Валидация, Предобработка, Моделирование) импортирует
id напрямую; для чисто-frontend реестра (EDA CHECKS, единственно
существующего в .tsx) держит копию id-списка с явным комментарием
"синхронизировать при изменении TsAnalysisEDA.tsx :: CHECKS" --
альтернатива (вынести EDA CHECKS в общий JSON/YAML, из которого читают
и фронтенд и бэкенд) вынесена в открытые вопросы §12."""

from validation.rule_resolver import CHECK_IDS as VALIDATION_STAGE_IDS
from apps.api.routers.session import PREPROCESSING_CHECK_IDS
from apps.api.model_readiness import MODELING_STAGE_IDS

STAGES = ("upload", "validation", "preprocessing", "eda", "modeling", "forecasting")

STAGE_NODES: dict[str, tuple[str, ...]] = {
    "upload": ("structure_confirmed",),
    "validation": VALIDATION_STAGE_IDS,
    "preprocessing": PREPROCESSING_CHECK_IDS,
    "eda": (  # см. предупреждение в докстринге модуля
        "descriptive", "correlation", "ih_analysis", "seasonality",
        "stationarity", "distribution", "structural", "feature_select",
        "validation_strategy", "model_matrix",
    ),
    "modeling": MODELING_STAGE_IDS,
    "forecasting": (
        "forecast_generated", "forecast_compared",
        "forecast_sensitivity_computed", "forecast_exported",
    ),
}
```

`STAGES` в этом модуле — не новая копия, а обязана быть проверена на равенство `apps/api/session_store.py::STAGES` (тест на импорт-тайм инвариант, тот же паттерн, что уже используют `test_backtesting_engine.py`/`test_model_execution_contract.py` для `CERTIFIED_IDS` реестра моделей — не изобретается новый вид проверки, переиспользуется уже принятый на платформе).

## 3. Модель узла и статуса

Узел графа не изобретает новую статусную модель — переиспользует уже принятые платформой словари, и здесь их **два, не один**, что нужно явно развести, а не смешивать:

- **`CheckStatus`** (`packages/ui/components/StatusIcon.tsx`) — `done`/`warning`/`pending`/`skipped`/`running`/`error`. Используется узлами Валидации, Предобработки, EDA — там, где каждый узел содержательно про отдельную проверку/коррекцию данных с исходом pass/fail/needs-attention.
- **`StageStatus`** (`packages/ui/lib/stages.ts`, зеркало `apps/api/session_store.py::StageStatus`) — `pending`/`in_progress`/`done`. Используется узлами Моделирования (`session.modeling_pipeline[stage]`) и Прогнозирования (по факту наличия `ForecastRun`/конкретных `trace_events`, см. §4) — там, где узел про этап процесса, а не про диагностическую проверку.

```python
@dataclass
class PipelineNodeState:
    stage: str          # "validation" | "preprocessing" | "eda" | "modeling" | "forecasting" | ...
    node_id: str         # "missing" | "outliers" | "tuning" | "forecast_generated" | ...
    status: str           # CheckStatus ИЛИ StageStatus -- зависит от stage, не приводится
                          # насильно к одному словарю на уровне узла (см. выше)
    status_reason: str | None
    mode: str | None       # auto/enabled/disabled, где применимо (Валидация/Предобработка)
    last_touched_at: str | None   # ISO-timestamp последнего события по узлу (§4)
    summary_count: int | None      # то же число, что в правом бейдже узла (напр. total_missing)
```

Нормализация в единую **лёгкость восприятия** (не в единый словарь данных) происходит только на уровне агрегированного статуса **стадии** для рендера блок-схемы (§6.2): оба словаря сводятся к одному из трёх визуальных состояний блок-схемы — «пройдено» (зелёный лёгкий фон), «в работе/есть замечания» (жёлтый), «не начато» (нейтральный) — `done`→пройдено, `warning`/`in_progress`→в работе, `pending`/`skipped`(агрегатно)/`running`/`error`(агрегатно, при этом конкретная ошибка видна при разворачивании узла)→по контексту. Точная таблица свёртки — деталь реализации, не архитектурное решение.

Источник данных для КАЖДОГО узла — уже существующий endpoint профиля этого узла (`GET /dataset/missing-profile`, `GET /dataset/eda-structural-breaks`, `GET /v1/session/modeling/candidates` и т.д. для Моделирования, `GET /v1/session/modeling/forecast/history` для Прогнозирования). Сервис «Прогресс» не пересчитывает статистику самостоятельно — **опрашивает** (или получает push-обновление, см. §4.2) те же эндпоинты, что и штатный UI остановки.

### 3.1 `session.stages` (существующий глобальный трекер) — НЕ источник данных для Прогресса

Важное разграничение, которого не было в старой версии спецификации (не было известно на момент её написания, обнаружено проверкой кода): в `AnalysisSession` уже существует поле `stages: dict[str, StageStatus]` с методом `set_stage()`, читаемое Home page через `GET /v1/session/current` (`packages/ui/context/AppShellContext.tsx`). Проверено: этот механизм **сейчас реально вызывается только для `"upload"`** (автоматически, при загрузке файла) **и `"modeling"`** (`apps/api/routers/modeling_session.py:2480`); для остальных четырёх стадий эндпоинт `POST /v1/session/stage/{stage}` существует, но явно не вызывается — задокументировано в самом коде роута как незавершённый охват задачи. Использовать это поле как единственный источник статуса стадии для Прогресса было бы неверно — оно неполно заполнено и не про то (у него нет понятия узлов внутри стадии). Прогресс **не читает и не пишет** `session.stages` — вычисляет собственный агрегированный статус стадии из узлов (§2–3), независимо. `session.stages`/`AppShellContext.stages` остаются как есть, для узкой текущей задачи Home page (рабочий стол vs онбординг) — не расширяются и не трогаются этой спецификацией.

## 4. Трасса событий (Event Log / Trace)

### 4.1 Событие — канонический контракт

```python
@dataclass
class TraceEvent:
    event_id: str            # uuid
    run_id: str               # см. §5 -- идентификатор "исследования", НЕ session_id
    ts: str                    # ISO-timestamp, сервер
    stage: str                  # одна из STAGES (§2), включая "forecasting"
    node_id: str | None           # id узла (§2); None для событий уровня всей стадии,
                                    # не привязанных к конкретному узлу
    event_type: str                 # см. таблицу ниже -- разный набор значений по stage
    payload: dict[str, Any]           # состав зависит от event_type, см. ниже
    actor: str                          # "user" (сейчас единственный вариант; задел под "system"/"mentor")
```

`payload` не хранит сырые данные ряда (датасет может быть большим/чувствительным) — только **факты о решении и его результате**, тот же уровень детализации, что уже возвращают эндпоинты корректировок (`total_changed`, `strategy`, `method`, `rows_removed` и т.п. — переиспользуется форма ответа `DatasetXCorrectionResponse`, не изобретается заново).

**Согласование с `spec_forecasting2.md`.** Этот датакласс — канонический, единственный. Локальный `TraceEvent` в `spec_forecasting2.md §7` (поля `event_type`/`timestamp`/`payload`, без `event_id`/`run_id`/`stage`/`node_id`/`actor`) при реализации заменяется импортом отсюда, а не сосуществует как второй тип с тем же именем: `timestamp` → `ts`, `stage="forecasting"`, `node_id` = `None` (Прогнозирование — артефакт-ориентированный этап без под-узлов в смысле Валидации/Предобработки, каждый `ForecastRun` — самостоятельная единица, не «узел», см. §2). Четыре `event_type`, уже зафиксированные там, входят в общую таблицу ниже без изменений:

| Stage | `event_type` (примеры) | Источник |
|---|---|---|
| validation/preprocessing | `mode_changed`, `correction_previewed`, `correction_applied`, `target_column_changed` | `progress_ts_analysis.md` (унаследовано) |
| eda | `profile_viewed` (троттлится, см. §4.2), `passport_captured` | `progress_ts_analysis.md` (унаследовано) |
| modeling | `backtest_run`, `tuning_trial_completed`, `model_selected`, `model_card_generated` | новое, по факту существующих эндпоинтов `apps/api/routers/modeling_session.py` |
| forecasting | `forecast_generated`, `forecast_compared`, `forecast_sensitivity_computed`, `forecast_exported` | `spec_forecasting2.md §5.9`, дословно |
| session (любая стадия) | `run_paused`, `run_resumed`, `checkpoint_saved` | `progress_ts_analysis.md` (унаследовано), см. §5.1–5.2 |

### 4.2 Откуда берутся события — не полинг, а хук на запись

Полинг статусов всех узлов на каждый рендер панели — избыточная нагрузка. Вместо этого:

- **Изменяющие эндпоинты** (`POST .../corrections`, `PUT .../check-modes`, `POST /target-column`, `POST /v1/session/modeling/backtest`, `POST /v1/session/modeling/forecast`, и т.д.) получают **общий middleware/декоратор**, пишущий `TraceEvent` при успешном ответе — единая точка интеграции, не требует правки каждого из уже существующих роутов вручную. Технически: FastAPI `Depends` или dispatch-middleware, читающий `request.url.path`/`response.status_code`, сопоставляющий путь с `(stage, node_id, event_type)` через статическую таблицу маршрутов (генерируется из `pipeline_graph.py` + соглашения об именовании путей, уже единообразного: `/dataset/{concept}-corrections`, `/v1/session/modeling/{action}`).
- **Читающие эндпоинты** (`GET .../profile`) генерируют событие `profile_viewed` реже — троттлинг (не чаще 1 раза на узел за N минут активности), т.к. цель — трасса решений и переходов, а не лог каждого клика.
- Статус узла в правой панели (§6) при открытии — **живой опрос** актуальных profile-эндпоинтов только тех узлов, которые видны на экране/раскрыты, не всех разом.

## 5. Персистентность: `run_id` — не то же самое, что `session_id`

Ключевое архитектурное решение, вынуждающее выйти за пределы уже существующего `SessionStore`.

**Почему нельзя просто расширить `AnalysisSession`.** `SessionStore` (`apps/api/session_store.py`) — TTL 30 дней (`SESSION_TTL_SECONDS`, синхронизирован с `max_age` cookie), ключ — cookie браузера, in-memory или Redis. Это отлично подходит для целей 1 (онлайн-ориентация) и «паузы/восстановления» **в пределах одного браузера/устройства за 30 дней** — эти сценарии реализуются простым добавлением поля `pipeline_trace: list[TraceEvent]` в `AnalysisSession`, без нового хранилища. **Но не подходит** для целей 2 («отчёт для пользователя» — должен переживать очистку cookie/смену устройства), 3 (техподдержка обращается по `run_id`, который пользователь называет голосом/в письме — не может звучать как cookie), 5 (корпус трасс для банка кейсов/RAGFlow должен агрегироваться **по всем пользователям**, а Redis-ключи разных cookie-сессий для этого не предназначены) и админ-панели (§10, требует SQL-подобных агрегаций по множеству запусков).

**Решение — два слоя, не один:**

1. **Внутрисессионный (использует существующий `SessionStore`, без изменений архитектуры):** `AnalysisSession.pipeline_trace: list[TraceEvent]` — короткий буфер последних событий текущего браузерного сеанса, для мгновенного рендера панели без похода во внешнее хранилище. TTL = TTL сессии (30 дней), сбрасывается вместе с сессией.
2. **Долговременный, кросс-сессионный (новый слой, требует БД — впервые в проекте появляется постоянное хранилище за пределами Redis/памяти):** таблица `research_runs` (или документо-ориентированная коллекция) с полями `run_id (PK, уникальный, показывается пользователю)`, `session_id (последний известный, для связи с текущим браузером)`, `dataset_fingerprint`, `target_column`, `created_at`, `last_active_at`, `status (active/paused/completed/abandoned)`, и связанная таблица/коллекция `trace_events` (append-only, `run_id` — внешний ключ). Именно сюда пишет middleware из §4.2 — **в дополнение** к внутрисессионному буферу, не вместо него.

`run_id` генерируется при первом событии исследования (по факту первой загрузки датасета) и **не привязан к аутентификации** (её на платформе сейчас нет для `/v1/session/*`, см. §10) — просто устойчивый уникальный идентификатор, который можно показать пользователю («Ваш номер обращения для техподдержки: `RUN-8F2A91`») и по которому можно восстановить сессию на другом устройстве (см. §5.3).

### 5.1 Чекпоинты

Чекпоинт — не отдельная сущность с собственной моделью, а **именованная ссылка на конкретное событие в `trace_events`** («на этот момент указывает контрольная точка N») + опциональный человекочитаемый комментарий аналитика («перед экспериментом с агрессивным сглаживанием»). Создаётся явно (кнопка «Сохранить контрольную точку» в панели) — не автоматически на каждое событие, иначе чекпоинты обесцениваются количеством.

Проверено: у платформы уже есть узкий, но структурно идентичный прецедент — `PassportCheckpoint` (`apps/api/session_store.py`), «логическая точка передачи ряда между этапами» (`checkpoint_id`, `stage`, `snapshot_id`, `source_stage`, `confirmed_at`) — ссылка на снимок, а не копия данных, ровно тот же принцип. Чекпоинт «Прогресса» — обобщение этого же паттерна на произвольное событие любой стадии, а не только на паспорт-хендофф; существующий `PassportCheckpoint` не заменяется и не мигрирует — остаётся узкоспециализированным механизмом паспортов, как и был.

### 5.2 Пауза

«Пауза» не требует отдельного технического действия сверх уже происходящего: `AnalysisSession` и так переживает закрытие вкладки (Redis/TTL). «Пауза» на уровне UX — это просто **явная фиксация статуса `run.status = "paused"`** в `research_runs` с текущим timestamp, чтобы отличить «аналитик отошёл на 5 минут» от «аналитик сознательно поставил работу на паузу и вернётся позже» — второе учитывается в статистике платформы (цель 5) отдельно от брошенных (`abandoned`) сессий.

### 5.3 Восстановление на другом устройстве/после истечения cookie

`GET /v1/progress/runs/{run_id}/restore` — если предъявленный `run_id` валиден и его `research_runs.status != "completed"`, создаёт НОВУЮ `AnalysisSession` (новый cookie), **пере-загружает исходный датасет** (тут нужен физический доступ к сырому файлу — вне объёма этой спецификации: зависит от того, где вообще хранятся загруженные датасеты сейчас — если только в оперативной памяти процесса конкретного `AnalysisSession.dataframe`, восстановление возможно только с ПОВТОРНОЙ загрузкой исходного файла аналитиком; если появится персистентное хранилище файлов — восстановление станет автоматическим). Прогресс (какие узлы уже пройдены, какие решения приняты) восстанавливается из `trace_events`, но **сами промежуточные состояния DataFrame — нет**, если только каждое `apply=true`-событие также не сохраняет снапшот данных (дорого; в MVP не делается — см. §12, открытый вопрос).

### 5.4 Отчёт для пользователя (цель 2)

`GET /v1/progress/runs/{run_id}/report` (или `?format=pdf|html|md`) — рендерит `trace_events` в читаемый линейный отчёт: по каждому пройденному узлу — что нашли, что исправили, чем кончилось (переиспользует те же шаблоны текста, что уже пишутся для «Метрики и алгоритм» каждой остановки — терминология отчёта не изобретается заново). Для Прогнозирования этот отчёт напрямую переиспользует `GET .../forecast/{id}/export.json` (`spec_forecasting2.md §5.5/§9.3, п.2`) по ссылке — не дублирует сериализацию.

Не в объём MVP реализации, но контракт эндпоинта фиксируется здесь, чтобы модель `trace_events` проектировалась с расчётом на такой рендер (человекочитаемый `payload`, а не сырые числа без единиц).

## 7. «Наставник» — правило-движок

Как согласовано в обсуждении при первой версии спецификации: **без LLM в реальном времени**. Наставник решает ДВЕ разных по природе задачи, разведённые на два независимых потока правил с разными триггерами:

- **§7.1 «Следующий шаг»** — проактивная навигация по графу: что делать дальше, куда идти.
- **§7.2 «Обнаружение ошибок в Мастере»** — реактивная проверка результата ТОЛЬКО ЧТО совершённого действия: не ошибся ли аналитик в выборе метода/параметра.

Обе используют общий тип правила и общий текстовый рендерер (§8), но разные источники данных и разные точки вызова в UI.

### 7.1 «Следующий шаг» (навигация по графу)

```python
# app/core/mentor_rules.py (новый модуль)

@dataclass
class MentorRule:
    rule_id: str
    stage: str
    trigger: str                       # "on_demand" (§7.1) | "on_correction_result" (§7.2)
    condition: Callable[..., bool]       # чистая функция, без побочных эффектов; сигнатура
                                           # зависит от trigger -- см. §7.1/§7.2
    priority: int                         # порядок применения при нескольких сработавших правилах
    explanation_template: str              # параметризованный текст, тот же стиль,
                                              # что уже используют METRICS_DESCRIPTION-константы
    recommended_action: str | None          # deep-link на конкретный узел/вкладку, если есть

# Пример правила "Следующий шаг" (trigger="on_demand", condition: (nodes) -> bool):
MentorRule(
    rule_id="regularity_before_decomposition",
    stage="preprocessing",
    trigger="on_demand",
    condition=lambda nodes: (
        _status(nodes, "preprocessing", "regularity") == "warning"
        and _status(nodes, "preprocessing", "decomposition") in ("pending", "skipped")
    ),
    priority=10,
    explanation_template=(
        "В ряде остались нарушения регулярности временного шага. "
        "STL-декомпозиция и спектральный анализ требуют равномерной сетки дат — "
        "рекомендуем сначала исправить регулярность."
    ),
    recommended_action="preprocessing.regularity",
)

# Пример правила для Прогнозирования (данные -- прямо из ForecastRun, spec_forecasting2.md §9.3, п.4):
MentorRule(
    rule_id="forecast_not_compared_before_export",
    stage="forecasting",
    trigger="on_demand",
    condition=lambda nodes, latest_run: (
        latest_run is not None
        and "forecast_compared" not in {e.event_type for e in latest_run.trace_events}
        and "forecast_exported" not in {e.event_type for e in latest_run.trace_events}
    ),
    priority=10,
    explanation_template=(
        "Прогноз построен, но не сравнивался с альтернативными моделями — "
        "рассмотрите сравнение перед экспортом."
    ),
    recommended_action="forecasting.compare",
)
```

`GET /v1/progress/runs/{run_id}/mentor/next-step` — прогоняет текущее состояние графа (`list[PipelineNodeState]`) через отсортированный по `priority` список `trigger="on_demand"`-правил, возвращает **первое** сработавшее (не весь список — Наставник даёт ОДНУ рекомендацию за раз, не заваливает советами) + текст пояснения текущей фазы (шаблон по последнему активному `stage`) + краткую сводку уже полученных выводов (агрегация `summary_count`/`status_reason` уже пройденных узлов той же стадии, а для Прогнозирования — `ForecastRun.warnings`/`expected_accuracy` — не новая аналитика, а **пересказ уже посчитанного**). Вызывается по кнопке «Наставник» в панели (`MentorPanel.tsx`).

### 7.2 Обнаружение ошибок в Мастере (реактивная проверка результата)

**Мотивация.** Каждый Мастер исправления (Пропуски/Выбросы/Регулярность и далее по мере реализации остальных остановок) уже показывает блок «Прогноз влияния на статистики» на шаге «Предпросмотр» — но это просто ЧИСЛА (до→после), интерпретация которых целиком лежит на аналитике. Аналитик может не заметить, что: выбранный метод по факту ничего не исправил (неверный порог/параметр), исправление оказалось избыточно агрессивным (переглаживание, схлопывание дисперсии), или задел не ту колонку. Наставник должен уметь читать те же самые уже вычисленные числа (`stats_before`/`stats_after`, `changed_count`, `still_missing`/`still_outliers`, `rows_removed` — везде уже присутствуют в `DatasetXCorrectionResponse`) и явно предупреждать о характерных паттернах ошибки — **не запрещая действие**, а показывая предупреждение до подтверждения.

**Ключевое архитектурное решение: проверка встраивается в шаг «Предпросмотр» (`preview=true`, ДО применения), а не постфактум после `apply=true`.** Тем самым аналитик видит предупреждение прежде, чем нажмёт «Применить исправления» — тот же принцип, что уже действует в самом Мастере («preview → confirm → apply»), Наставник просто добавляет ещё один сигнал в ту же точку принятия решения, не создавая отдельный шаг.

```python
@dataclass
class SanityWarning:
    rule_id: str
    severity: str            # "info" | "warning"
    message: str
    suggested_action: str | None    # человекочитаемая подсказка ("попробуйте порог 3.0 вместо 1.5")

@dataclass
class CorrectionOutcomeSummary:
    """Нормализованная проекция того, что уже возвращает preview-ответ
    ЛЮБОГО мастера (Missing/Outliers/Regularity/...) -- не новые
    вычисления, только переупаковка уже существующих полей ответа
    в общую форму, чтобы правила §7.2 не знали про специфику
    конкретного мастера."""
    stage: str
    node_id: str
    strategy: str
    method: str | None
    affected_count_before: int          # missing_count / outlier_count / total_violations
    changed_count: int
    still_affected_count: int            # still_missing / still_outliers / total_violations_after
    rows_before: int
    rows_after: int
    stats_before: dict[str, float] | None   # mean/std/median, где применимо
    stats_after: dict[str, float] | None


def rule_no_effect(outcome: CorrectionOutcomeSummary) -> SanityWarning | None:
    """Стратегия выбрана, но по факту ничего не изменила -- типичный
    признак: порог/метод слишком мягкий, либо выборка слишком мала."""
    if outcome.affected_count_before > 0 and outcome.changed_count == 0:
        return SanityWarning(
            rule_id="no_effect",
            severity="warning",
            message="Выбранная стратегия не изменила ни одного значения.",
            suggested_action="Проверьте параметр/порог метода или попробуйте другой метод обнаружения.",
        )
    return None


def rule_over_aggressive(outcome: CorrectionOutcomeSummary) -> SanityWarning | None:
    """Стандартное отклонение после исправления схлопнулось намного
    сильнее, чем можно объяснить долей затронутых значений -- признак
    переглаживания/слишком грубой стратегии (напр. замена медианой
    большой доли выборки)."""
    if not (outcome.stats_before and outcome.stats_after):
        return None
    std_before, std_after = outcome.stats_before.get("std"), outcome.stats_after.get("std")
    if std_before and std_after is not None and std_after < std_before * 0.2:
        return SanityWarning(
            rule_id="over_aggressive",
            severity="warning",
            message="После исправления стандартное отклонение упало более чем в 5 раз — возможно, стратегия слишком агрессивна для этой доли данных.",
            suggested_action="Рассмотрите менее жёсткую стратегию (например, флаг вместо замены) или уточните порог метода.",
        )
    return None


def rule_excessive_data_loss(outcome: CorrectionOutcomeSummary) -> SanityWarning | None:
    """drop_rows/ресемплирование удалило значительную долю датасета --
    типичный признак слишком узкого порога или ошибочно выбранной колонки."""
    if outcome.rows_before == 0:
        return None
    removed_share = 1 - (outcome.rows_after / outcome.rows_before)
    if outcome.strategy == "drop_rows" and removed_share > 0.3:
        return SanityWarning(
            rule_id="excessive_data_loss",
            severity="warning",
            message=f"Стратегия удалит {removed_share:.0%} строк датасета.",
            suggested_action="Проверьте, не завышен ли порог метода, и не задета ли колонка, которую вы не собирались исправлять.",
        )
    return None
```

`POST /v1/progress/mentor/sanity-check` — принимает `CorrectionOutcomeSummary` (frontend строит его из уже полученного preview-ответа конкретного Мастера — маппинг тривиален, разный набор полей у Missing/Outliers/Regularity сводится к общим именам на клиенте перед отправкой), прогоняет через ВСЕ `trigger="on_correction_result"`-правила (в отличие от §7.1, здесь возвращается **весь список** сработавших предупреждений, а не одно — разные проблемы независимы и не взаимоисключающи), рендерит `MentorInlineWarning.tsx` над кнопкой «Применить исправления» в каждом Мастере.

**Правило "мечется" (`thrashing`) — отдельный, требующий истории `trace_events`, а не одного preview-ответа.** Если один и тот же узел за короткое окно (напр. 10 минут) многократно исправляется чередующимися стратегиями без итогового применения (несколько `correction_previewed` без единого `correction_applied`, либо применение → повторное применение другой стратегией → повторное… — паттерн «аналитик пробует всё подряд») — это не проверяется на одном preview-ответе, а требует чтения последних N событий `trace_events` того же `run_id`/`node_id`. Реализуется как `trigger="on_demand_with_history"` — третий вид триггера, вызывается не при каждом preview (дорого гонять историю на каждый клик), а при открытии панели/Наставника, и предупреждение показывается уже там, а не инлайн в Мастере:

```python
MentorRule(
    rule_id="thrashing_detected",
    stage="preprocessing",  # или любая
    trigger="on_demand_with_history",
    condition=lambda recent_events: (
        len({e.payload.get("strategy") for e in recent_events if e.event_type == "correction_previewed"}) >= 3
        and not any(e.event_type == "correction_applied" for e in recent_events)
    ),
    priority=5,
    explanation_template=(
        "На этой остановке опробовано несколько разных стратегий подряд без применения ни одной. "
        "Если не уверены в выборе — посмотрите раздел «Оценка методологии» в «Метрики и алгоритм» этой остановки, "
        "или зафиксируйте промежуточный результат чекпоинтом и продолжите позже."
    ),
    recommended_action=None,  # осознанно без deep-link -- это не "куда идти", а "как решать", рекомендация другого типа
)
```

**Пороговые значения эвристик (`0.2`, `0.3`, окно `10 минут`, `3` разных стратегии) — не окончательные, требуют калибровки на реальном использовании платформы.** Вынесены в конфигурацию (не хардкод), см. §12.

## 8. Точка расширения LLM (не реализуется сейчас)

Контракт зафиксирован здесь заранее, чтобы включение LLM позже не потребовало переписывать §7:

```python
class MentorTextRenderer(Protocol):
    """Единственная точка, где мог бы появиться LLM: ПЕРЕФОРМУЛИРОВКА
    уже вычисленного правило-движком факта (rule_id + параметры шаблона),
    НЕ вычисление самого факта/рекомендации/предупреждения. Дефолтная
    реализация -- просто .format() шаблона, без сети/модели. Применимо
    одинаково и к §7.1 (следующий шаг), и к §7.2 (sanity-предупреждения)."""
    def render(self, rule: MentorRule, context: dict[str, Any]) -> str: ...
```

Если понадобится: добавляется `LLMMentorTextRenderer(MentorTextRenderer)` за фиче-флагом, вызывается ПОСЛЕ того, как правило-движок уже определил `rule_id`/`recommended_action`/`severity` — LLM никогда не выбирает рекомендацию и не решает, есть ли ошибка, и не имеет доступа к сырым данным ряда, только к уже агрегированным текстовым фактам (тот же принцип, что уже использован в позиции по паспортам: LLM — рендерер, не источник истины).

## 9. Данные для аналитики/банка кейсов/RAGFlow/дообучения (цель 5)

Всё потребляет один и тот же корпус `trace_events` (§4–5), офлайн, батчем — не в горячем пути аналитика:

| Потребитель | Как использует корпус |
|---|---|
| Статистика платформы | SQL/агрегация по `research_runs`/`trace_events` (какие узлы чаще всего дают `warning`, средняя длительность стадии, доля `abandoned`, частота срабатывания правил §7.2 — сигнал, какие Мастера чаще всего приводят к ошибкам аналитиков; для Прогнозирования — какие модели/горизонты/`alpha` выбираются чаще, `spec_forecasting2.md §9.3, п.5`) |
| Банк кейсов | Отбор кандидатов — алгоритмическая эвристика (`run.status == "completed"`, финальный бэктест-скор выше порога, малое число `warning`-узлов и малое число сработавших `on_correction_result`-предупреждений на выходе — т.е. «чистые», без метаний, прохождения) → отобранные `run_id` идут в офлайн-процесс суммаризации трассы в читаемый кейс (**вот здесь у LLM легитимная роль уже сейчас в дизайне, но как офлайн-джоба, не часть этого сервиса** — вынесено в отдельный будущий тикет). Для Прогнозирования дополнительный материал — связка «профиль ряда → выбранная модель → построенный прогноз → фактическое покрытие интервала» (`spec_forecasting2.md §9.3, п.5`) — верификация надёжности интервалов платформы задним числом. |
| RAGFlow | Индексирует сгенерированные кейсы (не сырые `trace_events`) |
| Дообучение моделей | Отдельный офлайн-экспорт корпуса, вне объёма этой спецификации |

`trace_events` проектируются как **обезличиваемые по построению** — `payload` не содержит значений ряда, только факты о решениях (методы/стратегии/статусы), что снимает часть вопросов приватности до того, как они встанут остро.

## 10. Admin-панель мониторинга

Использует уже существующую ролевую модель (`apps/api/plans.py::Role`, `apps/api/auth.py::require_capability`) — **не изобретает новую систему прав**. Важное ограничение: `Role`/`require_capability` сейчас защищают `/v1/public`/`/v1/models` (API-ключ), а не `/v1/session/*` (cookie-based, без API-ключа) — микросервис «Прогресс» естественно живёт в `/v1/session/*` для аналитика, но admin-эндпоинты (`GET /v1/progress/admin/*`) должны требовать API-ключ с ролью `ADMIN`, а не cookie — то есть админ заходит другим путём, чем обычный аналитик (соответствует уже принятому на платформе разделению `internal`/`public`/`session`).

Состав панели (агрегаты по `research_runs`/`trace_events`, без раскрытия содержимого конкретных датасетов пользователей):
- Активные/приостановленные/завершённые запуски за период.
- Распределение времени по стадиям (где аналитики чаще всего застревают).
- Топ узлов с `status=warning`/`error` (какие проверки чаще всего требуют вмешательства — сигнал для приоритизации будущих улучшений методологии).
- Частота срабатывания правил «Следующий шаг» (§7.1) — какие рекомендации даются чаще всего.
- **Частота срабатывания sanity-предупреждений (§7.2) по правилу и по узлу** — прямой сигнал, где аналитики чаще всего ошибаются в выборе метода/параметра.

## 11. Поэтапный план реализации и хронология зависимостей от Моделирования/Прогнозирования

**Ключевая находка (проверено по коду на `bfe11cf`): «дождаться завершения Моделирования» — почти нигде не настоящий блокер.** 11-стадийный граф Моделирования (`MODELING_STAGE_IDS`) заморожен архитектурно с Task 122 и не меняется по мере роста числа сертифицированных моделей (сейчас 14/24 — Task 121–129, впереди ещё Tasks 130–143: мультивариантные модели, волатильность, нейросети, финальная матрица 24×11). Прогресс не спрашивает «сколько моделей готово» — он спрашивает «какие 11 узлов есть и какой у них статус», а эти 11 узлов существуют и отвечают на запросы **уже сейчас**, при любом текущем числе сертифицированных моделей. Поэтому почти всё для Моделирования можно строить параллельно, не дожидаясь Task 143.

**С Прогнозированием — наоборот, настоящий жёсткий блокер**, но узкий: сейчас нет ни одного эндпоинта (`spec_forecasting2.md` — «не реализовано», проверено — в `apps/api/` нет ни файла с упоминанием forecast/forecasting). Опросить нечего — не «неудобно», а буквально нечего.

Отсюда — не бинарный ответ «всё после X», а три категории:

### A. Немедленно, параллельно с продолжением Моделирования и до начала Прогнозирования — не блокируется ничем
- **Этап 0 — граф + внутрисессионная трасса.** `app/core/pipeline_graph.py`, `PipelineNodeState`, `AnalysisSession.pipeline_trace` — для всех **пяти** уже существующих стадий (Загрузка/Валидация/Предобработка/EDA/**Моделирование**, включая её 11 узлов — граф Моделирования включается сюда сразу, не в отдельный более поздний этап). Даёт цель 1 полностью.
- **Этап 1 — долговременное хранилище.** `run_id`, схема Postgres (`research_runs`/`trace_events`, §12 п.1), персистентность сырых датасетов (§12 п.3), снапшоты чекпоинтов (§12 п.4) — чистая инфраструктура, нулевая зависимость от содержимого Моделирования/Прогнозирования.
- **Этап 2 — Наставник v1: «Следующий шаг» (§7.1) для стадий 1–4** (Пропуски/Выбросы/Регулярность/Декомпозиция/Стабилизация дисперсии/Сглаживание — уже реализованные Мастера) **и базовые правила для Моделирования** (например: «бэктест не запускался», «есть кандидаты, но ни один не выбран») — используют уже существующие 11 узлов и `MODEL_EXECUTION_REGISTRY`, не зависят от того, 14 или 24 модели сертифицировано.
- **Этап 2.1 — sanity-предупреждения в Мастере (§7.2)** для тех же уже реализованных Мастеров.
- **UI-панель (§6), ModuleNav-замена «Логи событий» → «Прогресс».**

### B. Инкрементально, по мере продолжения Моделирования (Task 130–143) — не «после», а «вместе», без остановки предыдущих этапов
- Mentor-правила, ссылающиеся на **конкретные ещё не реализованные семейства моделей** (мультивариантные VAR/VECM — Task 131–133, волатильность GARCH/EGARCH — Task 134–136, нейросети — Task 137+) — правило «попробуйте GARCH для этого ряда» физически бессмысленно писать до Task 135. Добавляется по одному правилу на каждую новую сертифицированную модель/семейство, тем же PR, что и саму модель — не отдельный этап, требующий ожидания.
- Расширение узла «Моделирование» в блок-схеме доп. деталями по мере роста каталога — косметическое дополнение, не переработка.

### C. Жёстко ждёт как минимум MVP Прогнозирования (backtest-точечный прогноз + `forecast_generated`) — здесь действительно «после», а не «вместе»
- Узел «Прогнозирование» и его 4 типа события (§2, §4) — опрашивать нечего до появления первого эндпоинта.
- §5.4 «Отчёт для пользователя» в части переиспользования `GET .../forecast/{id}/export.json` — эндпоинта не существует.
- Mentor-правило `forecast_not_compared_before_export` (§7.1) — данных для условия правила ещё нет.
- Часть §9 про «профиль ряда → выбранная модель → построенный прогноз → фактическое покрытие интервала» — нет `ForecastRun`, нечего агрегировать.

Практическое следствие: узел «Прогнозирование» в панели первое время будет честно показывать «не начат» — это не баг реализации Прогресса, а точное отражение реального состояния платформы; включать этот узел в граф (категория A, Этап 0) можно и нужно сразу — данные под него появятся сами по мере того, как заработает Прогнозирование, без изменений в коде Прогресса.

### D. Отдельная, третья ось — не зависит ни от Моделирования, ни от Прогнозирования, а от времени/объёма реального использования
Не путать с категориями A/B/C — это не архитектурная, а временнáя зависимость:
- **Этап 3 — офлайн-потребители** (§9: статистика, отбор кейсов) — технически готовы сразу после Этапа 1, но бессмысленны без нескольких недель накопленных `trace_events`.
- **Этап 4 — admin-панель** (§10) — по той же причине: агрегаты по пустому корпусу неинформативны.
- **Этап 5 (отдельный тикет) — LLM-суммаризация/`LLMMentorTextRenderer`** (§8) — сознательно вне этой спецификации, не гейтится ни Моделированием, ни Прогнозированием, ни объёмом данных — отдельное решение о запуске.

## 12. Открытые вопросы и рекомендации (production-среда: on-prem, CPU-only, RAM достаточно)

**Целевая production-среда зафиксирована как вводная для рекомендаций ниже**, не как отдельный открытый вопрос: собственный корпоративный виртуальный сервер, **Linux**-гостевая VM на Linux-хосте (обоснование — см. ответ на вопрос про Windows выше по переписке; кратко: Redis не имеет официальной Windows-сборки, `cmdstanpy`/Prophet заметно менее надёжен на Windows, вся существующая CI/Docker-инфраструктура репозитория (`ubuntu-latest`, `python:3.10-slim`) уже Linux-native — второй тулчейн под Windows не даёт выгоды, раз материнский хост и так Linux). CPU-only не создаёт новых ограничений для уже спроектированного функционала: ни Наставник (правило-движок, не модель), ни существующие 11 сертифицированных моделей Моделирования (Task 121–125, все statsmodels/Prophet/statsforecast — CPU-bound по конструкции, GPU/neural-семейство ещё не реализовано) не требуют GPU. RAM «достаточно» напрямую разрешает пункты 3–4 ниже в пользу более полнофункционального MVP, чем предполагалось изначально.

1. **Технология долговременного хранилища (§5) — рекомендация: Postgres.** Не документная БД и не расширение Redis. Обоснование: (а) admin-панель (§10) по конструкции — SQL-агрегации («топ узлов с `warning`», гистограмма времени по стадиям) — реляционная модель для этого естественна, документная потребовала бы либо агрегационного конвейера поверх, либо периодической выгрузки в аналитическую БД — лишний слой без надобности; (б) `TraceEvent` — фиксированная, спроектированная здесь схема (§4.1), не эволюционирующий произвольный документ — гибкость schemaless не даёт выгоды, только теряет целостность; (в) Redis остаётся тем, чем спроектирован — кэшем/сессией с TTL-выселением; смешивать в него данные, которые обязаны переживать выселение и участвовать в аналитике (§9), — предполагает разную семантику надёжности в одном хранилище, лишний операционный риск; (г) on-prem корпоративная среда почти всегда уже имеет эксплуатационный опыт с Postgres (бэкапы, мониторинг) — не нужно заводить новую компетенцию ради этого сервиса. При ожидаемых объёмах (одна платформа, не интернет-масштаб) — один инстанс Postgres на том же VM или соседнем, без кластера.
2. **EDA CHECKS как единственный frontend-only реестр (§2) — рекомендация: вынести сейчас, не откладывать.** Один общий JSON (например, `shared/pipeline_nodes/eda_checks.json`), читаемый и `TsAnalysisEDA.tsx` (импорт/fetch), и `pipeline_graph.py` (чтение файла на старте). Стоимость минимальна, а откладывание означает, что `pipeline_graph.py` уйдёт в реализацию с уже задублированным списком id — тогда исправление станет миграцией с риском рассинхронизации, а не разовой правкой при первом касании.
3. **Восстановление сырых данных на другом устройстве (§5.3) — рекомендация: решается, входит в MVP, не откладывается.** Открытый вопрос был сформулирован в предположении эфемерного/облачного хостинга, где постоянный диск — это стоимость/сложность. На собственном корпоративном сервере локальный диск дёшев и уже персистентен по умолчанию (не пересоздаётся при перезапуске процесса, в отличие от эфемерного контейнера в облаке). Рекомендация: каталог `data/uploads/` на локальном диске VM (или корпоративный NAS/SMB-шара, если ИТ-отдел уже её предоставляет — тогда бэкап вообще бесплатный побочный эффект), файлы — по ключу `dataset_fingerprint` (уже вычисляется платформой для сверки когорт — переиспользуется, не изобретается новый хэш), retention — привязан к `research_runs` (удаление файла через N дней после `status IN ("completed","abandoned")` и отсутствия восстановлений). Это снимает пункт «восстановление ограничено метаданными трассы» — с этой инфраструктурой восстановление становится полным, а не частичным, уже в MVP.
4. **Снапшоты DataFrame на каждый чекпоинт — рекомендация: да, входит в MVP, но с ограничением (не «на каждый», а последние N).** RAM «достаточно» и локальный диск на корпоративном сервере дёшев — это снимает изначальное «дорого по месту» беспокойство, которое было сформулировано с оглядкой на облачную стоимость хранения. Конкретно: хранить последние 5 чекпоинтов на `run_id` в формате Parquet (колоночный, для временных рядов существенно компактнее сырого DataFrame в памяти; запись — лёгкая CPU-операция, не узкое место при однопользовательских по факту сессиях), старше — вытеснять по количеству или TTL, что наступит раньше. Даёт настоящий откат «вернуться к состоянию на точке», а не только список событий — качественно более полезный MVP, чем изначально осторожно предполагалось.

6. **Гранулярность троттлинга `profile_viewed`-событий (§4.2) — рекомендация: дефолт 5 минут на узел на `run_id`, конфигурируемо через переменную окружения, калибровать по факту первых недель эксплуатации на этом же сервере.** От типа инфраструктуры не зависит — реальные данные использования появятся только после запуска, откладывать калибровку до них — единственно осмысленный путь.
7. **Пороговые значения sanity-эвристик §7.2 — рекомендация: не хардкод, а `rules/*.yaml`, тем же паттерном, что уже хранит IQR-множитель 1.5 и пороги D05 в спецификации Моделирования.** Не изобретается новый конфиг-механизм ради Наставника — переиспользуется уже принятый на платформе способ хранить калибруемые константы отдельно от кода. Сами значения (`0.2`/`0.3`/`10 минут`/`3` стратегии) — стартовые дефолты, требуют калибровки по реальному использованию; от инфраструктуры не зависят.
8. **Блокирует ли `MentorInlineWarning` кнопку «Применить исправления»? — рекомендация: нет, не блокирует, но делает предупреждение визуально заметным (цветной баннер с явной формулировкой «Продолжить всё равно»), а не тихой инлайн-подсказкой.** Агрессивная коррекция иногда осознанный выбор эксперта — жёсткая блокировка раздражает опытных пользователей чаще, чем предотвращает реальные ошибки; видимость важнее принуждения.
9. **Ширина и адаптив правой панели (§6.1–6.2)** — деталь вёрстки фронтенда, не архитектурное решение и не зависит от инфраструктуры сервера — остаётся на усмотрение реализации.
10. **Правило свёртки `CheckStatus`/`StageStatus` в три визуальных состояния карточки (§3) — рекомендация: любой единичный `error`/`warning` в стадии переводит всю карточку в жёлтый статус, независимо от того, сколько остальных узлов `done`.** Для инструмента контроля качества данных пропущенная проблема (ложноотрицательный «всё зелёное») дороже, чем лишний не раздражающий жёлтый бейдж (ложноположительная лишняя видимость) — при своде статуса разумно ошибаться в сторону заметности проблемы, а не в сторону чистоты общей картины.
