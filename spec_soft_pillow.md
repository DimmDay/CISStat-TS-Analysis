# Спецификация: Soft Pillow — балансировка визуальных пустот в многоколоночных секциях

**Задача:** Task 101 (продолжение worklog2.md)
**Синхронизация:** `main` @ `0d1786f9050e0b313097a25a14ed60acadb8e07d`
**Статус:** Архитектурный дизайн, готов к ревью тимлидом перед стадией TDD-реализации
**Автор:** Claude (Senior dev), платформа CISStat TS Analysis
**Дата:** 2026-09-03
**Затрагиваемые области:** `packages/ui` (общий переиспользуемый layout-примитив), все страницы платформы, где секция состоит из нескольких колонок (Validation / Preprocessing / EDA / Modeling)

---

## 1. Проблема

Секции страниц платформы построены из нескольких соседних колонок
(например, колонка параметров/управления и колонка результатов/Обзора,
либо несколько карточек в ряд). Высота содержимого каждой колонки
непостоянна: она зависит от текущего состояния — количества
отображаемых полей, наличия предупреждений/ошибок, выбранного
представления, набора визуализаций и т.д. Когда колонки одной секции
получают разную высоту содержимого, нижняя граница более короткой
колонки заканчивается раньше — визуально это читается как случайная,
незавершённая пустота, а не как осознанное решение вёрстки, и общая
нижняя граница секции (а для последней секции — фактически и всей
страницы) выглядит «рваной».

## 2. Цель

Дать каждой колонке многоколоночной секции механизм самостоятельного
"дозаполнения" своей нижней границы декоративной, статичной, светло-серой
подложкой ("подушкой"), которая:
- не несёт данных и не интерактивна;
- динамически подстраивается под текущее состояние соседних колонок,
  выравнивая нижнюю границу **всех** колонок секции по самой длинной из
  них;
- визуально соответствует стандарту платформы (закруглённые углы, без
  рамок, приглушённый фон);
- активна только там, где колонки реально показываются рядом (широкий
  экран); на мобильной раскладке, где колонки складываются в один
  вертикальный поток, подушка не нужна и не должна создавать лишних
  вычислений.

### Вне рамок задачи (non-goals)
- Выравнивание/растягивание **самого содержимого** колонок (это не
  «resize» контента, а добавление декоративного элемента после него).
- Выравнивание ширины колонок — задача касается только высоты.
- Общая перестройка сетки страниц — Soft Pillow встраивается в уже
  существующую многоколоночную раскладку, не заменяет её.
- Внутренняя раскладка вложенных графиков внутри «Обзора» (468px-контракт
  Task 88 и раскрытие графика на всё окно Обзора, Task 97 — «Expandable
  Chart Panel») — это отдельный, более мелкий уровень вложенности; Soft
  Pillow работает на уровне **макро-колонок страницы/секции**, а не
  внутри уже зафиксированного по высоте окна Обзора (см. §8 о
  разграничении с Task 97).

## 3. Пользовательский сценарий

1. Аналитик открывает любую вкладку с двумя (или более) колонками в
   секции — например, «Параметры» слева и «Результаты/Обзор» справа.
2. Одна из колонок в моменте короче другой (например, панель параметров
   свернула часть полей, или Обзор ещё не показывает дополнительный
   блок диагностики).
3. Под содержимым более короткой колонки появляется ровный светло-серый
   прямоугольник со скруглёнными углами, без рамки, который дозаполняет
   пространство ровно до уровня нижней границы самой длинной колонки —
   визуально секция выглядит целостной, обе колонки заканчиваются на
   одной высоте.
4. При изменении состояния (аналитик раскрыл дополнительный блок,
   выбрал другое представление, появилось предупреждение и т.д.) высота
   содержимого одной из колонок меняется — подушки во всех колонках
   секции пересчитываются автоматически, без перезагрузки страницы и без
   моргания layout.
5. Если самая длинная колонка сама становится короче (то есть исчезает
   причина неравенства высот) — подушки соответствующих колонок плавно
   уменьшаются, вплоть до нуля (не рендерятся вовсе), когда все колонки
   секции уже равны по высоте.
6. На узком экране (мобильная раскладка, колонки уже не стоят рядом, а
   идут одна под другой) подушки не отображаются вовсе — там нет визуальной
   проблемы «рваной» общей границы, так как колонки не делят одну строку.

## 4. Архитектура компонентов (packages/ui)

Как и `ExpandableChartPanel` (Task 97) — это **общий переиспользуемый
layout-примитив** в `packages/ui`, не завязанный на конкретную вкладку,
чтобы одна реализация работала одинаково на всех страницах и в обоих
приложениях (embedded/standalone).

```
packages/ui/
  components/
    layout/
      SoftPillowSection.tsx        — провайдер контекста на уровень
                                      одной группы соседних колонок
      SoftPillowSection.test.tsx
      SoftPillowColumn.tsx         — обёртка одной колонки: измеряет
                                      свой контент, регистрируется в
                                      провайдере, рендерит Pillow снизу
      SoftPillowColumn.test.tsx
      SoftPillow.tsx               — чисто презентационный элемент
                                      (сам светло-серый бейдж-заполнитель)
      SoftPillow.test.tsx
  hooks/
    useSoftPillowMeasurement.ts    — обёртка над ResizeObserver с
                                      батчингом через requestAnimationFrame
    useIsWideLayout.ts             — обёртка над matchMedia для брейкпоинта
                                      (см. §6); переиспользуется, если в
                                      проекте уже есть аналогичный хук —
                                      см. §7.1
```

### 4.1 `SoftPillowSection` — провайдер

Создаёт единый контекст измерений для одной группы «соседних» колонок
(одна секция страницы = один провайдер; секции не пересекаются между
собой).

```tsx
type ColumnId = string;

type SoftPillowSectionState = {
  heights: Map<ColumnId, number>; // высота собственного контента колонки
  register: (id: ColumnId, height: number) => void;
  unregister: (id: ColumnId) => void;
};

const SoftPillowSectionContext = createContext<{
  maxHeight: number;
  isWide: boolean;
  register: (id: ColumnId, height: number) => void;
  unregister: (id: ColumnId) => void;
} | null>(null);

export function SoftPillowSection({ children }: PropsWithChildren) {
  const [heights, setHeights] = useState<Map<ColumnId, number>>(new Map());
  const isWide = useIsWideLayout(); // §6

  const register = useCallback((id: ColumnId, height: number) => {
    setHeights(prev => {
      if (prev.get(id) === height) return prev; // без лишних ре-рендеров
      const next = new Map(prev);
      next.set(id, height);
      return next;
    });
  }, []);

  const unregister = useCallback((id: ColumnId) => {
    setHeights(prev => {
      if (!prev.has(id)) return prev;
      const next = new Map(prev);
      next.delete(id);
      return next;
    });
  }, []);

  const maxHeight = useMemo(
    () => (heights.size ? Math.max(...heights.values()) : 0),
    [heights]
  );

  return (
    <SoftPillowSectionContext.Provider value={{ maxHeight, isWide, register, unregister }}>
      {children}
    </SoftPillowSectionContext.Provider>
  );
}
```

Инварианты:
- Если `isWide === false` (мобильная раскладка, §6) — `maxHeight` не
  используется для рендера подушек: `SoftPillowColumn` при этом вообще не
  подписывается на `ResizeObserver` и не рендерит `SoftPillow`
  (нет лишней работы там, где колонки и так идут друг под другом).
- Округление высот до целых пикселей и порог обновления состояния
  (`Math.abs(next - prev) > 1`) — защита от подпиксельного дребезга,
  который в браузерах может провоцировать предупреждение
  "ResizeObserver loop limit exceeded" (см. §9).

### 4.2 `SoftPillowColumn` — обёртка колонки

```tsx
type SoftPillowColumnProps = {
  columnId: string; // стабилен, уникален в пределах секции
  className?: string;
  children: ReactNode;
};

export function SoftPillowColumn({ columnId, className, children }: SoftPillowColumnProps) {
  const { maxHeight, isWide, register, unregister } = useSoftPillowSection();
  const contentRef = useRef<HTMLDivElement>(null);
  const ownHeight = useSoftPillowMeasurement(contentRef, { enabled: isWide });

  useEffect(() => {
    if (!isWide) return;
    register(columnId, ownHeight);
    return () => unregister(columnId);
  }, [columnId, ownHeight, isWide, register, unregister]);

  const pillowHeight = isWide ? Math.max(0, maxHeight - ownHeight) : 0;

  return (
    <div className={cn('flex flex-col', className)}>
      {/* ВАЖНО: измеряется именно contentRef — обёртка контента без
          подушки, чтобы подушка не влияла сама на себя (см. §9) */}
      <div ref={contentRef}>{children}</div>
      <SoftPillow height={pillowHeight} />
    </div>
  );
}
```

Ключевой момент — разделение «измеряемого контента» и «подушки» на
разные DOM-узлы: `ResizeObserver` наблюдает только `contentRef`, подушка
рендерится **рядом**, не внутри наблюдаемого узла — иначе появление
подушки само меняло бы измеряемую высоту и создавало цикл обратной
связи.

### 4.3 `SoftPillow` — презентационный элемент

```tsx
type SoftPillowProps = { height: number };

export function SoftPillow({ height }: SoftPillowProps) {
  if (height <= 0) return null;
  return (
    <div
      aria-hidden="true"
      className="mt-3 shrink-0 rounded-[var(--radius-card)] bg-[var(--surface-muted)]"
      style={{ height }}
    />
  );
}
```

- `aria-hidden="true"` — элемент декоративный, не несёт информации,
  должен быть исключён из дерева доступности (не мешает
  screen-reader'ам).
- Цвет и радиус — **не новые токены**, а переиспользование уже принятых
  в системе дизайна платформы (см. §7): тот же класс приглушённой
  поверхности, что используют skeleton/empty-state состояния, и тот же
  радиус скругления, что у карточек/панелей Обзора.
- `height <= 0` → компонент не рендерится вовсе (`null`), а не
  схлопывается через `height: 0` — так подушка полностью выпадает из
  DOM там, где колонки уже выровнены, что дешевле для рендера при частых
  пересчётах.

## 5. Использование на страницах

```tsx
<SoftPillowSection>
  <div className="grid grid-cols-1 gap-4 lg:grid-cols-2">
    <SoftPillowColumn columnId="parameters">
      {/* колонка параметров — переменная высота */}
    </SoftPillowColumn>
    <SoftPillowColumn columnId="overview">
      {/* колонка с Обзором — переменная высота */}
    </SoftPillowColumn>
  </div>
</SoftPillowSection>
```

Секция и брейкпоинт переключения `grid-cols-1 → lg:grid-cols-2` берутся
из **уже существующей** разметки страницы — `SoftPillowSection`/
`SoftPillowColumn` не диктуют сетку, они лишь оборачивают уже готовые
колонки. Это намеренное решение: интеграция должна быть точечной
(обернуть существующие колонки), а не требовать переписывания layout
страниц.

Если у секции больше двух колонок (например, три карточки в ряд) —
модель расширяется тривиально: каждая оборачивается своим
`SoftPillowColumn` с уникальным `columnId`, `maxHeight` в провайдере
считается по всем зарегистрированным колонкам одинаково (`Math.max` не
завязан на конкретное число участников).

## 6. Активация только на широких экранах

`useIsWideLayout()` — тонкая обёртка над `matchMedia`, привязанная к
**тому же брейкпоинту**, на котором сама сетка страницы переключается
с одноколоночной на многоколоночную (в примере §5 — `lg`, но должен быть
взят из фактического токена/константы брейкпоинта, уже используемого в
существующих сетках страниц, а не захардкожен заново, см. §7.2).

```ts
export function useIsWideLayout(breakpointPx = LAYOUT_BREAKPOINT_PX) {
  const [isWide, setIsWide] = useState(
    () => typeof window !== 'undefined' && window.matchMedia(`(min-width: ${breakpointPx}px)`).matches
  );
  useEffect(() => {
    const mql = window.matchMedia(`(min-width: ${breakpointPx}px)`);
    const onChange = () => setIsWide(mql.matches);
    onChange();
    mql.addEventListener('change', onChange);
    return () => mql.removeEventListener('change', onChange);
  }, [breakpointPx]);
  return isWide;
}
```

Ниже брейкпоинта: `SoftPillowColumn` не подписывает `ResizeObserver`
(`enabled: isWide` прокидывается в `useSoftPillowMeasurement`) и не
регистрируется в провайдере — секция с мобильной раскладкой не платит
никакой производительностью за фичу, которая там визуально не нужна.

SSR/гидратация: на сервере `window` недоступен, поэтому исходное
состояние — `isWide = false` (безопасный дефолт, без подушек), реальное
значение выставляется на клиенте в `useEffect` — стандартный паттерн,
исключающий hydration mismatch (аналогично тому, как уже решается
адаптивный рендер `ResponsiveContainer` графиков, Task 89).

## 7. Переиспользование существующих реализаций

### 7.1 Frontend

- **Измерение высоты через ResizeObserver.** Если в проекте уже есть
  собственный хук измерения размеров DOM-узла (вероятный кандидат —
  инфраструктура, поддерживающая адаптивность вложенных графиков,
  Task 89, где `ResponsiveContainer` должен был реагировать на изменение
  размеров родителя), `useSoftPillowMeasurement` должен быть **тонкой
  специализацией** этого существующего хука (добавляющей только
  debounce через `requestAnimationFrame` и опцию `enabled`), а не
  параллельной независимой реализацией. Это первое, что нужно проверить
  на Этапе 1 (см. §10) перед тем, как писать новый хук с нуля.
- **Дизайн-токены.** Цвет подложки (`--surface-muted` в примерах выше —
  условное имя) и радиус скругления (`--radius-card`) должны быть взяты
  из уже существующих переменных темы платформы, а не заведены заново:
  - радиус — тот же, что уже используется в карточках/панелях самого
    Обзора (единообразие «стандарта платформы по закруглению углов»,
    прямо требуемое в задаче);
  - цвет — тот же приглушённый светло-серый фон, что уже используется
    для skeleton-заглушек/empty-state плейсхолдеров, если такой паттерн
    в проекте уже есть (высокая вероятность, учитывая уже принятую
    палитру бейджей `--badge-bg` из Task 97) — тогда Soft Pillow
    буквально использует тот же токен, просто в форме прямоугольника, а
    не круглого бейджа.
- **Контекст-провайдер по образцу `ExpandableChartsProvider`.** Паттерн
  «провайдер на уровень одной локальной группы UI-элементов + хук
  доступа» уже применён в Task 97 и здесь переиспользуется один в один
  (та же архитектурная идиома, тот же стиль публичного API — `register`/
  `unregister`/производное значение через `useMemo`).
- **Брейкпоинт.** Если в проекте уже есть общая константа/токен
  брейкпоинта, на котором многоколоночные секции переходят в
  одноколоночный режим (весьма вероятно — иначе на каждой странице был
  бы свой рассинхронизированный `lg:`/`md:`), `useIsWideLayout` обязан
  использовать именно её, а не собственное магическое число.

### 7.2 Backend

Soft Pillow — это исключительно клиентская, декоративная layout-фича:
она не работает с данными пользователя, не запрашивает и не изменяет
состояние сессии анализа. **Изменений в `apps/api` эта задача не
требует.** Единственная точка, которую стоит явно проверить на
Этапе 1, — не хранится ли дизайн-система (цвета, радиусы) в едином
источнике правды, который параллельно используется backend'ом при
генерации экспортируемых отчётов/PDF (см. `pdf`-скилл платформы, если
экспорт отчётов уже воспроизводит фирменные скругления/палитру) — если
такой общий источник токенов существует, он не меняется, а просто
референсится фронтендом как есть (без дублирования значений).

## 8. Разграничение с Task 97 (Expandable Chart Panel)

Обе фичи работают с «геометрией» страницы, но на разных уровнях
вложенности и не пересекаются в реализации:

| | Task 97 — Expandable Chart Panel | Task 101 — Soft Pillow |
|---|---|---|
| Уровень | Внутри одного «Обзора» (фиксированные 468px) | Между колонками секции страницы (макро-layout) |
| Что делает | Один вложенный график временно занимает всё окно Обзора | Декоративно дозаполняет разницу высот между соседними колонками |
| Триггер | Явное действие аналитика (клик по иконке) | Полностью автоматически, без действий пользователя |
| Меняет ли высоту контейнера | Нет — высота Обзора (468px) неизменна | Нет — только добавляет декоративный элемент после контента, не меняя высоту самого контента |

Раскрытие графика внутри Обзора (Task 97) не влияет на общую высоту
макро-колонки страницы (Обзор как единица зафиксирован по высоте,
Task 88), поэтому оно не должно триггерить пересчёт Soft Pillow —
это два независимых, не конфликтующих контура измерения.

## 9. Риски и меры

| Риск | Мера |
|---|---|
| Цикл обратной связи: подушка меняет высоту → триггерит собственный ResizeObserver → пересчитывает подушку до бесконечности | Наблюдается только `contentRef` (контент без подушки), подушка — соседний, не наблюдаемый узел (§4.2) |
| "ResizeObserver loop limit exceeded" при частых обновлениях | Батчинг через `requestAnimationFrame`, обновление состояния только при изменении высоты более чем на 1px, округление до целых px |
| Лишняя нагрузка на мобильной раскладке | `ResizeObserver` вообще не подписывается при `isWide === false` (§6) |
| Hydration mismatch в SSR | Безопасный дефолт `isWide = false` на сервере, реальное значение — на клиенте через `useEffect` (§6) |
| Дублирование дизайн-токенов (новый цвет/радиус вместо переиспользования) | Явное требование в §7.1 — сверка с существующими токенами на Этапе 1 до написания кода |
| Подушка появляется/пропадает рывком при пограничных значениях высоты | Плавный `transition` по высоте на уровне `SoftPillow` (CSS `transition-[height]`), в рамках разумной длительности (не длиннее, чем уже принятые transition'ы в проекте, например 200мс из Task 97) |
| Секции с очень большим числом колонок (много вызовов `register`) создают избыточные ре-рендеры провайдера | `Map`-based состояние с ранним `return prev` при отсутствии изменений (уже заложено в §4.1) — стандартная защита от лишних ре-рендеров |
