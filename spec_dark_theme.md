## 1. Постановка и границы

Цель: общесистемная тёмная тема для обеих оболочек платформы (standalone —
первичный носитель переключателя; embedded — см. открытый вопрос §10.2),
с переключателем в `ProductHeader` справа, рядом с «РУС / ENG»: иконки
луна/солнце сменяют друг друга, отражая и переключая текущую тему.

Явные границы (что НЕ входит):

- Backend/API, Redis, генерация CSV/JSON — не затрагиваются: тема —
  исключительно клиентская презентационная оболочка.
- Локализация (РУС/ENG — сейчас заглушка-кнопка без поведения): тема
  реализуется независимо, но кнопка ставится рядом и повторяет её
  визуальный паттерн; связности с локализацией нет.
- Вёрстка, геометрия, контракт высоты 468px, компоновки, анимации —
  неизменны; меняются ТОЛЬКО значения цветов. Тёмная тема не «второй
  дизайн», а та же вёрстка с другим каталогом значений.

## 3. Рассмотренные стратегии и выбор (решение с обоснованием)

### 3.1 Вариант A — `dark:`-вариант на каждом классе (строковый)

`darkMode: "class"` + ко-класс `dark:bg-neutral-900` рядом с каждым
`bg-white` и т.д. Отвергнут:

- ~2 680 нейтральных + ~657 брендовых + ~800 статусных инстансов →
  удвоение строк классов в 139 файлах, гигантский diff-шум на годы.
- **Ломает guard-тесты**, пинящие точные строки классов: сотни правок
  тестов без смысловой ценности.
- Вечная дисциплина «не забудь dark:-пару» на каждый будущий компонент —
  ошибка проявится только глазами в тёмной теме, автоматически не ловится.

### 3.2 Вариант B — CSS `filter: invert()`

Отвергнут сразу как нечестный: инвертирует изображения, логотип,
графики и статусные оттенки в непредсказуемые цвета; не проходит
программную сверку контраста; противоречит практике платформы
(«честное значение вместо побочного эффекта»).

### 3.3 Вариант C (ВЫБРАН) — «имена классов не меняются, меняются значения»: токенизация палитры через CSS-переменные

В `tailwind-preset.ts` каждый цветовой шаг палитры переопределяется на
CSS-переменную в формате `rgb(var(--c-*) / <alpha-value>)`; в
`globals.css` объявляются `:root` (светлые значения — ТОЧНО текущие hex,
байт-инвариант светлой темы) и `.dark` (тёмные значения).

Следствия выбора:

1. **Ноль правок в 139 компонентах** по всей нейтральной/статусной/брендовой
   массе: класс `bg-white` сам рисует тёмную карточку в тёмной теме.
   Guard-тесты, пинящие строки классов, продолжают проходить БЕЗ правок.
2. **Слэш-прозрачность сохраняется** (~150 инстансов `bg-brand-light/50`,
   `border-brand/30`, `bg-brand/10`...): формат `rgb(var(--x) /
   <alpha-value>)` — штатная поддержка Tailwind 3.4. Требование формата
   страхуется тестом компиляции CSS-бандла (§8).
3. Точечные правки остаются только там, где цвета уже сейчас hex-константы
   (42 файла: Recharts, SVG-фоны, флоучарты) — они и так не покрываются
   классами (§6.3).
4. Новые компоненты пишутся в существующих классах палитры — тёмная тема
   достаётся им бесплатно; «дисциплины пар» из Варианта A нет.
5. Стоимость выбора: **одна и та же строка класса означает разные
   фактические цвета в разных темах**. Это осознанный контракт, он
   документируется в шапке пресета и страхуется каталог-тестом значений
   (§8). Роли закрепляются за уровнями светлоты (лёгкий фон → тёмный
   фон, серый текст → светлый серый текст), рампа §6.1 составлена по
   этому принципу.

## 4. Архитектура решения (Вариант C, покомпонентно)

### 4.1 `packages/ui/tailwind-preset.ts` — единственная точка отображения

- `darkMode: "class"` (переключение классом `.dark` на `<html>`).
- Цвета палитры, используемые компонентами, переопределяются на
  переменные: `white`, полный занятый поддиапазон `neutral-50…950`,
  `brand`/`brand-light`, статусные семейства (green/red/amber/blue/
  emerald/violet/sky/cyan — занятые шаги). Формат:
  `"neutral-200": "rgb(var(--c-neutral-200) / <alpha-value>)"`.
- `--c-*` — тройки каналов RGB (`"229 229 229"`), чтобы работал
  alpha-модификатор.
- Каталог-комментарий: каждый шаг = его роль (фон страницы / карточка /
  граница / текст-1 / текст-2 / статус-поверхность / статус-текст).

### 4.2 `packages/ui/globals.css` — значения обеих тем

- `:root { --c-neutral-200: 229 229 229; ... }` — точные текущие значения
  (светлая тема остаётся попиксельно прежней — инвариант, проверяемый §8).
- `.dark { ... }` — тёмная ревизия (начальный проект — §6.1; финальная
  калибровка и контраст-аудит — DKT-2).
- Служебные: `.dark` скроллбар-цвета `feed-scroll`, `color-scheme`
  (нативные скроллбары/инпуты), `meta theme-color` обновляется
  переключателем.

### 4.3 `packages/ui/context/ThemeContext.tsx` — новый провайдер (hand-rolled)

- Состояние: `"light" | "dark"`; источник истины при инициализации —
  `localStorage["cisstat-theme"]`, при отсутствии — системный
  `prefers-color-scheme` (открытый вопрос §10.3), далее выбор
  пользователя персистится.
- Применение: `document.documentElement.classList.toggle("dark", ...)`.
- Класс на первом кадре ставит no-FOUC-скрипт (§4.5), провайдер
  подхватывает в `useEffect` и далее владеет переключением.
  Кросс-таб-синхронизация — `storage`-событие.
- **Почему без `next-themes`**: решаемые им задачи (FOUC, hydration,
  персист) закрываются ~50 строками своего провайдера; прецедент
  NAVSTG-2 — отказ от отдельного пакета ради одной утилиты. Альтернатива
  остаётся допустимой по решению тимлида (§10.5) — контракт темы (ключ
  localStorage, имя класса, точки монтирования) от этого не меняется.

### 4.4 Точка монтирования

`apps/standalone/app/layout.tsx`: `<html>` получает
`suppressHydrationWarning` (класс ставится скриптом — расхождение
атрибутов ожидаемо и ограничено атрибутом `class`), содержимое оборачивается
в `<ThemeProvider>` (клиентский, из `@cisstat/ui`). Embedded-монтирование —
открытый вопрос §10.2 (переменные и компоненты готовы; решает тимлид).

### 4.5 No-FOUC-скрипт

Блокирующий inline-скрипт в `<head>` layout (до гидратации): читает
`localStorage["cisstat-theme"]`, при отсутствии — `matchMedia` — ставит
класс `.dark` на `<html>` и `color-scheme`. ~10 строк, без зависимостей.

### 4.6 Переключатель в ProductHeader

- Расположение: справа, рядом с «РУС / ENG» (в той же flex-группе,
  между «РУС / ENG» и кнопкой кабинета — постановка «рядом с рус/eng»
  трактуется как непосредственное соседство).
- Поведение: одна иконка, меняющаяся состоянием — **Moon** в светлой теме
  («включить тёмную»), **Sun** в тёмной («включить светлую»);
  lucide-react `Moon`/`Sun` `size={14}`, паттерн соседа — кнопка
  `text-neutral-500 hover:text-neutral-900` (в тёмной теме — те же
  классы, значения которых уже токенизированы).
- Доступность: `aria-label` по состоянию («Включить тёмную тему» /
  «Включить светлую тему»), `aria-pressed`.
- Тёмная шапка: `bg-white` в тёмной ревизии = тёмная поверхность;
  логотип и навигация — аудит DKT-2 (§2: логотип читаем).

## 5. Контракт темы (стабильные имена, фиксируются спекой)

- Ключ хранения: `localStorage["cisstat-theme"]`, значения `"light"|"dark"`.
- Класс-триггер: `.dark` на `<html>`; отсутствие класса = светлая тема.
- Порядок инициализации: localStorage → системная схема → `"light"`.
- Обе оболочки используют ОДИН ключ и ОДИН класс (общий packages/ui).

### 6.2 Исключения «один класс — разные роли» (инвентаризация DKT-2)

- `bg-neutral-950` + `text-neutral-100` (Model Card JSON): в тёмной теме
  текст-пара нейтрального код-блока теряла бы контраст. Решение — явный
  `dark:`-оверрайд ТОЛЬКО на этом блоке (например
  `dark:border dark:border-neutral-800`) — исключение документируется в
  коде и каталоге; инвентаризация ищет аналогичные инверсные поверхности
  по всей библиотеке.
- Тени (`shadow-lg/sm/xl`): в тёмной теме тени приглушаются и/или
  заменяются светлой границей; решение — точечное, на уровне утилит
  globals.css (`.dark .shadow-lg { ... }` допустим), без правки компонентов.

### 6.4 Экспорт PNG при тёмной теме (решение — §10.1)

`ForecastExportMenu.tsx` перед сериализацией резолвит переменные в клоне
SVG (обход элементов, `getComputedStyle` → подстановка вычисленных
значений вместо `var(...)`), иначе сериализованный SVG теряет контекст
стилей. Заливка canvas — по решению тимлида: рекомендация —
«всегда светлый» печатный артефакт (консистентность отчётов независимо
от темы просмотра; резолв из `:root`-значений). Альтернатива «как на
экране» технически эквивалентна по объёму.

## 7. Декомпозиция на под-задачи (каждая — полный цикл AGENTS.md: TDD RED→GREEN, полная регрессия, typecheck/build, ZIP в download, запись в worklog6.md)

Последовательность линейная (каждый следующий срез опирается на артефакты
предыдущего); DKT-1 — фундамент, без него остальное не исполняется.

- `ProductHeader.tsx`: кнопка-переключатель Moon/Sun справа от «РУС / ENG».
- Тесты: каталог-тест (каждый занятый шаг имеет var-отображение; значения
  `:root` == факт-инвентарь светлой темы), компиляция слэш-прозрачности,

## 8. Тестовая стратегия (TDD, общий контур)

1. **Каталог-тест токенов** (DKT-1): единственный источник перечня
   занятых шагов палитры = программный инвентарь `rg` (тот же метод, что
   дал цифры §2); тест утверждает: (а) каждый занятый шаг отображён на
   var; (б) `:root`-значения равны текущим фактам (инвариант светлой);
   (в) `.dark`-значения равны каталогу §6 (фиксация вердикта калибровки).
2. **Компиляция прозрачности**: тест собранного CSS-бандла — класс
   `bg-brand-light/50` компилируется в правило с `rgb(var(...) / .5)`
   (ловит деградацию формата var-троек).
3. **Провайдер**: jsdom-юниты init/toggle/персист/storage/
   system-fallback; matchMedia-стаб в `jest.setup.js`.
4. **Переключатель**: ProductHeader — иконка и aria по состоянию,
   клик меняет класс на `<html>` и ключ localStorage.
5. **Guard-тесты светлой темы**: существующие ~1 100 тестов остаются
   зелёными БЕЗ правок (контрольный факт); любое падение = сигнал, что
   правка задела вёрстку, а не значения.
6. **Мутационная кампания** (DKT-1/DKT-CERT): подмена источника init
   (localStorage→всегда system), инверсия toggle, снятие no-FOUC-скрипта,
   подмена ключа хранения, инверсия условия `.dark` — все KILLED на
   независимых оракулах.
7. **Экспорт PNG** (DKT-3): юнит на резолв var() в клоне SVG (до
   сериализации) — RED на отсутствии резолва.

## 9. Риски и меры

| ID | Риск | Мера |
|---|---|---|
| R-1 | Деградация слэш-прозрачности при неверном формате var | Формат `rgb(var() / <alpha-value>)` + тест компиляции бандла (§8.2) |
| R-2 | «Класс ≠ роль»: инверсные поверхности теряют контраст в тёмной | Инвентаризация DKT-2, точечные оверрайды, каталог исключений |
| R-3 | Один токен brand — две роли (заливка/текст) | Компромисс #4A4ED9 + точечная пара `dark:text-brand-bright` по инвентаризации (§6.3) |
| R-4 | FOUC при первом рендере тёмной темы | Блокирующий no-FOUC-скрипт до гидратации + `suppressHydrationWarning` только на `<html>` |
| R-5 | PNG-экспорт с несериализуемыми var() | Резолв computed-значений перед сериализацией + юнит-тест (§6.4) |
| R-6 | Guard-тесты вёрстки, пинящие классы, «сломаются» | По построению Варианта C — НЕ ломаются; контрольная арифметика регрессии в DKT-1 |
| R-7 | sonner/recharts — собственные дефолты вне токенов | DKT-4 (theme prop) / DKT-3 (атрибуты на var) |
| R-8 | Логотип/иконки с фиксированными цветами на тёмном | Аудит DKT-2 (логотип читаем — §2); при находке — ассет-вариант отдельным решением |
| R-9 | Разъезд тем двух оболочек (общие классы, разные точки монтирования) | Единый контракт §5; embedded-решение — §10.2 |
